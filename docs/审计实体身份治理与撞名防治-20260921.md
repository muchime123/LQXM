# 审计实体身份治理与「撞名」防治

日期：2026-09-21
触发：LQ 提问「审计实体名撞名这个问题在后续建设中感觉还会出现很多次，有一个比较好的解决方法吗？」

> 结论先行：**这不是命名问题，是「同一件事写了两份审计」的问题。**
> 项目里其实**已经有正确答案**（`erp.row_change_log.target_table`），只是 ERP 业务又额外往老通道 `audit_logs` 写了一份身份更弱的副本 —— 撞名就出在那一份上。

---

## 1. 实测：当前 48 个实体名的全貌

一次性普查（`_AuditCensus.java`，只读零写库），`audit_logs` 共 **97,846 行 / 48 个 `entity_type`**。

自动判据下**疑似 3 个**，逐个核实后：

| entity_type | 行数 | id 范围 | 触发判据 | 核实结论 |
|---|---|---|---|---|
| `SalesOutbound` | 660 | 0 .. 257,452 | 动作分裂 | ⚠️ **真撞名** —— 见 §2 |
| `SalesOutboundProfit` | 75,142 | 2 .. 337,242 | id 双峰 | ✅ **不是撞名**：只有 1 种动作 `PROFIT_RECALCULATE`，是**同一实体的 id 空间迁移**（先 ERP 小 id 后氚云 row id） |
| `Customer` | 5,788 | 0 .. 99,699 | 动作分裂 | ✅ **不是撞名**：`CUST_*`（客户档案 CRUD）与 `H3_OUTBOUND_*`（氚云出库治理）**写的是同一张 `customers` 表**，属"同源多入口" |
| `Employee` | 39 | 0 .. 163 | 动作分裂 | ✅ 同上，`EMP_*` 与 `H3_IDENTITY_BACKFILL` 同一张 `employees` 表 |

**现状可控**：真正撞名只有 `SalesOutbound` 一处，且本轮已用 `ErpSalesOutbound` 规避（实测 `ErpSalesOutbound` 5 行、氚云侧 `SalesOutbound` 660 行互不污染）。

**但机制缺陷仍在**，下一次换个表名还会重演 —— 因为下面这条结构性原因没动。

> ⚠️ 附带发现：判据 B「动作分裂」**会误报**。`Customer`/`Employee` 是**一张表既被业务写又被氚云治理写**，不是撞名。真判据应当是"同一 `entity_type` 下 id 跨越 ≥3 个数量级"（需人工复核），不能只看动作前缀。

---

## 2. 根因：`entity_type` 一个字段扛了两件事

`audit_logs` 表结构（实测）：

| 列 | 类型 | 说明 |
|---|---|---|
| `entity_type` | **varchar(30) NOT NULL** | 唯一的"身份"字段 |
| `entity_id` | bigint NOT NULL | null 会被写成 `0` |
| `model_name` | varchar(200) | 展示名 |
| `action` | varchar(64) | 动作 |
| `changes` | text | 摘要 |

问题三条：

1. **`entity_type` 同时要表达「哪张表」和「什么业务对象」** —— 一旦两个模块对同名概念用同一个词，就撞。
2. **它是自由字符串，无约束、无注册表、无所有权声明** —— 编译器不检查，DB 不检查，撞了**不报错**，只是查询时混在一起。
3. **没有操作人 / 请求键 / 追踪号** —— 出事时查不出"谁在什么时候为什么改的"。

第 3 条直接导致本轮出库单要另找通道（决策 #14 要求 `operator_id` 必填）。

> ⚠️ **长度是硬约束**：`varchar(30)` + `sql_mode` 含 `STRICT_TRANS_TABLES`（实测）→ 超长**直接报错**，不是静默截断。
> 任何"加长前缀"的方案都有 30 字上限。反例：`ErpManufacturingMaterialRequirement` = 35 字符，**会插入失败**。

## 3. 关键发现：项目里已经写好了正确答案

`erp.row_change_log`（ERP 侧变更日志，M0 契约基建，V**）

| 列 | 类型 | 作用 |
|---|---|---|
| `target_table` | **varchar(64)** | **schema 限定表名**，如 `product_archive.erp_sales_outbounds` |
| `target_id` | bigint | 行主键 |
| `action` / `changed_fields` | varchar(20) / json | 动作与前后值 |
| `operator_id` / `operator_name` | bigint / varchar(100) | **操作人（决策 #14 必填）** |
| `request_key` | varchar(100) | **幂等请求键（决策 #12）** |
| `trace_id` | varchar(64) | 追踪号 |

**`target_table` 是物理唯一的表名** —— 同一个 schema 里不可能有两张同名表 → **身份天然不可能撞**。

而且 ERP 业务**已经在写它了**，且写法完全一致：

```
ManufacturingService        : "product_archive.manufacturing_orders"            ×3
ManufacturingExecutionService: "product_archive.manufacturing_work_reports"     ×2
                               "product_archive.manufacturing_inspections"      ×1
                               "product_archive.manufacturing_orders"           ×1
SalesOutboundService        : "product_archive.erp_sales_outbounds"             ×4
```

**所以撞名的真正来源**：ERP 业务在写 `row_change_log` 的同时，**又往 `audit_logs` 写了一份**，用的正是那个弱身份 `entity_type`。出库单实证：

```java
// SalesOutboundService —— 同一处，两次审计
changeLog.write(ErpChangeLogWriter.of(actor, "product_archive.erp_sales_outbounds", id, "INSERT", …)); // ✅ 强身份
audit.log(AUDIT_ENTITY, id, no, "CREATE", …);                                                          // ⚠️ 弱身份副本
```

**这是个全项目一致的模式**（制造域先这么写，出库单照抄），不是某一个模块的疏漏。

## 4. 为什么会双写：因为只有老通道有页面

`erp.row_change_log` **没有任何后端查询端点**（实测：全仓 `row_change_log` 无 Controller / 无 `@GetMapping`）。
前端「系统管理 → 操作日志」(`OperationLogView.vue`) 只读 `/api/audit-logs`。

→ 于是形成循环：**想让人看见 → 就得写 `audit_logs` → 就引入撞名风险**。

**结论：修这个问题的关键动作是「让强身份通道可见」，而不是「把弱身份的名字起得更好」。**

## 5. 三个方案对比

| | **A. ERP 域审计单通道**（推荐） | **B. 双通道 + 枚举收口** | **C. 只加体检** |
|---|---|---|---|
| 做法 | ERP 自建实体**不再写 `audit_logs`**，统一走 `row_change_log`；补 `row_change_log` 查询端点 + 前端合并数据源 | 保留双写，把 `entity_type` 收口为枚举常量 + 注册表 + 启动自检 | 只固化普查脚本，发现撞名再改名 |
| 撞名风险 | **归零**（不再用 `entity_type` 表达 ERP 身份） | 降低但仍存在（靠纪律，30 字上限） | 不降低，只是发现得早 |
| 信息完整度 | **提升**（补上 operator / request_key / trace_id） | 不变（`audit_logs` 仍无操作人） | 不变 |
| 前端可见性 | **提升**（现在 `row_change_log` 写了没人看） | 不变 | 不变 |
| 改动面 | 出库 4 处 + 制造域 ~19 处 + 1 个新端点 + 前端 1 页 | 51 处调用点机械替换 | 0（只加测试） |
| 是否根治 | ✅ | ⚠️ 部分 | ❌ |

### 推荐 A，理由

1. **一次解决三个问题**：撞名归零 + 审计信息补全 + ERP 变更终于可见。
2. **不需要新的抽象**：`target_table` 已经存在、已经在用、已经被决策 #19/#20 钉死纪律，只是没接到前端。
3. **规则可下降为断言**："ERP 业务 Service 不得依赖 `AuditLogService`"，一条 ArchUnit 测试就能永久守住。
4. **上一轮的 `ErpSalesOutbound` 命名规则**降级为**兜底**（万一有必须写 `audit_logs` 的场景才需要避让命名），不再作为主策略。

### A 案的边界（不做什么）

- **不动** `audit_logs` 表结构（不加 `target_table` 列）—— 历史 9.7 万行的语义无法可靠回填，加一个恒为 NULL 的列没有收益。
- **不动**氚云治理/客户/档案/知识库/网站/证书这些**非 ERP** 业务的写入 —— 它们的 `entity_type` 是自洽的（同一张表 + 同一批动作）。
- **不给 48 个历史实体名改名** —— 现状已核实无真冲突，改名只会制造无谓的历史断层。

## 6. 防复发机制（不论选哪个方案都该做）

三层，从"编译期最硬"到"运行期兜底"：

| 层 | 机制 | 拦住什么 | 成本 |
|---|---|---|---|
| L1 编译期 | ArchUnit / 单测：`erp..` 包与 ERP 业务 Service **禁止依赖 `AuditLogService`** | 新模块照抄双写模式 | 低 |
| L2 运行期自检 | 启动时 / 每次加新模块前，跑一次实体名体检：`entity_type` 超 30 字、id 跨 ≥3 数量级、动作前缀混用 | 历史与新引入的撞名 | 低（脚本已写好） |
| L3 开工检查项 | 新导入/新模块的落地清单（skill `h3-import-kind-onboarding`）加一条："我的审计写哪条通道？身份字段是什么？" | 从流程上不问就不开工 | 极低 |

**体检脚本**已开发完成并可重复运行：仓库根 `_AuditCensus.java`（只读、零写库），输出 `entity_type` 全谱 + 撞名判据标记。建议把它的判据固化为一只单测，纳入后端门禁。

## 7. 附带修正：命名规则表述要更准

上一轮定的「ERP 自建单据 → `Erp*` 实体名」应修正为：

> **首选：ERP 自建实体不写 `audit_logs`**（走 `row_change_log`，身份 = `target_table`）。
> **兜底**：若因历史原因必须写 `audit_logs`，则该 `entity_type` 必须避让同名台账表 —— 避让方式优先用 `E:` 短前缀（如 `E:SalesOutbound`），而非 `Erp`，因为 `entity_type` 只有 **30 字符**。

同时明确：**`ManufacturingOrder` / `ManufacturingWorkReport` 等不需要加前缀**。
判据不是"是不是 ERP 自建"，而是**"有没有同名的氚云台账表可能撞"**。制造域恰恰是全项目**唯一没有台账底座的域**（决策 #26 已证实）→ 无撞名对象 → 无需前缀。

| 3 | 新增 `row_change_log` 查询端点 | ✅ `ErpChangeLogController` `GET /api/erp-change-logs`（分页 + `targetTable`/`action`/`operatorName`/`keyword`/日期过滤 + `facets`，复用 `system.employee.manage` 权限） |

**为什么第 3 步是必需的**：`row_change_log` 从 M0 起就在写，但**没有查询端点** → ERP 审计"写了没人看得见" → 这正是双写得以长期存在的起因。补上端点，方案 A 才成立（不补就是"把审计藏起来"）。

### 10.2 三个必须记住的实现约束

1. **自动放行的审计行必须带请求键**。自动放行是「报工」的副作用，请求键必须从 `report()` 一路穿透 `recalculate()` → `autoConfirmInspection()`。传 `null` 会在审计账里留下「有幂等键、无对应审计」的断链 —— 契约测试 `fullLoopIsIdempotentAndAudited` 就是钉这个的。
2. **`changed_fields` 是 json 列，断言前先压空白**。序列化形态是 `"inspectionSource": "AUTO"`（键值间有空格），按紧凑写法 `contains("\"inspectionSource\":\"AUTO\"")` 会**假失败**。
3. **门禁扫描源码前必须先剥注释**。单通道改造会在被改造的类里留下 `勿加回 AuditLogService` 这类说明性注释，纯子串匹配会把注释当成真实依赖 → 门禁对自己的改造结果报假失败（本次实际踩到）。

## 11. 附带发现：材料域有一个「调用即 500」的僵尸缺陷

| 项 | 事实 |
|---|---|
| 位置 | `ManufacturingMaterialService`（`audit.log("ManufacturingMaterialRequirement", …)`） |
| 缺陷 | 实体名 **32 字符 > `varchar(30)`**，且库为 `STRICT_TRANS_TABLES` → 该端点**每次调用都 1406 报错** |
| 佐证 | `audit_logs` 里 `CHAR_LENGTH(entity_type) > 30` 的行数 = **0**，最长仅 **28** → 这条路径**从未成功插入过** |
| 暴露面 | 后端路由在（`ManufacturingController` 的 `/orders/{id}/materials`、`/material-issues`、`/material-returns`）；前端 API 已定义（`api/manufacturing/index.ts`）但**无任何页面调用** |
| 处置 | **不改** —— 决策 #17 已判材料 / 领料域不建（四张表全 0 行）。给僵尸代码改名会制造「它还活着」的假象；已在 `AuditChannelHygieneTest` 里**显式记账**（`ZOMBIE_OVERLONG_ENTITY_TYPES` + 一条"清单不得腐烂"的门禁），清理该域时会被提醒一并删除 |

**给 LQ 的判断**：这条不影响任何在跑的业务，但它是"**路由存在 ≠ 功能可用**"的活样本 —— 将来若有人从页面接上材料领用，第一次点就会 500。建议在 §11 清理材料域时顺手做掉。

## 12. 结论（不变）

撞名的根子在**双写**，不在**名字**。所以正解是**通道收敛**，不是改名 —— 改名只是治标，且受 `varchar(30)` 限制几乎无可改。
