## 1. 分析入口全景（四层）

生产跟单的数据分析不是单一功能，而是**四个层次**，各回答不同问题。

### 1.0 先把技术四层翻译成用户视角的三类出口

技术上是四个端点，但用户用起来只关心三件事。**这两套划分不冲突** —— 三类是入口组织方式，四层是实现与口径划分：

| 用户视角 | 回答的问题 | 对应技术层 |
|---|---|---|
| **日常生产跟单工作台** | 现在有哪些任务要处理 | 列表页判据 + L1 待办提醒（`/summary`，暂未接入） |
| **生产交期达成分析** | 预计某段时间完成的任务，实际完成得怎么样 | L3（`/analytics`） |
| **数据导出与专项分析** | 线下复盘、原因归因、节点耗时、管理汇报 | L4（导出）+ L2 车间概览（`/dashboard`，暂未接入，属专项视角） |

不需要把每一类都做成系统页面。**当前阶段的重心是 L3**：先确保应完成任务数、完工分类、交期调整、取消任务、下钻明细这五件事**一致且可验证**，而不是继续加图表。

| 层 | 端点 | 前端载体 | 回答的问题 | 状态 |
|---|---|---|---|---|
| **L1 待办提醒** | `GET /summary` | ❌ 无（`fetchTrackingSummary` 已定义但 0 调用） | 今天该先看哪几单 | ⏸ 暂未接入，见 §1.4 |
| **L2 车间概览** | `GET /dashboard` | ❌ 无（API 层连函数都没有） | 各车间现在压了多少在制、多少已超期 | ⏸ 暂未接入，见 §1.4 |
| **L3 交期达成分析** | `GET /analytics`<br>`GET /analytics/orders` | `ProductionTrackingAnalyticsDrawer.vue`（90% 宽抽屉，列表页「生产分析」） | 一段交期范围内的履约质量如何、为什么 | ✅ 唯一在用 |
| **L4 线下分析** | `GET /export`（html / xlsx） | 导出弹窗（列可选） | 拿去做透视表、归因、给领导看 | ✅ 在用，见 §1.3 |

另外还有一个**既不是入口也不是分析的判据源**：`node-benchmarks`（节点参考完成天数）。它决定列表里「滞后」怎么算，本身却理应由历史数据反推（§8 P1）。

### 1.1 共同前提：可见范围

四层共享同一个 `ProductionTrackingService.visible(params)` —— **跟单列表看得见什么，分析就算什么**。这是硬约束：分析口径若自行放开权限，下钻点开详情会 404；若自行收窄，用户会以为数据丢了。

### 1.2 L3 的日期归属口径（唯一一种）

`dateBasis` 只接受 `baseline` 一个值，后端显式拒绝其它输入：

> 任务归入哪段统计区间，只看 **`COALESCE(t.forecast_finish_date, p.expected_completion_date)`**（即 §2 的 `EFFECTIVE_EXPECTED_DATE`）是否落在起止日之间，**起止均含边界**。

三个推论（用户常问）：
- 车间改了预计完成日期 → 任务**会跳到新月份**，历史区间的数字会跟着变（抽屉里已写明这句提示）
- 实际完工日即使在另一个月，**也不改变归属**
- 两个预计日期都没有的任务 → 落在任何区间之外，单独计入 `missingExpected` 供人工核实，不冒充达标也不冒充逾期

历史上有过三种日期口径（`submitted` / `inbound` / `active`），现已全部收敛为这一种（旧口径见 §10）。

### 1.3 L4 线下分析的定位

导出不是「把列表拷一份出来」，而是**给线下自由分析供料**。为此它比页面多了三类字段（2026-10-15 补）：

| 字段 | 用途 | 备注 |
|---|---|---|
| 逾期原因 | 逾期归因 | 与 L3 的 `overdueReasons` 榜同源（都取 OVERDUE 核实记录） |
| 其他时间核实原因 | 其余五类核实合并成「类目：原因」 | 常年稀疏，做成一列而非六列空列 |
| 节点备注 | 过程留痕 | ⚠️ 禁止并入「各节点完成日期」——那列是导回可写列，混文本会破坏导回解析 |

网页与 Excel 的字段选择**不一样**：网页版「产品」是不可拆的整体字段（名称 + 数量徽标 + 规格 / 模具副行，表头只写「产品」），Excel 里四者各成一列以保住导回锚点。

### 1.4 两个暂未接入的端点怎么办：先确认业务价值，暂保留

`/summary` 返回：`untracked`（一个跟单节点都没登记）、`due`、`overdue`、`delayed`、`timeReviewDue`（该核实的日期到了）。
`/dashboard` 返回：按车间的 `total / active / overdueOpen / dueSoon / noBaseline / onTime / deliveredOverdue / deliveredNoBaseline / inboundBeforeReport`，外加 `visibility`。

**结论（2026-10-19）：暂保留，不接页面也不删代码。** 「当前没有前端调用」只说明没接，不说明没价值 —— 尤其 `/dashboard` 讲的是**车间在制 / 超期 / 入库异常**，和 L3「按预计完成日期看一批任务的履约结果」是两个不同视角，不能因为 L3 已上线就判定 `/dashboard` 多余。

待办（不急）：
1. 先明确「要不要建生产概览」这个产品问题，再决定 `/dashboard` 的命运
2. `/summary` 若要接，改动量最小 —— API 函数现成，做成列表页顶部待办卡片即可
3. `/dashboard` 的 `inboundBeforeReport`（入库早于报工）是**数据质量探针**，即使页面不做也值得单独留出一条查询入口

真要下线时再按项目惯例清干净（Controller 端点 + Service 方法 + 前端死函数），避免有人误以为「看板已经做了」。在那之前，**不要把它们当作已完成的待清理项写进 plan**。

## 2. 口径字典（唯一来源）

分析结论出错，九成是因为同一个概念在不同层级是**两段不同的 SQL 表达式**。下面四个就是全部：

| 常量 | 表达式 | 用在哪 | 语义 |
|---|---|---|---|
| `EFFECTIVE_EXPECTED_DATE` | `COALESCE(forecast_finish_date, expected_completion_date)` | **仅 L3 分析** | 「车间当前有效预计」。车间没给就视为待核实，**绝不回退到业务员要求日** |
| `DELIVERY_BASELINE` | `COALESCE(forecast_finish_date, expected_completion_date, VALID_REQUIRED_DATE)` | 列表页面、L2 概览 | 「交付基准」。车间两个日期都没有时，**兜业务员要求日** |
| `COMPLETE_DATE` | `COALESCE(warehouse_in_date, iq.full_in)` | **仅 L3 分析** | 「整单完工日」。人工确认优先；否则要求同任务编号下入库**累计达到计划数量**（严格） |
| `DELIVERED_IN_DATE` | `COALESCE(warehouse_in_date, ib.first_in)` | 列表页面、L2 概览 | 「入库进度日」。**任一来源有入库就算**（宽松），明确不代表整单完工 |

`VALID_REQUIRED_DATE`：只有要求完成日 ≥ 申请日**且** ≥ 任务单提交日时才有效，否则判为填错（业务员把要求填得比提交还早）。

### 2.3 ⚠️ 两处刻意不一致 —— 别去「修」

**不一致 A｜基准：`EFFECTIVE_EXPECTED_DATE` vs `DELIVERY_BASELINE`**
列表要「总能给个说法」（所以兜业务员要求日），分析则要「分母干净」（缺车间预计就进 `missingExpected` 待核实，而不是拿要求日凑数冒充达标）。**分析一旦兜底，缺车间的单会被算成按期，准交率虚高。**

**不一致 B｜完工：`COMPLETE_DATE` vs `DELIVERED_IN_DATE`**
首次采购入库就当完工，会把**分批入库的单误判成提前完工**。`COMPLETE_DATE` 加了三重限制才推定整单完工：

1. 同 `production_order_no` 下**品名唯一**（`COUNT(DISTINCT product_name)=1`）
2. **单位唯一**（`COUNT(DISTINCT unit)=1`）
3. 累计数量首次 ≥ 计划数量时，取该次入库日期（`SUM(...) OVER (ORDER BY 日期) running_quantity`）

达不到这三条的（混合产品 / 单位、部分入库、缺计划量）→ **不推定，留人工核实**。氚云生产任务的产品名是短类目、采购入库品名是规格化名称，严格按名称相等关联命中 0 张 —— 这个限制不是洁癖。

> **用词铁律（贯穿全部层级）**：「逾期」= 实际晚于基准这一**既成事实**；「延期」= 协商另订新日期这一**主动动作**（落在 `forecast_finish_date`）。两者禁止混用。
>
> ⚠️ 但这**不等于**要求把「业务员要求达成率」摆到与按期达成率同等的位置 —— 业务员要求日本身存在数据质量问题（见 §3.3），它只作参考，不做考核口径。

## 3. 指标定义（L3）

### 3.1 状态划分（互斥、闭合）

**前置事实**：L3 的正式筛选规则（§1.2）已经规定 —— **没有当前有效车间预计完成日期的任务，不进入正常统计区间**，而是单独计入 `missingExpected` 由人工核实。所以在正常区间内部，「没有基准」这个分支**理论上不成立**，`deliveredNoBaseline` / `openNoBaseline` 不必再画进树里。

```
查询区间内全部任务 total
├─ 已确认取消 cancelled ──────────── 排除出履约分母（源任务状态为明确的取消 / 作废）
└─ 应完成任务 dueTasks
   ├─ 已完工 delivered（有 COMPLETE_DATE）
   │  ├─ 按期完工 onTime   （完工日 ≤ 基准）
   │  └─ 逾期完工 overdue  （完工日 > 基准）
   └─ 未完工 open（无 COMPLETE_DATE）
      ├─ openOverdue  基准已早于今天
      ├─ openDueToday 基准 = 今天
      └─ openNotDue   基准在未来

（区间外，独立核实，不参与以上任何分类、不进任何履约分母）
缺基准 missingExpected ── 无 COALESCE(forecast_finish_date, expected_completion_date)
```

两处容易改错：
- `stopped`（停止本地跟单）**仍计入应完成任务** —— 停止跟单只是本地不再跟踪，不等于任务取消；只有源任务状态明确为取消 / 作废才排除。
- 取消判断只认源任务状态，**不根据「停止跟单」推断**。

> **接口兼容说明**：`deliveredNoBaseline` / `openNoBaseline` 两个字段**仍留在接口返回值里**（前端与导出可能引用），但分析模型不再把它们当作正常履约分支。不要为了整理文档去删后端代码；也不要在新写的前端逻辑里依赖它们。

### 3.2 比率一览

| 指标 | 计算式 | 回答什么 | 地位 |
|---|---|---|---|
| 完工率 `completionRate` | 已完工 ÷ 应完成 | 这批活干完了多少（进度） | **主指标** |
| 按期达成率 `onTimeAchievementRate` | 按期完工 ÷ 应完成 | **最严格**：没干完的都算没达标 | **主指标** |
| 已完工准交率 `completedOnTimeRate` | 按期完工 ÷ 已完工 | 干完的里面多少按时（质量） | **主指标** |
| 可比样本准交率 `onTimeRate` | 按期 ÷ `comparable`（已完工且有基准） | 剔除缺基准后的纯质量 | 参考 |
| 业务员要求达成率 `requestedOnTimeRate` | 完工日 ≤ 业务员要求日 的数量 ÷ 可比样本 | 客户视角（原始期望） | ⚠️ **参考，不作考核口径**（§3.3） |

分母为 0 一律返回 `null`，前端显示「样本不足」—— **不用 0% 冒充结论**。

### 3.3 三个主率怎么看；业务员要求达成率为什么降为参考

**现阶段主指标是这三个**（2026-10-19 定）：完工率、按期达成率、已完工准交率。

- 只看已完工准交率 → 没干完的单不进分母，拖得越久数字越好看
- 只看按期达成率 → 抹掉了「双方后来协商达成共识」这件事
- 所以**按期达成率与已完工准交率要并排看**：差额说明的是「还有多少活没干完」，**不能直接解释成某一方的责任**（两者分母本来就不同）

**业务员要求达成率 `requestedOnTimeRate` 降为参考指标，不再列为必须展示的核心指标。** 理由不是它没意义，而是**输入不可靠**：

- 业务员要求完成日存在**错误年份、原始值被改写**等数据问题；
- 「通过了基础日期校验」只说明它是个合法日期，**不代表它是一份可靠的履约考核依据**；
- 用它做考核，会把「当初填错了」算成车间没做到。

处理方式：**底层数据与下钻能力全部保留**（`requestedComparable` / `requestedOnTime` / `requestedOnTimeRate` 照旧返回），将来若要求日数据核实过一轮，可以再做客户视角分析；但现阶段页面不必把它摆在主指标位，也不参与任何考核结论。可比样本准交率 `onTimeRate` 同理，作为「剔除缺基准样本后的纯质量」参考。

### 3.4 分组维度

- **车间**：横向对比，`dueTasks` 排序；抽屉里同时给条形图（按期 / 逾期 / 未完工堆叠）和明细表
- **预计完成月份**：识别上月结转、看趋势。**近期月份必然「未完工多」**，这是样本偏差，不是数据质量问题

未来日期范围内查询出来的结果是**进度快照**，抽屉会显式提示不能直接当最终考核结论。

## 4. 下钻契约

汇总里每一个可点的数字都对应一个 `bucket`，走 `GET /analytics/orders` 返回**同一批已加载的行**：

`total` `dueTasks` `cancelled` `missingExpected` `stopped` `matured` `openNotDue` `openDueToday` `delivered` `comparable` `onTime` `overdue` `deliveredNoBaseline` `open` `openOverdue` `openDueSoon` `openNoBaseline` `requestedComparable` `requestedOnTime` `extended` `advanced` `extensionReasonMissing` `overdueReasonMissing` `overdue1to3` `overdue4to7` `overdue8plus` `receiptOnly` `manualOnly` `bothSources` `extensionReason` `overdueReason` `riskCategory`

（`completed` 已于 2026-10-19 移除：它与 `delivered` 完全同义，属于"能下钻出 7 条、卡片上却没这个数"的孤儿 bucket —— 由对拍测试 §7.1 抓出。）

> bucket 分三类：**正式统计**（§3.1 树里的那些）、**参考**（`requestedComparable` / `requestedOnTime`，客户视角，见 §3.3）、**兼容保留**（`deliveredNoBaseline` / `openNoBaseline`，模型不再列为正常分支但接口继续返回，见 §3.1）。**测试对拍三类都要覆盖，页面展示只推第一类。**

**契约要求（不是建议）**：
1. 汇总计数与下钻总数必须相等 —— 同一个判据要在汇总和下钻两处复用
2. 下钻列表与卡片读同一批 `rows`，不存在「点进去数字对不上」
3. 点任务号 → 打开生产跟单详情（上层抽屉），分析抽屉留在下层；关掉详情仍回到原指标位置

⚠️ **曾有风险，现已钉住**：`summarize()`（累加计数器）与 `matches()`（下钻过滤）是同一批判据的**两份独立实现**。任何只改一处的改动都会造成「卡片显示 39、点进去 41」。`ProductionTrackingAnalyticsConsistencyTest` 穷尽遍历 `BUCKETS` 逐个对拍，已堵住这个口子（§7.1）。改任一侧判据时，**必须同时改另一侧并跑通该测试**。

> **已修复（2026-10-19）**：「累计延后 N 天」原先是**独立卡片**，显示的是天数（`extensionDays`），点进去下钻出来的却是延后过的单数（`extended`）—— 两者量纲本来就不同，卡片与下钻必然对不上。修法不是让它也能下钻，而是**把天数降级为同一张卡的附注行**：主数字＝延后单数＝下钻条数，天数只作展示、不可点（协商延后 3 单 ↗（累计延后 80 天））。前端 e2e 新增第 5 条用例钉住「能点的那个数必须是单数」，变异验证有效（把主数字改回天数 → 立刻红）。

## 5. 原因数据的三个榜

| 榜 | 来源字段 | 触发条件 | 截断 |
|---|---|---|---|
| `extensionReasons` | `delay_reason`，缺则取 COMMITMENT 核实记录 | 延后的单 | 取前 12 |
| `riskCategories` | `risk_category` | 延后的单 | 取前 20 |
| `overdueReasons` | OVERDUE 核实记录的 `reason` | 逾期的单 | **不截断** |

**为什么逾期榜不截断**：逾期原因目前是跟单员自由填写的文本。截断会导致「分桶逾期数 ≠ 原因条目之和」——用户一加就发现对不上。而且长尾写法正是将来归纳**原因字典**的原材料，全量返回才有价值。

配套两个「缺口指标」：`extensionReasonMissing`（延后了却没填原因）、`overdueReasonMissing`（逾期了却没核实）。**这两个比原因榜本身更该先看** —— 它们衡量的是录入质量。

> 快照一致性：逾期原因只在记录的 `source_expected_date <=> 当前基准` 且 `source_inbound_date <=> 当前完工日` 时才采信。交期改过之后旧原因自动失效，避免拿旧口径的原因去解释新口径的数字。

## 10. 附录：10-15 旧版口径（已停用，留作溯因）

旧版提供三种日期口径：
- **期间在制（默认）**：提交 / 申请日 ≤ 截止日，且截止起始日尚未交付或停止 → 让十月分析包含九月提交的延续工单
- **按入库时间**：只含入库日落入范围者
- **按任务单提交时间**：只看新接任务

停用原因：三种口径各自的解释成本高，且「期间在制」依赖「起始日是否已交付」这一不稳定判据 —— 同样条件的查询，隔天重跑范围会变。现行口径用「唯一认车间有效预计日」换取了**可复算、可解释**；代价是历史区间数字会随改期变动，这一点已在抽屉界面明示。
