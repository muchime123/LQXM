# 项目建设评估与下一阶段建议

日期：2026-09-18。依据当前源码、路由、Git 工作区、建设文档及本地配置数据库只读查询。不是全系统验收，未修改业务代码或数据，未运行会重置 S0 数据的验证脚本。前端 `npm run typecheck` 本次通过；后端测试、浏览器业务流程和实际并发未重跑。

## 1. 总体判断

项目已具备产品/包材/模具等档案、官网运营、客户档案、组织权限、历史数据导入、库存参考和月度提成等现有能力；ERP 建设准备已推进到规则验证和技术映射。不能再按“只有蓝图”安排下一步，也不能把现有历史台账或 S0 骨架等同于正式 ERP 已建成。

建议由继续横向补表、补导入，转向一个正式业务纵向闭环。保留既有档案和运营能力，仅对新 ERP 的必要模型和事务边界做明确建设。

## 3. 应优先修正的建设判断

### 3.1 技术方案存在已过时或过强的结论

`ERP技术方案映射-20260917.md` 建议新增员工 assignment 表，但 `DepartmentService` 已维护 `employee_department_assignments`，真库已有 120 行。应评估现表缺少哪些约束，而非重复建设。

方案将 `product_archive` 概括为历史样本区不够准确：该库同时承载当前档案、组织权限和官网等活跃能力。建议称“现有业务库”，在其中明确哪些是历史来源表、哪些是可复用主数据、哪些是运营业务。

“无推倒重建风险”“维度预留后启用即可”等表述过强。双计量、货权、追溯粒度和多公司身份会改变约束及流程，应保留变更影响评估。

独立 schema、双连接池和跨域复用需要补充：每类写操作使用哪个事务管理器，是否允许跨连接池写入，失败怎样处理，Flyway 如何独立初始化。普通本地事务不能因 schema 同实例就自然覆盖两个 DataSource。建议先限定 ERP 过账全部在 ERP 事务内完成，共享组织只读消费；以集成测试证明边界。

独立 schema 本身不能证明导入代码不会写 ERP；需数据库账号权限、写入路径约束和真实隔离测试。引用完整性是否使用跨 schema 外键是设计选择，不应简单描述为同实例双 schema 必然不支持。

### 3.2 验证报告必须按实际断言分级

| 证据 | 实际边界 | 建议 |
|---|---|---|
| 43 例通过 | 验证脚本自己的 S0 行为，非正式 Java 服务 | 用例保留，新增正式接口/服务适配运行，不复制一套规则自证 |
| T06/B11 | 文档明确为顺序模拟 | 补双连接同步起跑、行锁等待、死锁/重试及余额断言 |
| T17 | 用草稿不能过账替代无权限校验；查询手工指定 company_id | 状态校验与权限分开；真实身份调用列表、详情、写接口 |
| B20 | 检查本 schema 无 h3 表，并比较状态；未真正重导 | 用隔离环境实际执行导入，比较 ERP 状态，并验证账号写权限 |
| DECIMAL 精度 | 库中定点，但 harness 多处 Number 转换及 EPS 比较 | 用十进制定点运算或整数缩放，补大金额、最小计量、循环换算边界 |

这些不否定已有验证价值，但报告应分别标注“模型通过、模拟通过、真实集成通过、未覆盖”，避免覆盖名称大于实际证据。

### 3.3 财务样本应转成业务设计结论

优先从供应商结算明细验证采购付款、折让、预付和超付；从日记账/银行流水验证资金事件、代收代付和内部转账；从实际发票验证申请与实开、红冲、退款之间的区别。

不要将销售出库收款、发票表收款、资金日记账、银行流水各记一遍资金事实。它们可能是同一资金发生的不同证据，应先定义资金唯一身份、来源映射、对账关系和重复判定。

个人账户样本提示“账户持有人、资金归属公司、实际付款人、业务往来方”不能混成一个字段。内部转账也不能直接当销售收入或采购付款。

### 3.4 工程基线需要跟上新增能力

Git 已初始化，有两条可见提交；本次仍有导入链路改动及 V312 等未提交文件。这不是错误，但需要尽快形成按业务能力可回退的提交，并记录代码版本与迁移版本。

已有 GitHub workflow 会调用后端测试及前端类型检查、单测、构建、E2E，基础值得保留；本轮未查到最新后端 surefire 报告，不能据此声称当前完整回归已通过。S0 的 MySQL 验证未见接入此 workflow，应为隔离验证数据库建立专门任务。

`H3FactImportService.java` 当前约 2,573 行，导入种类仍增长。建议新增种类时抽取类型处理器（识别、解析、校验、持久化），保留统一批次、幂等和历史机制；先保护真实样本回归，不做无收益的全仓重构。

## 4. 建议的执行顺序

| 顺序 | 工作 | 退出条件 |
|---|---|---|
| P0 | 统一建设状态和决策登记，修正技术方案的任职表、数据分区、事务与隔离表述；保存当前可回退版本 | 一份当前状态清单；每个待决规则有结论或阻塞范围 |
| P1 | 财务代表性样本取证，补真实并发、精度、权限、导入隔离验证 | 付款/折让/预收预付等口径清楚；验证结论分级可靠 |
| P2 | 一个公司、一个仓库、一组标准商品的正式纵向闭环 | 主档→采购入库→销售出库→收付款核销→退货退款，全链可追溯、可复算 |
| P3 | 扩生产/委外、实际开票、成本、复杂单位及跨主体场景 | 各域有独立验收、业务责任人和异常处理 |
| P4 | 期初、未结事项、盘点、对账、切换和恢复演练 | 业务签认数据与切换结果 |

P2 按小切片逐段交付，并在已接入阶段包含权限、审计、请求幂等和事务测试；不能先做完所有业务再补安全与审计。成本政策在未影响试点数量账时可后置，但不能在成本未定义时承诺正式库存价值和毛利。

下一次最有价值的实施包建议是：**技术方案纠偏 + 验证补强 + 试点范围冻结**。继续补导入只针对明确缺失的验证证据，不以新增数据源数量作为 ERP 完成度指标。
