# 生产跟单工作台重新设计

日期：2026-10-07。依据：车间现用《生产跟单进度表.xlsx》、已导入的氚云生产任务及当前统一制造任务结构。本文件是新方案，旧跟单接口和表只用于清退核对，不作为新功能基础。

## 1. 要解决的日常工作

跟单员每天需要找出该跟进的任务，确认车间实际进度，判断能否按原要求日期完成，记录障碍和下一次跟进动作，并把交期变化传达给相关人员。系统应保留每次判断的依据和时间，避免多人编辑 Excel 覆盖彼此的记录。

首版对象是一张生产任务单；其下可有多个工序。任务来源可以是已接入的氚云任务，也可以是本地创建的制造任务。只展示已放行的任务；草稿和待审批任务不进入日常跟单池。已取消任务只在历史筛选中出现。

## 2. Excel 字段与系统归属

| Excel 内容 | 系统处理 | 说明 |
| --- | --- | --- |
| 订单号、产品、规格尺寸、数量、业务员、车间、要求完成日 | 读取统一生产任务，必要时展开氚云原始台账 | 不在跟单表重复维护。缺少源字段时显示“未提供”，不推断。 |
| 计划开工日 | 跟单计划字段 | 原始任务若有可信计划日期则显示来源值；手工计划另存并标识来源。 |
| 生产周期、倒计时、是否按期 | 查询时计算 | 周期按计划开工日至原要求完成日；剩余天数按当前有效预计完成日计算，且同时显示距原交期天数。 |
| 预计生产完成日期、延期原因 | 跟单预测 | 原交期不可被预测覆盖；预测晚于原交期必须填写延期原因。保留修订历史。 |
| 画图、备料、钣金、模具、组装、调试、模具生产 | 任务工序进度 | 优先读取正式工序事实；现场确认可单独记录，但不能改变报工数量、正式工序状态或下游放行。 |
| 入库、发货 | 独立交付事实及跟进信息 | 正式入库读取入库记录；发货读取可关联的销售出库。无法可靠关联时只能记录“待核实/跟进备注”，不能伪造完成事实。 |
| 备注 | 逐次跟进记录 | 每次追加，含记录人、时间、内容；支持下一次跟进日期和责任人。 |

工作簿有三张表：全自动气调机、半自动气调机、封口机。前两类的表格阶段为画图、备料、钣金、模具、组装、调试、入库；封口机为备料、模具生产、组装、入库。这些是界面展示顺序的参考，不应硬编码为所有任务的法定工序。实际工序以统一制造任务的工序行及车间配置为准；没有工序的任务仍可跟进交期和障碍。

## 3. 页面

### 跟单工作台

入口放在生产业务域。顶部显示“待首次跟进、今日应跟进、交期风险、已超原交期”数量。计数与列表使用同一权限和过滤口径。

默认列表只显示进行中任务，按需要处理的紧迫度排序：已超原交期、下次跟进已到期、预计延期、临近原交期、其他。支持“我的跟单 / 全部可见”、车间、业务员、任务状态、风险状态、关键字和交期范围筛选。表格至少显示任务号、产品、车间、数量、原交期、当前预测日、当前工序、最近跟进、下次跟进、风险及操作。可切换“按车间进度”横向视图，但不要求用户横向滚动才能看见风险。

点击任务打开详情抽屉，分为：任务与来源、工序时间线、交期与风险、跟进记录、交付核对。详情必须能看到氚云原始台账入口，便于核对差异。

### 一次跟进

表单必填“本次确认结果/沟通内容”；可更新预计完成日期、风险分类、延期原因、下一次跟进日期、责任人，并可记录某工序的现场确认日期和证据说明。保存后追加一条不可直接覆盖的历史；更正也以新的记录表达。保存成功后刷新工作台风险和待办状态。

## 4. 状态与提醒口径

任务生命周期使用制造任务的正式状态；跟单风险独立计算，不能将“预计延期”写成任务“已延期完工”。

| 风险 | 判定 |
| --- | --- |
| 待首次跟进 | 已放行、未完成、没有跟进记录。 |
| 今日应跟进 | 下一次跟进日期小于等于今天，且任务未关闭。 |
| 已超原交期 | 今天晚于原要求完成日，且没有可信的正式完成事实。 |
| 预计延期 | 当前预测完成日晚于原要求完成日，任务尚未正式完成。 |
| 临近交期 | 原交期在可配置的 N 天内，尚未正式完成且未落入更高风险。首版 N=3，可在代码常量中调整。 |
| 正常 | 其余进行中任务。 |

已完成、已取消任务不产生新的日常提醒，但保留跟进历史。原交期为空时不显示“按期/延期”结论；没有预测日时也不把原交期冒充预测日。`TODAY()` 式动态状态在查询时计算，不能把倒计时持久化。首版先做页面待办筛选，不发送自动消息。

## 5. 数据与接口契约

以 `manufacturing_orders.id` 作为跟单主键，覆盖氚云及本地任务；通过现有 `external_source/external_id` 访问氚云来源。原始 `production_orders` 和 `production_order_components` 只读，不从 Excel 反写。确认历史数据的映射质量后，再决定是否导入 Excel 的手填记录；绝不按产品名或行号自动匹配。

建议新建独立的跟单当前状态表和事件表。当前状态包含 `manufacturing_order_id` 唯一键、计划开工日、预测完成日、风险分类、延期原因、下一次跟进日、跟单责任人、版本号、最后跟进时间。事件表包含事件类型、结构化变更前后值、说明、创建人及时间；只增不改。现场确认阶段日期若首版需要，另建按 `manufacturing_order_id + operation_id` 唯一的确认表及其事件历史，明确 `source=MANUAL_CONFIRMATION`，不复用正式报工字段。

接口建议：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/manufacturing/followups` | 分页列表及同口径汇总，支持筛选和排序。 |
| `GET /api/manufacturing/followups/{orderId}` | 任务、来源、工序事实、跟单状态和历史。 |
| `POST /api/manufacturing/followups/{orderId}/entries` | 追加一次跟进，同时原子更新当前状态；要求幂等键及版本号。 |
| `POST /api/manufacturing/followups/{orderId}/stage-confirmations` | 追加现场确认或更正；与正式报工隔离。可在第二阶段实现。 |

读取沿用制造域的数据范围。写入使用单独的 `manufacturing.followup` 权限，并在每次写入前校验该任务对当前用户可见；分配为跟单员不能自动扩大其他制造数据的可见范围。列表、详情、汇总和写入均采用一致的范围判定。新写端点显式标注 `@RequirePermission`。版本号冲突时返回可识别的冲突错误，提示重新读取，不能悄悄覆盖。

## 6. 分步交付与验收

1. **清退旧链**：核对并移除旧的 `ProductionFollowUp*` 与 `ManufacturingController` 跟单端点及对应 Service 方法；已执行的 Flyway 历史脚本不修改。如旧表有真实记录，先导出和映射，再用新迁移处理，不直接丢弃。
2. **首版工作台**：新状态和事件表、列表与详情、追加跟进、交期风险、权限及前端入口。手机宽度仍能完成单次跟进；桌面表格能按紧急程度处理。
3. **阶段确认**：核验现有报工与氚云组件进度的映射后，再开放现场确认。界面并列展示“正式进度”和“现场确认”，不能合并成一个看似权威的完成日期。
4. **交付核对**：核验生产任务与入库、销售出库的关联后接入。无法确定关联的单保持“待核实”。

验收场景：同一任务两人同时保存不会覆盖；任务重新导入后本地跟进仍在；预测日期超过原交期必须说明原因；原交期缺失不产生错误逾期；正式报工和现场确认在详情中清楚区分；已完成任务从日常待办退出但历史仍可检索；没有关联依据时不显示“已发货”。

## 7. 实施前核对

当前仓库正在清理旧生产页面及接口。开始迁移和编码前，先确认旧跟单表中的实际行数及保留策略、统一生产任务与氚云台账的一对一关联、车间与工序配置、入库及发货关联的可靠性，并检查最新 Flyway 最大版本。上述核对影响数据迁移和事实展示，不影响工作台与跟进记录的基础设计。
