## 一、产品来源键三处口径同源化

### 为什么它是静默故障面

销售出库关联工作台 apply 时用 **SQL 表达式**算 key 写入 `source_identity_aliases`，重导时
`SourceIdentityService.resolveProduct` 用 **Java** 算 key 读回。两者一旦不等：

- 人工的产品归类结论**无法复用**，产品归类静默退回「待归类」
- 不报错、不告警、无日志；只有人发现「明明归类过又没了」才暴露

而这份 SQL 在代码里有**两份手工副本**（产品归类回填、工作台常量），Java 侧另有一份独立实现。

### 实测：先取证，再动手

工具 `tools/_VerifyProductSourceKey.java`（真库单连接事务，只读回滚，零残留）。
上一轮报告里我怀疑「可能已经漂移」，先把它证伪或证实。

| 层次 | 方法 | 结果 |
|---|---|---|
| A 逐行对拍 | 30414 条真实出库明细行，比对「工作台 SQL 表达式」与「服务端 Java」算出的 key | **零不一致** |
| B 存量可复现 | 4288 条 PRODUCT 别名中哈希型 1 条，检查 Java 能否复现 | **零孤儿** |
| C 边界对拍 | 14 条构造输入（全角空格 / 制表符 / 换行 / 全角拉丁字母…） | **4 条不一致** ← 差异点在此 |

**结论：现网未漂移**（上一轮的怀疑被证伪）。但差异客观存在于代码里，由 Java 与 MySQL 的空白语义不同造成：

| 输入 | SQL 侧（`TRIM`/`NULLIF`） | Java 侧（旧 `isBlank`/`trim`） | 根因 |
|---|---|---|---|
| `code="　"`（全角空格） | 当作编码原样返回 `"　"` | 判为空白 → 走哈希 | MySQL `TRIM()` 只认 U+0020 |
| `code="\t"` | 返回 `"\t"` | 判为空白 → 走哈希 | 同上 |
| `name="\t产品A"` | 哈希含制表符 | 哈希不含 | `String.trim()` 连制表符一起去 |
| `name="产品A\n"` | 哈希含换行 | 哈希不含 | 同上 |

当前 30414 行零命中，是因为氚云数据还没带这些字符——但 Excel 单元格软换行（Alt+Enter）导出时带 `\n`
是真实场景，所以这不是纯理论风险。**口径一律以 SQL 为准**（source_key 的落库权威路径是工作台 SQL）。

### 改动

| 文件 | 改动 |
|---|---|
| `util/ProductSourceKey.java`（新增） | 唯一口径来源：`of()` Java 实现 + `sqlExpr(alias)` SQL 渲染 |
| `service/SourceIdentityService.java` | 删除私有 `productSourceKey` 副本 → 改用 util；产品归类回填 SQL 改为 `sqlExpr("")` |
| `service/OutboundRelationGovernanceService.java` | `PRODUCT_KEY_EXPR` 常量改为 `sqlExpr("i")` |
| `test/.../util/ProductSourceKeyContractTest.java`（新增） | 11 项契约测试 |

**明确不动**：`V275__resolve_outbound_transaction_products.sql` —— 已应用的历史迁移是历史记录，
不回改（迁移用过的旧 SQL 文本与新口径在当前数据上等价，实测已证）。

顺手加的一层防御：`sqlExpr()` 的别名参数**接受 `"i"` 或 `"i."` 两种写法并统一补齐点号**。
写这段时我自己就踩了 `TRIM(i` + `product_code)` → `TRIM(iproduct_code)` 的粘字坑，
靠 harness 一跑就炸才发现。把它做成接口级防御，而不是靠调用方记得写点号。

### 零回归是怎么证明的

改前「旧 Java == SQL」全一致（A），改后「新 Java == SQL」仍全一致（A）⇒ 传递地证明 **新 == 旧，零回归**。
同时 C 从 4 条不一致收敛到 **0 条**。两个数字都要看：只看 A 不足以说明差异被修掉，只看 C 不足以说明没有回归。

## 二、客户身份簇映射覆盖保护

### 事实核对（推翻了两条原先的假设，因此修法与初版设想不同）

1. **`rememberCustomerCluster` 的三个调用点全是算法流程**（安全关联 / 多电话簇 / 电话簇建档），
   **没有任何人工入口**。所以它写入的 `status='CONFIRMED'` 是「算法自称已确认」，不是人工确认。
2. **`status` 有 `CONFIRMED` / `REVOKED` 两态**，撤销（`undoCustomerSplit` / `revokeClusterDecision`）
   一律按 `split_run_id` 走。
3. **客户拆分工作台的幂等护栏 `confirmedIdentityKeys` 建立在「有 CONFIRMED 映射即已定过归属」之上**，
   而关联工作台的算法流程却在校验之外无条件改写这张表 —— 两处假设自相矛盾。

→ 因此**朴素的加 `IF(status='CONFIRMED', ...)` 保护是错的**：由于 status 只可能由这些流程自己写成
CONFIRMED，加了之后这张表将**彻底不可变，且没有任何改判入口**，比「可被覆盖」更糟。

### 改动

`SourceIdentityService.rememberCustomerCluster` 的 `ON DUPLICATE KEY UPDATE` 改为：

```sql
customer_id = IF(split_run_id IS NULL AND status <> 'REVOKED', VALUES(customer_id), customer_id),
status      = IF(status = 'REVOKED', 'REVOKED', 'CONFIRMED'),
updated_at  = NOW()
```

保护范围精确到两类**不可被算法推翻的人工结论**：

- **人工拆分结论**（`split_run_id` 非空）→ `customer_id` 不改写
- **已撤销结论**（`status='REVOKED'`）→ 不复活、不改写

**自动来源（无 `split_run_id`、未撤销）仍允许更新**，保留自愈能力；改写人工结论的正确通道是
客户拆分工作台本身（`applyClusterDecision` 的 `ON DUPLICATE` 无条件写）。

### 验证

`tools/_VerifyCustomerClusterGuard.java`，6 组正反例共 **11 项断言全过**，事务回滚零残留：

| 用例 | 期望 | 结果 |
|---|---|---|
| 人工拆分结论被算法覆盖 | `customer_id` / `status` / `split_run_id` 均不变 | 通过 |
| 已撤销结论被算法复活 | 保持 `REVOKED`、`customer_id` 不改 | 通过 |
| 自动来源被更好的算法结论更新 | **允许更新**（自愈保留） | 通过 |
| 全新簇建档 / 同值重复调用幂等 / 空名称不落库 | 正常 | 通过 |

## 三、需要 LQ 决策或知悉

1. **`REVOKED` 簇在重导后的归属（不幂等，需你拍板）**
   撤销只把 `status` 置 `REVOKED`，`customer_id` 保留的是**被撤销的拆分目标**。
   若重导时 `H3ResetService` 用 `PRESERVE_IDENTITIES` 保留该行，则该簇的映射是 REVOKED、不参与解析，
   而事实行的 `customer_id` 已变 NULL → 每轮重导都会重新走一遍自动关联。
   两个方向：要么撤销时把该行**删掉**（回到「从未决定」），要么**改回源客户**。
   这属于语义选择，本次没动。

2. **更正一条旧备忘**：`H3ResetService` 并非「不清 `customer_source_cluster_mappings`」，
   而是把它列进 `H3_RULE_TABLES`，按模式二选一 —— `PRESERVE_IDENTITIES` 保留、`REASSESS_IDENTITIES` 删除。
   （备忘已更正）

3. **并发提醒**：本次又遇到一次外部构建（IDE 或另一会话的 maven）瞬时清空 `target/classes`，
   导致 javac 报出「程序包不存在」的误导性错误。同仓库多会话操作时以 `target/_check` 隔离编译可免疫。
