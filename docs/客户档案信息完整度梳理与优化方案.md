## 3. 根因分析

### 3.1 回填设计如此（主因，经营字段 100% 缺）
原回填链路（`CustomerArchiveBackfillService.backfillAll()`，2026-09-14 已下线，其地址解析能力已并入导入链路 `ChinaAddressParser.parseLoose`）只从销售出库提取「名称/地址/联系人/业务员」，`customer_type`、`industry`、`credit_code`、`website`、`level`、`relation_status` 一律不落值。这是**设计使然**，不是 bug——销售出库本来就没有这些维度。

### 3.2 地址解析缺陷（可修复，影响 ~670 省 / 65 地址）
`parseAddressText()` 解析省市区时，region 兜底逻辑存在明显缺陷：

- region 值大量是 **`浙江省（浙）`、`广东省（粤）`、`新疆维吾尔（新）`、`香港特别行政区`、`国外`** 这类带括号简称或特殊后缀的格式；
- 而兜底判断只认 `endsWith("省"/"市"/"自治区")`，导致 `浙江省（浙）`（以 `）` 结尾）**匹配失败**，省份留空；
- 地址本身又常是 **`温州`、`宁海县西店镇…`、`广州白云区…`** 这类不含"省/市"关键字的简写或县镇开头，也无法从地址反推省。

两者叠加，产生 670 个"出库明明有 region/地址、档案省份却为空"的可修缺口。

### 3.3 源头缺失（无法修复，需人工/上游补录）
- 1410 个客户出库里**既无地址也无 region**；
- 1672 个客户出库里**无电话**；
- 395 个客户出库里**无业务员**。

这些是氚云源头就没填，系统层面补不了。

## 4. 优化方案（分三层）

### 第一层：自动补全（代码 + 重跑同步，收益约 670 省 + 65 地址 + 151 联系人 + 135 业务员）

**4.1.1 修复 region 省名解析**（原 `CustomerArchiveBackfillService.parseAddressText`，现统一由 `ChinaAddressParser.parseLoose` + `ChinaRegionDictionary` 承担）
- 支持 `XX省（X）`、`XX市（X）`、`XX自治区（X）`、`XX特别行政区`、`国外` 等格式；
- 简称补全：`新疆维吾尔（新）→ 新疆维吾尔自治区`、`广西壮族（桂）→ 广西壮族自治区`、`内蒙古（蒙）→ 内蒙古自治区`；
- **region 优先解析省**（region 多为规范省名），address 用于补市/区县与详细地址。

**4.1.2 补漏联系人/业务员**
- 151 个"出库有电话但档案无联系人"、135 个"出库有业务员但档案无关系"的客户，按回填同一套逻辑定向补建（幂等、只补空）。

**4.1.3 `short_name` 程序补齐**
- 9095 个无简称客户，可统一取 `customer_name` 前 N 字兜底（回填已有此逻辑，仅对缺失者补跑）。

**执行方式：** 修复代码 → 重启后端 → 走客户分布/地区整理的「自动解析」（`POST /api/customers/region/auto-parse/preview` → `/apply`）与定向补漏脚本（均为"只补空、不覆盖"的幂等操作）。

### 第二层：源头数据治理（人工 / 上游，无法自动化）
- 1410 无地址、1672 无电话、395 无业务员 → 需在氚云侧补录或人工在客户档案逐条补全。
- 可在前端加"无地址 / 无联系人 / 无业务员"的筛选入口，辅助人工查漏。

### 第三层：经营字段人工补全（前端引导，收益最大但需人力）
6 个经营字段 100% 缺失，建议加**信息完整度**能力：

1. **完整度标签**：列表卡片/详情头按"缺失经营字段数"打标（如 `待补全·6`）；
2. **待补全筛选**：搜索栏加「信息不完整」快捷筛选（类比现有「待标注（省份为空）」）；
3. **批量编辑增强**：已有 `PUT /customers/batch` 白名单已支持 `customerType/industry/level/relationStatus/status/source/remark`，可直接用于批量补全；可再补 `credit_code`/`website` 进白名单。

| 步骤 | 内容 | 收益 | 风险 |
