## 2. ⚠️ 根因复核：原判断的一半是错的

动手前先证伪，避免改错地方。实测代码后确认：

| 漂移类型 | 实际状态 | 结论 |
|---|---|---|
| 导出**列顺序**变化 | `hashGroup()` 已用 `TreeMap` 排序字段名 | **本来就免疫**（代码注释 line 531 即为此而写） |
| 导出**多带全空列** | `rowValues`/`endRow` 只放非空单元格 | **本来就免疫** |
| 表头**内部不规则空白** | 仅 CASHFLOW_JOURNAL 的 `客   户    供应商` 有局部补丁 | **真实暴露** |
| 表头**全角/半角**差异 | 无处理 | **真实暴露** |
| 值**数值渲染**差异 | 无处理 | **真实暴露** |
| 值**日期渲染**差异 | 无处理 | **真实暴露** |
| 字段真改名 | 应报为变化 | 保持报警（不掩盖） |

即：此前的「列顺序变化会全量误报 UPDATE」的说法**不成立**，README 级结论须更正。
真正的暴露面是**表头文本**与**值渲染**——这正是 `first(m,"修改时间(必填)","修改时间")` 这类散落补丁的由来。

## 3. 修法

### 3.1 判等口径抽成唯一 util

新增 `util/H3SnapshotKey`（与 `UnitNormalizer`/`ProductSourceKey` 同级，遵守「口径必须唯一实现」纪律）：

- `canonicalKey(header)`：NFKC（全角→半角）+ **删除全部空白**（与既有 `客   户    供应商` 补丁同口径）
- `canonicalValue(v)`：
  - NFKC + 统一换行 + trim；空/`-` → **丢弃该键**（新增空列不改哈希）
  - 数字形态 → `BigDecimal.stripTrailingZeros().toPlainString()`：`1234.50` / `1,234.5` / `１２３４.５０` 全部归到 `1234.5`；用 `toPlainString` 抵消 `1000→1E+3`
  - 日期形态 → `yyyy-MM-dd` / `yyyy-MM-ddTHH:mm:ss`：`2026/8/31`、`2026年8月31日`、`2026-08-31 00:00:00`、`2026-08-31T00:00:00.000` 全部归到 `2026-08-31`（零点折叠；秒缺失补 `00`）
- `canonicalize(map)`：返回 `TreeMap`，内部按原始键先排序再落桶 → 归一撞键时结果**不依赖 Map 迭代顺序**

`hashGroup()` 改为对该 util 的调用。**`raw_data` 仍存原始快照原文，审计不受影响**；解析与写入路径零改动。

### 3.2 过渡期「旧口径回退」——把迁移做成零风暴

换口径后，已入库行存的还是**旧口径哈希** → 若无处理，5 类会把全部行误判 UPDATE（约 2.1 万行一次性无谓写入；INVOICE_SALES 还会删重插 512 子行）。

`unchanged()` 增加一个**惰性回退**分支：

```
1) existing.hash == incoming.hash（现行口径）→ UNCHANGED
2) existing.hash == legacyHash(incoming)（旧口径，惰性计算）→ UNCHANGED，由 touch() 把哈希刷成新口径
3) 修改时间相同 → UNCHANGED
4) 否则 UPDATE
```

- **惰性**：稳态下第 1 步先命中，`legacyHash` 根本不执行 → **零常态开销**
- 第 2 步只在「口径升级期」命中：一轮之后 `touch()` 已把哈希刷成新口径，自动收敛
- **删除条件**：5 类各完成一轮重导后，`legacyHash()` 与其分支可移除。在此之前不得删除（删了立刻触发风暴）
- ✅ **已于 2026-09-21 删除**（条件达成，5 类实测零风暴）——见 §9

### 9.3 ⚠️ 被回退掩盖的一个既有 bug：期初行 `touch()` 跨表 id 混用

批次 220 那 3 行 UPDATE 全是「**账户#期初**」，追出根因（**既有问题，非本次改动引入**）：

1. `loadExistingFacts` 对流水日记账做了**跨表 UNION**——期初行的 existing 取自
   `h3_cash_accounts`（键 = `CONCAT(account_name,'#期初')`），其 `id` 是**账户表 id**（实测 687~721）；
2. `touch(type, id, hash)` 的实现却是 `UPDATE <table(type)> …`，即去更新**分录表**
   `h3_cashflow_entries`（id 区间 41580~49167）→ **恒命中 0 行，是个哑操作**；
3. 于是**账户表的 `source_hash` 永不刷新**：期初行每轮都靠「旧口径回退」才判 UNCHANGED；
   回退一删立刻变 UPDATE（随后由 UPDATE 分支 `saveCashflowEntry → upsertCashAccount` 把 hash 写对）。

证据：删回退前（批次 215/216 前后）账户表 35 行中只有 3 行 `last_synced_at` 是当天
（正是被判 UPDATE 的 695/700/701），其余 32 行停在 09-18。批次 222 重跑 → `0/0/7623`（**自愈**）。

**无数据污染**（已查证：两表 id 区间无交集，那条 UPDATE 恒命中 0 行）——但这是
**靠巧合安全的代码**：一旦 id 空间重叠，就会误改分录行的 `source_hash`。

**修法**（最小改动）：UNCHANGED 分支对期初行改走**账户表幂等 upsert**（与 UPDATE 分支同路径）；
并抽出 `CASHFLOW_OPENING_SUFFIX` 常量 + `isCashflowOpeningGroup()` / `cashflowAccountOf()`，
与 `cashflowRowKey` 的期初分支、以及 SQL 里的 `'#期初'` 保持同口径。

**验证判据（决定性）**：部署后重跑流水日记账（批次 223）→ `0/0/7623`，
且账户表 `last_synced_at` **当天刷新的账户数 = 35 / 35**（修复前仅 3 / 35）。
