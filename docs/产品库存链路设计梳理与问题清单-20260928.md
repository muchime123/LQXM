# 产品库存链路设计梳理与问题清单

> 2026-09-28 · 范围：氚云「产品信息 + 仓库明细」导入 → 产品库存页展示 → 与 ERP 库存账的关系
> 性质：**只读核实**（真库 + 代码），未改任何代码与数据。所有数字均为当日实测。
> 关联：`氚云导入中心与库存快照重设计-20260916.md`、`产品库存建设梳理-20260917.md`、`销售出库与库存主轴落地记录-20260921.md`

---

## 0. 一句话结论

「导入产品信息 + 仓库明细 → **合并**为产品库存」这个心智模型**与代码不符**，而且是两层不符：

1. **没有"合并"这个动作**：产品库存页是**查询时 JOIN 两张台账**的实时视图（导入完成即生效），「合并入库」入口已于 2026-09-16 撤下。
2. **真正的「合并」在别处复活了**：2026-09-21 起，ERP 单据链路（销售出库 / 生产入库 / 采购到货）在写 `product_inventory_balances` —— 这是**活的正式库存账**。

结果是系统里同时存在**两个都叫「库存」的真相**：

| | 产品库存页看到的 | ERP 单据在扣的 |
|---|---|---|
| 来源 | 氚云两张台账实时 JOIN | `product_inventory_balances` + 流水 |
| 粒度 | 氚云编号 + 仓库 + 单位 | **canonical SKU** + 仓库 + 单位 |
| 更新时机 | 谁导文件谁更新（人工） | 过账/冲销/收货即变（事务内） |
| 今日实测 | **16,481 行有值** | **0 行** |

两者没有同步机制、没有对账提示、粒度也不同。**09-16 文档里「现阶段库存只有一个概念 = 氚云库存快照，没有正式库存账」的结论，已被 09-21 的 ERP 建设推翻**，但那份文档没有回改，任何人按它理解现状都会被带偏。

## 1. 现状链路（代码 + 真库核实）

### 1.1 实际是四层

```

      ├──────────────────────────────┐
      ▼                              ▼
```

## 2. 做对的部分（保持，不要动）

1. **两张台账 = 唯一事实源，查询时组合、不落物化**。没有第二份会漂移的库存数据 —— 这个选择本身是对的（前提是它是唯一的那份，见 3.1）。
2. **口径 util 单一来源**：`UnitNormalizer`（单位）/ `ProductFeeFilter`（费用项名单）/ `LedgerHeaderGuard`（表头指纹）各自只有一处实现。
3. **表头指纹校验**：上游改列序/导错类型 → 整批拒绝，不会静默错位。实测挡下过「仓库明细文件选了产品信息类型」。
4. **状态化台账（V304）**：氚云删行不在本地物理删；改为 `last_seen_at` 覆盖标记 + 30 天软提示 + 人工「下架」。部分导入天然安全，不做 staging 原子替换 —— 这个判断是对的。
5. **观测列（氚云系统列）回填不计入 `updated_count`**：`source_*` 只在新行/业务字段变化/UNCHANGED 但观测不一致时写，不污染幂等统计。
6. **数值浮点残差的处理**：`cellDecimal` 归零 + `nEq` 加 1e-9 容差，把「每轮 61 行永不收敛」修成稳态零 UPDATE。
7. **确认阶段 `@Transactional` + `FOR UPDATE`**：并发双击不会重复写入，失败整体回滚。
8. **权限读写双分**：类上 `product_inventory.read`，写端点（导入确认 / 处置 / 下架 / 身份复核）各自 `product_inventory.manage`。

## 3. 问题清单

> 严重度：**S1 = 结构性，会让业务判断出错** / S2 = 口径与一致性 / S3 = 工程债与性能

### 3.1 【S1】系统里有两个「库存」，且无桥、无提示

**现象**：同一个系统，两处都叫库存，数字必然不同。

- 产品库存页显示的是**氚云台账那个时点**的数量（L2），只有导文件才会变；
- 销售出库「选货」/ 生产入库 / 采购到货动的是**ERP 余额账**（L3），过账即变。

**为什么现在最危险**：L3 的键在 V320 之后是 **canonical SKU**，而 L2 的键是**氚云编号 + 仓库 + 单位**，两者连"同一个东西"的判断标准都不一样 —— 后者无法表达"多张工单产出的同款货累加"。

**实测佐证**：L2 有 16,481 行有值，L3 是 0 行。也就是说今天打开产品库存页看到满屏库存，去销售出库选货**一件也选不到**（`availableStock` JOIN `sales_products`，而它是空的）。这不是数据没导好 —— 是**两个口径本来就不同步**。

**唯一的接触点 `attachBalances` 还有键缺陷**：它用 `(sales_products.external_id, warehouse_id)` 匹配台账行，**键里没有 unit**：

```sql
WHERE (sp.external_id, b.warehouse_id) IN (...)   -- 命中后 putIfAbsent 取第一条
```

而台账一仓一编号可以有多单位行（实测 21 个编号）→ 这些单位行会**全部挂到同一条余额行**上，「已确认入库」标记与更新时间落在错误的行。键口径与 `uk_h3ws_wh_code_unit`（含单位）不一致。

**性质**：这是**定位未表达**问题，不是数据错。两个账各有各的用途，但系统里没有一处文字/字段说明"哪个是哪个、以谁为准、什么时候会不一致"。

---

### 3.2 【S1】冻结期的代码还在生产路径上，且对账信号的口径已经过期

09-16 把 L3 判为「冻结 / 无真实消费者」，只撤了 UI。但后端这些仍在跑：

| 位置 | 现状 | 后果 |
|---|---|---|
| `POST /product-inventory/merge/{preview,confirm}` | 端点仍在，权限 `product_inventory.manage` | **任何有该权限的人仍可调用**，把台账数据按旧口径写进 `product_inventory_balances`，绕过 ERP 的单据/幂等/审计链路 |
| `ProductInventoryMergeService`（1,069 行） | 列入「不删」清单 | 每次大重构都要带着它跑；它的键口径（仓库+氚云编号+归一单位）**与 ERP 的 canonical 键不是一套** |
| `snapshot-info.balanceVanished / balanceDrifted` | 仍在算，前端已撤黄条 | 无人消费；**且算法用的是旧键** |

**对账信号为什么已经失效**：divergence 的 SQL 是

```sql
FROM product_inventory_balances b
JOIN sales_products sp ON sp.id = b.sales_product_id   -- ← 旧身份
... ON ws.code = TRIM(sp.external_id)
```

V320 之后余额行按 **canonical** 聚合，`b.sales_product_id` 只是"首次创建该行时的身份"，在 `MFG-<工单号>` 场景下它的 `external_id` 是工单号而**不是氚云编号** → 匹配不上台账 → 被系统性判为 `vanished`。键应改成 `b.canonical_product_id` 对应 `sales_products.external_id`。

**性质**：一个已被判定"没有消费者"的机制，在 ERP 上线后**重新有了消费者**（"台账与正式账差了多少"现在正是需要回答的问题），但代码停留在旧口径。要么修好恢复使用，要么彻底摘掉 —— 现在是第三种状态：留着、算着、没人看、算错。

### 3.3 【S2】仓库名对不上 → 数据**静默消失**，而且没有任何入口

`VIEW_FROM` 的可见性条件是：

```sql
WHERE COALESCE(m.warehouse_id, w.id) IS NOT NULL
```

即：氚云仓库名在 `h3_warehouse_name_mappings`（0 行）和 `warehouses`（温州仓/代发仓/安徽仓）里**都匹配不上 → 这一行直接从清单消失**，无异常、无计数、无提示。

更隐蔽的是第二支 UNION 的兜底也会一起失效：

```sql
SELECT ... FROM h3_product_catalog pc
WHERE NOT EXISTS (SELECT 1 FROM h3_warehouse_stock x
                  WHERE TRIM(x.product_code)=TRIM(pc.product_code))   -- ← 不看仓库
```

只要该编号在仓库明细里**存在**（哪怕那行因仓库名对不上被丢弃），就**不会**产生"台账独有"兜底行 → **这个产品在页面上彻底看不见**。

**不对称之处**：编号对不上有 `MISSING_PRODUCT` 异常 + 处置台账 + 抽屉入口；仓库名对不上**一处都没有**。而仓库是比编号更容易变的东西（新增一个仓、氚云里改个名）。

**实测 0 行**（当前仓库名与 `warehouses` 完全一致）→ 现在是靠"仓库只有 3 个且名字没改过"压着，不是机制保证。

### 3.4 【S2】单位不一致时，库存金额**静默失真**

口径是 `金额 = 仓库明细数量 × 产品信息台账采购价`。当两侧单位不同，这个乘积**没有意义**，但页面照算、照汇总、不提示。

实测 **98 个编号**两侧单位不一致，其中有库存的真实样本：

| 编号 | 仓库明细单位 | 产品台账单位 | 数量 | 台账单价 | 页面算出的金额 | 实际含义 |
|---|---|---|---|---|---|---|
| `009YY` | kg | 个 | 500 | 0.27 | 135 | 500 kg × 「每个 0.27」 |
| `定做膜780` | 卷 | kg | 1 | 24 | 24 | 1 卷 × 「每 kg 24」 |
| `295QZDQTJ` | 台 | (空) | 1 | (空) | 0 | 缺价 |

09-16 文档的结论是「单位一致率 99.37% → 当前阶段不需要单位换算表」。**在那个时点成立，但结论被写成了永久性判断** —— 现在不一致的编号是 98 个，且会随每次导入变化。至少应该：**在页面把"两侧单位不一致"标出来**（现有 `codeConflict` 标记是同类做法，可直接复用），而不是让它混在金额里。

---

### 3.5 【S2】缺价行的金额按 **0** 计，与文档定的口径相反

文档 §3.3 明确：

> 有效采购价 = 产品信息.采购价格（唯一来源）… 为空 → 该行标「缺采购价」，**金额置 null，不填 0**

实现是：

```java
AMOUNT_EXPR = "ROUND(" + QUANTITY_EXPR + "*COALESCE(" + PRICE_EXPR + ",0),4)"
```

→ 缺价行金额算成 **`0.00`**，在页面上与"真的是 0 元"**不可区分**，并且会**静静地少算进汇总金额**。

实测：783 个产品采购价空/0，其中 **24 行有库存**（如 `295QZDQTJ` 台/1 件/无价）。异常入口（`MISSING_PRICE`）能列出它们，但那是另一个视图 —— 用户在看金额汇总时不会知道少了 24 行。

这是**文档与实现的直接分叉**，两处都是"权威"，需要择一。

---

### 3.6 【S2】同一业务键，三处 TRIM 口径分叉

| 位置 | 写法 | 是否 TRIM |
|---|---|---|
| 导入 upsert 判存在 | `WHERE product_code=?` / `WHERE warehouse<=>? AND product_code=? AND unit<=>?` | ✗ |
| 覆盖标记 `markCatalogSeen` | `WHERE product_code IN (...)` | ✗ |
| 页面主 JOIN | `LEFT JOIN h3_product_catalog pc ON pc.product_code = v.product_code` | ✗ |
| 页面 UNION 兜底 / 异常 / 详情 / 覆盖报告 | `TRIM(a)=TRIM(b)` | ✓ |
| 下架状态写入 | `WHERE TRIM(product_code) IN (...)` | ✓ |

**当前实测无影响**（编号含空格的行数 = 0，TRIM 与不 TRIM 两种 JOIN 命中数相同，都是 308）。

**但机制上是雷**：一旦氚云导出带前后空格，会同时出现

- 主 JOIN 取不到产品 → 该行显示「缺价 / 缺产品」；
- 异常视图用的是 TRIM 版本 → 判定产品**存在**，不报异常。

**同一个页面自己和自己矛盾**，且没有任何日志。这也正是 `产品库存建设梳理-20260917.md` §三 顺带项里已经点出、但一直没修的那条。

### 3.7 【S2】B 域的 `source_hash` 是**只写不读**的死列，而且与判等口径不同源

- **判等**走的是 `catalogEqual()` / `stockEqual()`：逐字段比较，数值走 `nEq`（1e-9 容差）；
- **`source_hash`** 由 `sha256(k + "=" + v ...)` 拼成，**从不被读取**（全仓 grep 无读取点），且 `BigDecimal` 的 `toString` 会带标度 —— `10.5` 与 `10.5000` 算出**不同哈希**。

后果有两层：

1. 它是纯存储浪费 + 误导（前端「导入与系统信息」区块把它作为**来源哈希**展示，用户会以为它就是判等依据）；
2. **同一个列名在 A 域和 B 域是两种语义**：A 域的 `source_hash` 是 `H3SnapshotKey` 归一化后的**判等主键**；B 域的它只是展示字段。

这违反项目自己的纪律「同一业务概念只允许一处定义」。要么让 B 域也走 `H3SnapshotKey`（并真正参与判等），要么把这一列从展示里摘掉。

### 3.8 【S2】空映射表被 4 处查询白白 LEFT JOIN

`h3_warehouse_name_mappings` **0 行**，仍出现在：

1. `VIEW_FROM`（清单主视图，每页 5 次汇总 + 1 次列表）
2. `ISSUE_JOINS`（异常视图）
3. `rowDetail` 的仓库明细回查
4. `snapshot-info` 的 divergence 子查询

四处都是"映射优先 → 名称兜底"的双路 JOIN。代价当前可忽略（15k 行、索引齐），但它**掩盖了一个事实**：仓库名映射机制没有任何人维护，且没有任何入口能表达"这两个氚云仓库名其实是同一个仓"。

---

### 3.9 【S3】零库存 89.7% 与「台账独有行」混在同一个桶里

- 零库存 **14,781 / 16,481**；
- 其中 **588 行**是"仓库明细里根本没这个编号"（显示「未记录仓库」、数量按 0 呈现）；
- 汇总卡片的 `zeroCount` 把两者**加在一起**。

语义上这是两件事：「仓里是 0」和「这份仓库明细里没有这个货」。后者更可能是**导出范围问题**（比如仓库明细只导了 3 个仓）而不是真没货，却被算进"零库存"。

页面有 `warehouseRecorded` 字段可以区分，但汇总口径没有。

---

### 3.10 【S3】导入写入是逐行 SQL

`applyCatalog` / `applyStock` 对**每一行**分别执行一次 `SELECT`（判存在）+ 一次 `INSERT`/`UPDATE`。16,481 行 = 约 3.3 万次往返。

实测：批次 225（16,481 行）从 `14:00:24` 到 `14:03:51`，**3 分 27 秒**。

（对比：`markStockSeen` 的覆盖标记已经用了 `batchUpdate`。）整体在 `@Transactional` 里，原子性没问题，但慢且随数据量线性增长。改成「一次 IN 查询捞出全部已存在行 + `batchUpdate` 写入」可以把耗时压到秒级。

---

### 3.11 【S3】未验证项（如实列出）

- **类目向下填充的边界**：`parseCatalog` 用 `lastCategory` 对"产品类目"（列 0，属主表字段）做向下填充。若某主记录的类目为空，会**继承上一条主记录的类目** → 错误归类。本次未构造该场景验证，也未查全库是否已存在。
- **`h3_product_catalog` 幂等键是 `product_code` 单列**：同文件内重复编号已被 `dedupe()` 处理；跨文件重复则是"后者覆盖前者"，属正常 upsert 语义，但如果氚云同一编号变成两条不同明细，本地只会留一条，**无提示**。
- 上游 09-16 文档的「L3 冻结」段落未回改，与 09-21 之后的实际状态冲突（见 §0）。

## 4. 建议路线

每阶段独立可验证、可单独叫停。
