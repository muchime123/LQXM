## 2. 账本对象与权限边界

- `h3_cash_accounts` 是当前账本账户身份；`cashflow_entities` 是资金归属，不能按名称推定法律主体。`cashflow_account_opening` 每账户每年最多一行；`active` 表示参与计算，`finance_confirmed` 表示财务凭外部凭据核对了该金额。二者独立。
- `h3_cashflow_entries` 是历史流水事实。当前部分查询仍按 `account_name` 关联账户，改名及导入身份改造须留到稳定 `account_id` 回填与导入兼容同批实施。账户停用不删除历史流水或期初。
- `company_accounts` 是现有对外收款资料（账号、SWIFT、收款码等），目前与账本账户无稳定关联。逐户核实后才可关联；不要复制其直接删除功能到资金账户管理。详见 `cashflow-account-consolidation-review-20261026.md`。
- `cashflow.read`、`cashflow.manage`、`cashflow.opening.confirm` 各管读取、账户/期初管理、独立财务确认。当前服务对资金范围仅接受 `ALL`，无法可靠表达账户级范围时保持拒绝。期初确认不等于流水逐笔对账，也不等于年度正式结账。

## 3. B-3.3 已确认期初更正：拟议业务契约

### 3.1 更正的前提与状态

更正用于证明原期初金额有误，并以新金额替换当前计算值。它不是“再次确认”，不能覆盖旧证据。更正必须指定账户、年度、原金额、新金额、原因和依据编号；金额遵循 `DECIMAL(18,4)`，不舍入，负数允许。若新旧金额相同，应拒绝并提示无需更正。

| 当前记录 | 更正请求 | 结果 |
| --- | --- | --- |
| 缺失期初 | 拒绝；走人工建立 | 不创建伪更正 |
| `active=0` 候选 | 拒绝；候选调整须另设规则 | 不影响当前计算 |
| `active=1, finance_confirmed=0` | 可在独立权限下申请更正 | 旧金额及原因留痕；新金额继续待确认 |
| `active=1, finance_confirmed=1` | 可在独立权限下申请更正 | 原确认记录永久保留；更正生效后当前确认复位为 0，`confirmed_by/at` 清空；新金额须重新财务确认 |

**更正不应先把 `active` 改为 0**，否则账户期间余额立即不可计算。建议分成“待应用更正”和“应用更正”两步：申请阶段只保存候选新金额、理由、旧金额快照和报表影响预览；应用阶段在同一事务里锁定期初并核对原金额、原确认状态和申请版本，原子更新金额，保持 `active=1`，复位财务确认，追加更正事件和审计。应用前报表不变化，应用后报表按新期初计算，并明确显示“已更正、待重新核对”。任何旧查询结果可能变化，因此应用动作须显示差额和受影响年度/账户，保存可追溯的生效时间，不得静默覆盖。

更正事件至少保存：账户/年度、旧金额、新金额、原 `finance_confirmed`、原确认事件 ID、原因、外部依据编号、申请人/时间、应用人/时间、请求键、状态。`cashflow_opening_confirmation` 的历史行不更新、不删除；更正后再确认时追加新证据行，并保存新金额快照。若原行没有确认事件，不能伪造一个。

### 3.2 并发、权限和失败契约

- 更正申请与应用需要明确的独立权限或经单独审核的 `cashflow.manage` 动作，不能由 `cashflow.opening.confirm` 推导。最终授权角色在实施前核定；当前无可靠账户级范围时沿用 `CASHFLOW=ALL` 且重放前再次校验。
- 申请和应用均使用独立幂等 action 与请求键。同键同载荷重放原结果，异载荷同键冲突；两个申请竞争同一账户年度时只允许一个待应用。应用时行锁加旧金额/状态条件检查，过期申请返回 409。
- 金额更新、更正事件、审计和幂等结果必须同事务提交；审计失败全部回滚。不要依赖已失败的事务继续查询。
- 2026 迁移期初更正会影响既有报表金额，必须在隔离库以不同金额反证并重跑 P1 34 项对拍。正式 35 户不得用于写入测试。正式使用前需确定谁有权批准历史年度更正；本稿不把财务依据文本视为银行已核对。

以上是 B-3.3 的**设计建议**，不是已实现接口或迁移。尤其“申请/应用”两步和授权人仍须在实施时与财务操作流程核对；不能从本稿直接推断生产表结构已存在。

## 4. 后续依赖顺序

1. **先收口现有候选**：B-3.1 的三条正式库幂等测试记录只在项目负责人明确批准且执行环境审批通过后按既定精确方案清理；不按 `result_ref` 删除任何期初。部署 B-3.1 新代码、确认数据源和幂等绑定、复跑只读回归。V410 所在 Flyway 队列单独审查，正常迁移后再验 B-3.2，不能跳过或 `repair` 伪装完成。
2. **B-3.3 期初更正**：按上节细化申请、预览、应用、重确认及权限，在隔离库完成状态/并发/回滚测试；正式库不做合成写入。
3. **B-4 年度选择与查询**：提供实际可用年度列表；同一请求不跨年度。每账户独立读取该年度 `active=1` 的期初，缺失时余额为不可计算而非 0，收入/支出仍可显示。2027 只有一户有期初也允许查看该户；各币种仅汇总可计算余额并标明缺期初户数。以 2026 全期间报表逐位不变为回归门槛。
4. **P2-C 手工流水**：先给流水建立稳定内部账户关联并验证历史行回填、账户名更改、全量导入兼容和同日同额重复笔数，再开放人工新增/更正/作废。手工流水与导入流水同账本但保留来源、审计和不可无痕覆盖；先实现记账，再逐步接银行逐笔对账。
5. **自动结转与正式结账**：只有可靠的上一年度正式结账记录与期间差额处理规则已建立后才开放自动结转。人工建立下一年度期初继续可用，但不自动标记银行已核对。

## 5. 本轮设计边界

本轮只整理状态、规则和实施顺序；不新增写接口、Flyway 迁移、前端操作或正式库写入。`company_accounts` 的整合单独逐户对拍，不能作为 B-3.3、B-4 或手工流水的隐式前提。B-3.1、B-3.2 的正式环境状态仍按各自验收记录判定。
