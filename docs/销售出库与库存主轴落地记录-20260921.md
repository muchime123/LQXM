# 销售出库与库存主轴落地记录（P1 库存主轴 → P2 销售出库）

日期：2026-09-21
上游：[ERP 建设现状梳理与下一步路线](ERP建设现状梳理与下一步路线-20260921.md) P1 / P2、[ERP 决策登记](ERP决策登记-20260921.md) #28（Q1 canonical 归一）、[完工入库到销售出库的身份断链与闭环设计](完工入库到销售出库的身份断链与闭环设计-20260921.md)
范围：**只做「有货直接出库」这条主线** —— 库存主轴的聚合口径（P1）+ 销售出库单的建单/改单/过账/冲销（P2）。「无货 → 下生产任务 → 车间 → 入库」已在制造域落地，本轮不重复。
性质：只写**已执行且可复核**的内容；未做到的一律列在 §6。

## 1. 结论

- **「有货直接出库」已经能跑真单据**：业务员在系统里选可售库存 → 建出库单 → 过账扣库存 → 冲销回补，全程走 M0 契约（请求键 + 操作人 + 行级审计），库存与单据同事务。
- **Q1 按建议落地**：`MFG-<工单号>` 编码**保留**（可追溯到工单），但**不再作为库存聚合维度** —— 新增 `canonical_product_id` 把它归一到标准 SKU（`H3-`）。同一件货不论由多少张工单产出，库存累加在**同一余额行**，「还有没有货」才判断得出来。
- **U16 的解法是「主库 + `erp_` 前缀」，不是独立 `erp` schema**：出库单、库存扣减、库存流水必须同库同事务，而库存账在主库、制造域也早已落在主库。隔离目的由表名前缀达成，不牺牲事务完整性。
- 验证过程中**发现并修复两个只在真人操作时才暴露的缺陷**（§5）：幂等哈希缺 Java 8 时间模块（**任何带日期字段的写动作整条 400**）、审计实体名与氚云台账撞名（一名两实体）。
- 交付证据：真库端到端 **19/19 断言全绿**（含超量拒绝、幂等重放、同键换内容报冲突）；新增**持久契约测试** `SalesOutboundContractMysqlTest` **2/2**（隔离 schema、零残留）；正式库**零污染**（验证残留已按业务标记清理并复核归零）。

> **一句话经验**：本轮真正的事故点不在出库的 SQL，而在「**日期类型**」和「**名字**」。放一个 `LocalDate` 进幂等载荷能让整条写路径 400，而报错文案指向「序列化」，看着像客户端传参问题；把 ERP 自建单的审计实体名写成 `SalesOutbound`，会让审计页把「氚云台账行的归类动作」和「ERP 出库单的建单/过账/冲销」混成一锅。两者都不报错、都只在真人操作时才现形。

### 4.1 端到端 19 条断言明细

正例（建单 → 改单 → 过账 → 冲销）：

1. 建单成功（**含 `LocalDate` payload，幂等哈希可算** —— 缺陷 #1 的回归点）
2. 建单后库存未动（草稿不碰库存）
3. 同键同内容重放 → 复用首次单据 id
4. 同键换内容 → 拒绝并报 `IDEMPOTENCY_PAYLOAD_CONFLICT`
5. 改单成功（含 `LocalDate` payload）
6. 改单后单据信息已更新 / 状态仍为 `DRAFT`
7. 过账成功 / 过账后库存按改单数量扣减 / 同键重放**不重复扣减**
8. 过账后状态为 `POSTED`
9. 冲销成功 / 冲销后库存**回到原值** / 状态为 `REVERSED` 且记录冲销原因

反例（超量出库）：

10. 超量单可建为草稿（草稿不校验库存）
11. 超量过账被拒，文案为「产品「…」在温州仓库存不足：可用 50200，本次出库 999999999 只」
12. 被拒后单据**仍为 `DRAFT`**（证明事务未落库）
13. 被拒后库存**未被扣减**

列表与可见性：列表可读且含本次单据。

> 残留清理用「**与 id 无关**」的判据（客户名 `ZZTEST` / 请求键前缀 `e2e-`）——MySQL 的 `AUTO_INCREMENT` 不因 `DELETE` 回退，写死 id 的清理脚本第二次就会漏删。删除前先导出可回放 `INSERT` 备份，删除后**同事务内自检**，任一条不达标即整体回滚。

## 5. 发现并修复的缺陷

### 5.1 缺陷 #1：幂等哈希缺 Java 8 时间模块 → 所有带日期的写动作整条 400

- **现象**：建销售出库单报 `400 INVALID_ARGUMENT`「请求内容无法序列化，无法计算幂等哈希：Java 8 date/time type `java.time.LocalDate` not supported by default」。
- **根因**：`ErpPayloadHasher` 自建 `ObjectMapper` 但**未注册 `JavaTimeModule`**。而写动作的 payload 直接放业务入参，入参天然带日期（`LocalDate outboundDate` / `LocalDate dueDate` / `LocalDateTime completedAt`）。
- **影响面比想象大**：**制造域的「建生产任务单」也在同一条路上**（`ManufacturingService.create` 的 payload 带 `LocalDate dueDate`），此前只是没被真人跑过 —— 制造域契约测试里 `dueDate` 传的是 `null`，所以从未触发。
- **为什么危险**：报错文案指向「序列化」，看着像客户端传参问题；实际是服务端一个 mapper 少注册一个模块，**所有带日期字段的写动作全挂**。
- **修法**：注册 `JavaTimeModule` 并关闭 `WRITE_DATES_AS_TIMESTAMPS`，让日期固定为 `"2026-09-21"` 这种 ISO-8601 文本（文本形态在排查哈希冲突时能肉眼比对，数组形态不能；且不受时区/纪元设置影响）。
- **回归钉死**：`ErpPayloadHasherTest` 新增 4 条（`LocalDate` / `LocalDateTime` 秒级差异 / null 值 / `BigDecimal` 标度必须区分）。

### 5.2 缺陷 #2：审计实体名与氚云台账撞名（一名两实体）

- **现象**：清理验证残留时发现 `audit_logs` 里 `entity_type='SalesOutbound'` 有 **665 行**，其中只有 5 行是本次 ERP 出库单。
- **根因**：`SalesOutbound` 这个实体名**早就被氚云侧的治理动作占用** —— `OutboundRelationGovernanceService`（产品归类 / 客户关联）、`SalesOutboundNatureService`（退换货类型确认），那些行的 `entity_id` 是**氚云销售出库台账行 id**（量级 10 万+）；而 ERP 自建单的 `entity_id` 是 `erp_sales_outbounds.id`（从 1 起）。**同一个实体名下两套 id 空间、两种含义。**
- **危害**：操作日志页按「实体类型 = SalesOutbound」筛选会同时命中两类动作，审计时无法区分；且随着两套 id 增长存在数值撞车可能。
- **修法**：ERP 自建单的审计实体名改为 **`ErpSalesOutbound`**，并写明命名规则：**ERP 自建单据 → `Erp*` 实体名 + `erp_*` 表名**（与制造域 `Manufacturing*` 同款「领域前缀」写法）。前端 `entityType` 是**动态选项**（来自后端 `f.entityTypes`），因此无需改前端。
- **回归钉死**：契约测试断言 `audit.log` 收到 `ErpSalesOutbound` 且**从未**收到 `SalesOutbound`。

### 5.3 顺带澄清：审计写入器的降级路径不是 java.time 的锅

`ErpChangeLogWriter` 在 `changed_fields` 序列化失败时会降级为 `{"_serializationError":"…"}` 摘要（设计如此，避免审计写入吞掉业务结果）。排查缺陷 #1 时一度怀疑审计侧也有同样的「缺时间模块」问题，**实测结论是它早就解决了**：构造器里有 `objectMapper.findAndRegisterModules()`，所以即便调用方传 `new ObjectMapper()`（未显式注册 `JavaTimeModule`）也能正常写入 `java.time` 值。已补一条回归断言
`ErpChangeLogWriterTest.javaTimeValueDoesNotDegradeAuditContent` **钉死「别把 `findAndRegisterModules()` 删掉」** —— 删了它，审计行还在，但「改前改后是什么」会静默丢成一条错误桩，而制造执行段真库验证时正是这样踩过一次。

> 两处的日期**序列化形态**刻意不同、不强行统一：审计 `changed_fields` 保留 Jackson 默认的组件数组（`[2026,9,21]`），幂等哈希则关掉 `WRITE_DATES_AS_TIMESTAMPS` 走 ISO 文本 —— 前者只给人看，后者要参与哈希计算，文本形态在排查哈希冲突时能肉眼比对。

> **给后续契约测试的提醒**：写制造域/出库类契约测试时，如果 payload 里带日期，请**别传 `null`** —— 传真实日期才能真正覆盖这条路径。制造域契约测试正是因为 `dueDate` 传 `null`，让缺陷 #1 躲过了此前所有验证。
