## 2. 总体架构决策

### DA1 ERP 正式业务区 = 同实例独立 schema `erp`

| 方案 | 优点 | 缺点 | 判定 |
|---|---|---|---|
| **独立 schema `erp`**（推荐） | 与历史样本物理隔离（蓝图 §1.2 三分区落地最干净）；备份/恢复/清理可独立做；权限可按 schema 收口；B20「重导氚云不动 ERP」从结构上成立（跨 schema 写入需要显式代码，不会误写） | 跨域查询需 `erp.x JOIN product_archive.y` 显式限定；Flyway 需为 erp 单独配 history 表 | ✅ 采用 |
| 同库 `erp_` 前缀 | 单 Flyway 管线、无跨库语法 | 300+ 迁移混在一起；隔离靠纪律不靠结构；误写历史表的面包越来越大 | ❌ |
| 独立数据库实例 | 隔离最彻底 | 运维成本、本地开发不便、跨实例事务不可用（当前需求不需要） | ❌ 暂不 |

实施要点：Flyway 第二套配置（`spring.flyway.schemas=erp` + 独立 history 表 `erp_flyway_history`），版本号独立从头编（避免与 product_archive 的 V1–V311 混淆）；应用侧两个 DataSource（主库照旧，erp 走独立连接池，Hikari 各自命名）。

### DA2 分区落地

| 分区（蓝图 §1.2） | 落点 | 说明 |
|---|---|---|
| 历史样本区 | `product_archive` 现状（h3_* / sales_outbounds / receipts 等） | 不改语义、不改结构；只读参考 + 候选来源 |
| 设计验证区 | `erp_s0_verify` 现状 | 43 用例继续跑；新规则先在 S0 立用例再进 erp |
| ERP 正式业务区 | `erp`（新建） | 只装经确认的主档、新单据、事件、核销 |

跨区唯一合法通道 = `erp.external_id_map`（映射表）与只读查询；**任何写入路径不得从历史区自动生成正式区数据**（U 系列约束，M15/B20 用例守护）。

### DA3 单据建模：按族分表

| 方案 | 优点 | 缺点 | 判定 |
|---|---|---|---|
| **按单据族分表**（推荐） | 每表列语义直白（无 30% 空列）；索引/约束可按族定制；与现有代码风格一致 | 「单据中心」类跨族查询需 UNION 或读事件表 | ✅ 采用 |
| 统一 doc/doc_line（S0 式） | 跨单据查询简单 | 生产字段差异大 → 大量 NULL 列或 JSON 黑洞；行级约束难做 | ❌ 仅限 S0 |
| 统一头 + 族扩展表 | 折中 | 三层 JOIN，复杂度最高 | ❌ |

「族」的划分（契约 §5–§7 映射）：**订单族**（sales_order / purchase_order）、**执行单族**（delivery 销售出库 / receipt_in 采购入库 / return_in 销售退货 / return_out 采购退货）、**调拨族**（transfer_order 头 + transfer_shipment/transfer_receipt 两执行腿）、**调整族**（stocktake 盘点 / stock_adjustment 其他调整）、**资金族**（fund_doc / refund_doc）、**往来域**（ar_ap_item / item_adjustment / settlement_allocation）。跨族的「订单行→执行行」关系统一落全局 `execution_allocation`（契约 §4 的分配模型，S0 已验证）。

### DA4 库存：新建事件/余额双表，现有 V236 域不动

现有 `product_inventory_transactions` 维度（仓×成品批次×类型）无法承载契约 §6.1 的多维键（货权公司×仓×SKU×质量状态×批次/序列），且其 balance_after 冗余列与「事件不可变、余额可重算」的口径有微妙差异。**新建 `erp.stock_event` / `erp.stock_balance`**；V236 域继续服务现有产品库存页，两域并行，不互写。若未来切换，按 G3 期初方案一次性迁移（蓝图 §10.1），不做双写。

### DA5 主数据三分复用（逐对象见 §8 总表）

原则（字典 §1「复用决定逐对象说明」的落地）：

- **直接复用（增量加列）**：organization_companies（补 legal_identifier 等）、departments、employees（补任职assignment版本化）、warehouses（补 company_id/custodian/location）。这四类是**本地管理且已活跃**的域，ERP 复用其身份，通过 `erp` schema 中的表引用同实例 `product_archive` 的表（跨 schema 外键不建，靠应用层校验 + 定期对账）。
- **新建 + 外部映射**：party（往来方）、sku、unit 及其子表。customers/h3_supplier_catalog/product_models 是**候选来源**，经人工确认写入 `external_id_map(decisionStatus=CONFIRMED)` 后生效——这是字典 M15/B20（氚云重导不动 ERP）的结构保障。
- **退役不恢复**：formal_* 五表不接线、不复用、不删除；G3 切换期统一归档清理。

### DA6 formal_* 僵尸域处置

2026-09-17 全仓验证：`formal_sales_orders/formal_sales_shipments/formal_receipts/formal_receipt_allocations/formal_profit_snapshots` 后端零引用、前端零引用。处置：**保留原样（结构参考价值：其 status DRAFT/POSTED 设计与契约 §3 同源），写入本文档存档备查；G3 切换期按 V267 先例导出 CSV 留档后 DROP**。现在不做任何动作，防止误删并行会话可能的依赖（虽然已验证无引用，仍守「先备份后删」纪律）。

### DA7 编号、ID 与快照

- 内部主键：ERP 全部表用 `BIGINT AUTO_INCREMENT`（现有风格；字典 §2「物理 BIGINT/UUID 后续决定」→ 定 BIGINT，API 层转字符串防 JS 精度丢失）。
- 单号：新建 `erp.doc_no_rule`（company+docType → 前缀/日期格式/步长/当前值，行锁发放），单号唯一键 `uk(company_id, doc_type, doc_no)`（契约 §2）；作废号不复用。
- 快照：单据行固定 sku_code/name/spec + 单位 + 换算比率 + 换算版本 + 价格基数快照（契约 §2.1），落列不落 JSON，便于对账 SQL。

## 3. 公共列规范

### 3.1 主数据公共列（字典 §2 的 DDL 落地）

```sql
-- 所有 erp 主数据表的公共列（规范模板，非可执行 SQL）
id               BIGINT       NOT NULL AUTO_INCREMENT,
code             VARCHAR(64)  NULL,        -- 启用时必填；唯一范围见各表
name             VARCHAR(200) NOT NULL,    -- 去首尾空白后非空；名称不是身份键
lifecycle_status VARCHAR(20)  NOT NULL DEFAULT 'DRAFT',  -- DRAFT/ACTIVE/INACTIVE
version          INT          NOT NULL DEFAULT 0,        -- 乐观锁 @Version
change_reason    VARCHAR(1000) NULL,       -- 停用/合并/关键变更必填
created_by BIGINT, created_at DATETIME, updated_by BIGINT, updated_at DATETIME,
activated_at DATETIME, activated_by BIGINT, disabled_at DATETIME, disabled_by BIGINT
```

- 「唯一性只在启用范围生效」的落地：加存储生成列 `active_code VARCHAR(64) AS (IF(lifecycle_status='ACTIVE', code, NULL)) STORED` + `UNIQUE(active_code)`（或含 company 的组合）——DRAFT 可重码、停用编码不可复用（M02）。
- 编码大小写：MySQL 默认 collation 不区分大小写 → `code` 列显式用 `utf8mb4_0900_as_cs`，全系统统一，不依赖库默认（字典 §2 要求显式决定）。
- 空值语义：未知/不适用一律 NULL，禁用 0 或「默认个」掩盖缺失（字典 §2；C4 教训）。

### 3.2 单据公共列（契约 §2 落地）

```sql
id BIGINT, doc_no VARCHAR(64), doc_type VARCHAR(30),     -- 身份与编号（DA7）
company_id BIGINT NOT NULL,                              -- 过账后不可变更（应用校验）
business_date DATE NOT NULL,                             -- 业务日期（S 必填）
occurred_at DATETIME NULL, posted_at DATETIME NULL,      -- 实际发生 / 系统过账时间
approval_status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',    -- DRAFT/SUBMITTED/APPROVED/CANCELLED
posting_status  VARCHAR(20) NOT NULL DEFAULT 'UNPOSTED', -- UNPOSTED/POSTED（执行单族用）
revision INT NOT NULL DEFAULT 0,                         -- 业务修订（订单族）
version  INT NOT NULL DEFAULT 0,                         -- 并发乐观锁
party_id BIGINT NULL, company_role_id BIGINT NULL,       -- 往来类单据
currency VARCHAR(10) NOT NULL DEFAULT 'CNY',
pricing_basis VARCHAR(20) NOT NULL DEFAULT 'TAX_INCL',
rule_version VARCHAR(32) NOT NULL,                       -- 过账时固定政策版本
owner_employee_id BIGINT NULL, department_id BIGINT NULL,
reason_code VARCHAR(50) NULL, remark VARCHAR(1000) NULL, evidence_refs JSON NULL,
created_by/approved_by/posted_by + 时间列
-- execution_progress / closure_status / reversal_progress 不落列：
--   从 execution_allocation 与 stock_event 实时派生（契约 §3.1「不手工维护」）；
--   列表性能不足时再加物化列 + 事件驱动更新（实施期决定）。
```

> ⚠️ `version`（并发锁）与 `revision`（业务修订）**必须分列**——S0 骨架把两者合一了，生产表分开（契约 §2 明确是两个语义）。

## 5. API 映射

### 5.1 资源与端点模式

沿用现有风格（REST + ApiResponse 包装 + `@RequirePermission`）。ERP 端点统一前缀 `/api/erp/{domain}`：

| 模式 | 端点 | 说明 |
|---|---|---|
| 主数据 | `GET/POST /api/erp/parties`、`GET/PUT /api/erp/parties/{id}`、`POST /{id}/activate`、`POST /{id}/deactivate`、`POST /{id}/merge-confirm` | 字典 §7 六个动作逐一成端点；启用/停用带 `version` 与 `changeReason` |
| 单据 | `GET/POST /api/erp/sales-orders`…、`PUT /{id}`（DRAFT）、`POST /{id}/submit`、`POST /{id}/approve`、`POST /{id}/reject`、`POST /{id}/revise`、`POST /{id}/close-remaining` | 状态机动作端点化（契约 §3.2），每个动作独立权限点（D08 矩阵） |
| 过账 | `POST /api/erp/deliveries/{id}/post`、`…/receipts-in/{id}/post`、`…/refunds/{id}/confirm` | 过账 = 原子事务（§6 边界），请求携带 `requestKey` |
| 冲销 | `POST /api/erp/{docType}/{id}/reverse`（body: 原行引用 + 数量 + 原因） | 新建反向单据并独立过账，原单保持 POSTED |
| 幂等查询 | `GET /api/erp/requests/{requestKey}` | 超时后按键查结果，不让用户猜（契约 §8） |
| 查询 | `GET /api/erp/stock/balances?companyId&warehouseId&skuId…`、`GET /api/erp/stock/events?…`、`GET /api/erp/ar-ap/items?open=true` | 余额可按维度过滤；事件流支持重算对账 |

**校验失败返回体**（字典 §7 + 契约 §8 错误码）：`{code: 'INSUFFICIENT_AVAILABLE_STOCK', message: '中文修正说明', field: 'lines[0].quantity', detail: {available: 1, requested: 4}}`——业务码 + 字段定位 + 可修正数据。

### 5.2 业务错误码枚举（新增 `ErpErrorCode`）

现状：`GlobalExceptionHandler` 的 code 即 HTTP 状态码，无业务语义。新增枚举替换（HTTP 状态保留，`code` 字段换业务码）：

| 业务码 | HTTP | 语义（契约/字典出处） |
|---|---|---|
| INVALID_STATE / STALE_VERSION | 409 | 状态机非法迁移 / 乐观锁冲突（M12） |
| CODE_CONFLICT / EFFECTIVE_RANGE_OVERLAP | 409 | 编码冲突 / 换算区间重叠（M18） |
| REQUIRED_FOR_ACTIVATION / REFERENCE_INACTIVE / OWNERSHIP_CONFLICT | 422 | 启用校验三件套（M03/M14） |
| UNIT_CONVERSION_MISSING | 422 | 无换算阻断过账（蓝图 §7） |
| SOURCE_QUANTITY_EXCEEDED / ALLOCATION_EXCEEDED / REFUND_EXCEEDED | 422 | 三类额度超限（B06/B11/B13） |
| INSUFFICIENT_AVAILABLE_STOCK | 422 | 禁负库存（T06） |
| DOWNSTREAM_DEPENDENCY | 422 | 有下游不可改/不可撤（B08） |
| PERIOD_CLOSED | 422 | 期间已关（D08 期间控制） |
| IDEMPOTENCY_PAYLOAD_CONFLICT | 409 | 同键不同内容（B14） |
| CONVERSION_MISSING / STALE_VERSION 等字典错误码 | — | 与字典 §7 对齐，实施期合并为一张枚举表 |

### 5.3 幂等接入模式

写动作（submit/approve/post/reverse/refund/allocate）统一走「幂等模板」：拦截 `X-Request-Key`（或 body.requestKey）→ `idem_request` 查键 → 命中则比对 payload_hash（一致返回原 result_ref，不一致抛 IDEMPOTENCY_PAYLOAD_CONFLICT）→ 未命中则执行事务并在**同一事务**内写 idem_request（B15：事务回滚则键也不存在，可安全重试）。这与导入管线的「来源哈希幂等」是两层：请求键管 HTTP 重试，业务唯一键管业务重放，缺一不可。

## 6. 事务与并发

### 6.1 原子边界（契约 §8 → 事务方法）

| # | 事务方法 | 一起提交 | 失败语义 |
|---|---|---|---|
| 1 | `postDelivery` / `postReceiptIn` / `postReturn*` | posting_status + stock_event + stock_balance + execution_allocation + 订单行 executed_qty + idem_request | 任一失败全回滚（B15） |
| 2 | `shipTransfer` / `receiveTransfer` | 同次两腿事件 + 在途余额 + 累计执行量 | 任一腿失败整次失败（B09/B10） |
| 3 | `allocate` / `deallocate` | allocation + fund_doc 冗余列 + item.settled + row_change_log | 不允许只动一侧（B11） |
| 4 | `adjustItemWithSettlement`（调整带核销释放） | item_adjustment + 超额核销的 DEALLOCATE + 双侧冗余列 | 原子（契约 §7「同一受控流程」） |
| 5 | `confirmRefund` | refund_doc(HOLD→CONFIRMED) + fund_doc 额度转移 | 额度不脱节（B13） |
| 6 | `enable/disable/merge` 主数据 | 生命周期 + 审计 + external_id_map 决策 | 合并整体回滚（M 系列验收） |

### 6.2 锁策略表

| 冲突面 | 机制 | 理由与先例 |
|---|---|---|
| 单据头/主数据行 | 乐观锁 `version`（@Version） | 字典 §2；现状全仓无 @Version → ERP 实体统一加 |
| 余额行（并发过账） | 事务内 `SELECT … FOR UPDATE` 按 uk_balance 定位行 → 校验禁负 → 更新 | 行级热锁范围最小；先例 CommissionCalculationService:485 |
| 订单行执行量 / fund 额度 / item 未结额 | 同上 FOR UPDATE | 跨单据额度不能只靠 version（契约 §8 明示） |
| doc_no_rule 发号 | FOR UPDATE（主键行） | 单号连续性 |
| 盘点 | 冻结范围方案（S0 同款）：stocktake 激活期间范围 内事件过账拒绝 | 契约 §6.3；B16 |

隔离级别：默认 REPEATABLE READ（MySQL 默认）足够——额度校验全部走当前读（FOR UPDATE），不依赖快照读做额度判断。**乐观锁 version 不能替代跨单据额度行锁**（契约 §8 原文，DA5 依据）。

### 6.3 与现有基础设施的关系

- `@Transactional`（DataSource = erp 池）直接可用；跨 product_archive 的只读引用（organization_companies 等）**不进同一事务**——复用主数据的写入仍走现有服务，ERP 侧只读 + 定期对账（§8）。
- 现有 `GlobalExceptionHandler` 扩展 `ErpErrorCode`（§5.2），保持 ApiResponse 外壳不变，前端零改造。
- FOR UPDATE 先例的纪律照搬：只读事务禁 FOR UPDATE（CommissionCalculationService 已有注释约定）。

## 11. 风险与保留意见

1. **本文不构成实施许可**：D01/D04/D05/D06/D08 未决，§9 各里程碑退出前必须拿到对应结论；S0 假设依旧不是生产政策。
2. **formal_* 判定基于 2026-09-17 全仓 grep**；动手归档前必须重跑验证（并行会话原则）。
3. **性能未测**：FOR UPDATE 集中在余额行，单仓高频过账的锁竞争需在 M2 用样本规模压测（蓝图 §10.2「不凭空承诺」）；必要时引入余额行分桶（按 posting_group 哈希延迟合并）——留待实测数据说话。
4. **跨 schema 引用无外键**：复用主数据的引用完整性靠应用校验 + 定期对账任务（M0 交付清单），这是同实例双 schema 方案（DA1）的固有代价。
5. **审计基类是纪律约束**：row_change_log 依赖写路径统一走 Service 基类；绕过基类的原生 SQL 更新不会留痕——实施期加 ArchUnit 规则静态检查。
6. **单位换算迁入 unit_alias 前必须人工评审**：UnitNormalizer 现表含「kg/箱→kg」这类危险映射，评审拒绝项要留痕（M05 用例）。
7. **本文与蓝图系文档一样是草案**：评审通过前，不建表、不写代码、不改现有业务行为。
