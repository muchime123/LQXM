# 销售订单产品名称与最终库存产品身份梳理

> 日期：2026-09-28  
> 范围：ERP 销售订单 → 自产配置 → 生产任务 → 产出清单 → 完工入库 → 产品库存。  
> 结论：当前问题不是“名称文案不好看”，而是基础品类、配置后产品、库存身份和来源批次仍在混用。

## 1. 当前真实链路

自产销售订单目前按下面的方式传递产品信息：

```text
销售订单选择产线、基础品类和配置
  ↓
ProductConfigurationNaming 已生成：
  nameSnapshot / specificationSnapshot
  ↓（但订单没有使用 nameSnapshot）
erp_sales_order_items.product_name_snapshot
  = productionConfig.productName
  = “手动片膜 / 气动卷膜 / 模具”等制程品类
  ↓
manufacturing_orders.product_name_snapshot
  = 同一个制程品类
  ↓
manufacturing_order_outputs.product_name_snapshot
  = 同一个制程品类，sales_product_id 通常为空
  ↓
完工质检时人工从 sales_products 选择一个旧库存产品
  ↓
产出清单补 sales_product_id / canonical_product_id
  ↓
库存名称取被选中的旧 sales_products.product_name
```

因此订单上看到的“产品名称”并不是最终产品名称，而是制程解析用的基础品类；最终库存身份也不是由订单配置自然产生，而是在完工入库时人工重新判断。

## 2. 已确认的具体缺陷

### 2.1 规则引擎生成的名称被丢弃

`ProductConfigurationService.snapshot()` 已经生成并保存：

- `nameSnapshot`，例如 `气动卷膜｜方盒200×138mm｜一出四｜220V`；
- `specificationSnapshot`；
- `baseProductId`、`configRuleId`、`configRuleVersion`；
- 规范化配置及确认事项。

但 `ErpSalesOrderService.productName()` 仍返回 `productionConfig.productName`，即基础品类。前端 `applyProductionConfig()` 也把订单行名称设置成 `config.productName`。这导致名称规则只在配置弹窗预览中有效，离开弹窗后正式业务数据退回品类名。

### 2.2 一个字段承担了三种不同含义

当前 `product_name_snapshot` 同时被当作：

1. 制程品类，如“手动片膜”；
2. 销售订单给人看的产品名称；
3. 生产产出及完工入库名称。

这三个概念不能继续共用一列。制程品类用于决定工艺，订单显示名用于沟通客户需求，库存产品身份用于聚合数量。

### 2.3 自产订单没有稳定的产品身份

自产行会主动清空 `salesProductId`。生产主产出建立时也通常不带 `sales_product_id`。直到质检入库才要求人工选择旧 `sales_products`。

结果是：

- 同一配置重复生产时，系统在完工前不知道它们是不是同款；
- 车间或质检人员必须理解旧库存产品的混乱命名；
- 选错产品会直接把库存加到错误身份上；
- 找不到旧产品时没有规范的新产品建档路径；
- 订单名称与最终库存名称可能完全不同，但系统没有表达“为什么不同”。

### 2.4 已完成的 `skuKey` 设计尚未接线

`ProductIdentityKeys` 已能从“品类 + 结构化尺寸 + 模具排列”生成稳定 `skuKey`，但当前：

- `manufacturing_order_outputs` 没有 `sku_key`；
- 销售订单明细没有产品身份快照；
- 建生产任务时没有计算并传递 `skuKey`；
- 完工入库仍按 `sales_product_id` 人工选择，而不是先按 `skuKey` 查找或建立库存产品。

### 2.5 附加产出仍未完全表达

一张工单可能产出主产品、模具和配件。当前销售订单只显示一条自产产品名称，`extraMold` 只是配置确认项，并不会自动形成明确的附加产出身份。主产品名称问题解决后，模具和配件仍应通过独立产出行表达，不能拼进主产品名称。

## 3. 正确的概念分层

建议固定为五层：

| 层级 | 示例 | 用途 | 是否身份 |
|---|---|---|---|
| 基础品类 `baseProduct` | 气动卷膜 | 决定配置规则与制程 | 否 |
| 配置快照 `configuration` | 方盒 200×138、一出四、220V | 表达客户本次需求 | 身份输入 |
| 规范显示名 `displayName` | 气动卷膜｜方盒200×138mm｜一出四｜220V | 订单、工单、入库、库存给人看 | 否，允许重复 |
| 产品身份键 `skuKey` | `气动卷膜|200x138|一出四` | 判断同款、聚合库存 | 是，唯一 |
| 生产批次/来源 | MO00001234 / FG00005678 | 追溯哪张工单生产 | 否，不参与同款聚合 |

关系应为：

```text
基础品类 + 配置
       │
       ├─ 规则引擎 → displayName / specificationSnapshot
       └─ 身份函数 → skuKey
                         │
                         ↓
                    库存产品身份
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
          工单批次 A               工单批次 B
```

同款产品由 `skuKey` 聚合；工单号和成品批次只负责追溯。

## 4. 建议的数据落位

### 4.1 销售订单明细

保留订单快照，但明确语义：

- `base_product_id`：配置目录中的基础品类；
- `process_category_snapshot`：制程品类名称；
- `product_display_name_snapshot`：规则引擎生成的产品显示名；
- `product_specification_snapshot`：规则引擎生成的完整规格；
- `sku_key_snapshot`：本次确认时计算出的身份键；
- `configuration_snapshot_json`：完整、带规则版本的配置快照；
- `sales_product_id`：若 `skuKey` 已对应正式库存产品则保存，否则可空。

旧 `product_name_snapshot` 可先兼容保留，但新写入统一写规范显示名，制程不得再通过它反推。

### 4.2 生产任务与产出清单

生产任务头继续保留一个主产品显示名方便列表展示，但制程解析必须读取 `process_category` 或配置中的 `baseProductId`。

每条 `manufacturing_order_outputs` 应保存：

- `sku_key`；
- `product_display_name_snapshot`；
- `specification_snapshot`；
- `sales_product_id` / `canonical_product_id`；
- `identity_status`：`RESOLVED`、`PENDING_PRODUCT`、`NON_STANDARD`；
- 计划数量和已入库数量。

### 4.3 产品库存

库存聚合顺序应为：

1. 有 `skuKey`：按 `skuKey` 查唯一正式产品；
2. 找到：直接复用该产品；
3. 未找到的规格化产品：按 `skuKey` 建立一条待审核产品身份，显示名取规则引擎快照；
4. 模具、配件等非标工装：使用独立身份或 `MFG-{工单号}-{产出行}`，不与主产品合并；
5. 完工入库只确认数量、仓库和必要的异常身份，不再要求每张正常工单人工搜索旧库存名称。

## 5. 页面调整

### 销售订单

自产行应显示：

```text
基础品类：气动卷膜
订单产品：气动卷膜｜方盒200×138mm｜一出四｜220V
规格摘要：盒高…；盒材质…；全部选配…
身份状态：将建立新产品 / 已匹配库存产品 / 非标独立产出
```

“产品名称”输入框不再承载自产产品。用户只选择基础品类和配置，规范名称由系统生成并只读展示。

### 生产任务

列表主标题显示规范产品名；“制程品类”单独显示。不要让用户把两者误认为同一字段。

### 完工入库

正常规格化产出若 `skuKey` 已解析，直接显示：

```text
入库产品：气动卷膜｜方盒200×138mm｜一出四｜220V
产品身份：CFG-… / 已匹配产品编码…
```

只有 `PENDING_PRODUCT` 或冲突状态才显示人工选择/建档控件。人工处理应是异常路径，不是每张工单的标准动作。

## 6. 建设顺序

### P0：名称接线

1. 销售订单保存时用服务端 `nameSnapshot` 写订单显示名；
2. 制程品类单独传给生产任务；
3. 订单、生产任务页面同时展示“产品名称”和“制程品类”；
4. 禁止前端自行拼名称。

这一阶段立即解决“新建订单产品名太粗”的问题，不改变库存账。

### P1：身份键落库

1. 给订单明细、产出清单增加 `sku_key`；
2. 服务端从最终配置快照计算 `skuKey`；
3. 把规则版本、显示名、规格和身份键作为同一份不可分割快照传到生产任务；
4. 增加同配置重复生产的契约测试。

### P2：库存产品自动解析

1. 建立 `skuKey → sales_product` 唯一映射；
2. 规格化新品自动建立待审核产品；
3. 完工入库自动复用身份，只有冲突才人工处理；
4. 库存余额按正式产品/规范身份聚合。

### P3：多产出与非标件

1. 主产品、模具、配件分别成为产出行；
2. 模具/配件补图纸号或独立名称字段；
3. `extraMold` 不能只停留在提示，必须生成待确认的附加产出；
4. 销售出库从已入库产出中选择，不再按名称猜测。

## 7. 本轮边界

- 不用历史库存名称作为新名称模板；历史名称本身没有统一标准。
- 暂不自动把 `200x138` 映射成历史压号 `2014`；后续单独建设新旧身份映射。
- 不把包材模具与本次产品模具混为一类。
- 不直接批量改写历史订单、历史产品或库存余额。
- `displayName` 只由 `ProductConfigurationNaming` 生成；`ProductIdentityKeys` 只负责 `skuKey`。

## 8. 最终判断

当前设计已有两个正确基础：结构化产品配置和规则引擎名称预览；缺的是把它们接到正式订单与库存身份上。

下一步不应继续微调输入框文案，也不应让完工人员更方便地搜索旧库存名称。应先执行 P0 和 P1，让“订单配置确认的产品”从销售订单开始就拥有规范显示名和稳定身份键，再让完工入库自动解析库存产品。

## 9. 2026-09-28 实施状态

P0、P1 已完成：

- 销售订单自产明细的 `product_name_snapshot` 改为服务端规则引擎生成的规范显示名；
- `process_category_snapshot` 独立保存制程品类，生产任务不再从最终产品名反推制程；
- 销售订单明细、生产任务和主产出行均保存同源 `skuKey`；
- 产出行增加 `RESOLVED / PENDING_PRODUCT / NON_STANDARD` 身份状态；
- 销售订单和生产任务详情同时展示规范名称、制程品类和产品身份键；
- V354 已应用，未批量改写历史订单、历史库存产品和库存余额。

P2 第一段也已完成：

- `sales_products.sku_key` 建立唯一映射，阻止同配置跨工单重复建档；
- 完工检验提交时先按 `skuKey` 自动解析产品；
- 唯一精确命中存量产品时，直接给存量产品建立身份键映射；
- 未命中时建立稳定 `CFG-{hash}` 产品档案，状态为 `PENDING_REVIEW`；
- 自动建档产品立即拥有 canonical 身份并正常进入批次、库存流水与库存余额；
- 无 `skuKey` 的模具、配件等非标产出继续走人工选择，不进行危险的模糊合并；
- 完工检验页已经把“自动解析”和“需人工匹配”分开显示。

P2 下一段是待审核产品治理：提供 CFG 待审核清单，允许确认新产品或把它安全归并到既有产品，同时迁移 canonical 库存口径。
