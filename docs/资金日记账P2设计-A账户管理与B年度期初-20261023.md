## 0. LQ 定的两个边界（本文严格遵守）

1. **多公司主体口径**：全部人民币账户合计 ≠ 某个主体的资金合计。P2-A 先补「所属主体」，支持按主体筛选；默认展示范围按财务权限与习惯定。
2. **不扩大 `CashflowOrderEvidence`**：路径锁定只是**导入数据的辅助核验**。P2 手工记账、保存流水、更新余额**不以它为前置**。核心是：正确保存收支 + 可靠期初 + 实际对账确认。

实施顺序按 LQ 拍板：A 账户管理 → B 年度期初 → C 手工录入 → D 更正 → E 保护权限。本文只覆盖 A+B。

## 1. 真库现状（设计依据）

### 1.1 `h3_cash_accounts`（35 行）

| 事实 | 对设计的影响 |
|---|---|
| 12 列，**无** `entity`、无 `status` | P2-A 要补两列（P0 草案 4.1-6 已列） |
| `account_name` 全局唯一（`uk_cash_acct_name`） | 账户身份目前就是名字；改名=换账户。P2 必须保留这条唯一约束 |
| `currency` 只有 CNY31/USD2/EUR2 | 主体筛选必须与币种筛选正交（主体内也有外币户） |
| `opening_balance`：25 户非零、10 户零，无重复值 | 这个列就是「2026 年期初」，值已可信（P0：期初+全年收支=末行结存 27/27 户）。P2-B 把它**迁移进期初表**而非另起炉灶 |
| 全部 `external_source='H3YUN'` | 账户也来自导入。entity/status 是本地维护列，导入不得覆盖 |

### 1.2 `h3_cashflow_entries`（8,751 行）

| 事实 | 对设计的影响 |
|---|---|
| **无 `account_id`**，靠 `account_name` 关联（有普通索引 `idx_cashflow_acct_date`，非唯一） | P0 草案的加列+回填（35 行映射）保留，但**归入 P2-C**（手工录入前才需要）。A+B 阶段不碰这张表 |
| `entry_date` 全在 2026-01-01 ~ 10-22，**之前零数据** | 2026 是第一个账年。P2-B 期初表首年就是「承接 `opening_balance`」，不存在历史年度回溯 |
| 无任何人工/分类列 | 同上，P2-C 一起加 |

### 1.3 主体识别：账户名前缀≠可靠主体

35 个账户名能按前缀聚出约 15 组：浙江利强(8)、于清山(5)、于帅帅(4)、于士强(2)、李红伟(2)、温州睿包(3)、安徽盒多多(2)，以及单户的 李南/祁发红/温州永铭/温州数创/宋文/浙江艺强/强子科技/利强包装微信零钱/安徽利强。

**三个不规整点**（这就是不能纯字符串切分的理由）：
- 「利强包装微信零钱」与「浙江利强*」：同主体？财务说了算；
- 「安徽利强中国银行」与「浙江利强*」：名字都含"利强"，主体不同；
- 「强子科技兴业银行」：前缀与谁都不像。

⇒ **结论：主体是人工认领的主数据，程序只做"建议初值"，不自动落库。**

## 2. P2-A 资金账户管理

### 2.1 数据模型

```sql
-- 主体字典（新表，行数=主体数，个位数到十几行）
CREATE TABLE cashflow_entities (
  id        BIGINT AUTO_INCREMENT PRIMARY KEY,
  name      VARCHAR(64) NOT NULL,
  entity_type VARCHAR(16) NOT NULL DEFAULT 'OTHER',
    -- 【LQ 修订 1】COMPANY=企业 / INDIVIDUAL=个人 / OTHER=其他资金归属
    -- Excel 中既有浙江利强、安徽盒多多，也有于清山、于帅帅等个人名义账户
  status    VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',   -- ACTIVE / INACTIVE
  note      VARCHAR(255) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_entity_name (name)
);

-- 账户表补两列（P0 草案 4.1-6 修订：entity_name 改 entity_id 外键）
ALTER TABLE h3_cash_accounts
  ADD COLUMN entity_id BIGINT NULL,
  ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',   -- ACTIVE / INACTIVE / ARCHIVED
  ADD CONSTRAINT fk_cash_acct_entity FOREIGN KEY (entity_id) REFERENCES cashflow_entities(id);
```

**为什么 `entity_id` 外键而不是 P0 草案的 `entity_name` 文本**：主体名将来可能改名（如「浙江利强」改成营业执照全称），文本列改名要刷 35 行+所有历史查询口径；外键改一行。本项目主数据改造的一贯原则（氚云镜像/字典镜像）也要求字典单一来源。

**【LQ 修订 1】主体 ≠ 企业法人**：`cashflow_entities` 的准确含义是「**资金归属主体**」。银行账户户名、账户实际控制方、内部核算归属可能不一致，**不得单凭账户名称认定法律归属**——`entity_type` 只是归类标签，程序不做任何法人推断。初始阶段允许主体未认领，但**未认领账户不得通过猜测结果形成正式的公司资金合计**。

**【LQ 修订·补充】A 阶段账户名称不可改**：流水表仍按 `account_name` 文本关联（无 `account_id`），允许改账户名 = 历史流水断链。A 阶段端点不提供改名能力；「已存在账户名称修改」放到 **P2-C 的 `account_id` 回填完成之后**再开放。

### 2.2 主体认领交互（程序建议 + 财务确认）

- 后端提供 `GET /cashflow/entities/suggest`：按账户名前缀启发式（最长公共前缀，≥2 字）给「账户 → 建议主体」映射；
- 页面一次性表格：左列账户（35），右列下拉选主体（可新建）；**保存时才落库**；
- 未认领的账户 `entity_id = NULL`，前端标「待认领」，**不参与任何按主体的合计**（宁缺勿错）。

### 2.3 查询与筛选口径

| 口径 | 规则 |
|---|---|
| 按主体合计 | 只算 `entity_id = X AND currency = 'CNY'`；跨币种合计**永远不直接相加**（沿用 P1 口径，外币只给笔数与原币余额） |
| 默认展示范围 | 默认**全部有权限的账户**（现状兼容）；「我的主体」快捷键按员工-主体授权过滤（P2-E 再做授权表） |
| 【LQ 修订 2】停用账户 | **停用只影响未来操作，绝不改变历史统计结果**：<br>① 当前账户管理：默认隐藏，`includeInactive=1` 可查看；<br>② 新增流水（P2-C 起）：停用户默认不可选；<br>③ 历史流水查询：**正常查询**；<br>④ 历史期间汇总（含按主体合计）：**正常统计**——2027 年查 2026 年报表，当年内停用的账户必须照常出现；<br>⑤ 当前资金账户余额：按查询口径展示，前端提供「含停用」筛选开关 |
| 导入保护 | 账户导入的 `ON DUPLICATE KEY UPDATE` 列清单里**不得出现** `entity_id`/`status`（P0 4.3 的同一条原则，提前到 A 执行） |

### 2.4 端点（A 阶段）

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /cashflow/entities` | `cashflow.read` | 字典列表（含 entity_type）+ 各主体账户计数 |
| `POST /cashflow/entities` | `cashflow.manage` | 新建主体（name + entity_type） |
| `PUT /cashflow/entities/{id}` | `cashflow.manage` | 改名/改 entity_type/停用（改名不影响账户外键） |
| `POST /cashflow/accounts/assign-entity` | `cashflow.manage` | 批量认领 `{accountId → entityId}` |
| `PUT /cashflow/accounts/{id}/status` | `cashflow.manage` | 停用/启用（只影响未来操作，见 §2.3） |

A 阶段**不提供**账户改名端点（§2.1 的 LQ 修订·补充）。

权限码沿用 P0 4.4 并按 LQ 要求收紧为**读/管两个独立码**：
- `cashflow.read`：财务数据读取权限。**A 阶段虽不做员工-主体细粒度授权，但不能默认所有系统用户可见财务数据**——所有 `/cashflow/**` 读端点挂 `@RequirePermission("cashflow.read")`；
- `cashflow.manage`：管理权限（主体 CRUD、认领、停用、期初操作），**不**从 `integration.h3` 继承。

**【LQ 修订 5·A-0 范围必须含存量路由】**：P1 的实际接口前缀是 **`/api/cashflow-journal/**`**（`CashflowJournalController`），不是新设计的 `/cashflow/**`。A-0 必须**同时**处理：
1. `CashflowJournalController` 类级 `@RequirePermission("cashflow.read")`——否则会出现新账户接口已限权、旧资金日记账仍凭 `integration.h3` 看全量财务数据的漏洞；
2. 前端资金日记账路由 + 侧边栏入口挂 `cashflow.read` 门禁；
3. `system_role_feature_grants` 只授财务/管理员角色（V386 铁律：授权须同落 grants 表）。

⚠️ 存量用户回填：两个权限码落地时须同落 `system_role_feature_grants`，初始只授给财务/管理员角色。

## 3. P2-B 年度期初

### 3.1 数据模型（P0 草案 4.1-3 基本沿用，两处修订）

```sql
CREATE TABLE cashflow_account_opening (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  account_id   BIGINT NOT NULL,
  fiscal_year  SMALLINT NOT NULL,
  amount       DECIMAL(18,4) NOT NULL,
  source       VARCHAR(16) NOT NULL,      -- H3_OPENING / CARRY_FORWARD / MANUAL_OPENING
  active       TINYINT(1) NOT NULL DEFAULT 0,   -- 【LQ 修订 3】「可用于计算」：=1 才进 before_net/期初口径
  finance_confirmed TINYINT(1) NOT NULL DEFAULT 0,  -- 【LQ 修订 3】「财务人工已核对」：独立状态，与可计算无关
  confirmed_by BIGINT NULL,
  confirmed_at DATETIME NULL,
  basis        VARCHAR(255) NULL,         -- 【LQ 修订 4】期初依据（人工期初必填）
  note         VARCHAR(255) NULL,         -- ① 结转差额说明
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_opening (account_id, fiscal_year),
  CONSTRAINT fk_opening_acct FOREIGN KEY (account_id)
    REFERENCES h3_cash_accounts(id)          -- ② 新增：账户删除前先清期初
);
```

修订理由：① 追溯调整产生差额时，`note` 是唯一能说明"为什么 2027 期初 ≠ 2026 确认期末"的地方；② 无外键时删账户会留孤儿期初（本项目删表铁律：先解外键、拓扑序）；③④ 见下。

**【LQ 修订 3】「可计算」与「财务已核对」是两回事，拆成两个字段**：
- P0 对拍证明的是 `期初 + 收入 − 支出 = 来源期末`，**并不能独立证明期初金额与真实银行余额核对一致**；
- `active=1`：该值可参与报表计算（延续 P1 口径）。2026 迁移行 `active=1, finance_confirmed=0`——报表结果不变，但**界面不得展示为"财务已核对"**，展示为「迁移值·待财务核对」；
- `finance_confirmed=1`：财务人工核对通过，须记 `confirmed_by/at`。核对动作属于 P3 的对账闭环，B 阶段只留状态位和记录字段，不假装已完成。

### 3.2 期初的三个来源与优先级

| source | 何时产生 | active 初值 | finance_confirmed 初值 |
|---|---|---|---|
| `H3_OPENING` | P2-B 上线时迁移：把 `h3_cash_accounts.opening_balance` 35 行写为 **2026 年期初**（依据：P0 对拍 27/27 户闭合，口径延续） | 1（可直接用于计算） | 0（**待财务核对，界面不得显示"已核对"**） |
| `CARRY_FORWARD` | 上年 12 月期间对账 CONFIRMED 后，自动生成下年候选行 | 0 | 0 |
| `MANUAL_OPENING` | 【LQ 修订 4+6】有权限的财务**人工建立期初**：填金额 + `basis` 依据（必填）+ `note`；保存生效时 `active=1`、`finance_confirmed=0`（**已生效·待核对**）——提交依据 ≠ 银行余额已核对；后续财务核实银行账单后单独确认 `finance_confirmed=1`（记录 confirmed_by/at） | 确认时置 1 | **不随保存置 1**，核实依据后单独确认（【LQ 修订 6】） |

**`h3_cash_accounts.opening_balance` 列的去留**：P2-B 上线后该列降级为「只读的 2026 期初镜像」，新年度不再用它；`validatePeriod` 放开时，所有 `before_net` 类 SQL 的硬编码 `'2026-01-01'` 起点改为**查期初表**（`fiscal_year = YEAR(start)` 的 confirmed 行）。这一条是 B 阶段最大的代码改动点，涉及 `CashflowJournalController.accounts` 与 `monthly` 两处 SQL。

### 3.3 下年期初的两条路径（【LQ 修订 4】：不让 2027 记账依赖尚未开发的 P3）

**路径一：正常结转（自动）**
```
上年 12 月期间存在 CONFIRMED 对账记录（cashflow_reconcile_confirmation）
  → 允许生成下年 CARRY_FORWARD 候选（active=0）
  → 财务确认 → active=1 生效
上年未结账 ⇒ 结转接口返回 409，不生成候选   ← 只约束「自动结转」这条路
上年结账后追溯调整 ⇒ 只算差额写提示 + note，绝不自动改已生效期初
```

**路径二：人工建立期初（并行可用）**
```
有 cashflow.manage 权限的财务直接录入下年期初：
  金额 + basis（依据，必填，如"2026-12-31 银行对账单余额"）+ note
  → 保存生效 active=1（新年度即可记账），finance_confirmed=0（【LQ 修订 6】已生效·待核对）
  → 财务核实银行账单后单独确认 finance_confirmed=1（confirmed_by/at 留痕）
  → 全程审计（created_at/confirmed_by + 保留原值可查）
人工期初不假装已完成上年对账，也不假装银行余额已核对；生效后界面明确提示
「XX 年度尚有未完成的上年核对事项」「该期初尚未经银行余额核对」。
```

**依赖诚实化**：`cashflow_reconcile_confirmation` 属 P0 草案 4.1-4 的表，但对账确认操作属 **P3**。B 阶段交付的是期初表 + 2026 迁移 + validatePeriod 放开 + **两条路径的端点**——路径一在 P3 前会因无对账记录而 409（正常空转），路径二**不依赖 P3**，P3 延迟也不阻断财务启用新年度账本。

### 3.4 `validatePeriod` 放开条件 + **【LQ 修订 7】期初状态按账户判断**

```java
// 伪码
int year = start.getYear();
if (!Objects.equals(year, end.getYear())) return error("期间不得跨年");   // 跨年仍禁
if (year < 2026) return error("早于首个账年");
if (!openingRepository.hasActive(year)) return error("该年度期初未生效"); // 年度级：该年一条 active 期初都没有才拦
// 2026 由 H3_OPENING 迁移行（active=1）天然满足 ⇒ 行为与 P1 完全一致；2027 起走结转或人工期初
```

**年度级 `hasActive` 只是入口闸门，不是计算口径**。期初是否可用必须**逐账户判断**（LQ 修订 7）：
- 2027 年哪怕只有工商银行一家建立了期初，年度也可以进入查询；
- **已有** active 期初的账户：正常计算期初+收支=期末；
- **缺少** active 期初的账户：**不得把期初当 0**——该账户行显示「期初未建立，期末不可计算」，收入/支出笔数照常给出，余额列置空并标注原因；
- 汇总行只累加**可计算账户**，并在汇总旁标注「N 户因期初未建立未计入」。

⇒ `fiscal-years` 返回年度是否可进入；账户列表接口按 `{accountId, year}` 逐户判 `hasActiveOpening`，派生 `openingStatus: ACTIVE | MISSING` 字段。

前端 `useCashflowPeriod.ts` 的 2026 上限改为**读接口返回的可用年度列表**（`GET /cashflow/fiscal-years`），不再硬编码。

### 3.5 端点（B 阶段）

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /cashflow/fiscal-years` | `cashflow.read` | 可用账年列表（期初表 DISTINCT fiscal_year WHERE active=1） |

| `POST /cashflow/accounts/opening/carry-forward/{year}` | `cashflow.manage` | 生成下年候选；上年未结账 → 409（仅自动路径受闸门约束） |
| `POST /cashflow/accounts/opening/manual` | `cashflow.manage` | 【LQ 修订 4+6】人工期初：`{accountId, fiscalYear, amount, basis(必填), note}`；生效 active=1、finance_confirmed=0（已生效·待核对）；审计留痕；返回「上年未完成核对事项」+「期初未经银行核对」提示 |
| `POST /cashflow/accounts/opening/{id}/finance-confirm` | `cashflow.manage` | 【LQ 修订 6】财务核实银行账单后单独确认 finance_confirmed=1（confirmed_by/at） |
| `POST /cashflow/accounts/opening/confirm` | `cashflow.manage` | 批量确认 CARRY_FORWARD 候选行（幂等：只确认 active=0 的行） |

## 4. A+B 的边界（防 overrun）

| 刻意不做 | 理由 |
|---|---|
| 流水表加列 / account_id 回填 | P2-C 手工录入才需要，且加列后导入保护要同批改，放一起做一次验证 |
| `CashflowOrderEvidence` 接入手工流水 | LQ 边界 2：手工数不进路径锁定 |
| 员工-主体授权表 | P2-E；但 A 阶段所有财务读端点仍挂 `cashflow.read`（§2.4），不默认全员可见 |
| 已存在账户的名称修改 | P2-C 的 `account_id` 回填完成后才开放（历史流水按账户名关联，A 阶段改名=断链） |
| 对账确认页面 | P3；B 阶段只建表和闸门判断，人工期初路径（§3.3 路径二）不依赖它 |
| 币种折算/本位币汇总 | 财务未提需求，外币维持 P1 的"只给原币"口径 |
| 财务科目体系 | LQ 原话：业务分类字典随手工录入一起完成 |

## 5. 实施切片（每片可独立验收）

| 切片 | 内容 | 验收断言（写进验收脚本） |
|---|---|---|
| A-0 | `cashflow.read` / `cashflow.manage` 权限码 + 角色授予（同落 grants 表）；**存量收口**：`CashflowJournalController` 类级 `@RequirePermission("cashflow.read")` + 前端资金日记账路由/侧边栏门禁 | 无权限员工访问 `/cashflow/**` 与 `/api/cashflow-journal/**` 读端点 → 403；此前凭 `integration.h3` 能看资金日记账的员工、无 `cashflow.read` 时同样 403（漏洞关闭的证据）；财务/管理员角色可读 |
| A-1 | `cashflow_entities` 表（含 entity_type）+ 主体 CRUD + 建议初值接口 | 建议表覆盖**能识别的账户**；识别不出的明确标「待认领」——**不要求 35 户全有建议**（LQ 调整）；未确认前 `entity_id` 全 NULL |
| A-2 | 账户列表/汇总加 `entityId` 筛选 + 「待认领」徽标 | 按主体筛选后，CNY 合计 == 手工加总该主体 CNY 账户余额（闭环断言）；`entity_id=NULL` 账户不出现在任何主体合计 |
| A-3 | 账户停用 | 停用户从默认账户管理列表消失但 `GET /accounts?includeInactive=1` 可见；**历史流水查询正常；历史期间汇总（含按主体合计）数值与停用前逐位一致**（LQ 修订 2 的核心断言：停用前后跑同一期间对拍，diff 为空） |
| B-1 | 期初表 + 2026 迁移（H3_OPENING, active=1, finance_confirmed=0） | 迁移后 35 行；逐户 `amount == h3_cash_accounts.opening_balance`（迁移前后闭环）；界面/接口口径为「迁移值·待财务核对」 |
| B-2 | `validatePeriod`/`before_net` 改查期初表 | **回归断言：P1 的 34 项验收脚本仍全绿**（口径必须逐位不变）；`GET /accounts?start=2026-01-01` 与改前逐字段 diff 为空 |
| B-3 | 结转端点+闸门 + **人工期初端点**（LQ 修订 4+6+7） | 2026→2027 自动结转返回 409（2026-12 未到，仅自动路径）；人工期初：缺 basis → 400；成功后 active=1、**finance_confirmed=0**（待核对）；finance-confirm 端点确认后 =1；年度仅 1 户有期初时其余账户行 `openingStatus=MISSING`、余额不为 0 而是标注不可计算；确认端点对 active=1 行幂等 |
| B-4 | 前端期间选择器读 `fiscal-years` | 2026 可选；页面上不再出现写死 2026；期初展示区分「迁移值·待财务核对」与「财务已核对」两种徽标 |

**B-2 是风险最高的切片**：`before_net` 起点从常量改查表，动了所有期间金额的来路。所以它的验收不是新功能，而是**P1 34 项断言原样全绿 + 独立 SQL 对拍**。
