# 氚云导入链路 —— 不足与优化清单

> 核查日期：2026-09-14
> 方法：逐文件读源码 + 迁移脚本 + 测试目录，凡结论均给出行号与证据。
> 配套文档：`氚云导入全链路设计梳理-20260914.md`（讲"是什么"）、本文（讲"哪里不行"）。

---

## 0. 总体判断

链路骨架是对的：Excel 只解析一次、事实写完不等于批次完成、导入不猜身份、读合写分。
**主要欠账不在架构，在"守卫"和"规模"两个维度**：

- **守卫缺失**：这套设计大量依赖"人工纪律"维持正确性（三处同口径、人工结论复用、映射不被覆盖），但几乎没有自动化守护。纪律一旦破防，后果是**静默的**——不报错，只是数据悄悄错。
- **规模未验证**：多个环节是"全量入内存 + 逐条 SQL + 单事务"，在当前数据量下能跑，量级上台阶就会暴露。

按"出事概率 × 出事后果 × 修复成本"排序，下面展开。

---

## 一、正确性风险（会静默出错，最高优先级）

### 1.1 产品来源键三处同口径，零守护测试 ⚠️ 最高危

**现状**：同一个业务概念"出库明细行的产品来源键"由三段代码独立实现：

| # | 位置 | 形态 |
|---|---|---|
| 1 | `service/SourceIdentityService.java:2181` | Java 方法 `productSourceKey()` |
| 2 | `service/SourceIdentityService.java:2093` | 回填 SQL 里的 `CONCAT('NAME|',SHA2(...))` |
| 3 | `service/OutboundRelationGovernanceService.java:34` | SQL 常量 `PRODUCT_KEY_EXPR` |

第 30–36 行注释明确写着"必须与 productSourceKey 及库内既有口径一致"——**用注释约束的契约**。

**证据**：`grep -rln "productSourceKey\|PRODUCT_KEY_EXPR" backend/src/test/` → **零命中**。

**后果**：改任一处、漏改另两处，重导后所有人工产品归类结论**静默失效**（不报错，只是匹配不上，重新变回待归类）。发现时通常已经是几周后，且无法判断是"漏改"还是"业务变化"。

**建议**：
- 立刻补一个契约测试：用同一组输入（有编码 / 无编码+中文名+规格+单位 / 全空）分别调用 Java 方法与在 MySQL 里执行 `PRODUCT_KEY_EXPR`，断言结果字符串完全相等。这条测试能在 30 分钟内写完，挡住后续所有此类事故。
- 中期：把键的生成收口到**一处**——SQL 侧改为调用 Java 预计算并存列，或反过来由 SQL 生成、Java 只读取，消灭"两份实现"这个前提。

---

### 1.2 确认阶段无 CAS 守卫，存在 TOCTOU 竞态

**证据**：`service/H3FactImportService.java:1104-1128`

```java
if (List.of("CONFIRMING","COMPLETED").contains(status)) { ...幂等返回... }   // 1109 读状态
if (!"PREVIEW_READY".equals(status)) throw ...                                // 1119 判状态
...
jdbc.update("UPDATE h3_import_batches SET status='CONFIRMING', ... WHERE id=?", batchId); // 1128 无状态条件
```

**问题**：第 1128 行的 UPDATE **没有 `AND status='PREVIEW_READY'` 条件**。两个并发请求（用户双击 / 前端重试 / 双标签页）可以同时通过 1109–1121 的检查，然后并行进入 1136 起的写库循环。

**后果**：
- `created_count` / `updated_count` 计数翻倍失真；
- `H3PostImportAsyncService` 编排跑两遍（编排本身幂等，但浪费且日志混乱）；
- `commissions.trackOutboundChanges` 对同一批出库单重复跟踪，可能产生重复的提成变化记录。

**修法**（一行）：
```sql
UPDATE h3_import_batches SET status='CONFIRMING', ... WHERE id=? AND status='PREVIEW_READY'
```
然后检查 `update()` 返回的受影响行数：为 0 说明别人已经抢先，直接走幂等返回路径。

---

### 1.3 异步收尾失败：无重试、无补偿入口

**证据**：`service/H3PostImportAsyncService.java:24-36`

```java
} catch(Exception e) {
    jdbc.update("UPDATE h3_import_batches SET status='PARTIAL_FAILED', ... error_message=?, ...");
    return;   // ← 到此为止，没有重试、没有告警、没有补偿入口
}
```

同时 `controller/H3ImportBatchController.java` 全文 **grep 不到任何 retry / rebalance / reorchestrate 端点**。

**后果**：批次一旦进入 `PARTIAL_FAILED`，**没有任何接口能让它重跑收尾**。用户唯一的出路是重新导入整批数据——而这一步会再次触发同样的失败。当前 `REBALANCE_OUTBOUND_SNAPSHOTS` 只在确认流程内部被调用，不通人工。

**建议**：
- 加 `POST /api/h3-imports/batches/{id}/reorchestrate`，内部复用 `orchestrator.orchestrateAfterImport`，仅允许 `PARTIAL_FAILED` 状态调用，权限 `integration.h3.manage`。
- 编排步骤本就设计为幂等（这一点做得好），所以重跑是安全的——这是它能廉价补齐的前提。
- 前端批次列表的 `PARTIAL_FAILED` 行加一个"重跑收尾"按钮。

---

### 1.4 应用重启留下僵尸批次

**证据**：`H3PostImportAsyncService` 用 `@Async("h3ImportExecutor")`（第 23 行）。线程池任务**不持久化**。

**后果**：应用在 `CONFIRMING` / `ORCHESTRATING` 阶段被重启（发版、OOM、手动 kill），该批次**永远停在非终态**。前端 `H3ImportCenterView.vue:892-895` 的轮询逻辑是"列表里存在非终态批次就每 5s 刷新一次"，于是每次打开导入中心都会看到它转圈，永远等不到结果。

**建议**：
- 启动时扫一遍 `status IN ('CONFIRMING')` 且 `completed_at IS NULL` 且 `updated_at` 超过 N 分钟的批次，标 `PARTIAL_FAILED` 并写 `error_message='应用重启导致编排中断，可重跑收尾'`。
- 配合 1.3 的重跑端点，就形成闭环：中断 → 标失败 → 一键重跑。
- 另外建议给 `h3_import_batches` 加 `updated_at` 自动更新（若尚无），否则判不出"卡了多久"。

---

### 1.5 银行级操作零审计

**证据**：`controller/H3ImportBatchController.java` 与 `service/H3FactImportService.java` 全文 grep `audit` → **零命中**。

**后果**：导入、确认、全量重置（`/reset/execute`）这三类高危操作**没有操作人、时间、影响范围的审计记录**。`h3_reset_runs` 表只记了运行本身，不记"谁点的"。出了数据事故无法回溯。

**建议**：把 `/reset/execute`、`/batches/{id}/confirm` 纳入既有审计机制（若项目有统一审计切面，挂上去即可）。

## 二、规模与性能（当前能跑，量级上台阶就崩）

### 2.1 暂存回读全量入内存

**证据**：`service/H3FactImportService.java:1124` → `loadStagingGroups(batchId)`（实现见 1392 行），一次性 `jdbc.query` 把**所有组**的 `main_json` + `rows_json` 反序列化成 `List<Group>`。

**问题**：上传上限配到了 **2GB**（`application.yml:38-39 max-file-size: 2GB`）。解析阶段已经做了流式处理（`OPCPackage` 事件模式，第 143 行，且 137 行注释明确说明是为了避免 `XSSFWorkbook` 堆耗尽——**这点做得很好**），但确认阶段又把全量读回内存，把前面的收益还回去了。

**建议**：`loadStagingGroups` 改按 `row_seq` 游标分片（如每 500 组一批），循环内写库。`uk_h3isr_batch_seq (batch_id, row_seq)` 唯一键天生支持这种顺序扫描，改造代价不高。

---

### 2.2 暂存写入逐条 INSERT

**证据**：`service/H3FactImportService.java:1281-1290`，`insertStagingSlice` 是 `for` 循环内逐条调 `pipeline.insertStagingRow(...)`（单条 `jdbc.update`）。

**建议**：`JdbcTemplate.batchUpdate` 按 slice 批量提交，吞吐通常有 5–10 倍提升。

---

### 2.3 确认是单个巨型事务

**证据**：`confirmFromStaging` 整个方法标注 `@Transactional`（第 1103 行），循环体（1136–1183）在**同一事务内**完成所有事实表写入 + 所有子表写入 + `h3_import_rows` 审计写入。

**后果**：大批次下是典型的长事务——undo log 膨胀、行锁持有时间长、任一条失败全量回滚（代价 = 重跑整批）。且事务内还夹着 `updateProgress` 写库（推进度百分比），进一步拉长事务。

**建议**：分片提交。按组批次（500/批）各自独立事务，用批次级状态 + 一个"已提交到 seq=N"的水位线保证可恢复。这会牺牲"全批原子性"，但对导入场景而言，"部分成功 + 可续跑"比"全或无"更实用——况且设计上已经允许 `PARTIAL_FAILED` 这个中间态了。

---

### 2.4 同一份单据 JSON 在库里存三遍

| 存储点 | 字段 | 用途 |
|---|---|---|
| `h3_import_staging_rows` | `main_json` | 预览/确认 |
| `h3_import_staging_rows` | `rows_json` | 预览/确认 |
| `h3_import_rows` | `raw_data`（`groupJson(group)`，见 725 行） | 审计留痕 |

`saveImportRow` 把 `groupJson` 里 `main` + `rows` 又完整序列化一份写审计表。加上暂存表本身的两列，**同一份源数据落库三份**。

**建议**：审计表 `raw_data` 改为只存 `source_hash` + 差异摘要；需要原始报文时从暂存表按 `(batch_id, external_id)` 回查（`idx_h3isr_batch_external` 就是为这个建的）。或者审计表只存 `external_id`，彻底依赖暂存表——但要注意 2.6 的清理策略会冲突。

---

### 2.5 暂存表无清理策略

**证据**：`h3_import_staging_rows` 全仓只在 4 个 Java 文件 + `V173__create_h3_import_staging_rows.sql` 出现；`grep "DELETE FROM h3_import_staging_rows\|TRUNCATE.*staging"` → **零命中**（唯一例外是 `H3ResetService:152` 的全量重置会清空它）。

**讽刺点**：建表脚本第 41–42 行专门建了 `KEY idx_h3isr_parsed_at (parsed_at) COMMENT '按解析时间清理过期暂存行'`——**索引建了，清理逻辑从来没写**。

**后果**：暂存表随时间无限膨胀，成为库里最大的表之一。而它存的是"临时数据"，理论上确认后即可释放。

**建议**：加一个清理任务，删除 `parsed_at < NOW() - INTERVAL 30 DAY` 且批次已终态的暂存行。不建议"确认即删"——预览回看和问题排查还需要它，保留 30 天是合理折中。

---

### 2.6 失败报告定位不到 Excel 原始行

**证据**：`saveImportRow`（725 行）`INSERT INTO h3_import_rows(... source_row_number ...) VALUES(?, ?, NULL, ...)` —— **恒传 NULL**。

**后果**：批次失败报告（前端 `H3ImportCenterView.vue` 的 CSV 导出）无法给出"是 Excel 第几行出问题"，用户只能凭 `external_id` 自己回表里找。

**建议**：解析阶段记录每个组对应的起始行号，存进 `h3_import_staging_rows`，确认时透传到 `h3_import_rows`。

## 三、治理闭环缺口（功能层）

### 3.1 库存目标值直接修正，未分层 ⭐ 业务影响最大

**现状**：仓库明细全量导入 → `ProductInventoryMergeService` 直接修正库存目标值。

**问题**：**"系统启用前的期初" 与 "启用后的盘点差异" 被混为一谈**。启用后每次导入都会把差异**无声抹平**，不留痕迹。管理层看不到"这个月仓库报了 3 次差异"这类信号。

**建议**：按启用日期分层——
- 启用日之前 → 作为期初直接设定；
- 启用日之后 → 不直接覆盖，生成**对账差异记录**，经人工确认后转成库存调整流水。

### 3.2 收款核对链未建

`收款记录` / `多订单结清` 两类事实目前只做台账落入，与**出库单内嵌的收款快照**之间没有核对。同一笔收款在两条来源里金额/日期不一致时，系统不提示。

**建议**：建只读核对链，产出 `MATCHED / AMOUNT_DIFFERENT / DATE_DIFFERENT / MISSING_* / REVIEW` 状态，**只提示矛盾，不改权威金额**（与"导入不猜身份"同一原则）。

### 3.3 批次结果视图只有解析进度

批次详情当前展示的是解析进度与计数，缺少"这次导入**业务上**造成了什么"——新增/修正了多少客户、多少出库单身份被自动绑定、多少进了复核队列、多少金额发生变化。

**建议**：批次详情补"事实 / 身份 / 业务 / 财务"四类影响卡片 + 各自跳转入口，让导入从"技术动作"变成"业务结果"。

### 3.4 客户地区治理仍是纯人工触发

好消息：建档时已带省市区（`createPendingCustomer` 内部调 `ChinaAddressParser.parseLoose`），这是上一轮刚补齐的。

缺口：解析**失败或退化**的地址（`UNCLEAR / UNRECOGNIZED / PARTIAL`）只是静静躺在库里，需要人去点"批量诊断"。没有"新导入客户的异常地址自动进复核队列"的机制。

**建议**：导入收尾时，把本批新客户里 `address_tidy_status` 非 `NORMAL` 的自动推入地区复核待办，与身份复核队列（`V271` 那套）同一形态。

### 3.5 血缘抽屉仍有历史模型残留

批次追溯抽屉里还能看到属于**旧匹配模型**的候选/业务单信息。既然旧链路已整体下线，这些残留会误导排查。

## 四、可维护性

### 4.1 测试覆盖与风险严重程度严重不匹配 ⭐

**证据**：`backend/src/test` 共 30 个测试文件，氚云相关仅 5 个：

| 有测试 | 无测试（且都是高风险大文件） |
|---|---|
| `H3EmployeeIdentityServiceTest` | `H3FactImportService`（**1434 行**，核心写入逻辑） |
| `H3FactImportServiceCustomerNameParseTest` | `SourceIdentityService`（**2308 行**，客户识别优先级 + 来源键） |
| `H3ImportOrchestratorServiceTest` | `OutboundRelationGovernanceService`（**789 行**，全部治理 SQL） |
| `BatchImportPipelineServiceTest`（165 行服务） | `ProductInventoryMergeService`（432 行，库存写入口） |
| `ImportKindDescriptorTest` | `H3BusinessQueryService`（592 行，全量读端点） |

**前端 h3 测试：0 个。**

最要命的是：**恰好是最容易出错、后果最隐蔽的三块——客户识别优先级、产品来源键、地区解析——没有任何测试**。这三块的 correctness 目前完全靠人工纪律。

**建议**（按性价比排序）：
1. 产品来源键三处一致性契约测试（见 1.1）——**半天内可完成，挡掉最高危风险**；
2. `SourceIdentityService.resolveCustomer` 的优先级表测试——把它那套"已确认簇 → 名称级复用 → 电话唯一 → 名称+电话 → 名称+地址 → 仅名称，多候选/泛化名一律 REVIEW"的决策表，用参数化测试逐条钉死；
3. `ChinaAddressParser.parseLoose` 的回归样本集——把已知踩过的坑（石家庄无后缀、吉林市省市同名、马鞍山市、长沙市 vs 长沙县）固化成用例。

### 4.2 `H3ImportCenterView.vue` 已超阈值

**证据**：`wc -l` → **1080 行**，超出 `AGENTS.md` 里"Vue 文件 > 1000 行需拆分"的约定。

**建议**：按既有惯例拆 composables（项目已有 `composables/catalog/`、`composables/upload/`、`composables/list/` 三套先例）：批次列表与轮询 / 上传与解析 / 预览与确认 / 台账浏览 四块各自独立。

对照：`H3OutboundRelationView.vue` 仅 256 行、`CustomerView.vue` 575 行，都健康。只有导入中心这一个超标。

### 4.3 读权限"任一放行"粒度偏宽（已知取舍）

`H3ImportBatchController` 的读者只要持有 `integration.h3` **或** `product_inventory.read` 任一，即可读**全量**台账（六类）。

这是有意的过渡设计（文档第 27–28 行有说明，为不破坏 B 域既有只读调用）。但意味着 **B 域只读用户能看到 A 域全部销售数据**。如果 B 域用户范围比 A 域宽（比如仓库管理员多于销售管理者），这是个隐性数据暴露。

**建议**：列入待办，待 B 域调用方全部迁移后收紧为"按 kind 校验对应域权限"。
