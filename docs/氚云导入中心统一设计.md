# 氚云导入中心统一设计（现状梳理 + 目标规范 + 迁移路线图）

> 版本：2026-09-03　|　状态：设计稿（本轮不改代码）
> 范围：前端 `H3ImportCenterView.vue` 与相关 API 层、后端 `/api/h3-facts`、`/api/product-inventory` 两套导入管线、共享的 `h3_import_batches` 批次模型。
> 阅读对象：负责氚云导入 / 产品库存域的开发与评审人员。

---

## 0. 一句话结论

氚云导入中心已经"长成两套同构管线"：

1. **四类业务事实导入**（outbound/production/receipt/settlement），落 `sales_outbounds`、`production_orders`、`receipts`，确认后触发结算/毛利/佣金/匹配等**自动编排**，具备完整进度与终态语义；
2. **两类产品台账导入**（catalog/stock = 产品信息/仓库明细），落 `h3_product_catalog`、`h3_warehouse_stock`，只增改不覆盖，**确认是同步事务**，无编排、无 CONFIRMING/部分失败语义。

两套管线**共用同一张批次表 `h3_import_batches` 与暂存表 `h3_import_staging_rows`、同一个异步执行器 `h3ImportExecutor`、同一份 `BatchProgress` 形状**，但各自复制了整套「登记批次→哈希幂等→异步解析→落暂存→进度更新→预览→确认→失败打标」逻辑，端点为两套前缀与两套权限，前端也各写了一套入口卡、类型与轮询函数。**统一的目标不是消灭差异（业务行为确实不同），而是把「导入骨架」收敛为一份契约 + 每类数据源只保留一个 Handler 定义差异。**

## 1. 领域全景（现状 as-is）

### 1.1 与导入中心相关的管线

| 域 | 控制器前缀 | 服务 | 数据类型(data_type) | 目标表 | 是否有批次/进度 | 是否本中心页面 |
|---|---|---|---|---|---|---|
| A. 四类业务事实导入 | `/api/h3-facts` | `H3FactImportService` + `H3ImportOrchestratorService` | `OUTBOUND / PRODUCTION / RECEIPT / SETTLEMENT` | `sales_outbounds`、`production_orders`、`receipts` | 是，全状态机 | 是（4 张卡） |
| B. 产品台账批次导入 | `/api/product-inventory` | `ProductInventoryLedgerImportService` | `PRODUCT_INFO / WAREHOUSE_STOCK` | `h3_product_catalog`、`h3_warehouse_stock` | 是，子集状态机 | 是（2 张卡） |
| B2. 台账合并入库 | `/api/product-inventory` | `ProductInventoryMergeService` | —（无文件、无批次） | `product_inventory_balances`、`product_inventory_transactions`、`sales_products` | 否（同步预览/确认） | 是（1 张卡：库存合并入库） |
| C. 期初库存准备（旧/历史入口） | `/api/h3-preparation` | `ProductInventoryService.prepareOpening/postOpening` | `STOCK`（H3 原始） | `product_inventory_opening_*` → 余额 | 独立旧表 `h3_preparation_batches` | 否（另一入口，不在本页） |

> 结论：**A、B 是同构的"批次导入"；B2 是导入后的下一跳（按台账合并库存）；C 是历史遗留入口**，本文只统一 A/B，B2/C 仅在命名与页面组织上对齐。

### 1.2 共享数据模型

两张核心表（A/B 共用，是天然的统一载体）：

- `h3_import_batches`（批次主表）
  - 基线字段（V126 之前）+ V172 扩展：`file_size`、`file_hash CHAR(64)`（`(data_type,file_hash,status)` 幂等索引）、`progress_pct 0~100`、`progress_stage VARCHAR(64)`（V195 由 30→64）、`field_version`、`preview_json LONGTEXT`（预览缓存）、`error_message`、`error_detail TEXT`（≤64KB 堆栈）。
  - 统计字段：`total_count / created_count / updated_count / unchanged_count`、`completed_at`。
  - V190 候选统计：`candidate_total / candidate_pending / candidate_confirmed / candidate_rejected / candidate_stats_updated_at`（仅收款类编排/裁决使用）。
  - V135 遗留：历史 `data_type='NORMAL'` 已迁移为 `OUTBOUND`，但前端/后端仍保留 `NORMAL→OUTBOUND` 防御归一（见 R6）。
  - V194 终态归一：历史 COMPLETED 批次补齐 `progress_pct=100 / progress_stage='DONE' / completed_at`；带错误历史批次置 `PARTIAL_FAILED`。
- `h3_import_staging_rows`（V173 暂存行表）：A/B 共用的"落暂存、预览与确认从 DB 读"结构。
- A 特有：确认后写入行级原始快照 `h3_import_rows`，并在 `preview_json.orchestration` 缓存编排结果。

### 1.3 后端入口与权限（现状）

**A 域：`H3FactImportController`**（类级 `@RequirePermission("integration.h3")`，前缀 `/api/h3-facts`）

**B 域：`ProductInventoryController`**（类级 `@RequirePermission("product_inventory.read")`，前缀 `/api/product-inventory`）

| 端点 | 方法 | 作用 | 权限 |
|---|---|---|---|
| `/{kind}/stage`（kind=catalog|stock） | POST | 上传登记批次 → 后台异步解析 | 方法级 `product_inventory.manage` |
| `/ledger-batches/{id}/progress` | GET | 进度轮询（BatchProgress 同形） | 读（类级） |

| `/merge/preview`、`/merge/confirm` | POST | 合并入库（B2，无批次） | confirm 方法级 manage |
| `/ledger-batches/{id}/progress` | GET | —— 与上表 progress 重复列出，见上 | |

**差异点：**

- **前缀不一致**：A 全部收在 `/h3-facts`；B 中"导入/批次"收在 `/product-inventory/ledger-batches`，而 B 域批次**也出现在 A 域的 `/h3-facts/import-batches` 列表里**（同一张表）——「批次」语义被拆到两个前缀，查询入口却在另一个域。
- **权限码两套**：`integration.h3` vs `product_inventory.read/manage`。当前页能同时看到两域，说明实际用户被授予了权限并集；但「产品台账导入」依赖 `integration.h3` 的批次列表做展示，是**隐式耦合**。
- **返回信封不统一**：A 用强类型 DTO（`StageAccepted/Preview/Result/BatchProgress/StagingPreview`，record 风格）；B 的 stage/preview/confirm 返回 `Map<String,Object>`（手拼 camelCase key），progress 才复用 `BatchProgress`。
- **错误行为基本一致**（批次不存在抛 `NoSuchElementException`），但 stage 期 B 域 async 解析失败后 stage 返回成功、靠轮询看 FAILED（符合新管线）；A 域旧 `confirm(String type, File)` 直连路径仍存在（`rejectStoppedFactTypes` 已为空壳，全类型开放），是多写一套入口的“死肉”。

### 1.4 两套异步管线的阶段差异（关键）

| 阶段 | A 四类业务事实 | B 产品台账 | 说明 |
|---|---|---|---|
| 登记 | `UPLOADED / UPLOAD / 0` | 同 | 同表同 SQL（各写一份） |
| 幂等 | `(data_type,file_hash)` 命中 `PREVIEW_READY` 即复用，`StageAccepted.hashHit=true` | 同逻辑 | 命中查询 SQL 各自复制 |
| 解析 | `PARSING/PARSING/5→50` | `PARSING/PARSING/5` | |
| 落暂存 | `PARSING/STAGING/50→90`（分批 200） | `PARSING/STAGING/50→90`（分批 200） | 同策略复制 |
| 预览就绪 | `PREVIEW_READY/PREVIEW/100`，写 `preview_json` | 同 | 同 |
| 失败 | `FAILED/…/error_message+error_detail` | 同 | 同 |
| **确认** | `CONFIRMING/WRITING/5→95` → `ORCHESTRATING/98` → `COMPLETED|PARTIAL_FAILED`（写 `h3_import_rows` 快照、自动编排、写 `preview_json.orchestration`） | **同步单事务**：FOR UPDATE 批次 → 增量写台账 → `COMPLETED/DONE/100`（无中间态、无快照、无编排） | **本质差异** |
| 后续可查 | 编排结果抽屉 / 血缘追溯 / 候选裁决统计 | 无 | 列级展示差异（前端已按 data_type 隐藏） |

> 设计判断：确认语义的差异是**业务性的、应当保留**；解析/登记/预览骨架的差异是**工程性的、应当合并**。

### 1.5 前端现状

文件：`frontend/src/views/governance/H3ImportCenterView.vue`（~1670 行），`components/h3/H3LedgerPanel.vue`（~298 行），`api/business/orders.ts`、`api/productInventory.ts`。调用方仅此页面与台账面板，无第二套入口。

**页面结构：**

- 一级分区 `section: 'import' | 'ledger'`，URL 深链 `?tab=ledger&ledger=xxx`。
- **导入与批次**：
  - 上方 `import-grid` 由 `factImportCards = importTypes.filter(!ledgerKind)` 渲染 4 张业务事实卡；
  - 下方 `merge-section` **手写** 3 张卡（产品信息台账 / 仓库明细台账 / 库存合并入库）——产品/仓库两张卡与 `importTypes[]` 里的 product/stock 元信息**双份维护**（标题/描述/图标/颜色/关键字几乎相同，见 R7）；
  - 底部「最近导入」批次表共用 A+B 数据（列：批次/文件/数据类型/状态/导入结果/待确认/完成时间/建议下一步），其中"待确认"列仅收款类有内容，"更多(编排详情/血缘)"按 `isLedgerBatchType` 隐藏；
  - 批次状态标签颜色、进度阶段中文、类型标签、动作标签由若干局部函数提供（`batchStatusType/Label`、`progressStageLabel`、`typeLabel`、`actionLabel`）。
- 弹窗状态机（`LqDialog`）：选文件 → `parseProgress` 进度条（`progressPct` + `progressStageLabel` + `progressElStatus`）→ 预览表（按 `isLedgerImport` 分**台账逐行表**与**事实预览表**两套列）→ 确认 → 结果条。按钮文案/禁用随状态：`开始解析 / 解析中… / 重试解析 / 确认导入`。
- 导入入口统一在 `importConfirm()`，按 `selectedImport.ledgerKind` 分派到 `importLedgerConfirm()` 或事实分支 `stageH3Fact→waitH3BatchUntil→fetchH3StagingPreview`；台账分支 `stageLedgerImport→waitLedgerBatchUntil→fetchLedgerBatchPreview`。
- `H3LedgerPanel` 接收 `ledgerType: H3LedgerKind`（6 值），模板 `v-if/v-else-if` 六段各自定义列与 fetch 函数。

**API/类型（现状）**

| | `api/business/orders.ts` | `api/productInventory.ts` |
|---|---|---|
| 导入类型 union | `H3FactType`（4 值） | `LedgerImportKind='catalog'|'stock'` |
| 轮询 | `fetchH3BatchProgress` + `waitH3BatchUntil`（500ms/600s，FAILED 提前返回） | `fetchLedgerBatchProgress` + `waitLedgerBatchUntil`（**函数体逐字重复**） |
| stage 返回 | `StageAccepted{batchId,dataType,fileName,hashHit,status,message}` | `LedgerImportStageResult`（同形状异名） |
| 预览 | `ImportPreview`（行：businessKey/externalId/amount/…） | `LedgerImportPreview`（行：productCode/quantity/changes/…） |
| 批次进度 | `BatchProgress` 定义于 orders.ts | productInventory.ts `import type { BatchProgress }`（跨模块类型依赖） |
| 台账页类型 | `LedgerPage`（orders.ts 内定义） | `LedgerPage`（productInventory.ts 内**重复定义**） |
| 批次列表 | `fetchImportBatches`（A 域前缀，拉 A+B） | 无（依赖 A 域） |
| 超时 | `IMPORT_TIMEOUT=600000`；stage 用 30s，confirm 用 600s | stage 无显式超时；confirm `{timeout:600000}` 硬编码 |

## 2. 目标统一设计（to-be）

### 2.1 目标架构

```
                     ┌──────────────────────────────────────────────┐
                     │            统一批次导入管线 (Pipeline)          │
 入口层(按域暴露)      │  1 register(批次登记)   2 stage(异步解析+落暂存) │
 /api/h3-imports/... │  3 progress(轮询)       4 preview(读DB)        │
                     │  5 confirm(按 Handler 分派) 6 batches(列表)     │
                     ├──────────────────────────────────────────────┤
                     │  Kind 描述器 (每个数据源一张卡，只写差异)          │
                     │   OutboundHandler · ProductionHandler · …     │
                     │   ProductCatalogHandler · WarehouseStockHandler│
                     └──────────────────────────────────────────────┘
                        共享设施：h3_import_batches / staging_rows /
                        h3ImportExecutor / 哈希幂等 / 失败打标 / 错误契约
```

**设计原则：**

1. **骨架单一、差异下沉**：登记→解析→进度→暂存→预览→失败打标全部收敛到管线服务；每个数据源只提供一个 Handler（解析表头、行拆分/去重、diff、写库、编排步骤）。
2. **契约即文档**：状态机枚举、`data_type` 枚举、进度语义、错误格式都成为共享类型/DTO 的唯一事实源；中文文案由单一映射表生成。
3. **域与权限按"域统一、权限不变"**：推荐批次类能力统一暴露在 `/api/h3-imports/**`（或保留原前缀 + 兼容层），写操作权限 = 域权限的并集规范（见 2.4 权限矩阵），避免隐式依赖另一域端点。
4. **改前先立契约、迁移期双端兼容**：先用灰度/兼容转发，再删旧。

### 2.2 统一数据契约

**2.2.1 枚举值规范（未来共享）**

| 概念 | 建议值 | 说明 |
|---|---|---|
| 路由 type | `outbound / production / receipt / settlement / catalog / stock` | 前端 URL 与后端路由统一用小写别名 |
| 存储 data_type | `OUTBOUND / PRODUCTION / RECEIPT / SETTLEMENT / PRODUCT_INFO / WAREHOUSE_STOCK` | 数据库既有值，**保持不动**（避免大规模数据迁移）；`NORMAL` 归一逻辑只在服务端收口一处 |
| 统一业务类目 | `businessFact`（4）vs `ledger`（catalog/stock）vs `merge`（无批次） | 页面分组、预览骨架、列表操作以此为分派键，取代 `ledgerKind/isLedgerBatchType/…` 分散判断 |

**2.2.2 批次状态机（建议收敛为一套 + kind 能力位）**

状态 `status`：`UPLOADED → PARSING → PREVIEW_READY → CONFIRMING → COMPLETED`，旁路 `FAILED`、终态 `PARTIAL_FAILED`。
进度阶段 `progress_stage`：`UPLOAD / PARSING / STAGING / PREVIEW / WRITING / ORCHESTRATING / DONE`。
批次**能力位**（由 Handler 声明，落在 DTO/元数据而非前端 data_type 分支）：
`supportsOrchestration`（A 域 true / B 域 false）、`supportsCandidateStats`（仅收款类）、`supportsSnapshot`、`confirmIsAsync`（A true / B 暂 false）。

> 由此，前端批次列表的列显隐、"更多"下拉、待确认列、下一步动作都由**能力位**推导，`isLedgerBatchType/isReceiptBatch` 之类分散判断消亡。

**2.2.3 统一 DTO（后端一张契约，前端一个类型文件）**

| DTO | 字段 | 服务范围 |
|---|---|---|
| `StageAccepted` | `batchId/dataType/fileName/hashHit/status/message` | A+B 共用（B 不再返回 Map） |
| `BatchProgress` | `batchId/status/progressPct/progressStage/errorMessage/total/create/update/unchanged/completedAt` | 已有，全局唯一引用 |
| `StagingPreview` | `batchId/preview{rows…}` | A 已有；B 的 preview 建议统一成 `rows` 内聚类型（列由 kind 决定），不再返回 Map |
| `BatchListPage` | `items/total/page/size` | A+B 统一 |
| `ImportResult` | `batchId/dataType/total/created/updated/unchanged/childCount` | 统一；B 的 `childCount` 固定 0 |
