## 3. 接入业务前必须收口的事项

### 3.1 请求幂等的入口契约

`ErpIdempotencyService.execute` 无 requestKey 时直接 `work.get()`，不会经过本类 TransactionTemplate。如果未来调用方依赖模板保证事务，会失去保护。建议受控写动作强制请求键，或明确无键时仍进事务；外部副作用不得假设可随数据库回滚。

读取已存在键时只比较 payloadHash，不比较 action。同键、同载荷用于不同动作会返回旧动作结果。应将动作纳入匹配或命名空间，并明确身份权限在重放返回前校验；created_by 目前没有写入路径。

并发同键通过“业务后插幂等键，冲突回滚”处理，只在所有业务写入确实属于同一 ERP 事务时成立。应以两个真实连接验证同键同载荷、异载荷、失败回滚及重试，不用哈希单测替代。

### 3.2 编码终身唯一与启用期唯一冲突

主数据字典 M02 明确停用编码不复用；`ErpCommonColumns.MASTER_DATA_DDL` 却通过 ACTIVE 才赋值的 active_code 唯一列允许停用后另建同码。两者必须选定同一政策再建 M1 表，建议沿用历史身份不复用原则。当前只是 DDL 模板，尚未在 ERP 业务表形成存量负担。

### 3.3 资金判重不能直接等同于资金唯一身份

待决清单中“主体+账户+日期+金额+方向+对方”及更弱的五项组合，只能作为候选匹配条件：同一天向同一对象发生两笔同金额收付款完全可能。用户对银行事实权威、日记账语义补充的确认，不等于已证明这个组合唯一。

建议资金事件使用独立 ID；银行来源优先账户+银行稳定交易号建立来源幂等；无交易号时保留每条来源记录并做冲突复核，不能直接合并。来源、人工标注、业务分配分别保存。

### 3.4 预收、生产范围和检验的决策同步

待决清单建议负欠款表达预收，但原单据契约禁止负应收并保留未分配资金。不能让两个方案同时进入实现。应收/应付触发时点、预收预付及退款抹零仍须确认；可先建设不依赖金额政策的制造数量链。

旧试点门槛文件仍说序列号、自制和 SKU 粒度未决，已被后续待决清单部分解决。建议统一决策登记：已定的型号+档位、不单台追溯、自制三段不重复询问；未决的是材料单位、工单/BOM或领料依据、损耗/退料、检验和成本范围。

### 3.5 审计及隔离还需要实际业务证据

审计写入器接受可空操作人，序列化异常会降级为错误摘要；尚未证明业务失败日志回滚、日志失败业务回滚、操作者来源可靠。应在首个主档/单据服务接入时同时完善，不能只等 M4。

ERP 与现有库目前复用数据库账号；双池和双 schema 实现连接分离，不等于数据库权限隔离。还需账号授权、实际导入隔离及 API 跨身份测试。

## 4. 建议下一阶段

1. **M0 收口**：修正幂等动作/无键契约、编码策略，补 Java 数据库事务与审计集成测试。
2. **M1 主档切片**：正式确认公司/温州仓 ID；建全自动气调机型号+档位身份、台数单位、订单配置快照和必要材料单位。避免照搬历史自由文本主档。
3. **制造数量闭环**：工单→领料/退料→报工→完工入库→销售出库；含重复提交、超领/超发、部分完成、撤销及退货。若首批无成本账，页面不显示正式库存价值/毛利。
4. **资金闭环**：确认触发节点和预收/退款规则后，再将样本证据接到资金事件、往来和核销，不叠加多源金额。
5. **上线门槛**：真实权限、并发、期初与未结、对账、恢复演练。当前均不可由 M0 或 S0 全绿替代。

不建议再扩一轮通用蓝图或按数据源数量衡量 ERP 进度。当前最有价值的产出是一个可运行、有真实验收证据的全自动气调机制造数量切片。
