## 0. 一句话结论

**主业务闭环已经落地并且实测能跑**：销售订单 → 履约评审 → 审批 → 自产/外采准备 → 出库 → 正式库存，前后端都接了真实接口、带权限与幂等，有 27 项 e2e 与源码门禁契约保护。
**但它是「就地长在现有档案管理系统里」（同一个应用、同一个侧栏、同一个登录），不是此前设想的独立 ERP 前端**；同时财务域是明确标注的占位，导航只挂了 6 个入口而非设计里的 8 个业务域。

## 3. 八个业务域的实现对照

设计文档《ERP-v3-整体设计与落地清单》第 2 节列了 8 个业务域。实际落地如下：

| 设计业务域 | 设计主入口 | 实际实现 | 状态 |
|---|---|---|---|
| 我的工作 | `/erp-workbench` | `ErpWorkbenchView.vue`（254 行）：按权限聚合 5 类待办队列 + 近期确认订单 | ✅ 可用 |
| 销售与客户 | `/erp-sales` | `/erp-sales` 被重定向到 `/sales-orders`；`ErpDomainView.vue` 的 `sales` 分支**未挂路由 = 死代码**；侧栏「销售管理」直指 `/sales-orders` | ⚠️ 入口与设计不符 |
| 生产协同 | `/erp-production` | `ErpOperationsView.vue`（area=production）：车间执行 / 待接需求 / 车间任务 / 待检验收货 | ✅ 可用 |
| 采购协同 | `/erp-purchase` | `ErpOperationsView.vue`（area=purchase）：待采购需求 / 待到货 / 部分到货 / 供应商直发 | ✅ 可用 |
| 仓储与交付 | `/erp-warehouse` | `ErpOperationsView.vue`（area=warehouse）：待发出库草稿 / 检验收货 / 待收货 | ✅ 可用 |
| 收付款 | `/erp-finance` | `ErpDomainView.vue`（area=finance）：4 个页签**全是纯文本"建设方案"，零 API、零按钮** | 🟡 报告式占位 |
| 基础资料 | `/erp-master` | `ErpDomainView.vue`（area=master）：6 组跳转聚合卡片；其中「供应商」「仓库」两项无跳转，仅"口径说明" | 🟡 部分接入 |
| 经营总览 | `/erp-overview` | `ErpOverviewView.vue`（106 行）：4 个数量卡，各调列表端点 `size:1` 取 `total` | 🟡 仅计数 |

**订单协作页**：`ErpOrderWorkspaceView.vue`（724 行，`/sales-orders/:id`）是最重的一页——四步流程条 + 页签 + 就绪度 + 审批动作 + 幂等键。页签实现 **5 个**（交付总览 / 产品与约定 / 准备进度 / 发货记录 / 协作与变更），设计文档第 5 节承诺 **6 个**，**缺「资金与往来」**。

### 3.1 侧栏入口只有 6 个，不是 8 个

`frontend/src/constants/erpNavigation.ts` 的 `erpMenu` 只有：工作台、销售管理、生产管理、采购管理、库存与交付、主数据。

- **收付款（`/erp-finance`）与经营总览（`/erp-overview`）没有侧栏入口**，只能直接改 URL 到达。
- `/erp-sales` 是一个 redirect（保留旧书签），不是一个页面。
- `erpTabs.sales` 只有「销售订单」「客户档案」，**没有设计里承诺的「需求登记」页签**——而 `ErpDomainView` 里其实已经把「需求登记 → `/sales-orders?status=DRAFT`」写好了，只是这个分支不可达。

## 5. 差距与风险（按优先级）

### P1 — 需要 LQ 拍板的分歧

1. **载体形态与原始诉求不一致。**
   此前两轮明确要的是「新 ERP 前端，不要放在档案管理里面」，并倾向独立应用 + 应用切换器。实际落地的是**在现有 `frontend/` 里加一个「ERP」导航分组**，共用登录、员工、权限、文件（设计文档第 1 节明确写了这个选择）。
   客观好处：复用权限与登录、无第二套部署、旧地址继续有效。
   客观代价：ERP 与档案仍在同一个侧栏、同一套路由与布局里演进——**"越来越乱"的结构性成因没有被消除，只是被重新分组了**。
   → 二选一：接受就地集成（省成本）；或按原设想把 ERP 拆成独立入口。

2. **财务域要不要启动。** 当前 `/erp-finance` 是纯文本建设方案（往来单、资金流水认领、核销、期初结存四块），后端**没有表、没有接口**。设计文档给了模型草案（第 6 节），但明确"尚未创建表或写接口"。

### P2 — 设计文档与实现不一致（文档说做了、代码里没有）

3. **订单协作页缺「资金与往来」页签**（文档承诺 6，实现 5）。
4. **侧栏缺「收付款」「经营总览」入口**（文档列 8 域，导航挂 6）。
5. **销售域的「需求登记」页签没挂上**；`ErpDomainView` 的 `sales` 分支是死代码。

### P3 — 技术债与静默风险面

6. **经营总览的口径无契约保护。** `ErpOverviewView` 用 `size:1` 取 `total` 当指标，口径散在前端，没有"卡片数字 = 点进去条数"的契约测试。项目在别处（制造看板、氚云执行看板）是用契约测试钉死这条的。
7. **两套「跟单」实现并存，前端都没接。**
   - `/api/production-followups/**`（源 `production_orders` + `production_followup_records`，4 端点）
   - `/api/manufacturing/followup-board`（源 `manufacturing_orders` + `manufacturing_order_follow_ups`）
   两套概念同名、数据源不同、前端 0 引用。这是"同一业务概念两套口径"的典型风险面。
8. **DB 列注释漂移**：采购单状态注释漏了 `PENDING_APPROVAL`；`erp_sales_order_changes.status` 注释漏了 `PENDING_CUSTOMER`。不改代码，但照注释写 SQL / 做报表会漏状态。
9. **`erp` schema 是空壳。** `db/erp-migration` 只有一张 `V1__erp_m0_infra.sql`（建 `idem_request`/`row_change_log` 两张基建表），**所有 ERP 业务表都建在主库 `product_archive`**。ERP 写路径靠"主库连接 + `erp.` 限定名"实现。`ErpContractConfig` 自己的注释警告：**新增写路径若选错数据源不会报错，只是保护静默失效**。这是最容易埋雷的配置面。
10. **前端残留**：`routeGroups.ts` 里 `sales`/`production`/`inventory`/`settlement` 四个空组声明（靠空组过滤才不显示）；`erp-workspace.css` 里 `.erp-entry*` 三个类无引用；ERP 相关**无任何 vitest 单测**（导航/权限映射/页签解析全靠 e2e）。
11. **在途未提交 145 项**，前后端两条线叠加，无法单独回滚任一条。

## 6. 建议的下一步顺序

1. **先拍板载体形态**（P1-1）——它决定后面所有页面往哪长。若接受就地集成，就把设计文档里"八个业务域主入口"改为与导航一致的 6 项，让文档与实现对齐；若坚持独立入口，则现在改动成本最低。
2. **对齐文档与实现的三处不一致**（P2-3/4/5）：补「资金与往来」占位页签、把缺的两个入口挂上（或从文档里删掉）、删掉 `ErpDomainView` 的 sales 死分支。
3. **给经营总览补后端聚合端点 + "卡片数字=行数"契约测试**（P3-6），把口径从前端收回后端。
4. **处置两套跟单**（P3-7）：定一套为正式口径，另一套标记退役或删除。
5. **统一真库契约回归**：待并行改动落定后，跑 `Erp*ContractMysqlTest` 全家 + 前端全量 e2e，再提交。
6. **财务域**（P1-2）按业务优先级单独排期，不要与上述收尾混在一起。
