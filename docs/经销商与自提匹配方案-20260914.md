# 经销商治理与自提出库匹配方案

> 2026-09-14 · 基于 `product_archive` 真实数据核查（18667 张出库单、10175 个客户档案、124 名员工）

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| 经销商要编入员工手册吗？ | **不要**。97 个经销商名与 124 名员工**零交集**，且员工表结构（部门/职位/入职离职/提成资格）与经销商语义冲突 |
| 经销商要像客户档案一样列出来吗？ | **要，但不该另起一套体系**。建议落在 `customers.customer_type='DEALER'` + 订单侧 `dealer_id`，复用已有客户治理能力 |
| 引入经销商能让数据更清楚吗？ | **能，且解决的是存量问题**。立刻能认领 17 张缺客户单；更能修掉提成口径、档案碎片、经销商价三处盲区 |
| 自提出库怎么管理匹配？ | **自提必须优先按 `dealer_name` 认领，而不是按客户名**。自提类经销商填充率 46.9%、纯自提 605 张里 42.5% 客户名就等于经销商名 |

## 二、现状事实（核查数据）

### 2.1 经销商字段早已存在，而且已被提成体系使用

`sales_outbounds.dealer_name`（氚云字段「选择经销商」）**不是空概念**：

- **5140 / 18667 张单填了经销商**（27.5%），共 **97 个不同经销商名**
- 提成体系正式依赖它：`CommissionPolicy.DEALER_CASE` = `dealer_name 非空 OR 毛利率 < 15% 兜底`，业务员在经销商单/零售单上取不同比例（`monthly_commission_rates.dealer_rate` / `retail_rate`）

**所以不是"要不要引入经销商"，而是"把已经存在 3 年的自由文本实体化"。**

## 三、Q1：经销商该放在哪？

### 三方案对比

| 维度 | A. 编入员工手册 | B. 新建独立经销商体系 | **C. 客户档案加类型（推荐）** |
|---|---|---|---|
| 语义正确性 | ✗ 员工=组织成员，经销商=渠道 | ✓ | ✓ 经销商也是"交易对手方" |
| 提成口径 | ✗ 污染 `is_salesperson`/提成资格/部门统计 | ✓ | ✓ 与提成 `DEALER/RETAIL` 标记解耦 |
| 复用既有治理 | ✗ 不适用 | ✗ 要重写地区/合并/待复核/电话归一 | ✓ 全部复用 |
| 对账/开票 | ✗ | ✓ | ✓ 与客户同构 |
| 实现成本 | 低但后患大 | 高（2~3 天 + 长期双轨维护） | **低（1~2 天）** |
| 经销商价/等级 | ✗ | ✓ | ✓（`level`/`remark` 可承载协议） |

### 推荐方案 C 的具体形态

```
customers
  ├─ customer_type = 'DEALER'   ← 新增枚举值（现枚举仅 6 值，无 DEALER）
  ├─ dealer_id                  ← 【已确认】该终端客户归属的经销商（下游归属）
  └─ 复用：province/city/district、address、phone、level、relation_status

sales_outbounds
  ├─ customer_id   → 终端收货方（现状不变）
  └─ dealer_id     → 经销商渠道（新增，由 dealer_name 解析；保留 dealer_name 原文做溯源）
```

### 「下游客户归属」已确认（2026-09-14 用户答复）

刘长金名下 1172 个客户**属于他自己的下游客户**。因此模型是三层：

```
利强  →  经销商（渠道）  →  经销商的终端客户
```

含义与影响：

- 这些终端客户**档案仍留在利强**（是利强的发货/开票对象），但通过 `customers.dealer_id` 标明"归属哪个经销商渠道"
- 出库单上的 `dealer_id` 是**逐单权威值**；`customers.dealer_id` 是**客户级默认归属**，便于筛选"某经销商名下全部客户"
- **归属唯一性核查通过**：3066 个有经销商归属的客户中，**3042 个（99.2%）只挂一个经销商**，仅 24 个挂 2 个以上（2 个经销商 20 人、3 个 1 人、4 个 2 人、5 个 1 人）。这 24 个以订单为准，客户级默认归属取占比最高者
- 可直接支撑"经销商台账"：某经销商名下客户数、活跃客户、复购率、渠道总额

### 另两项确认（2026-09-14）

| 待确认项 | 结论 | 落地动作 |
|---|---|---|
| 李楠（经销商，531 单 / ¥440,473）是否 = 员工李南（LQ005 温州仓） | **不是同一人** | 李楠独立建 `DEALER` 档案；员工李南不受影响（他另有 5 张自提单） |
| `半自动气调机车间` 是否算业务客户 | **当客户处理** | 建普通客户档案（`OTHER`），不做特殊标记；该单 `dealer_name=半自动气调机` 仅 1 张 ¥100，保留原文、不建经销商主档 |

> 李楠是原 97 个经销商里**零档案、金额第 8** 的缺口（531 单），独立建档后其名下 497 个下游客户可一并归集。

**要警惕的同名不同义**：前端提成页已有 `customerType: 'DEALER' | 'RETAIL'`，那是**单笔提成的口径标记**（同一张单按经销商/零售算不同比例），不是客户档案类型。实现时命名必须区分，否则一定混淆。

**不建议**把 `dealer_name` 直接改写成 `customer_id`：4622 张单的客户档案 ≠ 经销商，强行合并会把"终端客户"和"渠道"两层信息压成一层。

## 五、Q3：自提出库怎么管理匹配

### 5.1 自提的真实规模与特征

`shipping_method LIKE '%自提%'` 共 **1074 单 / ¥719.5 万**：

| 运输方式 | 单数 | 其中填了经销商 |
|---|---|---|
| 自提 | 605 | 380（62.8%） |
| 物流内付自提 | 275 | 34 |
| 物流到付自提 | 190 | 90 |
| 其他自提变体 | 4 | — |

**关键对比**：

| 分组 | 单数 | 经销商填充率 | 缺客户（有效） |
|---|---|---|---|
| 自提类 | 1074 | **46.9%** | 25 张 / ¥30.16 万 |
| 送货/发货类 | 17593 | 26.4% | 13 张 |

→ **自提与经销商强相关**，因为自提 = 货不走物流、买方自己来厂拉，本地渠道商/经销商的典型行为。

**纯"自提"605 张中：257 张（42.5%）客户名与经销商名完全相同**，另 15 张互相包含，只有 333 张是真不同。

### 5.2 自提类客户名的真实样貌（缺客户 25 张）

```
可被经销商认领（12 张 / ¥124,658）：
  铨威系列 8 张 → 客户名写着「东莞」「上海市」「湖南」「铨威」「林」「刘锦华」「铨威8线」
                  ← 同一个经销商的不同随手写法，dealer_name 全部是「铨威」
  刘长金   2 张 → 客户名「客户自提，」「客户自提 自取」  ← 纯描述，不含客户信息
  法麦格   1 张 → 「法麦格 客户自提」¥97,038
  苏蕾     1 张 → 「苏蕾陕西客户自提」¥16,359

无法自动认领（13 张）：
  仰义 ×4（¥5,910）      ← 已有「余（仰义）」档案，互为子串候选
  李佳宁山东（¥121,200）  ← 单张金额最大
  缪总、河北沧州黄先生、黄良军、张力宏、周建国[9691]、浙江客户、林浩然、温州客户
```

### 5.3 自提类匹配优先级（建议）

自提**没有收货地址**，所以地区不能从地址推、必须落客户档案。同时客户名常是口语化描述，**不能作为第一判据**：

```
① 标准化电话唯一命中        → 最权威（自提大多没填电话，命中率低）
② dealer_name 命中经销商主档 → 自提类的第一条有效路径【现在完全没做】
③ customer_name 精确命中客户档案
④ 剥离噪声词后再匹配：
     描述词：客户自提 / 自取 / 自提 / 客户 / 提货
     尾随标点：全角逗号「，」
     地名前缀后缀：山东 / 陕西 / 河北沧州 …
     编号后缀：[9691] / [548271]
⑤ 仍不唯一 → 进待复核，不自动绑定
```

**两个必须固化的规则**：
1. **`客户自提` 这类纯描述视为空客户名**，直接转入第②步，不要拿它去匹配档案（现在会产生噪声候选并触发 REVIEW）
2. **同一经销商的多写法归一**：`东莞`/`上海市`/`湖南`/`林`/`刘锦华`/`铨威8线` 在 dealer 都是「铨威」时，应统一归到铨威主档，而不是建 8 个客户

### 5.4 自提的业务员归属（顺带发现）

|---|---|---|
| 李水云 | 355 | **278（78%）** |
