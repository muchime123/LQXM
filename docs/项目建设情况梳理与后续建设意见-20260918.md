## 3. 必须优先处理的四个问题（本次新发现）

### 3.1 有三个批次处于非完成态（其中一个就发生在今天 16:03）

| id | 文件 | 类型 | 状态 | 阶段 | 结论 |
|---|---|---|---|---|---|
| 146 | 仓库明细_2026-09-15.xlsx | PRODUCT_INFO | FAILED | 5% PARSING | 表头校验拒绝导入（首 5 列与预期不符）——**这是正确行为**，防列错位 |
| 193 | invoice.xlsx | SUPPLIER_PAYABLE | FAILED | 90% STAGING | ✅ **已定性（09-18 17:2x 复核）：非代码 bug**，是迁移与批次解析的时序窗口，已被 194/195 取代（详见 §3.1 更正） |
| 196 | invoice.xlsx | CASHFLOW_JOURNAL | PARSING | 69% STAGING | **当前卡住**（16:03 创建，未完成） |

**⚠️ id=193 的更正（2026-09-18 17:2x 复核，推翻本节初判）**：

> 初判为"真 bug（加列未同步取数列）"，**复核后不成立**。错误 SQL 在 `WHERE external_source='H3YUN'` 后没有下文，是 Spring 消息格式的正常结尾，不是拼接截断。

**真实根因 = 迁移与批次解析的时序窗口**，证据链：

| 时间 | 事件 | 表结构状态 |
|---|---|---|
| 14:29 | **V313 建表** | 表**无** `source_updated_at` 列 |
| 14:29 | **批次 193 创建并解析** | 同上 → `loadExistingFacts` 统一读 4 列 → 列不存在 → Spring 包装为 `bad SQL grammar` → FAILED 90% |
| 14:31 | **V314 ALTER 补列** | 列就位 |
| 14:31 | 批次 194 | COMPLETED，CREATE 696 |
| 14:44 | 批次 195 | COMPLETED，**unchanged 696（完全收敛）** |

**反证**：把那条 SQL 原样重放到当前库上**执行成功**（已实测），说明代码与 SQL 本身合法；代码侧不存在"漏列"。`h3_supplier_payables` 列清单现已含 `source_updated_at`。

**结论**：**代码无需修改**。193 是 V314 应用前的一次性时序事故，其数据已被 194/195 完整取代并收敛。真正的教训是纪律层面的（见下）。

**顺带核实（非缺陷）**：`source_updated_at` 在 `h3_supplier_payables` / `h3_input_invoices` / `h3_sales_invoices` / `h3_cashflow_entries` / `h3_cashier_log` 五张表**全为 NULL**。已回到源文件确认：这些源**根本没有「修改时间」字段**（供应商明细只有月份/金额/付款列；发票明细只有开票日期/状态等）→ 写入 NULL **符合语义，不是漏写**。
> ⚠️ 但由此产生一个需知情的后果：`unchanged()` 的「修改时间回退判据」对这 5 类**恒不生效**，判等完全依赖 `source_hash`。**若同一份数据重新导出时列顺序变化，会全量误报 UPDATE**（表现为"不收敛"）。第 18/19 类两轮实测用的是同一文件，故未暴露。使用中若出现该 kind 全量 UPDATE，先查导出列顺序，不要误判为幂等 bug。

### 3.3 验证证据等级与结论不匹配（延续 0918 评估）

沿用今日评估报告的判断，并补充核实：

- `erp_s0_verify`（15 表）与 `erp_s0_hardening` 均在 **MySQL 脚本层**，不是正式 Java 服务。库中 `erp` schema **不存在**，Java 侧 ERP 代码 **0 个**（仅 2 个文件名撞 `erp` 的无关类）。
- 因此"43 例通过"的准确表述是：**S0 模型层规则验证通过**，不能表述为"ERP 功能已验证"。
- T06/B11 是**顺序模拟**，未覆盖双连接并发、行锁等待、死锁重试。
- DECIMAL 精度在 harness 中仍有 `Number` 转换与 EPS 比较，未用定点。

## 4. 后续建设意见

### 核心主张

> **停止把"新增数据源数量"当作完成度指标。** 下一步的价值不在横向扩容，而在三件事：**锁住已有成果（版本基线）→ 补齐证据等级（验证分级）→ 纵向打通一个闭环（试点切片）**。
>
> 与今日评估报告结论一致，但调整优先级：**Git 基线从 P0 提到最前**，因为它成本最低、不可逆风险最高。

### 现在**不要**做的事

1. **不要**继续以"再补一类导入"作为推进手段——除非是**明确缺失的验证证据**（如 G5 库存盘点、G4 退换货台账）。
2. **不要**把氚云温州仓快照当正式期初迁入 ERP，沙箱用合成期初。
3. **不要**为兼容历史数据做过度设计；也不要一次性清理 57 张空表——先分类再动手，归档表保留留档。
4. **不要**在成本政策未定义时承诺正式库存价值与毛利。
5. **不要**做无收益的全仓重构；只在新增导入种类时按 type handler 抽取。

## 5. 一句话总结

**已经建成的**：一个分层清晰、口径经反复对拍固化的档案 + 运营 + 历史数据资产平台（183 表 / 324 迁移 / 42 份设计文档 / 18 类导入全通）。
**最紧急的**：`git` 只有 2 个提交，最贵的三周成果处于随时可丢的状态——**今天先提交**。
**最该转向的**：从"补数据源"转向"锁版本 → 补证据分级 → 打通一个试点闭环"。
**最该守住的**：不要把 S0 脚本验证说成 ERP 已验证，不要把氚云台账当成正式 ERP 数据层。
