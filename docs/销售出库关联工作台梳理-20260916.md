# 销售出库关联工作台 — 建设与设计梳理

> 梳理日期：2026-09-16　｜　代码基线：后端 `H3ImportBatchController` + `OutboundRelationGovernanceService`(791 行) + `H3BusinessQueryService.outboundRelations`(67–121)，前端 `views/governance/H3OutboundRelationView.vue`(256 行)
> 说明：本文所有结论均可指到代码位置；标 ⚠️ 的是**尚未实测**、需要补验证的推断。

---

## 0. 结论速览

**它是什么**：氚云销售出库导入之后、各种下游统计之前的一道**关系治理层**。一行 = 一张销售出库，围绕业务单看客户 / 员工 / 产品 / 仓库四类关系是否齐备，并把「唯一精确命中」的那部分自动绑定。

**已经建成的**（设计骨架完整、可用）：

- 四类关系都有「预览 → 确认」两段式，确认前能看到影响面；
- 只自动处理唯一命中，多候选一律不处理——不会制造错误关联；
- 人工结论落到**领域映射表**而不是只改业务行，重导后自动复用（这是整个工作台的价值支点）；
- 原始台账保持只读，关系修改只有一个写入口；
- 有一个全链路验收端点做逐级对账。

**三个真缺口**（详见 §5）：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 产品来源键**三处独立实现、零契约测试** | 重导后产品归类结论可能**静默失效**，且不报错 |
| 2 | 需要人判断的项**没有人工录入入口** | 治理闭环缺最后一公里，异常项只能永远挂着 |
| 3 | 弹窗打开即全表扫，preview/apply 各算一遍 | 与已知的 MySQL 连接池拖死同源 |

## 2. 四类关系一览

| 关系 | 判定链（优先级自上而下） | 落点表 | 重导复用通道 | 自动化边界 |
|---|---|---|---|---|
| **员工** | 业务员姓名唯一命中在职员工（`preview()`，`HAVING COUNT(DISTINCT e.id)=1`） | `employee_external_mappings`（`external_user_id='NAME:<姓名>'`） | 出库导入时按姓名查映射表回填 `employee_id` | 重名不处理；**已 SETTLED 提成的出库不改 `employee_id`** |
| **仓库** | 来源仓库名唯一命中启用仓库（同 `preview()`） | `h3_warehouse_name_mappings(source_name→warehouse_id, 'EXACT_NAME')` | 出库导入查映射表（`H3FactImportService:626`） | 近似名称不处理；来源未填仓库不参与 |
| **客户** | ① 已确认身份簇 → ② 电话唯一命中 → ③ 名称级已有结论 | `customer_source_cluster_mappings`（CONFIRMED） + `source_identity_aliases`(CUSTOMER) | `resolveCustomer` 按同一优先级读回（`SourceIdentityService:214`） | **名称不单独决定客户**；同名不同电话、共享电话、泛化名称、仅地址相似一律不做 |
| **产品** | ① 同编码在多仓交集唯一 → ② 名称+规格+单位 → ③ 仅名称 → ④ 产品台账编号 → ⑤ 仓库明细编号/名称 → ⑥ 核心名称 | `source_identity_aliases`(PRODUCT, `source_key`) + `sales_product_source_aliases` | `resolveProduct` 先读 `source_key`，再退编号别名（`SourceIdentityService:84`） | 多候选/无候选不处理；**先绑仓库再匹配该仓库内产品**（`commonCandidates` 取多仓交集） |

**关键设计判断**：产品的候选是**按仓库交集**取的（`OutboundRelationGovernanceService:583`），不是全局取——同一编码在不同仓指向不同产品时不会误绑。这是这套设计里最细致的一处。

## 4. 设计上做对的地方（建议固化，勿回退）

1. **唯一命中才自动**。所有自动动作都建立在「候选恰好 1 个」上，多候选进 `AMBIGUOUS` / `REVIEW`，宁可不做。这条约束是整个工作台可信度的来源。
2. **人工结论落在映射表，不是只改业务行**。重导后 `resolveProduct` / `resolveCustomer` 自动复用，人工不必重复确认——这是它比「一次性数据修复工具」高一个层次的地方。
3. **写入口唯一**。原始台账只读，四类关系都从工作台进出。
4. **草稿全程排除**。统计、治理、归类都不含草稿（`outbound_status='DRAFT' OR status IN ('草稿','DRAFT')`），且草稿单数单独成卡，不混进分母。
5. **已结算提成保护**。`applyExact` 对 `sales_outbound_commissions.status='SETTLED'` 的出库不改 `employee_id`——避免动了钱已经算过的东西。
6. **产品候选按仓库交集**（见 §2）。
7. **执行端取全量、展示端截断**。`productPreview()` 展示限 500 条，`applyProductExact()` 调 `productPreview(false)` 取全量，注释里明确写了「不能误把界面展示上限当成处理上限」。
8. **验收不误报通过**。任一层 base 为 0 时该项标 `PENDING` 而不是 `PASS`。
9. **幂等**。所有写入都是 `UPDATE ... WHERE xxx IS NULL` 或 `ON DUPLICATE KEY UPDATE`，重复点击不产生重复数据（第二次结果为 0，UI 会 toast 0，语义正确但体验略怪）。

## 5. 缺口与风险

### 5.1 ⚠️【高】产品来源键三处实现，零契约测试

**现状**：同一个概念「出库明细行的产品来源键」由三段独立代码实现：

| # | 位置 | 形态 |
|---|---|---|
| 1 | `SourceIdentityService:2315` `productSourceKey()` | Java：有编码 `trim()`；无编码 `"NAME|"+sha256(normalize(名)+\"|\"+normalize(规格)+\"|\"+normalize(单位))` |
| 2 | `SourceIdentityService:2093` 回填 SQL | `CONCAT('NAME|',SHA2(CONCAT_WS('|',...)))` |
| 3 | `OutboundRelationGovernanceService:34` `PRODUCT_KEY_EXPR` | SQL 常量，工作台用它算 `source_key` 写 `source_identity_aliases` |

**证据**：`grep -rln "productSourceKey\|PRODUCT_KEY_EXPR" backend/src/test/` → **零命中**（2026-09-16 复核）。
`docs/氚云导入建设不足与优化清单-20260914.md` 已把它列为优化项 #1（估工作量：半天），**至今未落地**。

**两侧口径的差异点**（代码比对，未实测）：
- 边界空白：Java `trim()` 会去掉 `\t`/`\n`/`\u0000` 等 ≤U+0020 的字符，MySQL `TRIM()` 只去半角空格（全角空格靠额外 `REPLACE` 补）；
- 大小写：Java `toLowerCase(Locale.ROOT)` vs MySQL `LOWER()`（受排序规则影响）；
- 分隔：`String.join("|", ...)` vs `CONCAT_WS('|', ...)`（当前入参已 `COALESCE`，不存在 NULL 被跳过的风险）。

**后果**：命中 Java 侧 `source_key` 是产品归类结论**重导后复用**的唯一通道。两处一旦不等，`resolveProduct` 匹配不上 → 所有产品归类**静默退回「待归类」**，不报错、不告警，而且事后无法区分是「漏改」还是「业务变了」。
按 09-14 的预览数据量（数千组明细行）来算，这是工作台最有价值的那部分价值直接归零。

**建议**：半天补一个契约测试 `ProductSourceKeyContractTest`——同一组输入（有编码 / 无编码含中文名规格单位 / 含全角空格 / 含制表符 / 全空）分别调 Java 方法与在 MySQL 执行 `PRODUCT_KEY_EXPR`，断言字符串完全相等。这类测试是本项目性价比最高的一类护栏。

### 5.2 【高】需要人判断的项，没有人工录入入口

工作台把「能自动的」做完了，但**所有需要人看一眼的，系统不给录入结论的地方**：

| 位置 | 现状 |
|---|---|
| 客户异常 4 类（`customer-exceptions`） | 只读表格 + 「知道了」按钮，无操作列 |
| 多电话 `REVIEW` 簇 | 只读，界面上写「存在冲突，暂不处理」 |
| 产品归类 `AMBIGUOUS` / `NOT_FOUND` | 只读，显示「N 个候选」/「无候选」 |
| 台账详情抽屉 | 只能确认销售/退货/换货，改不了客户/产品/仓库 |

**后果**：`SHARED_PHONE`（电话属于多个档案）、`UNRESOLVED`、产品多候选这些**恰恰是人一眼能定的**，现在只能挂着，或者去改数据库。工作台的指标卡会长期停在一个降不下去的数字上，久而久之就没人看了。

**建议**（按性价比）：
1. 异常/多候选列表加「指定到…」操作列（客户：档案搜索选择；产品：产品搜索选择），写回同一套映射表，`resolution_status='CONFIRMED'`；
2. 复用现成的 `source_identity_aliases` 的 CONFIRMED 语义即可，不需要新表。

### 5.3 【中】客户侧人工结论可被自动结论静默覆盖（与产品侧不对称）

**证据**：`SourceIdentityService:399 rememberCustomerCluster()`

```sql
ON DUPLICATE KEY UPDATE customer_id=VALUES(customer_id),status='CONFIRMED',updated_at=NOW()
```

无条件覆盖。而产品侧 `applyProductExact`（`OutboundRelationGovernanceService:646`）是**有保护**的：

```sql
target_id = IF(resolution_status='CONFIRMED', target_id, VALUES(target_id))
```

**触发路径**：某个「名称+地址+电话」身份簇已 CONFIRMED 到客户 A；后续某次运行因为归一化差异（`normalize` vs `normalizeLoose` 的标点差异，见 `SourceIdentityService:2340` 注释里记载过的同类事故）没命中该簇，退到「电话唯一命中」得到客户 B → `rememberCustomerCluster` 把 CONFIRMED 记录静默改成 B。

**建议**：客户侧补上与产品侧同形的 `IF(status='CONFIRMED', customer_id, VALUES(customer_id))` 保护；确需改判时走显式的人工路径。

### 5.4 【中】preview / apply 双算，弹窗打开即全表扫

**证据**（都指向「每次点击重算一遍」）：

| 调用 | 重算内容 |
|---|---|
| `applyCustomerSafe` → `customerCandidates()` | 电话索引全表（`customer_contacts ∪ customer_addresses`）+ 未关联出库全表 |
| `customerExceptionPreview` → `customerCandidates()` **+** `newCustomerClusters()` | 上述索引与全表扫 **各再一遍** |
| `multiPhoneClusters()` | 电话索引 + 客户名全表 + 未关联出库，再来一遍 |
| `applyExact` → `preview()`、`applyProductExact` → `productPreview(false)` | 重算全部索引（产品索引还会 JOIN `product_inventory_balances` + `h3_product_catalog` + `h3_warehouse_stock` 取每仓每编码最新行） |

**量级**：把 4 个客户类弹窗挨个打开 ≈ **6~8 次 contacts/addresses 全表扫描 + 4 次未关联出库全表扫描**；产品归类再叠一次三表 JOIN。

**为什么算高风险**：这正是本库已知的卡死模式——全表扫 + 落盘聚合，10 并发即占满 Hikari(10)，且 `KILL` 对卡住的窗口函数会话无效（`innodb_buffer_pool_size` 仅 128MB 是放大器）。工作台是给人点的，多个人同时点就会复现。

**建议**：抽一个 `OutboundRelationIndex` 上下文对象，一次构建、四个预览共用；或给 `customer_contacts.phone` / `customer_addresses.contact_phone` 补可用索引并把电话索引落到物化表。至少先让 `customerExceptionPreview` 复用一次而不是算两遍。

### 5.5 【中】没有流程编排，也没有「只处理我勾选的」

- **顺序靠按钮排列隐含**：正确顺序是 员工/仓库 → 客户安全关联 → 按电话建档 → 多电话 → 产品归类，但界面上是 6 个平铺按钮 + 7 个指标卡。「剩余客户异常」是前面几步的补集，用户提前点会先看到一堆其实是安全候选的记录（代码里已排除，但语义上仍是「先做完前两步再看」）。
- **只能全量确认**：客户建档、多电话、产品归类都是「点一次处理全部」。想先建 20 个试点、或今天先不动某几条，没有入口。

**建议**：指标卡点击 → 引导式步骤条（完成态打勾）；confirm 接口支持传 id 子集。

### 5.6 【低】验收入口不在工作台

`/outbound-relations/acceptance` 已实现且有前端消费者，但入口在**导入中心的弹窗**里（`H3ImportCenterView.vue:279`），不在工作台页面。验收是这条链路的对账闭环，放在治理落点旁边更顺；覆盖率卡片也可以直接嵌进工作台头部。

### 5.7 【低】`sales_product_source_aliases` 的双写来源

工作台（`OutboundRelationGovernanceService:654`，`external_id=source_key`）和库存合并（`ProductInventoryMergeService:871`，`external_id=item.productCode()`）都往这张表写。
- 有编码时 `source_key = TRIM(product_code)`，与合并侧 `external_id` **同值**，命中同一行 → 一致，✓；
- 无编码时工作台写 `external_id='NAME|sha...'`、`source_product_code=NULL`，而两侧的别名读取都要求 `source_product_code` 非空 → 这类行**只有 `source_identity_aliases.source_key` 一条通道能命中**，进一步放大了 §5.1 的重要性。

## 6. 优化路线

| 阶段 | 事项 | 依赖 | 风险/收益 |
|---|---|---|---|
| **P0（半天）** | 补 `ProductSourceKeyContractTest`：Java `productSourceKey` ↔ SQL `PRODUCT_KEY_EXPR` 逐用例断言相等 | 无 | 收益：挡住「重导后产品归类静默失效」；风险：若断言失败说明现网已不一致，需先修口径 |
| **P0（半天）** | 客户侧 `rememberCustomerCluster` 补 CONFIRMED 保护，与产品侧对齐 | 无 | 收益：人工判定不再被自动流程改写 |
| **P1（1~2 天）** | 异常/多候选加「指定到…」操作列（客户 + 产品），写回映射表 `CONFIRMED` | §5.2 | 收益：治理闭环补齐，指标卡能降到 0；风险：需限定权限与二次确认 |
| **P1（1 天）** | `customerExceptionPreview` 复用一次索引（先不做全量缓存） | 无 | 收益：弹窗打开耗时与库压力立即减半 |
| **P2（2~3 天）** | 抽 `OutboundRelationIndex` 上下文，四预览共用；评估电话索引物化 | §5.4 | 收益：从「多人同时点就卡」到「可并发」 |
| **P2（1 天）** | 工作台加步骤条引导 + 验收结果内嵌 | §5.5、§5.6 | 收益：新人按顺序点就不会漏 |
| **P3** | confirm 支持 id 子集（试点 / 分批） | §5.5 | 体验 |
