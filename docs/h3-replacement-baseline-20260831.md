## 对目标模型的修正

1. **客户主体性质与销售渠道分开。** 现有 `customerType` 是企业、合作社、农场、个体、个人等。终端/经销商/代理商应增加独立属性或角色关系。若一单同时存在购买客户、经销商和收货客户，应保留各自角色引用，不强行合并成一个客户。客户去重不能只按名称。
2. **主链支持分支。** 销售订单可拆生产任务和出库明细；库存品直销不必经过生产，备货生产可以没有销售订单。合同是商业凭据，是否等同订单须以实际流程确认。已有 `business_orders` 不能未经分析直接改名为销售订单。
3. **收款分配目标必须明确。** 订单金额、已发货应收、预收款是不同口径。先核实原“多订单结清”引用的是订单还是出库单；新业务建议分离预收与应收核销，并明确应收确认事件。订单只汇总结果，不手工改已收金额。
4. **开票申请不等于已开票。** 开票资料属于客户档案，但申请应保存当时资料快照；实际发票单独记录，并支持申请/发票与订单或出库明细的分配关系。
5. **库存只在有效业务事件时过账。** 草稿、审批中不产生正式流水；确认、流水、余额更新在同一事务内完成，增加幂等约束和并发保护。调拨两边必须原子成功；已过账记录通过反向流水冲销，不直接删除。运费、服务等非库存明细不扣库存。
6. **库存余额可以更新，但必须可重建。** `inventory_balances` 是流水的受控汇总；禁止业务页面随意改数，并非禁止数据库执行 UPDATE。余额维度至少明确产品可交易规格、仓库、单位；批次、序列号按真实业务需要增加。
7. **不用通用流程引擎，也需要流程规则。** 第一版就要有每类单据的状态、允许操作人、提交/审核/驳回/撤销规则与审计；以后再抽象共同能力。

## 文件与流程核查

- 两份销售出库：先比文件哈希，再按表单标识、主记录 ID、子记录 ID、修改时间比较。区分完全重复、增量导出和同记录不同版本；同号不同 ID 必须列为冲突，不直接覆盖。
- 所有表单：识别主子表展开导致的主表金额重复，保留原始文件和逐行出处；缺失引用进入待核队列，不凭名称静默补齐。
- 流程：Excel 通常不能完整反映审批节点、条件分支、表单权限、公式、自动化、外部接口和通知规则。需补充氚云设计器配置或截图，区分历史实际值与系统计算规则。
- 明确收款和结清是否描述同一笔到账，避免迁移时双计；不要把累计已收当作本次收款。

## 实施与切换顺序

1. 源文件盘点、字段字典、流程矩阵和争议口径确认。
2. 复用主数据与权限，补足仓库、供应商、客户角色、产品映射。
3. 小范围跑通本地销售订单 → 可选生产任务 → 出库，并同时具备最小库存过账能力；不等所有库存页面完成才约束出库。
4. 完成采购入库、其他收发、调拨、盘点及冲销；验收重复提交、并发扣减、回滚与余额重建。
5. 完成收款、预收、核销、开票和新核算接口；验收部分付款、拆分发货、撤销、退款、跨客户误分配拦截。
6. 确定切换日：盘点期初库存，确认期初应收/预收和在途订单。采用期初余额时，不再把同一期间历史单据重复过账。按范围规定唯一写入系统，影子核对通过后切换，保留可执行回退方案。

财务/销售可有不同菜单入口，但收款、应收、开票应使用同一业务实现。产品复用既有档案并明确交易规格和单位；新增映射表不等于再造一套产品主数据。
