# 库存明细 / 产品信息 / 库存合并入库 —— 设计与「每次都有 60+ 更新」诊断

> 2026-09-15 · 结论已用真库数据与批次流水交叉验证

## 0. 一句话结论

三张表的分工没有问题，**问题出在「合并写入的粒度」**：

台账是「一行 = 一个氚云编号」，库存余额是「一行 = 一个产品 + 仓库」。两份台账之间天然存在**多行指向同一产品**的多对一关系（同物多码、老编号残影），而合并是**逐行写入同一个目标**——同一批次内多行连续覆盖同一个余额行，下一次再覆盖回来，于是永远收敛不了。

再叠加两个口径缺陷：

- 身份解析的「名称唯一」降级规则，把**同名但规格/价格不同**的编号吸到同一个产品（价格随之在两个口径间抖动）；
- 反向对账的快照键**含单位**，而两份台账的单位口径本来就不一致（110 个编号），导致「行还在台账里」却被判「已消失」并清零。

**结果**：最近 9 次合并，每次稳定上报 66~67 条「更新」，12 次累计 693 条；余额最终值**取决于行序**，存在真实错账风险（本例中 4~6 行余额曾在清零/写回之间反复）。

## 1. 三条链路的分工

| 链路 | 落表 | 业务键（去重键） | 写入语义 | 职责 |
| --- | --- | --- | --- | --- |
| 库存明细（仓库明细台账） | `h3_warehouse_stock` | 仓库 + 编号 + 单位 | 新增 / 更新，**不删除** | 「有多少货、在哪个仓」 |
| 产品信息（产品信息台账） | `h3_product_catalog` | 产品编号 | 新增 / 更新 | 「类目 / 名称 / 规格 / 单位 / 采购价」 |
| 库存合并入库 | 无独立表（写 `product_inventory_balances` + `product_inventory_transactions`，批次登记到 `h3_import_batches` 的 `INVENTORY_MERGE`） | 仓库 + 解析后产品 + 单位 | **目标值语义**：把余额修正为台账值 | 把台账事实落到账上 |

```
氚云 Excel ──(按 仓库+编号+单位 去重)──▶ h3_warehouse_stock ─┐
                                                            ├─▶ 合并预览 ─▶ 人工确认 ─▶ 余额修正 + OPENING 流水
氚云 Excel ──(按 编号 去重)──────────▶ h3_product_catalog ─┘        │
                                                                    └─▶ 反向对账（余额>0 但快照无此行 → 清零）
```

**关键设计点（这三点决定了后面的故障）**

1. 库存明细台账的键**含单位**，且明确注释「同仓库同编号的多单位行各自独立、不可互相去重」——所以同一个产品只要出现过多个编号，就会**并存多行**。
2. 台账导入**只新增/更新、从不删除**：上游换了编号，老编号那行不会消失（量被置 0 或直接停更），成为长期残影。
3. 合并侧把「台账行」当作写入单元，但**余额行的键是「产品+仓库」**——两者基数不同，多对一。

## 2. 逐环节设计

### 2.1 台账导入 `ProductInventoryLedgerImportService`

- 流程：解析 Excel → 同文件内按业务键去重（保留首行）→ 分批落暂存 → 与台账 diff（`existingOf` 按键定位、`equalOf` 逐字段比对）→ 确认时写入。
- 统计口径：CREATE / UPDATE / UNCHANGED，`UNCHANGED` 时不写库。**这一层是幂等的**（实测 09-15 的仓库明细批次：16291 行 / 新增 18 / 更新 255 / 忽略 16018）。
- 遗留特性：老编号行不清理（见上）。

### 2.2 合并预览 `ProductInventoryMergeService.doMerge`

依次做五件事：

1. **费用过滤**：`ProductFeeFilter.isFee(类目, 编号)` → 跳过。
2. **异常量裁决**：数量缺失 / 负数 → `REVIEW`（`QUANTITY_MISSING` / `NEGATIVE_QUANTITY`）；数量 = 0 不跳过（用于清零）。
3. **字段补全 `enrich`**：**产品信息台账优先**，仓库明细兜底 → 取到 名称/规格/**单位**/采购价。
4. **身份解析降级链 `resolveProduct`**：①编号命中别名且名称/规格/单位不冲突 → ②编号命中但名称不符（编码漂移）→ ③名称+规格+单位唯一 → ④名称唯一 → ⑤多候选 `REVIEW(PRODUCT_AMBIGUOUS)`，无候选则新建产品。
5. **相对余额 diff**：按 `(产品, 仓库)` 取余额行、再按单位挑行 → 判 `CREATE / UPDATE / UNCHANGED`；最后追加**反向对账**：余额 > 0 但「快照中无此行」→ 生成 `VANISHED_FROM_SNAPSHOT` 清零目标。

### 2.3 合并确认 `confirm`

- 请求体**只承担「选哪些行」**，数量/价格按业务键服务端重算（防篡改）。
- `UNCHANGED` → 跳过；`VANISHED` → 按**余额行主键**清零；其余 → `ensureProduct` → 按 `(仓库, 产品)` 锁定余额行 → 一致则忽略，否则 `UPDATE` 为目标值 + 写一条 `OPENING` 流水。
- 前端只提交 `status=READY && action !== 'UNCHANGED'` 的行，所以「更新数」= 预览里被判为变化的行数。

**也就是说：只要预览的 diff 不收敛，「每次都有 60+ 更新」就会一直出现。**

## 4. 根因（按杀伤力排序）

| # | 根因 | 表现 | 规模 | 性质 |
| --- | --- | --- | --- | --- |
| A | **合并按「台账行」写入，未按「产品+仓库」聚合**；同键多行互相覆盖 | 每次 66/67 条更新；余额原地振荡 | 76 组 / 163 行 | **致命**：最终余额取决于行序，可能真错账 |
| B | **「名称唯一」降级把同名不同规格/价格的编号吸到同一产品** | 采购价抖动；两个真身不同的产品被混在一起 | 示例 4 组（166SLH/368SLH、136/142吉源…） | 高：产品主数据与价格被污染 |
| C | **反向对账快照键含单位**（且用余额单位去比台账单位） | 「行还在」却被清零 | 110 编号单位不一致 → 6 余额行误清 | 高：误清真实库存 |
| D | 单位冲突未校验；`balance.unit` 会被最后处理的那行改写 | 余额单位在 个/只、台/套 之间翻转 | 5 组同名多单位 | 中 |
| E | 调试残留：`doMerge` 里 `System.err.println("[MERGE-PREVIEW-UPDATE]…")` | 每次预览往 stderr 打 66 行 | — | 低（清理项） |

## 5. 修复方案

### P0 止血（低风险，可立即上）

1. **反向对账键去掉单位**：判定「快照中存在」时只按 `仓库 + (任一别名编号 | 产品名)`，忽略单位。理由：误清的代价远高于漏判；宁可留人工复核，也不能把有货的行清零。
2. **移除调试输出**（`doMerge` 中的 `System.err.println`），或降为 `log.debug`。

### P1 根治振荡（需先定 §6 的两条业务规则）

3. **合并前把台账行聚合成「合并单元」**，聚合键 = `(解析后产品, 仓库)`：
   - 组内**取「编号已在别名表 RESOLVED」的行为权威行**，提供名称/规格/**单位**/价格；
   - 数量：默认**取唯一有量行**；组内出现 ≥2 行有量 → 按 §6 的决策处理（求和 / 人工裁决）；
   - 组内 0 量残影行**忽略但可见**：预览行上标注「已忽略 N 条同产品残影行（编号 X、Y）」；
   - 组内单位冲突 → `REVIEW(UNITS_CONFLICT)`；
   - **预览与确认必须共用同一套聚合结果**（预览产出的 `item` 就是确认的写入单元），从根上保证「一个键一个目标值」→ 幂等。
4. **收窄「名称唯一」降级**：编号未命中别名时，若 `名称+规格+单位` 唯一命中 → 允许绑定并**写入别名（标记 DRIFT）**；若名称命中但**规格或单位冲突** → 进 `REVIEW(SYNONYM_CODE_CONFLICT)` 人工确认「同一产品还是新产品」。这一步同时消除价格抖动。
5. **余额行单位只允许权威口径写入**，残影行不得改写余额的 `unit`。

### P2 数据质量

6. 台账导入增加**两表单位一致性校验**：同编号在 `h3_product_catalog` 与 `h3_warehouse_stock` 单位不一致 → 输出质量告警清单（当前 110 个编号），交业务修上游。
7. 库存明细台账增加**残影行标记**（老编号 superseded），台账页可筛选，便于业务清理（合并侧聚合后已能容忍，属长期治理）。

### 验收标准（幂等）

> 连续点两次「合并入库」：第二次 `updatedCount = 0`、预览 `update = 0`、不新增 OPENING 流水；余额与台账一致；价格不随编号切换而变化。

## 6. 业务规则（09-17 LQ 已拍板）

> ⚠️ **口径更正**：本节初版第 1 条按「同仓库 + 同产品名 + 同单位 + ≥2 行有量」分组，报出 **12 组**。09-17 逐组拉明细复核后发现该口径**混入了两类性质完全不同的数据**，正解见 §8。

**规则一（原「12 组怎么算」）→ 按两类分别处置（✅ LQ 09-17 11:03 确认）**：

| 类 | 定义 | 规模 | 处置 |
|---|---|---|---|
| **A 残影覆盖** | 多编号 → **同一产品**，其中 **1 行有量 + N 行 0 量** | **12 组** | **0 量残影行不得覆盖有量行**：聚合时只要组内存在数量≠0 的行，0 量行只做可见标记、不产生写入 |
| **B 都有量** | 多编号 → **同一产品**，且 **≥2 行有量** | **1 组**（温州仓「切刀」767模具=24 把 + 模具281=13 把 → 同产品 37124，规格均空、价均 50、单位均「把」） | **求和 = 37 把**（同物两码） |

**规则二（同名但规格/价格不同的编号算不算一个产品）→ 拍板：(b) 两个产品。**
- 实证：涉事 11 个产品名在主数据 `sales_products` 里**本就各有 2~3 条**（不同规格/价格）。如「1000ml透明抗冷冻-1200只」= `102KLD` 16g/268.8 与 `111KLD` 17g/285.6；「2014*5.5透明抗冷冻-1200只」有 3 条（15g/252、18g/302.4、14g/235.2）。
- 因此这些编号**各绑各自产品**是**正确行为，不是冲突** → 上轮报的「12 组」里有 **11 组属此类，无需任何处置**，只是命名重叠造成的观感。
- 落地含义：降级链第 ④ 步「名称唯一命中」**必须收窄**（§5-P1 第 4 条）——若名称命中但规格/单位与候选冲突 → 进 `REVIEW`，**不得吸附**。这也正是根因 B（价格抖动）的治法。

复跑 SQL：

```sql
-- 13 组：多编号解析到同一产品
SELECT s.warehouse, a.sales_product_id, p.product_code, p.specification,
       COUNT(DISTINCT s.product_code) AS codes,
       SUM(CASE WHEN s.quantity>0 THEN 1 ELSE 0 END) AS pos,
       GROUP_CONCAT(DISTINCT CONCAT(s.product_code,':',s.quantity) ORDER BY s.product_code SEPARATOR ' | ') AS rows_
FROM h3_warehouse_stock s
JOIN sales_product_source_aliases a ON a.source_product_code=s.product_code AND a.resolution_status='RESOLVED'
JOIN sales_products p ON p.id=a.sales_product_id
```

### 8.4 A 类 vs C 类为何不重叠

- **C 类**（同名不同规格）：主数据里该名称有 **2~3 条** → 降级链第 ④ 步「名称唯一」**不触发** → 走编号命中 → **各绑各自产品** → 天然无覆盖。
- **A 类**（多编号 → 同一产品）：主数据里该名称**只有 1 条**（或别名已把旧编号绑到同一产品）→ 多行汇聚到**同一个余额行** → 覆盖。
- 唯一例外是**切刀**：主数据 1 条 + 两个编号都有量 → 既进 C 类分组（同仓库同名同单位 ≥2 行有量）又属 B 类（同物两码）。

**关键设计：分组键 = 仓库 + 解析后产品 id**（不是编号、也不是名称）。
- 按编号分组 → 同一产品的多个编号被拆成多个目标值，振荡依旧；
- 按名称分组 → 「同名不同规格」的两个产品混成一个目标值，**引入新的错账**；
- 只有「解析后产品」才是正确粒度，而这要求**先解析、再聚合**——原实现逐行处置，等于把这两步的因果关系丢掉了。

### 9.3 顺带修掉的一个真实缺陷（原方案未列）

`模具498`（台账名「48一出九上下模具」）实测每轮预览都残留 1 条**假 CREATE**：

- 修法 ①b：`H3-<编号>` 只由台账合并建档产生，编号即稳定键，名称改字不再改判为新产品。

### 9.5 落地时的环境坑（供复现参考）

- 打包前须停后端（`-jar` 实例占用 jar），但 **`clean` 会先删 jar**：若此时源码处于别人正在编辑的半成品状态，编译失败就会同时丢掉 jar → **服务无法快速回滚**。建议：先 `mvn -o compile` 确认可编译，再停服务 + `clean package`。
- 同一仓库存在并行会话时，打包失败要**先看失败文件是不是自己的**：本次失败点在 `H3FactImportService.java`（另一会话的中间态），与本次改动无关。
