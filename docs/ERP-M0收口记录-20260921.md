## 4. 验证证据

### 4.1 全量测试（真库开关打开）

```
mvn -o test -Derp.foundation.mysql=true
→ Tests run: 254, Failures: 0, Errors: 0, Skipped: 0
→ BUILD SUCCESS
```

**为什么必须带 `-Derp.foundation.mysql=true`**：13 个需要真库的用例默认被 `@EnabledIfSystemProperty` 跳过。
不带开关时是 `49 个 ERP 用例 / 13 跳过`——**这就是"假绿"的来源**：命令成功、数字好看，
但恰好绕过了本轮要验证的那 13 个。

对照复核原文的口径：复核报告的「20/20」指的是**不连库的四个类**
（`ErpBusinessExceptionTest` 6 + `ErpCommonColumnsTest` 5 + `ErpErrorCodeTest` 4 + `ErpPayloadHasherTest` 5 = 20），
**数据库类用例当时根本不在通过名单里**——这正是复核 §2 那句
「没有 ErpIdempotencyService 和 ErpChangeLogWriter 的数据库集成测试，因此本次通过不能证明其真实事务边界」的来历。

本轮之后：ERP 相关用例 **49 个，0 跳过**（新增 19：`ErpM0TwoConnectionMysqlTest` 10 + `ErpChangeLogWriterTest` 5 + `ErpIdempotencyServiceTest` +4）。

### 4.2 新增的两连接事务证据（`erp_m0_test` schema，用完即删）

| 用例 | 验证的不变量 |
|---|---|
| `concurrentSameKeySamePayloadWritesBusinessExactlyOnce` | **12 轮**双连接竞态：每轮业务写入恰好 1 条、幂等键恰好 1 行、结果引用一致 |
| `concurrentSameKeyDifferentPayloadConflictsDeterministically` | 同键异载荷：恰好一方成功、另一方 `IDEMPOTENCY_PAYLOAD_CONFLICT`，不产生第二条业务记录 |
| `losingConnectionRollsBackBusinessWhenWinnerBecomesVisibleAtInsertTime` | **确定性**覆盖"业务后插键、冲突回滚"分支：失败方整笔回滚，不留"业务进了、键没进" |
| `sameKeyDifferentActionIsConflictOnRealDatabase` | 同键换动作按冲突拒绝，不能借旧键取回旧动作的结果 |
| `failedRequestLeavesNoKeyAndRetrySucceeds` | B15：业务失败 → 键与业务一起回滚；同键重试可成功 |
| `replayReturnsFirstResultWithoutSecondWrite` | 重放不执行业务体，业务写入不增加 |
| `auditRowRollsBackTogetherWithBusinessFailure` | 业务失败 → **审计行同步回滚**，不留假记录 |
| `auditWriteFailureRollsBackBusinessWrite` | 审计写入失败（真库 `Data too long`）→ **业务写入一并回滚** |
| `auditRejectsMissingOperatorBeforeTouchingDatabase` | 缺操作人：拒绝且零 DB 写入 |
| `auditRowCommitsWithBusinessAndStoresOperator` | 成功路径：审计行与业务同事务提交，操作人 id/姓名快照正确 |

竞态分支分布（测试自打印，可复核）：**12/12 轮命中「插入冲突回滚」分支**——即真实竞争路径被覆盖，不是只跑到了重放分支。
