## 2. 「常规/订做」：原设计的问题（你要重设计的就是这块）

原设计（见《车间常规尺寸管理与首版清单-20260924》§3）：

```
建单时：customized = 手工覆盖 ?: !shop_standard_sizes.exists( normalSize(盒子尺寸) )
      → derive(品类, 盒子尺寸, 一出N, 可选配置, customized)
      → 写 manufacturing_order_outputs.sku_key / display_name
```

### 硬伤 1：两侧不在同一个「尺寸空间」→ 判定必然全落订做

- 主数据键从**库存名**提取：`RECT:128x184`、`ROUND:250`、`RECT:2014`
- 建单入参现在是**结构化数值**（长 200 / 宽 140）→ 拼出来的串两边对不上

### 硬伤 2：43 个简写行的展开值是编造的，且与自家 util 自相矛盾

- V339 迁移注释写：`2014=141.2x201.4`、`2216=224.6x160.9`
- 真库实测：`141.2` / `201.4` / `224.6` / `160.9` **各 0 条**
- 库存名实测：`20x14` **11** 条、`200x140` **11** 条、`140x200` **0** 条 → **`2014` = 长 20 × 宽 14 = 200×140mm**
- `ProductIdentityKeys` 类注释写的 `2014`/`1812` = `20x14`/`18x12` —— **这个是对的**
- 那 43 行的 `length_mm` / `width_mm` / `diameter_mm` **全是 NULL**，就算口径对齐也比不上

### 硬伤 3：排序口径两个方向

| 来源 | 写法 |
|---|---|
| 台账 / 库存名 | **长在前（大在前）**：`200x140`、`330x225`、`184x128` |
| V339 的 `size_key` | **小在前**：`RECT:128x184`（`length_mm`=184、`width_mm`=128） |

两个方向相反，字符串比对必然失败。

### 硬伤 4：把「可变的判定」烤进「建单时点的结果」

`shop_standard_sizes` 是**可维护**的（管理页能开 / 停用）。建单时固化进 `display_name` 的 `[订做]` 前缀，在管理页补录或停用该尺寸后**不会重算** → 同一实物两个显示名（`sku_key` 相同、`display_name` 不同），人无法解释。而契约文档 §2 的身份键定义里**本来不含「订做」**。

### 硬伤 5：判定入参由前端拼

前端拼 `boxSize` → 后端拿它查表。契约文档 §3 自己写了「前端不得自己拼显示名或判订做」，但现状是判定的输入就是前端拼的。

## 3. 新设计（你已选「从常规尺寸清单里选」，下面是落地形态）

### 3.1 判定改为「选」，不靠猜

建单抽屉在**形状下面**给该形状的常规尺寸下拉（数据 = `shop_standard_sizes` 中该形状 `active=1` 的行，选项就是清单原文：`2014` / `128x184` / `φ250`）：

- **选中** → 常规；尺寸文本直接用清单写法（与库存名天然同源）
- **手填**（不在清单）→ 当场提示「该尺寸不在车间常规尺寸清单，按订做安排」
- **可手工覆盖** → 保留原设计说的「尺寸以外的原因由业务员勾选覆盖」

这样简写与展开的映射问题**自然消失**（由人认，不靠机器猜），主数据里的噪声项也不会误命中（业务员不选它就不算）。

### 3.2 「判定」与「身份」分离

| 用途 | 用什么 | 存哪 |
|---|---|---|
| 身份键 | **业务原文**（`2014` 就写 `2014`，不还原语义 —— 这是 `ProductIdentityKeys` 的铁律） | `sku_key` = `品类\|尺寸原文\|一出N` |
| 常规/订做判定 | 结构化数值（长/宽/直径），或以「是否来自清单」为准 | **独立列** `is_customized` + `customized_source`(AUTO/MANUAL) + `customized_basis` |
| 给人看 | 显示名可带 `[订做]` 前缀 | `display_name`（允许变，不承担唯一约束） |

**关键收益**：管理页改了判据表，只影响新单，旧单可一键重算 —— 因为判定不在身份里，重算**不会把同一实物裂成两个身份**。

### 3.3 顺带要修的数据（等你确认后再动）

1. 43 个简写行补数值：`2014` → 长 200 / 宽 140（`2216` → 220/160，同法）
2. `size_key` 排序口径统一为**长x宽**（`RECT:128x184` → `RECT:184x128`），或明确保留小x大、把语义与注释写死
3. 修掉 V339 里编造的展开值注释

## 6. 两个建单入口 + 现货闭环（09-24 16:4x 追加，LQ 定）

LQ 拍板：**两个位置产生生产任务单，都要保留** ——
① 新建销售订单时没有现货、需要自产 → 下生产任务单；
② 直接下生产任务单（提前备货或其他），先生产后入库，之后在新建销售订单时作为**现货**可选。

### 6.1 入口现状（均已存在，无需新增）

| 入口 | 位置 | 语义 |
| --- | --- | --- |
| 需求驱动 | 销售订单明细行（供货方式=自产）→「生成生产任务单」 | 带客户/数量/`salesOrderItemId`，产品配置只在任务单录一次 |
| 备货驱动 | 本地生产任务 →「新建生产任务单」 | 无销售订单，完工入库后进本地库存 |

### 6.2 本轮补上的缺口：现货选品原来与库存无关

「现货」明细的产品下拉原来搜的是**产品档案全表**（`sales_products`，≥2 字关键字），
选出来的产品不一定有货 ——「先生产入库 → 订单选作现货」这条链在 UI 上是断的。已改为：

- **现货行只能从「可售库存」里选**（`GET /api/sales-outbounds/available-stock`，与出库扣减同口径：
  `product_inventory_balances` canonical 口径、数量 > 0；含期初合并入库、完工入库、采购到货入库）。
  选不到货本身就是「该下生产任务单」的业务信号（后端注释原文如此）。
- 选项按**产品合计可用量**展示（`产品名 · 规格 · 可用 N单位`）；仓库到出库时才选。
- 选中即回填产品名/规格/单位，行内实时显示**缺口**（数量 > 可用时）。
- 行内提供「**没有现货？改为自产并建生产任务单**」：一键把该行切成自产并走既有建单抽屉。
- 自产/外采/待确定的选品保持原产品档案搜索不变。

### 6.4 备货任务类型（09-24 17:4x，LQ 拍板新增）

「备货」在原任务类型（打样/展会/展厅/内部领用/特殊定制/返工/返工替换）里没有语义对得上的选项。已新增：

- 前端：`ProductionTaskOrderDrawer` 任务类型新增 **`STOCK`「备货（先生产后入库）」**，并作为**直接建单的默认类型**；
  备货与展会/展厅/内部同属「内部用途」——需求方显示「内部用途」（disabled）、不要求客户；
  内部用途提示按类型区分（备货：完工入库后进可售库存，之后在订单里作为现货可选）。

- 验证：真库契约测试新增 `stockOrderNeedsNoCustomerAndMarksInternalPurpose`（建 STOCK 单无客户 →
