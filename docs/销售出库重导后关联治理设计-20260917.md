# 销售出库重导后关联治理设计

> 设计日期：2026-09-17  
> 适用场景：清理客户档案、重新导入氚云销售出库，再建立客户、员工、仓库和库存产品关系。  
> 本文是下一阶段实施基线；本轮只做设计，不修改业务数据。

## 1. 设计结论

销售出库是唯一核心事实，客户、员工、仓库和产品都是它的项目内关联结果。

```text
氚云 Excel / 原始批次
          ↓
sales_outbounds + sales_outbound_items
          ↓
销售出库关联工作台
   ├─ customer_id      → customers
   ├─ employee_id      → employees
   ├─ warehouse_id     → warehouses
   └─ sales_product_id → sales_products → product_inventory_balances
```

必须长期遵守以下边界：

1. 导入保存事实、恢复已确认关系，并在整批写入后自动执行确定性关联，不猜测冲突关系。
2. 唯一电话等安全条件可自动建档；冲突记录和人工改判集中在销售出库关联工作台。
3. 原始名称、电话、地址、产品和金额永远保留，不被正式档案覆盖。
4. 草稿保留在原始台账，但不参与自动治理、覆盖率和正式统计。
5. 客户、产品关联失败不能影响销售额、已收款、未收款和月度提成。
6. 人工确认必须落在稳定映射表中，重新导入后自动恢复。

导入后的固定自动顺序为：员工/仓库唯一精确关联 → 已有客户安全关联 → 单电话安全建档 → 多电话安全身份簇 → 库存产品唯一候选归类 → 回款一致性守护。工作台只保留一个“重新自动整理”重试入口，日常无需逐步点击。

## 2. 数据分层

### 2.1 来源事实层

| 数据 | 表 | 责任 |
|---|---|---|
| 导入批次 | `h3_import_batches` | 文件、批次状态、预览和差异 |
| 原始行快照 | `h3_import_rows` | 永久追溯原始数据 |
| 销售出库主单 | `sales_outbounds` | 金额、客户快照、业务员快照、仓库快照、收款事实 |
| 销售出库明细 | `sales_outbound_items` | 产品快照、数量、售价、采购价、利润、当时库存数 |

来源事实字段不能被客户档案或库存档案反向改写。

### 2.2 正式主数据层

| 对象 | 表 | 说明 |
|---|---|---|
| 客户 | `customers` | 一个现实客户一条主档，可有多个联系人和地址 |
| 联系人 | `customer_contacts` | 电话是客户身份识别的主要证据 |
| 地址 | `customer_addresses` | 收货地址、联系方式和历史使用情况 |
| 员工 | `employees` | 内部业务员身份 |
| 仓库 | `warehouses` | 三条正式仓库主数据 |
| 产品 | `sales_products` | 产品统一身份，不为每个非标描述无限创建 SKU |
| 库存余额 | `product_inventory_balances` | 仓库 × 产品 × 单位的当前余额 |

### 2.3 关系与规则层

| 规则 | 表 | 稳定来源键 |
|---|---|---|
| 客户名称/证据映射 | `source_identity_aliases`，`entity_type='CUSTOMER'` | 名称或 `CUSTOMER_CLUSTER:<hash>` |
| 客户身份簇 | `customer_source_cluster_mappings` | 归一名称 + 电话/地址簇键 |
| 员工映射 | `employee_external_mappings` | 氚云成员 ID 或 `NAME:<姓名>` |
| 仓库映射 | `h3_warehouse_name_mappings` | 氚云仓库名称 |
| 产品映射 | `source_identity_aliases`，`entity_type='PRODUCT'` | 产品编号；无编号时为名称规格单位哈希 |
| 产品来源别名 | `sales_product_source_aliases` | 氚云产品编号或来源键 |

事实表上的四个 ID 是关系结果；上述映射表才是重导后恢复关系的依据。

## 3. 导入阶段的目标行为

### 3.1 允许做的事

销售出库导入只允许：

1. 按氚云稳定业务 ID 新增或更新同一张销售出库；
2. 保存主单、产品明细和收款子表事实；
3. 通过仍然有效的已确认映射恢复客户、员工、仓库和产品 ID；
4. 计算来源哈希、业务性质推断和未结算利润参考；
5. 对无法恢复的关系保持 NULL，交给关联工作台。

### 3.2 禁止做的事

导入不得：

1. 仅凭新名称自动建立客户；
2. 仅凭名称相似自动合并客户；
3. 用自动结果覆盖人工确认关系；
4. 把软删除客户、停用员工、停用仓库、已删除产品视为有效目标；
5. 因本次解析失败而清空已有人工确认关系；
6. 根据出库中的 `stock_quantity` 更新当前库存。

### 3.3 更新已有出库的关系保护

重新导入同一张出库时：

| 情况 | 处理 |
|---|---|
| 新结果与已有人工结论一致 | 保留 |
| 新结果为空，已有人工结论有效 | 保留已有结论 |
| 新结果指向另一有效对象 | 不覆盖，生成关系冲突 |
| 已有目标已删除或停用 | 清空失效关系，重新进入治理 |
| 原始电话、地址或产品字段变化 | 保留新来源快照，重新校验映射是否仍适用 |

## 4. 有效关系判定

工作台所有统计必须判断目标对象仍有效，不能只判断 ID 非空。

```text
有效客户关系 = customer_id 非空
            AND customers.id 存在
            AND customers.deleted_at IS NULL

有效员工关系 = employee_id 非空
            AND employees.id 存在
            AND employees.status = ACTIVE

有效仓库关系 = warehouse_id 非空
            AND warehouses.id 存在
            AND warehouses.active = 1

有效产品关系 = sales_product_id 非空
            AND sales_products.id 存在
            AND sales_products.deleted_at IS NULL
```

“核心关联完整”必须同时满足四项有效关系；费用和服务明细不要求产品关联。

## 5. 客户识别设计

### 5.1 基本原则

- 电话是区分客户的主要依据；
- 地址是电话缺失时的辅助证据；
- 名称用于展示和收敛候选，不能独立吞并带新电话的身份；
- 一个客户允许多个电话、联系人和收货地址；
- “王先生、李经理、客户、经销商”等泛化名称不能单独形成自动结论。

### 5.2 唯一解析服务

导入和关联工作台必须调用同一套客户判定服务，不得各自实现名称兜底。

返回结果统一为：

```text
MATCHED       唯一安全命中已有客户
CREATE_SAFE   可以安全建立新客户
REVIEW        证据冲突，需要人工判断
INSUFFICIENT  证据不足，暂不处理
```

每个结果必须包含：

- 目标客户 ID（如有）；
- 匹配方法；
- 使用的电话、地址和来源名称；
- 候选数量；
- 是否来自人工确认规则；
- 可读原因。

### 5.3 自动匹配优先级

1. 人工确认的名称＋证据簇；
2. 同一证据组合的已确认映射；
3. 标准化电话唯一命中；
4. 名称与电话组合唯一命中；
5. 无有效电话时，名称与完整标准化地址唯一命中；
6. 无电话且不存在冲突时，复用人工确认的名称级结论；
7. 其余进入 REVIEW 或 INSUFFICIENT。

以下情况不得自动关联：

- 同名但出现未归属的新电话；
- 一个电话属于多个客户档案；
- 多个电话分别指向不同客户；
- 只有近似名称；
- 只有短地址或模糊地址；
- 泛化名称且无唯一电话。

### 5.4 安全建档

只在工作台执行，条件为：

1. 非草稿销售出库；
2. 没有有效客户关系；
3. 恰好一个有效电话，或者多电话集合经过安全簇规则确认；
4. 电话未属于任何有效客户；
5. 没有冲突的人工映射。

建档事务同时写入：

- `customers`；
- `customer_contacts`；
- `customer_addresses`；
- 客户来源映射；
- 客户身份簇映射；
- 对应销售出库的 `customer_id`。

### 5.5 删除客户

客户删除仍采用软删除，但必须在同一事务中处理引用：

1. 将指向该客户的未结算销售出库关系置空；
2. 将客户来源映射置为 REVIEW 或 REVOKED；
3. 将客户身份簇映射置为 REVOKED；
4. 已进入正式提成版本的来源不得静默改变，只标记“关联目标已失效”；
5. 审计日志记录受影响出库、映射和版本数量。

删除前必须提供影响预览，不允许列表页直接无提示删除。

## 6. 员工和仓库设计

### 6.1 员工

自动处理仅限：来源业务员唯一命中一名在职员工。

保护规则：

- 已结算提成涉及的出库不得自动更换员工；
- 重名员工进入人工选择；
- 保存映射后，同一来源成员身份在重导时复用；
- 姓名变化应优先使用稳定氚云成员 ID，而不是继续制造姓名映射。

### 6.2 仓库

自动处理仅限：来源仓库名唯一命中一条启用仓库。

仓库关联必须先于产品归类，因为产品候选需要在对应仓库范围内验证。三条仓库完成一次人工映射后，后续导入应全部自动恢复。

## 7. 产品与库存设计

### 7.1 三个不同概念

1. 出库产品快照：出库当时的名称、编号、规格、单位、数量、价格和库存数；
2. 产品身份：`sales_products`，用于统一产品分类和成本分析；
3. 当前库存：`product_inventory_balances`，表示当前时点仓库余额。

销售出库里的库存数量是历史快照，不能作为当前库存余额。

### 7.2 产品归类顺序

1. 先确认销售出库仓库；
2. 在该仓库现有库存产品中按编号匹配；
3. 再按名称＋规格＋单位匹配；
4. 再用产品信息台账和仓库明细补充零库存产品身份；
5. 只有唯一候选才自动归类；
6. 多候选和无候选进入人工处理。

产品信息台账和仓库明细可以补建产品身份，但不得凭空增加库存数量。

### 7.3 非标产品

非标差异主要是模具、配置、生产要求和包装差异，不应把每段销售描述都建成新产品。

```text
标准产品身份
   ├─ 销售出库快照：当时名称和备注
   ├─ 模具/工装选择
   ├─ 生产任务配置
   └─ 包装与交付要求
```

## 8. 工作台目标流程

页面从多个平铺按钮收敛为四步：

### 第一步：恢复确定关系

一个按钮预览并执行：

- 已确认客户映射；
- 员工唯一精确匹配；
- 仓库唯一精确匹配；
- 已确认产品映射。

### 第二步：建立安全客户

自动处理：

- 唯一新电话客户；
- 可安全判断的多电话身份簇。

展示拟建客户、覆盖出库、电话和地址，确认后批量执行。

### 第三步：归类库存产品

仓库关系完成后，展示：

- 唯一候选；
- 等待仓库；
- 多候选；
- 无候选。

默认只执行唯一候选。

### 第四步：处理真正异常并验收

异常页面提供明确操作：

- 指定已有客户；
- 建立新客户；
- 指定产品；
- 标记暂不处理；
- 查看原始销售出库。

最后展示全链路验收，不再要求用户从多个弹窗自行推断完成情况。

## 9. 页面指标

工作台顶部只保留以下指标：

| 指标 | 口径 |
|---|---|
| 有效销售出库 | 非草稿氚云销售出库 |
| 核心关联完整 | 四类有效关系全部完成 |
| 待客户处理 | 没有有效客户关系 |
| 待员工处理 | 没有有效员工关系 |
| 待仓库处理 | 来源仓库非空且没有有效仓库关系 |
| 待产品处理 | 至少一条 PRODUCT 明细没有有效产品关系 |
| 草稿 | 单独展示，不进入以上分母 |

一张出库可以同时缺多种关系，因此缺口指标不能相加后与总数比较；验收应以逐张出库的“完整/不完整”闭合。

## 10. 重导与幂等

### 10.1 稳定键

- 出库：氚云数据 ID，出库单号只作为冲突校验；
- 客户：来源名称＋标准化电话/地址证据键；
- 员工：氚云成员 ID，缺失时才使用确认后的姓名映射；
- 仓库：确认后的来源仓库名称；
- 产品：产品编号优先，无编号时名称＋规格＋单位哈希。

### 10.2 重导结果

同一份完整文件再次导入应满足：

- 主单数量不增加；
- 明细数量不重复；
- 金额与收款不变化；
- 人工确认关系自动恢复；
- 已完成关系不会重新进入待处理；
- 原始字段无变化时标记 UNCHANGED；
- 网页版与客户端导出的格式差异不产生伪更新。

## 11. 实施阶段

### P0：关系完整性修复

1. 所有关联统计改成“目标仍有效”，不再只看 ID 非空；
2. 修复软删除客户残留引用和失效映射；
3. 工作台客户候选统一调用客户解析服务，删除独立名称兜底；
4. 重导保护人工客户关联：新解析为空不得覆盖，冲突进入队列；
5. 为以上规则增加回归测试。

### P1：导入与建档职责收敛

1. 导入阶段只自动创建满足严格安全条件的新客户；
2. 保留已确认映射自动恢复；
3. 所有新客户统一从工作台预览、确认、建档；
4. 删除客户增加影响预览和映射撤销。

### P2：工作台流程改版

1. 六个按钮收敛为四步流程；
2. 多电话处理先于“剩余异常”；
3. 增加客户和产品人工指定入口；
4. 增加可勾选分批执行；
5. 把全链路验收放进工作台。

### P3：性能与长期维护

1. preview 和 apply 使用同一个带版本号的预览结果；
2. 客户电话索引和产品候选索引一次构建、多步骤复用；
3. 增加关系冲突审计和重导恢复报告；
4. 监控失效映射、孤儿 ID 和完整度变化。

## 12. P0 验收清单

P0 完成后必须证明：

1. `customer_id` 指向软删除客户时计入“缺客户”；
2. `sales_product_id` 指向已删除产品时计入“缺产品”；
3. 同名新电话不会通过工作台名称映射自动关联；
4. 唯一电话可以正确关联已有客户；
5. 无电话时可以复用人工确认的名称结论；
6. 重导解析为空不会抹掉人工确认关系；
7. 映射指向失效对象时不会恢复该关系；
8. 草稿不进入自动处理和正式覆盖率；
9. 销售额、已收款、未收款、运杂费和提成口径不受本轮修改影响；
10. 相同文件再次导入关系数量稳定，无重复客户和重复产品。

## 13. 本轮明确不做

- 不删除当前销售出库和产品库存数据；
- 不批量重新判断现有客户关系；
- 不修改月度提成公式；
- 不启用正式库存流水；
- 不恢复已删除的旧生产业务设计；
- 不把客户、产品、员工、仓库治理操作放回原始台账。
