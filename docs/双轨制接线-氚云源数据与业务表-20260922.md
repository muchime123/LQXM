# 双轨制接线：氚云源数据（只读台账） ↔ ERP 业务表（可写）

> 2026-09-22 · 生产侧 V323 + 销售侧 V324
> 承接 LQ 口径：「**要把氚云中的数据导入当前项目，可以在当前数据库对数据进行修改，
> 但氚云导入中心的台账要是氚云导入的源数据**」

---

## 1. 要解决的问题：两套数据各活各的

接线之前，项目里并行着两套互不相通的数据：

| | 氚云源侧（台账，只读） | ERP 业务侧（可写） | 接上了吗 |
|---|---|---|---|
| 生产任务单 | `production_orders` **5,691** | `manufacturing_orders` **1**（仅一张测试单） | ❌ |
| 销售出库 | `sales_outbounds` **18,966** + `sales_outbound_items` **35,159** | `erp_sales_outbounds` **0** + `erp_sales_outbound_items` **0** | ❌ |

症状：
- 氚云数据早就导进来了、字段也完整（客户/业务员/仓库/金额/毛利/明细），但**项目里没有任何入口能操作它们**；
- 而能操作的那套流程（制造域的报工/完工/收货，销售域的录单/过账/扣库存）**底下是空的**；
- 前端「销售管理 → 销售出库」页读的是 `erp_sales_outbounds`（0 行），页面上的注释还写着
  「台账出库在『氚云数据管理 → 销售出库关联』，只读历史」——**用户要的正是反过来**。

---

## 2. 解法：双轨制 = 两张表 + 镜像接线

**必须两张表**，单表做不到：

| | 源轨道（氚云台账） | 业务轨道（ERP 业务表） |
|---|---|---|
| 谁写 | 只有氚云导入管线 | 只有业务操作（人 / 流程） |
| 能改吗 | 不能（只读，忠实留存源数据） | 能改 |
| 重导会覆盖吗 | 会（这是导入管线的职责） | **不会**（业务改动不丢） |
| 关联方式 | — | `external_source='H3YUN'` + `external_id` |

若合成一张表，两个致命问题：
1. **改源行 → 台账失去忠实性**（不再是「氚云原样」）；
2. **重导覆盖业务改动**（业务侧补的 SKU、状态流转全被冲掉）。

镜像的纪律（两侧一致）：
- **只读源表、只写业务表**；源表的内容一个字都不改
  （生产侧例外：回写 `linked_manufacturing_order_id/no` 这一个反向指针，便于台账侧反查）；
- **不反向同步**：业务侧的改动绝不回写氚云台账；
- **幂等靠两重保险**：唯一索引 + 「源表左连业务表，只取连不上的」选取条件。
  不靠任何指针列（中间态会失真——「业务单已建但回写指针失败」时只信指针会重复建单）。

## 3. 生产侧（V323）

**代码**：`H3ManufacturingMirrorService` · 端点 `POST /api/manufacturing/mirror/h3-orders`

**迁移 V323** 做三件事：
1. 恢复 `production_orders.linked_manufacturing_order_id/no` + 索引
   （V287 曾主动 DROP，注释写明「生产模块已整体撤回等待重建」——P3 就是那次重建，恢复是正当的）；
2. 放宽 `manufacturing_orders` / `manufacturing_order_outputs` 几个 NOT NULL（氚云工单本就没 SKU、没单位、客户名只有 64%）；
3. 新增 `source_status_raw` / `source_progress_raw` / `source_warehoused_quantity` / `source_mirror_pending`。
   ⚠️ 只放开**数据库层**；Service 层手工建单校验保持不变。

**⭐ 能成立的關鍵前提**：氚云工单的 `product_name` 是**品类级**
（"手动片膜"/"模具"/"LQ260气调机卷膜"…），而制程解析正是按品类名精确匹配
`manufacturing_task_config_items.config_name`（`config_type='PRODUCT_NAME'`）→
**命中 5,688/5,688 = 100%**，所以镜像后工序能完整展开。
（对比：拿 SKU 名反推品类零命中 74.5%，此路不通。）

**车间判定**：45 个品类唯一命中一个车间；仅「模具」「配件」两品类同时存在于
车间 3（封口机）与车间 4（全自动气调机），用产线名消歧。

**实测结果**：`{"sourceTotal":5691,"mirrored":5691,"remaining":0,"pendingData":816}`

| 项 | 结果 |
|---|---|
| 状态分布 | COMPLETED 4,613 / RELEASED 860 / PENDING_RECEIPT 167 / CANCELLED 14 / DRAFT 14 / IN_PRODUCTION 23 |
| 待补 816 | 制程未配置 **633** / 氚云标记「无需报工」**180** / 氚云未填产品名 **3** |
| 工序 | 已展开 4,875 张、产出清单 5,688 行、工序 **14,625** 行 |

## 4. 销售侧（V324）

**代码**：`H3SalesOutboundMirrorService` · 端点 `POST /api/sales-outbounds/mirror/h3-orders`

**迁移 V324** 做四件事：
1. `erp_sales_outbounds` 补来源关联列（`external_source` / `external_id` / `source_outbound_no` /
   `source_status_raw` / `source_warehouse_name` / `source_ship_date` / `source_sales_amount` /
   `source_mirror_pending` / `source_mirrored_at`）+ `uk_eso_external` 唯一索引
   （对 ERP 自建单两列都是 NULL，MySQL 唯一索引允许多个 NULL 并存，不受影响）；
2. 放宽主表 NOT NULL：`customer_name_snapshot`（源 13 张没填）、`warehouse_id`（源 2 张没填）；
3. `erp_sales_outbound_items` 补 `line_type`（PRODUCT/FREIGHT/SERVICE，与氚云台账**同名口径**）+
   `external_id` + `source_category`；
4. 放宽明细 NOT NULL：`sales_product_id` / `canonical_product_id` / `product_name_snapshot` / `unit`。

### 4.1 ⭐ 两个决定成败的字段口径（实测踩出来，不是猜的）

**(a) 业务员必须取 `employee_id`，不能取 `salesperson_id`。**

源表里 `salesperson_id` 是**氚云侧原始 id**，`employee_id` 才是**本地员工 id**：

| source.salesperson_id | source.salesperson_name | 本地 employees[该 id] | source.employee_id | 本地 employees[该 id] |
|---|---|---|---|---|
| 23 | 李水云 | **于洋洋** ❌ | 17 | 李水云 ✅ |
| 15 | 徐恩永 | **刘杰** ❌ | 9 | 徐恩永 ✅ |
| 7 | 李晓梅 | **林琳琳** ❌ | 2 | 李晓梅 ✅ |

`SalesOutboundService` 的行级数据范围过滤字段正是 `o.salesperson_id` →
**直接搬源 `salesperson_id` 会让每个业务员看到别人的单，且不报错**。
实测镜像后：`salesperson_id = employee_id` **50/50**、`= 源 salesperson_id` **0/50**、姓名一致 50/50。

**(b) 客户 `customer_id` 可以直接搬**：实测 **18,757/18,757** 命中本地 `customers`
（209 行为空 = 氚云没匹配上，镜像留空）。

### 4.2 状态为什么一律落 DRAFT

ERP 出库单的 `POSTED` 语义是**扣减当前库存**。这 18,966 张是 2025-11 ~ 2026-09 的**历史已发生事实**，
若按氚云原状态（已生效 18,813 / 草稿 111 / 进行中 42）映射成 POSTED，
会在镜像的瞬间把当前库存冲成巨额负数。

→ **一律 DRAFT**，氚云原状态存 `source_status_raw` 备查。
这样也把「历史单该不该补扣库存」这个问题**显式暴露**在业务侧，而不是悄悄替用户做一个危险的决定。
前端过账确认弹窗对镜像单有专门措辞（「历史单扣当前库存通常会让库存变成负数」）。

### 4.3 长度截断

源列多为 TEXT，比 ERP 列宽，超长必须截断否则插入直接报错：
`outbound_no` 50 · `customer_name` 300 · `product_name` 500 · `specification` 1000 ·
`remark` 1000 · 明细 `remark` 500 · `source_mirror_pending` 300。
**截断只发生在 ERP 落库这一步，源表一个字不改。**

### 4.5 过账的新护栏（V324 放开 NOT NULL 引入的）

放开 NOT NULL 后，原来安全的解箱写法会 NPE，已补：

- `canonical_product_id IS NULL` 的明细（运费/服务费行、未绑 SKU 的商品行）→ **拒绝过账**并说明是几行；
- `warehouse_id IS NULL` 的单 → **拒绝过账**并提示「请先编辑补齐仓库」。

## 6. 已知待办（都是业务侧的事，不是代码缺陷）

1. **633 张生产工单「制程未配置」**：49 个品类的 `process_template_id` 一个都没绑；
   车间 2（半自动气调机）、车间 4（全自动气调机）的 `default_process_template_id` 是 NULL。
   - 最小解法：给这两个车间各设默认制程（车间 2 → 模板 5「半自动气调机」，车间 4 → 模板 6「全自动气调机」），
     一次覆盖约 535 张；
   - 剩余「模具」「配件」（约 98 张）跨车间，需按产线名消歧或人工指定。
   - ⚠️ **补完配置后需要一个「重新展开工序」入口** —— 现有镜像只取「连不上的」，
     已镜像但 pending 的单不会被重扫。**这是下一步要补的洞。**
2. **180 张「氚云标记无需报工」**：属既定事实，保持不展开工序。
3. **528 行负数数量、57 行空数量**：源脏数据，按纪律不清洗、不改代码、不报 bug。
4. **历史单过账语义**：是否允许、是否要设时间闸门，待 LQ 拍板。
