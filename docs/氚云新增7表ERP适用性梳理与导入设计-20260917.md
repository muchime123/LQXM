## 1. 实测结构

### 1.0 共有特征（8 份通用）

| 特征 | 说明 |
| --- | --- |
| 表头两行 | 第 1 行是氚云系统字段名（`SeqNo` / `F0000017` / `ObjectId`…），**第 2 行才是中文业务名**，第 3 行起是数据 |
| 主子结构 | 主表字段只写在首行，后续明细行的主表列一律为空（例：采购入库 63 825 行里主表编号只有 11 085 个非空） |
| 系统列 | 数据ID(不可修改) / 数据标题 / 拥有者(必填) / 所属部门(必填) / 创建人 / 创建时间 / 修改时间 / 数据状态 |
| 子表行唯一键 | 每行都有「数据ID(不可修改)」UUID → **这是天然幂等键**，不必自己造 |
| 值集表 | 附带 `Hidden_Options_*` 隐藏 sheet（如供应商状态=合作中/合作终止、发票类型枚举），**是官方枚举来源，应读取而非猜测** |

> ⚠️ **必须按第 2 行中文表头名匹配列，不能按第 1 行前缀解析**：其他入库的子表前缀被氚云写成了「**其他出库明细.**」（表单复制串名），按前缀解析会整表错列。

### 1.1 供应商信息（`供应商信息_2026-09-17-10-30-36-280.xlsx`，16 KB，单表 76 条）

主数据表，粒度 = 一个供应商一行。字段与**实测填充率**：

| 列 | 中文名 | 非空/76 | 去重 | 说明 |
| --- | --- | --- | --- | --- |

| B | **供应商状态** | 76 | 1（全「合作中」） | 枚举来自 `Hidden_Options_1` = 合作中 / 合作终止 |
| C/D/E | 对私开户名 / 账号 / 开户行 | 20 | 20 / 20 / 14 | 个人卡收付 |
| F/G/H | 对公开户名 / 账号 / 开户行 | 11 | 11 / 11 / 10 | 对公账户 |
| I | 数据ID(不可修改) | 76 | 76 | UUID，稳定主键 |
| J | 数据标题 | 76 | 76 | = **名称 + 4 个空格 + 状态**（如 `封口机车间    合作中`） |
| K/L | 拥有者 / 所属部门 | 76 | 3 / 1 | 部门恒为「浙江利强包装科技有限公司」 |
| M/N/O | 修改时间 / 创建人 / 创建时间 | 76 | 74 / 3 / 62 | 最近修改 2026-08-03 |
| **P/Q/R/S/T** | **联系人 / 联系方式 / 供应商地址 / 备注 / 附件** | **0** | — | **全部为空** |
| U | 数据状态 | 76 | 1（全「已生效」） | — |

**三条关键结论**：

1. **引用完全闭合**：采购入库「选择供应商」去重 **73 种**，剥离状态后缀后仍 73 种，**100% 命中本主表**，零孤立引用。→ 可以放心用「名称」做主键关系。
2. **12 组银行信息可用**（20 对私 + 11 对公 = 31/76 = 41%），但**联系人/电话/地址 100% 为空** → 供应商档案完整度治理清单基本是空的（与客户档案不同，无历史可补）。
3. **混入 6 条非供应商值，必须在导入时标记而非静默接受**：
   - 内部车间/产线 4 条：`称重机车间`、`封口机车间`、`半自动气调机`、`全自动气调机`
     （与生产工单「产线选择」枚举互证：封口机车间 / 全自动气调机车间 / 半自动气调机车间）
   - 串名脏值 2 条：`其他入库`（单据类型串入）、`温州市中坚薄膜销售出库单`（尾缀串入）
   - 另有若干个人/简称条目：`陈希伟`、`杨宇`、`黄朝晖`、`林齐友`、`峰源`、`义乌`、`木叶餐具`、`德康隆`、`宋保安 POF膜厂家`、`汕头博科`、`锐达包装机械`、`远康包装机械`、`夏林彩印`…

**未被采购入库引用**的 3 条（可能是新供应商或已停用）：`上海嘉迹实业有限公司`、`云浩吉包装`、`沧州金佰闰塑料包装材料有限公司`。

> ⚠️ **供应商 ≠ 经销商的关键差别**：经销商有氚云编号（`JXS…`）可做业务键，**供应商没有编号，只有名称**，而采购入库引用的是「名称+4 空格+状态」的**数据标题文本**。状态一旦从「合作中」变「合作终止」，引用文本就会失配 → **必须建别名表**（详见 §2.3）。

## 2. 导入功能设计

### 2.1 统一契约（沿用 `ImportKindDescriptor`，不另起一套）

现有 8 类之外**新增 6 类**（`data_type` / 前端 route key / 表头契约 / 能力位仍收口到同一个描述符）：

| route | dbType | keyHeader（第 2 行表头） | 展示名 | domain | 子表 |
| --- | --- | --- | --- | --- | --- |
| `supplier` | `SUPPLIER` | 供应商名称 | 供应商信息 | LEDGER（主数据） | ✗ |
| `purchase` | `PURCHASE_IN` | 采购入库编号 | 采购入库 | BUSINESS_FACT | ✅ |
| `otherIn` | `OTHER_IN` | 流水号 | 其他入库 | BUSINESS_FACT | ✅ |
| `otherOut` | `OTHER_OUT` | 其他出库编号 | 其他出库 | BUSINESS_FACT | ✅ |
| `transfer` | `TRANSFER` | 流水号 | 库存调拨 | BUSINESS_FACT | ✅ |

> ⚠️ `keyHeader` 对供应商是「名称」——它**不是唯一键**（改名/状态变更会漂），只作表头识别用；真正的键见 §2.2。

### 2.2 幂等键（照此实现，别自己造）

| 层级 | 键 | 依据 |
| --- | --- | --- |
| A 域主表 | 业务编号（采购入库编号 / 流水号） | 编号天然唯一 |
| A 域子表 | **「数据ID(不可修改)」UUID** | 氚云每行唯一，最稳 |
| 开票资料 | 税号 + 户名 | 户名单独不唯一（3 427 行仅 3 369 去重） |
| **供应商** | **数据ID UUID 为主键** + 「归一化名称」唯一索引 + **别名表兜历史文本** | 见下 |

**供应商为什么必须有别名表**：供应商**没有编号**，而采购入库引用的是「名称 + 4 空格 + 状态」的**数据标题文本**。一旦某供应商从「合作中」变「合作终止」，历史单据里的引用文本就与新主表对不上。所以：

```
h3_supplier_catalog   (source_object_id UUID 唯一, name, normalized_name 唯一,
                       supplier_status, is_internal, has_private_bank, has_public_bank, ...)
h3_supplier_aliases   (supplier_id, raw_text 唯一, source = 采购入库/其他…)
```

解析顺序：`原始文本 → 别名表` → 命中即返回；未命中 → **剥状态后缀 + 归一化（去空格/全半角/大小写）后匹配名称** → 命中则**自动写入别名表**（自愈）；仍不命中 → `REVIEW`（不静默新建，避免把脏值当供应商）。
