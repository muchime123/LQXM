## 0. 一句话结论

**氚云产品库存在新系统里的定位早就定了：它是 ERP 的「期初余额来源」，一次性结转入账，之后不再依赖氚云。**

依据是决策 `#27` 第②条（09-21 LQ 拍板：「台账 = 期初/初始来源，ERP = 在其上运行的正式模型」），且开账机制**现成且曾跑通** —— 09-16 开过 1,690 行余额 + 1,691 条 `OPENING` 流水。

但**现在它悬空着**：09-28 清库把已开好的期初连同产品表一起删了（`db_purge_backup_20260928/_purge.sql` 第 81–83 行），而重导台账**不会自动重开账**（开账是「台账合并 confirm」的副产物，合并入口 09-16 已从页面撤下）。

所以「这批数据该咋办」的答案**不是重新设计**，而是三步：

1. **切一个「切换日」**（这是唯一必须在动手前定死的事）
2. **按清洗口径把期初重开一次**
3. **此后 ERP 自己滚流水，氚云库存转只读对照**

> ✅ **09-28 状态**：LQ 已拍 Q2–Q6 五条口径（见 §7），**唯一切换日仍未定**（原话「现在还没有到切换的时候」）。口径已登记为决策 **`#38`**（`ERP决策登记-20260921.md`）。本轮只登记口径，**未动代码、未动数据**。

## 3. 断在哪（为什么现在悬空）

```
氚云台账（有数据）──✗──> 期初开账（无路径）
                              ↑
                    原本唯一的触发点：
              台账合并 confirm（09-16 已从页面撤下）
```

三处叠加：

1. **触发点被撤**：开账是 `ProductInventoryMergeService.confirm()` 的副产物（写 `balances` + `OPENING` 流水，`source_no='MERGE-IMPORT'`，`source_id` = 仓库明细批次 id）。09-16 合并入口从页面撤下后，**没有别的入口能开账**。
2. **清库删了结果**：09-28 把 `balances`/`transactions`/`sales_products` 一起清了。
3. **重导不触发**：今天 13:53 之后重导的两份台账只落 `h3_*` 表，**不会**回头去开账。

⇒ 现状就是「**氚云那边有数，ERP 这边无账**」，且没有任何自动弥合机制。

## 4. 这批数据在新设计里的三个去向（分层处置）

关键认识：**这份台账是「导入那一刻的当前余额」，不是「历史事实」。** 它没有业务时点（只有 `source_created_at` / `last_synced_at`），所以它的价值是**时效性的存量快照**，越拖越不值钱。据此分三层：

| 层 | 内容 | 行数 | 新系统里的去向 |
|---|---|---:|---|
| **①存量** | 数量 > 0、非代发仓、非费用/非标 | **1,649** | **→ 期初余额 `OPENING`**（一次性结转） |
| **②目录** | 产品名称/规格/单位/采购价 | 15,450 | **→ 产品主数据 / SKU 身份**（身份主轴，`H3-` 命名空间） |
| **③杂项** | 零行（14,781）、负行（7）、费用/非标（20）、代发仓（28）、NULL 行（2） | 14,832 | **→ 只作对照，不进账**（费用/非标与 NULL 行挂异常清单） |

**为什么零行不进账**：0 行入库没有会计意义，只会让余额表虚胖 8.7 倍，且与「有货/无货」判断无关。09-16 那次开账就是只开有数的 1,693 行 —— 这个口径是对的，沿用。

## 5. 三条路线对比

| | A 一次性期初结转（推荐） | B 每次导入刷新余额（孪生镜像） | C 从零起账 |
|---|---|---|---|
| 做法 | 切换日切一刀，把①层结转成 `OPENING`；之后 ERP 自己滚流水 | 每次重导氚云库存都覆盖刷新 `balances` | 期初全 0，靠实际盘点建账 |
| 与已定决策 | ✅ 完全自洽（`#27` ② + `U13` 甲 + `U15-Q4`） | ❌ 与 `#27` 冲突（等于放弃 ERP 正式账） | △ 不冲突，但放弃 `#27` ② |
| 「有货直接出库」分支 | ✅ 可判断 | ✅ 可判断 | ❌ **失效**（账上永远 0，全部走下单） |
| 对账 | ✅ 期初冻结，差异可归因 | ❌ **双记账，永远对不平**（ERP 出库不回写氚云） | ⚠️ 期初缺失，历史差异不可解释 |
| 主要代价 | 需定切换日 + 清洗 | 需接受"两套账打架" | 需一次全量实物盘点 |
| 结论 | **唯一自洽选项** | 短期苟且，长期债务 | 备选（若实物与台账严重不符） |

**B 为什么必错**：ERP 出库/完工入库**不会**回写氚云。一旦两边都在动，`balances` 就是「氚云某一刻的数 + ERP 之后的动」混在一起，任何时点都对不平。

## 6. 推荐路线：A + 三条前置

### 6.1 切换日（cutover）—— 唯一必须先定的事

**现这批库存是「今天 14:03 导入那一刻」的氚云状态**，它只在那一刻有效。切换日的定义是：

> **切换日 T：`T` 之前的库存变化归氚云；`T` 之后 ERP 记账，氚云库存不再作为依据。**

配套（**这三条是一体的，缺一不可**）：

1. `T` 之前，氚云库存要**导一次最终的、干净的**仓库明细（就是当前这份的最终版）
2. `T` 当天，按清洗口径**结转期初**
3. `T` 之后，氚云库存**停录、转只读** ✅ 已拍（否则必然分叉）

| P0 | **定切换日 T**（氚云**转只读已定** ✅） | 切换日**未定**（`U12` 尾巴） | 决策 |

> 1. **三值逻辑陷阱**：`NOT(TRIM(a)=TRIM(b))` 与 `TRIM(a)<>TRIM(b)` 在 `a`/`b` 为 NULL 时**都为 NULL（不满足）** → 只用「`name = code`」做判据会**静默漏掉那 2 行**。本轮正是靠「相减得 1,651 ≠ 分仓相加 1,649」的 2 行差才把它揪出来。**判据必须显式加 `IS NULL` 分支。**
> 2. **费用行不止 `name = code` 一种形态**：那 2 行里 `加工费` 是费用科目但名称列为空；另一行 `295QZDQTJ` 是**真产品**（有编号、单位「台」）却缺名称 —— 两者都进异常清单，但**性质不同**，处置时要分开看。
