## 3. ⭐ Odoo 的关键陷阱：免费边界

Odoo 不是「免费 ERP」，它是**open-core**——**财务正中心的功能在收费版**。而「财务正中心」恰好是 LQ 最缺的那块。

| 功能 | Odoo CE | Odoo EE | ERPNext |
|---|---|---|---|
| 基础进销存 / 开票 | ✅ | ✅ | ✅ |
| 会计科目表 / 凭证 / 增值税 | ✅ | ✅ | ✅ |
| ⭐ **财务报表（资产负债表/利润表/现金流量表）** | ❌（`account_reports` 是 EE 专有；CE 需 OCA 补） | ✅ | ✅ |
| 银行对账自动 / 银行同步 | ❌ 手动 | ✅ | ✅ |
| 固定资产 / 预算 / 递延收入 / 催款 / 合并报表 | ❌ | ✅ | ✅ |
| 审计轨迹 | 基础 | 高级 | ✅ |
| Studio（无代码定制） | ❌ | ✅ | 元数据低代码（原生） |
| PLM / 质量检验 / 设备维护 / 车间平板 | ❌ | ✅ | ✅（Quality 为独立模块） |
| 原生移动 App | ❌ 仅 Web | ✅ | 响应式 Web |
| 成本 | $0 | 订阅费 | $0 |

⚠️ Odoo CE 的补救路径是 **OCA 社区模块**（如 `account_financial_report`）。能补 70~80%，但**模块质量参差、升级阵痛**，且要自己承担维护。

## 4. 专业 ERP 的骨骼（LQ 缺的那一层）

```
① 主数据            物料 · 客户 · 供应商 · BOM · 仓库       （一次定义，处处引用）
        ↓
② 业务单据链         订单 → 生产/采购 → 入库 → 出库 → 发票
        ↓
③ 过账层 ⭐          每个单据动作 → 自动生成【会计凭证 + 库存分录】
        ↓
④ 总账与报表         试算平衡 → 资产负债表 / 利润表 / 现金流量表

横切全链：审计轨迹 · 权限 · 审批流
```

**LQXM 现状**：①②**部分具备**，③④**是空的** —— 这是决策 `#21`「财务＝业务财务 + 资金」目前只到业务侧的根因。
👉 **「专业 ERP 长什么样」的答案：不是页面多，而是中间那层自动过账。**

## 5. 逐项对比（按对 LQ 的重要度排序）

| 维度 | ERPNext v16 | Odoo 19 CE | 对 LQ 的意义 |
|---|---|---|---|
| **完整会计 + 过账 + 报表** | ✅ 免费全含 | ❌ EE 才有 | ⭐ **决定性**：这正是最缺的一层 |
| 制造业贴合度 | BOM + WO + Job Card + 分包 + 质量 | CE：BOM / MO / WO / 基本工序；PLM·Quality·车间平板 = EE | ⚠️ **最大不确定项**，两边都必须实测 |
| 中国本地化 | 薄。中文科目表/三大报表靠社区 app `erpnext_china`（Gitee `yuzelin`，MIT，1.61 MiB，**个人维护量级**） | 厚。官方 `l10n_cn`（CAS 科目表+增值税）在 CE 内；OCA `l10n-china`（AGPLv3） | Odoo 明显占优 |
| 金税 / 电子发票 | 「支持金税」是**宣传语**，深度需自验；Frappe 云中国「**即将**」登陆（＝未落地） | 第三方连接器已生产级（百望 Baiwang 等）；深圳 Majorbird 等有落地方案 | Odoo 明显占优 |
| 服务商 / 有人帮 | 中国大陆**几乎没有**；只能靠自己或 Frappe 认证伙伴 | 已分层：综合实施商（算数科技，11 年 6000+ 项目）、本地化方案商、跨境服务商、国际服务商、OCA 社区 | Odoo 明显占优 |
| UI / 体验 | 一般 | 明显更现代 | Odoo 占优 |
| 定制上手难度 | 较低（DocType 元数据 + 低代码） | 较高（ORM + XML 视图 + Owl） | ERPNext 占优 |
| 与「自主可控」契合度 | ✅ 最纯粹：单版本、无功能阉割、GPL 全开 | ⚠️ CE 自托管可以，但会**持续撞到「这功能在 EE」** | ERPNext 占优 |
| 数据库 | MariaDB | PostgreSQL（国产库达梦/OceanBase/TiDB 兼容 PG 协议，信创角度更顺） | 视信创要求 |

> Odoo 在中国的公认短板（中文行业分析自承）：**原生财务模块不兼容中国会计准则、金税对接需额外开发、IT 门槛高、品牌认知低于用友金蝶、本地化服务网络仍在建设**。

## 6. 建议路线（分阶段）

**Step 0 · 照镜子（1~2 天，先做这个）**
同一条主链「销售订单 → 生产任务单 → 完工入库 → 出库 → 开票/应收」，**在两个系统里各手工录一遍**，回答三问：
1. 它的数据模型与 38 条口径，**哪几条冲突**？冲突的**是我们错了，还是它不适合我们**？
2. **哪些模块我们确实不该自己写**？（候选：总账、应收应付、固定资产、税务报表、报表引擎）
3. 「氚云编号 / 代发仓 / 箱规压号 / 跟单员」能否在它里面自然表达？

> 判定权重建议：制造业贴合度 40% ｜ 中文与金税 30% ｜ 定制难度 20% ｜ 生态与有人帮 10%。
> 不管最后切不切，这份产出**都能直接用来治理 LQXM**。

**Step 1 · 边界切分（低风险，可立刻做）**
LQXM 只做**业务事实源**（订单 / 生产 / 库存事实）；**会计与税务整体外挂**，用接口传凭证。

**Step 2 · 单模块试点（1~2 个月）**
选「采购 → 到货入库 → 应付」——口径最标准、与独特业务耦合最小。

**Step 3 · 期初切换**
复用已有开账干跑产出（进账 1,621 单元 / 1,515 主轴 / ¥2,920.8 万；**口径缺口 27 行须先处置**），并敲定决策 `#38` 一直悬着的**切换日**。

**Step 4 · 收尾**
氚云转只读；档案侧（证书 / 知识产权 / 资质）保留在 LQXM。

**全程铁律：一个业务事实只允许一个权威源，不要双写。**

## 7. 改造姿势（硬约束，两边通用）

> ❌ **不要改核心源码。**
> - Frappe：不要改 `frappe/erpnext`，**新建自定义 app**。
> - Odoo：不要改 `odoo/addons` 原生模块，**新建自定义 addon**。
>
> 「在专业项目上改」＝**在它的模型里扩展**，不是改它的代码。搞反了，第一次升级就死。

## 8. 另一条路（ChatGPT 不会推）

若核心诉求变成「不想再自己写」→ 国内包装/制造业的**成熟商业 ERP**（鼎捷、管家婆、用友 / 金蝶）有实施商、有本地化、有售后。开源方案的「免费」在中国大陆的真实含义是：**没有服务商兜底，你还得自己写**——ERPNext 是换 Java→Python，Odoo 是换 Java→Python + 大概率买 EE。

> 想在 **Java 栈**里找「专业 ERP 底座」→ 目前没有堪用的开源 ERP；只有 JEPAAS / 若依这类**低代码平台**，那等于又回到自己建。

## 9. 开源 ERP / CRM 全景与推荐（含 Twenty）

### 9.1 ⚠️ 先分清两类：CRM ≠ ERP

LQ 追问的 **Twenty 是 CRM，不是 ERP**。边界：

| | ERP | CRM |
|---|---|---|
| 管什么 | 物料 · 库存 · 生产 · 采购 · **会计与过账** | 线索 · 商机 · 联系人 · 跟进 · 销售管道 |
| 核心产出 | 会计凭证 / 库存分录 / 三大报表 | 销售管道推进 |
| 对 LQ 瓶颈 | ⭐ **直接命中** | ❌ **一条都不沾** |

**关键判断**：四个缺口（①过账层 ②完整会计与三大报表 ③库存桥 / 主数据 ④销售过程管理）中，**前三只有 ERP 能补**。现在引入 CRM ＝ 多出第 4 套孤岛，正好加重「三套库存无桥」那种病。
另注：LQXM 已有「客户档案」，它是 ERP 单据链的一环（销售订单客户必须锚定档案），**不是独立 CRM**。

### 9.2 Twenty（LQ 点名）

| 项 | 值 |
|---|---|
| 仓库 | `twentyhq/twenty`（YC 背景，自称 #1 open-source CRM） |
| 许可 | **AGPL-3.0**（部分包 MIT）；另有专有云附加服务 |
| 版本 / 活跃 | 最新 v2.x（发版 **v2.39.0 @ 2026-09-14**）；≈5.6~5.7 万 star；近 12 个月 **12/12 月有提交、6,640 commits**（健康度满分） |
| 栈 | **TypeScript**（React + Jotai + Linaria）+ **NestJS + BullMQ** + **PostgreSQL** + **Redis** + GraphQL / REST；Nx monorepo |
| 自托管 | Docker Compose，$10 VPS 约 10 分钟起步 |
| 亮点 | ⭐ **运行时自定义对象 / 字段**（元数据层「代码即数据模型」：`defineObject`，可 git 版本化）+ **GraphQL API 由元数据模型生成** + 工作流 / Webhook + v2.x 内置 AI agents（自带模型 key） |
| 短板 | ⚠️ 功能面比老牌 CRM **窄**（无大型邮件营销 / 复杂报表）；迭代极快、数据模型会变；多服务运维（NestJS + worker + PG + Redis） |
| **对 LQ** | **值得看、别现在上。** 它的价值是「让你看见现代 CRM 的数据模型长什么样」；真要上，必须先打通 ERP 主轴 |

### 9.3 ERP 候选全景（按对 LQ 的相关度排）

| 系统 | 许可 / 栈 | 一句话判断 |
|---|---|---|
| **ERPNext v16** | GPL-3.0 / Python + MariaDB | ⭐ **首选参照**：单版本全含会计 + 制造 + 审批 + 报表。⚠️ 两个实测坑：Frappe 用**字符串主键**，有报告称约 **70 万行后**出现性能瓶颈（LQ 现 1.5 万行，远未触及）；DACH 经验是「**先选伙伴再选系统**」，中国同理 |
| **Odoo 19** | LGPL-3 CE + 专有 EE / Python + PostgreSQL | 生态最大、中文与金税落地最好；但**完整会计 / 报表在 EE**（见 §3） |
| **Axelor** | AGPL-3 / **Java + PostgreSQL** | ⭐ **对他栈最友好**（Java 阵营唯一现代货），原生低代码 studio。短板：社区小、集中法国；AGPL copyleft；低代码堆复杂逻辑会让大版本升级变成维护工程；企业条款约 €30 / 用户 / 月起 |
| **metasfresh** | GPL / Java + Docker | 德国货，面向**批发 / 食品 / 高单据量制造**，批次 / 保质期 / FIFO-FEFO 在内核里。短板：生态小、**软件反过来规定流程**（要改业务去适应系统） |
| **Tryton** | GPL-3 / Python | 代码最干净、升级最稳、会计内核强；但 UI 落后、无真 CRM、仅约 300 模块（vs Odoo 数千）、无伙伴几乎上不了手 |
| iDempiere / ADempiere | GPL-2 / Java | 企业级会计与多公司强，但 UI 老旧、文档稀、学习曲线陡 |
| Apache OFBiz | Apache-2.0 / Java | 协议对法务最友好，实为「**2006 年的自己动手套件**」→ 等于又回到自己建 |
| Dolibarr | GPL-3 / PHP | 微企业够用；**无真 MRP、制造业很弱、架构显老** → 不适合 |
| MixERP / Invoice Ninja | 各异 | 太轻；Invoice Ninja **连总账都没有**，只是开票 |

### 9.4 CRM 候选全景（如果将来真要做）

| 系统 | 许可 / 栈 | 一句话判断 |
|---|---|---|
| **Twenty** | AGPL-3 / TS + PG | 最现代、开发者体验最好（见 §9.2） |
| **EspoCRM** | AGPL-3 / PHP + MySQL/PG | 2014 年至今，**功能面最广**（营销活动 / 工单 / 报表 / VoIP / 邮件同步）、no-code 定制强 → **要「立刻能用」选它** |
| SuiteCRM | GPL / PHP | SugarCRM 血统，功能全但技术栈老 |
| ⭐ **悟空AI CRM（国产）** | 协议**需自行核实** / **Java 21 + Spring Boot 3.3 + Spring AI + MyBatis-Plus + PostgreSQL 17 + Redis + MinIO**；**Vue 3.4 + TS + Element Plus + Pinia + Tailwind + Vite** | ⭐ **技术栈与 LQXM 几乎同构**（唯一差异：PG vs MySQL）。中文原生、Docker Compose、社区活跃、含 AI。**但它只是 CRM**；国产开源常有商用限制，**协议必须先核实** |
| Odoo CRM | 随 Odoo | 若选 Odoo 则自带，无需另找 |

### 9.5 低代码底座（想留 Java 栈又不想从零）

JEPAAS / 若依（RuoYi）—— Java 低代码 / 脚手架，**但不是 ERP**，等于又回到自己建。

> ⭐ **结论：没有堪用的 Java 开源 ERP。** Java 阵营只有 iDempiere / OFBiz 这类老家伙和 Axelor（法国）。**这才是真正的取舍点：要么换栈（拿功能），要么留栈（只拿 CRM）。**

## 11. ⭐ 换栈决定（LQ 已定 · 2026-09-30）

| 项 | 结论 |
|---|---|
| **是否愿意换栈** | ✅ **愿意**（Python 可接受） |
| 系统定位 | 只自家内部用 → GPL-3.0 copyleft 义务基本不触发 |
| **主线候选** | **ERPNext v16** —— 单版本即含「过账层 + 完整会计 + 三大报表 + 制造」 |
| 对照候选 | Odoo 19 CE —— 中文与金税强，但**财务报表在 EE**（§3） |
| Java 退路 | Axelor（AGPL-3 / Java + PostgreSQL）—— 若最终不愿离开 Java 栈 |

### 11.1 ⚠️ 换栈的三段话说在前面

**① 「愿意换栈」≠「马上停掉 LQXM」。** 过渡期两条线并行：照镜子的 1~2 周里，LQXM 该修的还得修（尤其「订单→出库跑不通」那三条数据面断桥）。理由：若 ERPNext 最后不选，LQXM 还得用；若选了，过渡期也要它继续跑真单。

**② 换栈换掉的是「底座」，不是「口径」。** 你的 38 条口径（SKU 身份键、占用判据、费用项判据、审批两字段分离……）是**业务知识，不是 Java 代码**。它们在 ERPNext 里要**重新表达一遍**，而不是搬过去。所以真正的成本不在「重写代码」，而在「**把 38 条口径在新数据模型里重新落地并验证**」。

**③ 会失去的资产要算进去**：后端 407 个测试 / 前端 379 个测试 / `ProductSourceKey`·`UnitNormalizer`·`ProductFeeFilter` 这套键 util / 档案侧（证书·知识产权·资质台账）—— 最后一项 **ERPNext 完全不覆盖**（§9.3），必然留在 LQXM → **双系统是既定事实，不是选项**。

### 11.2 换栈「值不值」的判定标准

不要凭感觉判。**用 §13 照镜子产出的冲突清单量化**：

| 指标 | 倾向换栈 | 倾向留栈自补 |
|---|---|---|
| 38 条口径里「能自然表达」的条数 | ≥ 25 条 | < 15 条 |
| 过账层自建工作量（人月） | > 3 个月 | ≤ 1 个月 |
| 制程 / 工序 / 任务单 / 报工 贴合度 | 能贴住（可扩展表达） | 必须扭曲业务 |
| 财务与税务 | 想彻底不自己写 | 可接受自建凭证表 |
| 双系统同步成本 | 能接受 1 个同步边界 | 能接受 N 个同步边界 |

### 12.2 Ubuntu 装好后先验证（WSL2）

> **LQ 已确认走这条路**：`wsl --install -d Ubuntu-24.04`（2026-09-30）。
> ⚠️ `wsl --install` 之后**需要重启 Windows**（首次启用 WSL 组件时）；重启后 Ubuntu 首次启动会引导创建 UNIX 用户名与密码 —— **密码输入不回显（看不见字符）是正常的**，别以为键盘坏了。

```bash
# Windows 侧（PowerShell / CMD）
wsl --list --verbose          # 确认 VERSION = 2（不是 1）；STATE 应为 Running/Stopped
wsl --set-default-version 2   # 若新装的是 1（极少见）
wsl -d Ubuntu-24.04           # 进入 Ubuntu

# Ubuntu 侧
lsb_release -a                # 应为 Ubuntu 24.04.x LTS
```

**① 换 Ubuntu apt 源为国内（不换的话 `apt` 会慢到怀疑人生）**

```bash
sudo cp /etc/apt/sources.list.d/ubuntu.sources /etc/apt/sources.list.d/ubuntu.sources.bak
sudo sed -i 's|//archive.ubuntu.com|//mirrors.aliyun.com|g; s|//security.ubuntu.com|//mirrors.aliyun.com|g; s|//ports.ubuntu.com|//mirrors.aliyun.com|g' /etc/apt/sources.list.d/ubuntu.sources
sudo apt update && sudo apt upgrade -y
```

⚠️ Ubuntu 24.04 用的是**新格式 `/etc/apt/sources.list.d/ubuntu.sources`**（不是老的 `/etc/apt/sources.list`），改错文件不生效。改完 `apt update` 若报错，用 `.bak` 还原。

**② 检查 systemd（Docker 靠它托管服务）—— 先查，别急着改**

```bash
cat /etc/wsl.conf 2>/dev/null || echo "no /etc/wsl.conf"
stat -c '%N' /sbin/init        # 若指向 /lib/systemd/systemd 的软链，说明已在用 systemd
```

> 💡 较新的 WSL 默认已启用 systemd。**先检查、再决定要不要改**（见 12.5）—— 不要盲目覆盖 `/etc/wsl.conf`，里面可能已有别的配置（比如自动挂载选项）。

**③ 装完贴给我这份输出，一次判定环境是否就绪**

```bash
echo "=== 1. OS ==="; lsb_release -ds; uname -r
echo "=== 2. systemd ==="; stat -c '%N' /sbin/init; grep -r . /etc/wsl.conf 2>/dev/null || echo "no wsl.conf"
echo "=== 3. apt 源 ==="; grep -h '^URIs:' /etc/apt/sources.list.d/ubuntu.sources 2>/dev/null | head -3
echo "=== 4. docker ==="; docker --version 2>/dev/null || echo "docker 未装"; docker compose version 2>/dev/null || echo "compose 未装"
echo "=== 5. resolv ==="; cat /etc/resolv.conf
echo "=== 6. 资源 ==="; free -h | head -2; df -h / | tail -1
echo "=== 7. 宿主端口（在 Windows 侧跑）==="; echo "见 §12.0 实测表"
```

### 12.3 给 WSL 定资源上限（Windows 侧）

新建 `C:\Users\20676\.wslconfig`（**本机当前无此文件，可直接创建**）：

```ini
[wsl2]
memory=12GB
processors=8
swap=4GB
swapFile=D:\\wsl\\swap.vhdx
```

```powershell
wsl --shutdown     # 改完必须执行才生效
```

⚠️ 两条注意：
- WSL2 默认只拿宿主 **50% 内存**（你 31.8 G → 约 15 G）；显式写 12 GB 是为了**别把 Windows 侧挤爆**（LQXM 后端 + vite + MySQL 还在跑）。
- **WSL 的磁盘镜像默认落 C 盘**（`%LOCALAPPDATA%\Packages\...\ext4.vhdx`）。ERPNext + Odoo 镜像约 5~8 GB，C 盘 208 GB 空闲够用；想搬 D 盘可后续用 `wsl --export/--import` 迁。

### 12.4 在 Ubuntu 里装 Docker Engine（官方 apt 源，不用 Docker Desktop）

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

> 💡 **国内加速选项**：把上面 `deb` 行里的 `https://download.docker.com` 换成阿里云镜像 `https://mirrors.aliyun.com/docker-ce`，apt 拉包会快很多（GPG key 仍用官方那份，内容一致）。不加也能装，只是慢。

**启用 systemd 服务 + 免 sudo**：

```bash
sudo systemctl enable --now docker

sudo usermod -aG docker $USER
newgrp docker            # 或退出重进 WSL

# 验证（三条都要过）
docker --version
docker compose version
docker run --rm hello-world
```

⚠️ **前置条件**：Docker 作为 systemd 服务运行，`/etc/wsl.conf` 里必须 `systemd=true`（见 §12.5）。

### 12.5 WSL 两个必备修正（不改会在容器里踩坑）

编辑 `/etc/wsl.conf`：

```ini
[boot]
systemd=true

[network]
generateResolvConf = false
```

再固定 DNS（国内用阿里 + 腾讯）：

```bash
sudo rm -f /etc/resolv.conf
sudo tee /etc/resolv.conf > /dev/null <<'EOF'
nameserver 223.5.5.5
nameserver 119.29.29.29
EOF

# 回 Windows 侧执行，让配置生效
wsl --shutdown
```

⚠️ 为什么要做：WSL 自动生成的 `resolv.conf` 在容器内会导致 **DNS 解析间歇性失败**（表现为 `docker compose up` 卡在拉镜像 / `apt` 超时）。

### 12.6 国内镜像加速（不配基本拉不动）

新建 `/etc/docker/daemon.json`：

```json
{
  "registry-mirrors": [
    "https://docker.xuanyuan.run",
    "https://docker.1ms.run"
  ],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

```bash

```

- `log-opts` 是防坑：ERPNext 11 个容器日志不限制会吃满磁盘。
