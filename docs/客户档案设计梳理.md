# 客户档案设计梳理

> 一句话定位：**客户档案是系统的一级业务实体（主数据）**，其客户信息**主要（约 95%）由氚云销售出库台账（`sales_outbounds`）回填生成**。但回填聚合会同时读收款单 `receipts` 与生产工单 `production_orders`，导致**少量客户名只出现在收款/生产、而不在销售出库**时也会被"凭空"建档（主档地址/电话为空）；另有约 384 个"客户编码误当客户名"的历史脏数据。前端默认落地页即客户档案（`/customers`）。

---

## 1. 数据来源：客户信息如何从销售出库得到

客户档案不是靠人工逐条录入建立的，而是**随氚云导入自动建档**：导入时按 `customer_name` 识别客户（`SourceIdentityService.resolveCustomer`），未命中已有档案即建档（`createPendingCustomer`），地址随单解析为省/市/区县一并写入。**当前系统尚未人工新增任何客户**。聚合口径（原 `aggregateRawCustomerInfo()`，现由导入链路逐单等价承担）会同时覆盖 `sales_outbounds` / `receipts` / `production_orders` 三张表按 `customer_name` 去重，**只要客户名出现在任意一张表，就会建出一个客户档案**：

| 来源表 | 提取字段 | 落到客户档案的哪张表 |
| --- | --- | --- |
| `sales_outbounds`（销售出库台账） | `customer_name`、`customer_address`、`region`、`contact_phone`、`salesperson_name`、频次 | 客户主档（名称/地址/联系人）、业务员关系（**主档字段唯一来源**） |
| `receipts`（收款单） | `customer_name`、`salesperson_name`、频次 | 业务员关系 + **也会建档**（主档地址/电话为空） |
| `production_orders`（生产工单） | `customer_name`、`salesperson_name`、频次 | 业务员关系 + **也会建档**（主档地址/电话为空） |

> 注意：收款单与生产工单在聚合 SQL 中 `addresses/regions/phones` 均为 `NULL`，**不贡献主档任何字段**；但它们独有的客户名同样会触发建档，产生"只有业务员关系、无地址/电话"的空壳客户（见第 7 节数据验证）。

**字段级映射关系：**

| 客户档案字段 | 来源（`sales_outbounds`） | 说明 |
| --- | --- | --- |
| `customer_name` | `customer_name` | 直接取客户名（trim 后作唯一性依据） |
| `short_name` | 客户名 | 仅当客户名 > 100 字时截断前 100 字 |
| `province / city / district / address` | `customer_address` 优先，`region` 兜底 | 由地址文本正则解析省/市/区县推导 |
| `remark` | 聚合元信息 | 「系统从氚云历史业务数据自动回填；来源业务：OUTBOUND/RECEIPT/PRODUCTION；业务频次：约 N 单」 |
| `customer_type` | 无 | 固定 `OTHER`（其他） |
| `source` | 无 | 固定 `H3YUN_BACKFILL` |
| `level` | 无 | 回填不设等级（NULL） |
| `relation_status` / `status` | 无 | 固定 `NORMAL` / `ACTIVE` |
| 联系人 | `contact_phone` | 正则提取手机号/座机号，逐号建联系人 |
| 业务员关系 | `salesperson_name` | 按客户名分组去重，高频者排前、首条设 PRIMARY |

**关键结论：** 回填建立的客户主档字段只覆盖「名称 / 简称 / 地址（省市区）/ 备注 / 来源」，`customer_type`、`industry`、`credit_code`、`website`、`level`、`relation_status` 等经营类字段**全部留空待人工补全**——即回填只负责"把客户从业务台账里捞出来"，画像质量由后续人工维护。

## 2. 数据模型（5 张表）

### 2.1 `customers` —— 客户主档
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 主键 |
| `customer_code` | VARCHAR(20) 唯一 | `CUS000001` 格式 |
| `customer_name` | VARCHAR(200) | 客户正式名称 |
| `short_name` | VARCHAR(100) | 简称 |
| `customer_type` | VARCHAR(20) | `ENTERPRISE/COOPERATIVE/FARM/INDIVIDUAL/PERSONAL/OTHER`（DB 存英文） |
| `industry` | VARCHAR(100) | 行业（自由文本） |
| `credit_code` | VARCHAR(30) | 统一社会信用代码 |
| `province / city / district` | VARCHAR(50) | 省 / 市 / 区县 |
| `address` | VARCHAR(300) | 公司地址 |
| `website` | VARCHAR(200) | 官网 |
| `source` | VARCHAR(50) | 客户来源 |
| `level` | VARCHAR(20) | `KEY`（重点）/ `COMMON`（普通） |
| `relation_status` | VARCHAR(20) | `NORMAL/KEY_INTEREST/STOPPED/NO_CONTACT` |
| `status` | VARCHAR(20) | `ACTIVE/INACTIVE` |
| `remark` | VARCHAR(1000) | 备注 |
| `deleted_at` | DATETIME | 软删除时间戳（`@SQLRestriction("deleted_at IS NULL")` 全局过滤） |

### 2.2 `customer_contacts` —— 联系人
`customer_id`、`name`（必填）、`department`、`position`、`mobile`、`wechat`、`email`、`contact_type`（决策人/采购/技术/财务/其他）、`is_primary`、`remark`。

### 2.3 `customer_salesperson_relations` —— 业务员关系
`customer_id`、`salesperson_id`（关联公司成员，可空）、`salesperson_name`（姓名快照，必填）、`role`（`PRIMARY/HISTORY/COLLABORATOR`）、`start_date`、`end_date`。

### 2.4 `customer_addresses` —— 收货地址（V272 引入）
`address_name`、`contact_name/phone`、`province/city/district`、`detail_address`（必填）、`normalized_address`（归一化索引，用于去重/合并）、`is_default`、`source`（`MANUAL/CUSTOMER_ARCHIVE`）、`remark`。默认地址会**反向同步**到 `customers.province/city/district/address`。

### 2.5 `customer_merge_history` —— 合并历史（V272 引入）
记录「曾并入当前主客户的历史档案」，仅来源追溯：`primary_customer_id`、`merged_customer_id/name/address`、`merge_reason`、`merged_at`。

## 3. 省市区补齐与档案回填

### 3.1 现役路径：导入即补齐（治本）

1. **建档即带省市区** —— `SourceIdentityService.createPendingCustomer(name, address)`：INSERT 阶段用 `ChinaAddressParser.parseLoose`（区划字典文本扫描兜底）解析地址，直接写入 `province/city/district/address`。
2. **导入期增量补空** —— `H3FactImportService.enrichCustomerFromOutbound()`：每张销售出库导入时，按「客户详细地址」（为空时兜底「地区」字段）解析，`COALESCE` 仅补空、不覆盖人工维护值。
3. **人工兜底工作台** —— 客户分布/地区整理（`/api/customers/region/**`、`CustomerRegionService` + `CustomerAddressTidyService`）：别名字典维护、CSV 导入导出、自动解析 preview/apply，处理解析不出的历史脏值与待标注地区。

> 补齐语义统一为「只补空、不覆盖」的幂等操作；解析委托同一个 `ChinaAddressParser`，避免各写一套切分逻辑。

### 3.2 已下线：一次性全量回填（历史记录）

> **2026-09-14 移除：** `CustomerArchiveBackfillService` 与端点 `POST /api/h3-facts/customer-archive/backfill` 已删除，省市区补齐前移到导入链路（见 §3.1）。以下为历史设计记录：

入口：`POST /api/h3-facts/customer-archive/backfill`（权限 `customer.manage`，实现于 `CustomerArchiveBackfillService`）。流程分 6 步：

1. **聚合**：对 `sales_outbounds` / `receipts` / `production_orders` 按 `customer_name` 分组，聚合出每个客户的地址集、地区集、电话集、业务员集、频次、来源集合。
2. **建索引**：一次性拉取现有客户名→id、业务员名→{memberId, employeeId}、(客户名,业务员)→最早日期/频次，避免 N+1 查询。
3. **分批写客户主档**：新客户走批量 INSERT（`customer_code` = `CUS` + 6 位递增序号），已存在客户走 `patchExistingCustomer`（仅补空地址/来源，不覆盖已有值）。
4. **回填联系人**：从 `contact_phone` 正则提取号码，逐号建 `customer_contacts`，首个设 `is_primary`。
5. **回填业务员关系**：按频次排序业务员，首条设 `PRIMARY`，其余 `COLLABORATOR`；`start_date` 取三表最早业务日期。
6. **关联 customer_id**：按 `customer_name` 匹配，回填 `sales_outbounds.customer_id` / `receipts.customer_id` / `production_orders.customer_id`（分段批量 UPDATE JOIN）。

**幂等性：** 重复执行只回填新增客户、只补空字段，不覆盖人工维护的既有主档数据。

> 原「地址同步 `syncCustomerAddressFromOutbound()`」（`POST /api/h3-facts/customer-archive/address-sync` + 台账工具栏「同步客户档案」按钮）已删除：该能力与 §3.1「导入期增量补空」重复，代码与前端入口均已不存在。

### 枚举转换约定
前端传中文、DB 存英文，Service 层双向转换：
- `CustomerType`：企业/合作社/农场/个体/个人/其他 ↔ `ENTERPRISE/COOPERATIVE/FARM/INDIVIDUAL/PERSONAL/OTHER`
- `CustomerRelationStatus`：正常/重点关注/停止合作/禁止联系 ↔ `NORMAL/KEY_INTEREST/STOPPED/NO_CONTACT`
- 启用状态：启用/停用 ↔ `ACTIVE/INACTIVE`；客户等级：重点/普通 ↔ `KEY/COMMON`

### 批量更新字段白名单
`customerType / industry / province / city / district / source / level / relationStatus / status / remark`。**名称与编号不在白名单内**，避免误改主档案。

### 5.4 区域分布
`GET /distribution` 按省归并（浙江/浙江省 → 浙江省），省下按市计数，`filterValue` 取该省最常见的原始写法用于列表地区筛选精确匹配；另支持「待标注（省份为空）」入口，便于逐条人工补全省份。

### 5.5 地区治理（`address_tidy_status` + 批量地址解析）

地区治理状态由 `CustomerAddressTidyService.scanStatuses()` 计算（**只算状态、不改地址与省市区县字段**），是「未标注地区」筛选、CSV 导出与批量解析清单的共同口径：

| 状态 | 含义 | 是否算「未标注地区」 |
| --- | --- | --- |
| `NORMAL` | 无需治理（字段完整且通过地址选择器三级校验） | 否 |
| `NO_ADDRESS` | 档案无公司地址，但最近出库地址非空 | 视省份是否已合法 |
| `MISSING` | 省市县存在可解析补齐的空白项 | 视省份是否已合法 |
| `MISMATCH` | 档案省市县与地址解析结果不一致 | 否（省份合法） |
| `PARTIAL` | **省份已合法可上地图，但市/区县缺失或无法识别** | **否** |
| `UNCLEAR` | 省份都无法确定（地址无省名或省份写法非法） | 是 |
| `UNRECOGNIZED` | 地址或当前字段含地址选择器无法识别的值 | 否（省份合法） |

**「未标注地区」的口径（2026-09-11 放宽）**：一律以**省份是否可上地图**为准——`province` 为空或不是官方省名才算未标注；省份已合法但市/区县缺失的客户归入 `PARTIAL`，在客户列表地区筛选中以「待补市县」单独呈现（`regionPartial=true`），不再混进未标注红名单。改动点：`CustomerService.search` / `CustomerRegionService.buildRegionCsv` 的筛选条件、`CustomerRepository.countCustomersWithoutProvince`（分布弹窗计数）统一改为省级判定。

**批量地址解析**（`CustomerDistributionDialog` 底部「批量解析地址」按钮）严格遵守以下口径：

1. **先信任已有字段**：若省市区县**已完整且能被地址选择器识别**，直接判为 `NORMAL`，不参与解析、不被覆盖。这保证了人工填写的规范值不会因地址文本里混入企业名/园区名（如"科山西工业区"误命中"山西省"）而被反推覆盖。
2. **仅对不完整/不合法者解析公司地址**（缺省时回退最近一单已生效出库的客户地址）。
3. **解析结果逐级校验、能补几级补几级**（2026-09-14 起）：省必须是官方省名，否则整条不写回（上不了地图，写了也没用）；市、区县能过地址选择器校验就补，过不了就留空——**不再要求三级齐全才写回**。写回时按列判断：**该列为空或不是规范值才写，已有合法值一律保留**。
4. **只有省级冲突才否决**：档案已填的省份合法且与地址解析结果不一致时跳过，交人工裁决；市/区县即使与解析结果不同也不否决，因为写回本来就不会覆盖已有合法值。

| 端点 | 作用 | 权限 |
| --- | --- | --- |
| `POST /api/customers/region/auto-parse/preview` | 扫描并按 `READY`/`ERROR` 预览，**不写库** | `customer.manage` |
| `POST /api/customers/region/auto-parse/apply` | 只写回 `READY` 行，随后重算治理状态 | `customer.manage` |

前端采用**预览后确认写回**：弹窗区分「可补全 / 无法处理」，展示「当前省市区县 → 解析结果」对照与原因，确认后才执行。

**关键修复（2026-09-10）：同省不同市重名区县的判定**。`ChinaRegionDictionary.resolveDistrictToken` 原先**只用省份消歧**，遇到「向阳区」这类在黑龙江省内同时属于鹤岗市与佳木斯市的区县即返回 `null`，导致 `isSelectableDistrict` 判定失败、客户被误置 `UNRECOGNIZED` 并错误出现在「未标注地区」中（如 `CUS041526`：档案为 黑龙江省/鹤岗市/向阳区，全部合法却长期显示未标注）。修复方案：新增 `ChinaRegionDictionary.districtBelongsTo(district, province, city)` 做**省+市+区县三级联合校验**，`isSelectableDistrict` 在市级已知且精确归属时直接通过；旧的 `resolveDistrictToken` 保留，仅在市级缺失时作兜底（重名歧义仍不猜测）。

**关键补充（2026-09-11）：县级市「当市级」归一 + 自辖回退**。客户档案与地址文本里，县级市常被直接填在市字段（湖北省/仙桃市、江苏省/江阴市）。按地址选择器严格口径第二级应是归属地级市，但省直辖县级行政区划下的县级市没有真实地级市可归，故统一为：

- `ChinaRegionDictionary.asCityOfCountyLevelCity(token, province)`：有真实地级市父级时返回父地级市（江阴市 → 无锡市）；父层为「省直辖县级行政区划」伪层时返回自身（仙桃市/天门市/济源市/海南各县级市）。
- `isUsableAsCity` 让这类写法通过市级校验；`isCountyCitySelfDistrict` 允许区县与市同名（市=仙桃市、区=仙桃市）。
- 批量解析 `CustomerRegionService.diagnose()`：县级市当市级且区县解析不出规范值时，**区县回退为该县级市自身**（湖北省天门市石家河镇 → 省=湖北省、市=天门市、区=天门市）。

**关键改进（2026-09-14）：宽松解析 `ChinaAddressParser.parseLoose()` + 分级写回**。客户档案全量重导后（9975 家）复核发现，旧的「三级齐全才写回」口径对真实数据**命中率为 0**：绝大多数地址是「省+市已明确、只差区县」（功能区/市场名/镇级）或「城市名不带行政后缀」的写法，整条被判失败。改造要点：

- **字典文本扫描兜底**：`parseLoose()` 在 `parse()` 切分结果不完整时，拿区划字典（`allCities()` / `citiesOfProvince()` / `districtsOfCity()`）对原文做包含匹配，长名优先。覆盖三类 `parse()` 切不出来的写法：
  1. 城市名不带行政后缀 —— 「河北石家庄…」「温州乐清…」「烟台开发区…」；
  2. 省市同名被省名抢先消耗 —— 「吉林市船营区…」（省名命中「吉林」后余下「市船营区」，原逻辑取不到市）；
  3. 城市与省不符 —— 「安徽省马鞍山市…」被切成「马」+「鞍山市」，按省重扫纠正。
- **防误判**：区县主干匹配排除与城市同名的项（`长沙市` 不会被误判成 `长沙县`、`南昌市` 不会成 `南昌县`），并排除「新区/城区/开发区/工业区」等在路名市场名里高频出现的泛化词。
- **分级写回**：`ParseResult` 的 `reason == null` 表示「至少能补省级」，`summary()` 给出人话说明（可写回省/市/区县、可写回省/市（区县待人工补）、仅可写回省）。

## 6. 关键设计决策与约定

1. **主数据与业务事实分离**：`customers` 是主数据，`sales_outbounds` 是事实表，二者通过 `customer_id` 关联；回填阶段负责"从事实抽取主数据 + 修复关联"。
2. **姓名是关联的唯一钥匙**：客户名（trim 后）既是回填去重的依据，也是 `customer_id` 回填 JOIN 的匹配键。**没有信用代码/外部 ID 作为强唯一键**，同名客户会被归并到同一档案（风险点见第 7 节）。
3. **回填只补空、不覆盖**：保证人工维护的经营字段（类型/行业/等级/关系状态）不被回填冲掉。
4. **业务员姓名快照**：`customer_salesperson_relations.salesperson_name` 是快照文本，`salesperson_id`（公司成员 ID）可空，历史合同导入时只有姓名也能建关系。
5. **负责人唯一**：`role=PRIMARY` 每客户至多一条；新设 PRIMARY 时旧 PRIMARY 自动降级为 COLLABORATOR；`is_primary` 联系人同理互斥。
6. **软删除**：客户用 `deleted_at` 软删除，`@SQLRestriction` 全局过滤，不影响历史业务表关联。
7. **省名清洗**：区域分布对省名做规范化（短写→全名）以匹配 ECharts 中国地图，但库内仍存原始写法。
8. **概览不冗余**：订单数/金额/首购/最近采购均从 `sales_contracts`（合同表）实时聚合，不落冗余字段。

## 7. 已知边界与风险

- **非销售出库来源的空壳客户（数据验证）**：截至 2026-09-08 实测，客户主档共 32651 条，其中 **1457 条未关联到销售出库**（`sales_outbounds.customer_id` 为空）。归因如下：
  - **生产工单凭空建档 965 条 + 生产/收款双来源 9 条**：客户名只出现在 `production_orders`，回填时被 `computeIfAbsent` 建出空壳档案（`source=H3YUN_BACKFILL`，主档地址/电话为空）。
  - **收款单凭空建档 45 条**：客户名只出现在 `receipts`，同理。
  - **历史脏数据 392 条**：其中 **384 条 `customer_name` 被误写为 `CUS009983` 这类"客户编码"**（`customer_name == customer_code`，`source=null`、地址为空，集中生成于 2026-08-24~25），疑似某次导入/回填把"客户编码"当成"客户名"写入；另有 1 条 `H3YUN_BACKFILL`、1 条 `H3YUN_IMPORT`。
  - **46 条名字能匹配出库但 `customer_id` 未关联**：多为历史遗留或名字存在细微差异（trim 后仍不相等）。
- **同名归并风险**：因以 `customer_name` 为唯一关联键，同名但实际不同的客户会被合并到同一档案，需人工辨别（`customer_merge_history` 提供合并来源追溯，但反向"拆分"能力不存在）。
- **回填字段有限**：类型/行业/信用代码/官网等经营字段回填一律留空，依赖后续人工补全或批量编辑。
- **地址解析是启发式**：省/市/区县从地址文本正则推导，对不规范地址可能解析失败或错位，故提供「待标注」筛选、批量解析与人工批量修正。
  - **重名区县的历史误判已修复（2026-09-10）**：旧逻辑仅用省份消歧区县，同省跨市重名（如「向阳区」同属鹤岗市与佳木斯市）会被误判为无法识别。已改为「省+市+区县」三级联合校验；修复后重扫，**205 家**字段本就完整合法但状态滞后的客户纠正为 `NORMAL`，`UNRECOGNIZED` 从 1359 降至 1154。
  - **批量解析的预期收益**：对剩余待处理客户抽样，可自动补全的量级有限，多数因**源头地址本身缺层级或混入企业名/园区名**而无法判定——这类需源头补录或人工修正，不是解析能力问题。
- **「业务」页签受数据权限限制**：客户详情下的销售出库列表受当前账号数据权限过滤，非全部可见。
