# 前端载体拆分：应用边界落地记录（2026-09-29）

> 承接问题：「载体形态这块就地集成和拆独立入口各有什么优缺点，你推荐哪个」→ LQ 决定「拆」。
> 本文记录**方案取舍的判据**与**本次实际落地到哪一步**，以及踩到的坑。不写没验证的结论。

---

## 1. 结论（先给）

| 层 | 拆法 | 本次是否落地 |
|---|---|---|
| **代码** | `apps/erp/**` 与 `apps/archive/**` 各自持有「路由表 + 导航根 + 视图目录」 | ✅ 已落地 |
| **构建** | 一个 Vite 工程 vs 两个 | ❌ 暂不拆（仍一个工程） |
| **运行时** | 一个 SPA vs 两个 | ❌ 暂不拆（仍一个 SPA、同域、hash 路由） |

**关键判据（决定「拆」不能拆成两个域名）：**
登录凭据存在 `localStorage['lq.token']`（`frontend/src/api/http.ts`），而 `localStorage` 按**源**隔离。
→ **同域天然共享登录；跨域必然要重新登录**。所以「拆独立入口」只能是**同域下的子应用**，
不是两个域名/两个部署。跨域那一刀属于最后一步，且要先解决单点登录。

---

## 2. 为什么不是「只在侧栏加一个分组」

拆之前的状态：ERP 与档案两套业务的文件混在 4 个顶层目录里

- 49 条业务路由全挤在 `router/index.ts`，两套路径交替出现（ERP 的 `/sales-orders` 夹在档案的
  `/products` 与 `/h3-imports` 之间）；
- 侧栏只有一个聚合的 `constants/navigation.ts`；
- 改一个业务要同时动 `router` / `constants` / `views` / `components` 四处 → **diff 互相踩**。

只在侧栏加分组 = **UI 层的假边界**：改了菜单仍要在 navigation / routeGroups / router meta 三处对齐。
所以边界必须同时落在**路由表 + 导航根 + 文件目录**三处。

---

## 3. 本次落地的结构

```
frontend/src/apps/
  types.ts                     # 外壳层共用：NavItem / AppKey / AppDefinition
  index.ts                     # 应用注册表 + GROUP_TO_APP（应用边界的唯一判据）
  erp/
    routes.ts                  # ERP 路由表
    navigation.ts              # ERP 导航根（单个「ERP」父节点 + 六个业务域子项）
    components/ErpAreaNav.vue
    styles/erp-workspace.css
    views/                     # 15 个视图：应用外壳 6 + 业务域 9
      ErpWorkbenchView.vue / ErpOperationsView.vue / ErpDomainView.vue
      ErpInventoryView.vue / ErpOverviewView.vue / ErpOrderWorkspaceView.vue
      sales/SalesOrderView.vue / sales/CustomerView.vue
      sales/SalesFulfillmentReviewView.vue / sales/SalesOutboundView.vue
      production/ProductionDemandView.vue / production/ManufacturingExecutionView.vue
      production/ManufacturingProcessManagementView.vue / production/ManufacturingTaskConfigView.vue
      procurement/PurchaseOrderView.vue
  archive/
    routes.ts                  # 档案/运营路由表
    navigation.ts              # 档案导航根（product / marketing / h3 / system）
```

- `router/index.ts` 收缩为**纯聚合层**：`[...erpRoutes, ...archiveRoutes]` + 全局守卫 + 403/404。
- **应用边界唯一判据 = 路由自己的 `meta.group`**（`GROUP_TO_APP`），不另建「路径 → 应用」映射表
  —— 多一份映射就多一个会分叉的口径。

### 迁移原则（这次刻意守住的）

- **path / name / meta / permission 一字未改**，路由模式仍是 `createWebHashHistory`。
  → 现有 URL、书签、深链全部不变。
- **侧栏呈现形状不变**（见 §5 的坑）。
- 顺手清理：`RouteGroup` 从 9 个收敛到 5 个（`sales/production/inventory/settlement` 全仓零匹配，
  只活在这两个定义文件里，属于「定义与实现漂移」）。

## 4. 边界证据（可复核）

```
apps/erp/**  →  @/views/     引用数 = 0      ← ERP 应用自洽
apps/archive/** → @/views/   引用数 = 25     ← 档案视图仍散在 views/（本次未物理搬迁，见 §6）
views/**     →  @/apps/      引用数 = 0
components/** →  @/apps/     引用数 = 0
composables/** → @/apps/     引用数 = 0
```
即依赖方向单向收敛：`外壳 → apps → 各应用`，无反向依赖。
`ErpAreaNav.vue` 现在只被 `apps/erp/**` 内部引用（搬迁前被 6 个散在 `views/` 的历史 ERP 视图引用）。

### 四道验证闸门

| 闸门 | 结果 |
|---|---|
| 路由集一致性（`_check_routes.cjs`，与改造前逐项对拍） | 路径 **51/51**、路由名 **47/47**，无缺失无多出 |
| 导入完整性（`_check_imports.cjs`，全 src 1403 条 import） | 无法解析 **0** |
| 类型（`vue-tsc --noEmit --skipLibCheck`） | **0 错误** |
| 真实构建（`vite build`） | ✅ 成功（48.8s） |
| ERP e2e（5 个 spec） | **27/27 全绿** |

⚠️ **类型检查不是闸门**：`vue-tsc` 不校验 `.vue` 的 import 路径是否存在（靠通配 `.d.ts` 声明兜底），
所以「搬了组件忘改引用」它**不报错**，只有 `vite build` 会。这次就是先被 build 抓住的。

## 5. 踩坑：`.nav-submenu` 是测试契约，不是装饰

第一版把 ERP 的六个业务域**拍平成一级导航项**（认为「独立成应用后六项应并列」）。
结果 ERP e2e **4 条失败**：

- `erp-v3.spec.ts`「ERP 导航聚焦已接入业务域…」
- `erp-v3.spec.ts`「从采购业务域进入外采评审保持正确模式和侧栏归属」
- `erp-operations.spec.ts`「ERP 子菜单连续切换更新队列…」
- `erp-operations.spec.ts`「采购工作台分开到仓、部分到货与代发…」

判据（写死在用例里）：
```ts
const menu = page.locator('.nav-submenu').filter({ has: page.getByRole('link', { name: '工作台' }) })
await expect(menu.getByRole('link')).toHaveText(['工作台','销售管理','生产管理','采购管理','库存与交付','主数据'])
```

→ 恢复成「单个 `ERP` 父节点 + 六个子项」后 **27/27 全绿**。
**教训**：拆应用时「代码边界」可以动，「侧栏呈现形状」是被 e2e 钉住的既有契约，别顺手改。
顺带记录：`NavItem.icon` 是必填，子项共用父图标时写 `icon: ''`。

## 8. Phase 0.5：档案侧物理搬迁（2026-09-30 补记）

LQ 确认继续建设后，同日完成档案侧搬迁。**`src/views/` 目录整个消失**。

### 落了什么

- **24 个档案业务视图** → `apps/archive/views/{product,marketing,governance,production,settlement,system}/`，
  子目录结构与原 `views/` 一致（含 `product/mold/`、`settlement/commission/`）。
- **3 个外壳视图** → 新建 `src/shell/`：`LoginView.vue`（登录）、`ForbiddenView.vue`（403）、
  `NotFoundView.vue`（404）。它们不属于任何应用（登录服务两个应用、错误页是路由壳），
  放应用里都会造成反向依赖，故独立成外壳层。
- `apps/archive/routes.ts`：24 条 import 改 `@/apps/archive/views/...`，登录页改 `@/shell/LoginView.vue`。
- `router/index.ts`：403/404 改 `../shell/...`。

### 搬迁中踩的两个坑（都有检查器兜住）

1. **相对导入层级算错**：`H3ProductionExecutionView.vue` 的 `../../api/...` 搬深两层后应为
   `../../../../api/...`，我第一次只加了三层。`_check_imports.cjs`（1403 条全量导入扫描）当场抓住。
2. **`<style src>` 形式的相对路径不在 `from` 模式里**：`H3ImportCenterView.vue` 有
   `<style scoped src="../../styles/h3-import-center.css">`，构建（vite build）当场抓住。
   已改为别名 `@/styles/h3-import-center.css`——**样式/资源类相对引用要用别一类模式扫**。

## 7. 环境备注（复现本记录用的命令）

```bash
# 1) 起 e2e 用的 dev server（⚠️ 必须自己起，不能让 playwright 用 npm 起）
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 4173 --strictPort &
# 2) 跑 spec（reuseExistingServer=true 会复用上面这个）
node node_modules/@playwright/test/cli.js test e2e/erp-*.spec.ts --reporter=list
```

**坑**：`playwright.config.ts` 的 `webServer.command` 是 `npm run dev -- …`。
本机 bash 的 PATH 会被 shim 重置 → 找不到 `npm` → webServer 起不来 → playwright 静默等 120s。
**规避**：自己用 `node node_modules/vite/bin/vite.js` 起 server，让它复用。
另外：上次被 kill 的 e2e 会在 4173 留一个孤儿 vite，先 `netstat` 查占用者再起。
