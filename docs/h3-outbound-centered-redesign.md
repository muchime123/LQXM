# 氚云导入中心：以销售出库为核心的重建设计

## 1. 唯一核心

`sales_outbounds` 与 `sales_outbound_items` 是氚云历史经营数据的核心事实。客户、员工、产品归类、仓库、收款、未收款、利润和月度提成，都从销售出库向外建立关系。氚云原始字段必须保留，项目内档案只作为关联结果，不能覆盖来源快照。

```text
客户档案 ← customer_id       ┌→ 收款/未收款/开票
员工档案 ← employee_id       │
                              │
                    销售出库主单
                              │
仓库档案 ← warehouse link    ├→ 利润口径 → 月度提成版本
                              │
产品归类 ← item.sales_product_id
```

## 2. 页面职责

### 氚云导入中心

只负责文件导入、批次状态、更新差异、原始台账、重导准备和全链路验收。历史台账只读；允许查看来源字段和跳转到项目内档案，不承载批量建档、拆分客户、改员工或改产品等操作。

### 销售出库关联工作台

替代泛化的“身份解析”。一行代表一张销售出库，围绕业务单展示：

- 客户：来源名称、电话、地址、已关联客户和判断依据；
- 员工：来源业务员、已关联员工；
- 产品：产品明细总行数、已归类行数、未归类行数；
- 仓库：来源仓库名称、已关联仓库；
- 结果：完整、部分完整、待处理。

工作台支持按“仅看缺客户、缺员工、缺产品、缺仓库”筛选。人工处理作用于明确的业务关系，不再产生含义不清的 CUSTOMER/EMPLOYEE/PRODUCT/WAREHOUSE 身份队列。

### 客户档案

客户档案只保存稳定主数据和反向业务视图：基本资料、联系人、地址、负责员工、全部销售出库。客户页不再承担来源身份审核。

从销售出库识别客户时采用以下优先级：

1. 标准化电话精确一致；
2. 客户名称与电话组合一致；
3. 客户名称与标准化地址组合一致；
4. 只有名称相似时只给候选，不自动合并；
5. “王先生、李经理、客户”等泛化名称不得单独作为合并依据。

同一客户允许多个电话、联系人和收货地址。销售出库仍保存当时的电话和地址快照，因此档案修改不会改写历史。

### 产品与库存

氚云产品行分成两层：

- 来源产品快照：产品编号、名称、规格、单位、备注，永久保留在出库明细；
- 项目内产品归类：可选关联 `sales_products`，用于库存聚合、成本和统计。

`sales_products` 在界面统一称为“产品归类”或“库存产品”，不再称“交易产品档案”。标准设备作为产品主体；客户模具、配置、电压、包装等差异保留在出库明细、生产要求或批次信息中，不为每个定制描述无限创建 SKU。

### 员工与仓库

员工按业务员姓名映射到 `employees`，映射结论可复用到同名来源记录。仓库按来源仓库名称映射到三条正式仓库主数据。销售出库后续应增加稳定 `warehouse_id`，来源 `warehouse` 字符串继续保留。

## 3. 重导与人工结论

重导必须幂等：相同氚云业务 ID 更新同一销售出库。来源哈希只比较经过统一格式化的业务字段，不能因网页版和客户端的单元格格式差异触发伪更新。

人工确认不能只存在于会被重导删除的事实行中。客户、员工、仓库使用来源特征到主档的领域映射；产品使用来源产品签名到产品归类的映射。导入时先恢复这些结论，再生成待处理项。

## 4. 建设顺序

> 进度（2026-09-11）：1–7 均已落地并通过直连库验证。1 的台账列表、2 的工作台、4 的自动关联、
> 5 的产品归类、6 的领域映射与重导复用、7 的验收对账均已可用；3 的客户重建按电话优先规则实现。
> 验证脚本 29 项断言全绿（产品归类分级、领域映射重导复用、员工/仓库精确关联、9 项验收对账、
> 客户识别 6 级优先级）。

1. **关联可见化**：台账列表和详情展示客户、员工、产品、仓库关联状态与档案跳转。（已完成）
2. **关联工作台**：新增按销售出库组织的关系完整度列表和筛选，替换旧身份解析入口。（已完成）
3. **客户重建**：用电话优先规则生成客户候选；用户只处理冲突，不逐条确认正常数据。（已完成）
4. **员工与仓库自动关联**：唯一精确命中自动绑定，冲突才进入工作台。（已完成）
5. **产品归类**：按产品编号优先、名称规格单位辅助生成建议；允许保持未归类，不阻塞销售金额和提成。（已完成）
6. **持久化人工结论**：领域映射在重导后自动复用，并记录依据、操作人和时间。（已完成）
7. **全链路验收**：按出库总数、金额、已收、未收、业务员、客户、产品行和关联覆盖率逐级对账。（已完成）

### 实现要点（改动时勿破坏）

- **产品来源键三处同口径**：`SourceIdentityService.productSourceKey`（Java）、
  `OutboundRelationGovernanceService.PRODUCT_KEY_EXPR`（SQL）、`SourceIdentityService` 的
  PRODUCT 回填语句。编码优先，否则 `'NAME|' + SHA2('名称|规格|单位' 归一, 256)`。改一处必须同步另两处。
- **排序规则**：本库历史表为 `utf8mb4_unicode_ci`、新表为 `utf8mb4_0900_ai_ci`，**两个列直接比较会
  报 ERROR 1267**。列与列比较统一写 `LOWER(CONVERT(TRIM(x) USING utf8mb4))`，不要写死 `COLLATE`。
- **自动绑定边界**：只有唯一命中才自动绑定；多候选、泛化客户名称（王先生/李经理/客户…）只入复核队列。


## 5. 完成标准

- 任意销售出库都能看到氚云原始快照和四类项目内关系；
- 任意客户档案都能反查全部关联销售出库；
- 自动匹配只处理确定关系，人工只处理冲突和无法判断项；
- 删除并重导氚云事实后，已确认关系可以恢复；
- 产品未归类不会影响销售、收款和提成核算，但会明确标记为库存/产品统计待治理；
- 历史台账保持只读，所有关系修改集中在销售出库关联工作台。
