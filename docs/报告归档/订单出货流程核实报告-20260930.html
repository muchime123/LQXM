1主轴流程图

ERP 主轴 5 节点：销售订单 → 履约评审 → 生产 / 采购 → 完工入库 → 销售出库。每个节点衍生一个子模块（需求挂账 / 异常单 / 报工返工质检 / 代发直发 / 利润提成结算）。

2节点逐一说明

① 销售订单 · SalesOrderView.vue

入口与状态机
/sales-orders

入口：列表「新建订单」按钮 → 抽屉。状态机：DRAFT（草稿）→ PENDING_APPROVAL（待审批）→ CONFIRMED（已确认）。审批是独立权限 sales_order.approve，与 sales_order.manage 分离；驳回回 DRAFT，审批状态单独一列。

新建流程
  1. 选客户：必须锚定客户档案（搜索/就地建档，落 customers 表，customer_id 往下游传）
  2. 加明细行，每行选供货方式：
    • STOCK 从可售库存选；缺货可点「改为自产」转 MAKE
    • MAKE 点「配置自产产品」开 ProductionTaskOrderDrawer
    • BUY 点「配置外采需求」填型号/品牌/技术要求等
    • UNDECIDED 提交审批前必须确定
  3. 保存草稿（草稿不形成生产/采购/出库事实）
  4. MAKE/BUY 行送履约评审
  5. 提交审批 → 老板审批通过 → CONFIRMED

② 履约评审 · SalesFulfillmentReviewView.vue

职责
/sales-fulfillment-reviews

分两岗 Tab：车间·自产 / 采购·外采。销售订单确认前只做一次需求可行性评审。

  • 结论：ACCEPTED（可履约）/ CHANGE_REQUIRED（需调整，必填原因）
  • 可填建议交期；销售改产品/数量/交期后意见自动失效
  • 已确认订单变更（数量/交期）也走这里复评：纯交期调整只需客户确认，数量变要重新商业审批

订单协作详情 · ErpOrderWorkspaceView.vue（流转枢纽）

/sales-orders/:id

同一张订单的流转枢纽，4 步流程条：客户需求 → 履约确认 → 供应准备 → 发货交付。

确认后每个明细按供货方式分流：

  • MAKE：跳 /local-manufacturing-execution?taskId=MO...
  • BUY：跳 /purchase-orders?purchaseId=...
  • STOCK：直接「安排发货」开 OrderDeliveryDialog → 生成出库草稿

③a 生产任务 · ManufacturingExecutionView.vue

/local-manufacturing-execution

含次级 Tab：任务单总览 / 执行看板 / 报工记录 / 返工 / 质检 / 完工交仓。

状态机：RELEASED → SCHEDULED → IN_PRODUCTION → PENDING_INSPECTION → PENDING_REINSPECTION → PENDING_RECEIPT → PARTIALLY_RECEIVED → COMPLETED / REWORK

流程：销售订单 MAKE 行确认后下达 → 多道工序报工（可累计，超额需权限）→ 全部完成 → 人工检验 → 完工入库（写 product_inventory_balances 增加可售库存）→ 不合格走 REWORK

③b 采购订单 · PurchaseOrderView.vue

/purchase-orders

顶部「待采购需求」卡片 = 销售订单 BUY 行确认后的待办。

履约方式两分叉：

  • WAREHOUSE 到货入库：分批到货入本地仓 → 增加可售库存
  • DROP_SHIP 供应商直发客户：不入本地仓，直接形成客户交付事实

状态机：DRAFT → PENDING_APPROVAL → CONFIRMED → RECEIVING → PARTIALLY_RECEIVED → RECEIVED

④ 完工入库 / 到货入库（不独立成页）

归 ManufacturingExecutionView 的次级 Tab「完工交仓」。生产完工入库 + 采购到货入库 都写入 product_inventory_balances 余额表，被销售订单 STOCK 选品与出库选货共用同一口径。

⑤ 销售出库 · SalesOutboundView.vue

/sales-outbounds

关键约束：不可直接新建，只能两个来源：

  1. 销售订单确认后 STOCK 行「办理发货」→ OrderDeliveryDialog → 出库草稿
  2. 代发采购单 DROP_SHIP 后端自动生成草稿（fulfillment_source=FULFILLMENT_DROP_SHIP）

状态机：DRAFT（草稿）→ POSTED（已过账，扣库存）→ REVERSED（已冲销，回补）/ CANCELLED（已取消）

流程：出库草稿 → 编辑（选仓库、从可售库存选货）→ 过账（扣 product_inventory_balances，形成交付事实）→ 如需更正走冲销（终态）

33 个严重问题核实结论

初步判断的 3 个严重问题，经后端代码核实后的真实定性如下。

问题 1：冲销是否回退订单已发数量？

非 BUG 数据天然一致 · 无需修复

初步判断：SalesOutboundService.doReverse 没有更新 sales_order_items.shipped_quantity，疑似数据不一致。

核实真相：shippedQuantity 不是存储字段，而是实时子查询聚合。

-- ErpSalesOrderService.java:278-280
(SELECT COALESCE(SUM(oi.quantity),0) FROM erp_sales_outbound_items oi
 JOIN erp_sales_outbounds o ON o.id=oi.outbound_id
 WHERE oi.sales_order_item_id=erp_sales_order_items.id
   AND o.status='POSTED') shippedQuantity

erp_sales_order_items 表根本没有 shipped_quantity 字段（迁移脚本无任何匹配；V221 的 shipped_quantity 是已下线的 formal_sales_order_items 表）。

冲销把出库单 status 从 POSTED 改为 REVERSED 后，子查询的 WHERE o.status='POSTED' 自动排除该出库单，shippedQuantity 自动回退。同理 allocatedQuantity 用 IN ('DRAFT','POSTED') 过滤，REVERSED 也不算在内。

代发 DROP_SHIP 出库单也写入 erp_sales_outbounds，冲销后同样被排除。数据流天然一致。

ErpSalesOrderService.java:275-280（子查询）+ SalesOutboundService.java:577-618（doReverse）+ grep 全后端无 erp_sales_order_items.shipped_quantity 字段定义

问题 2：DROP_SHIP 采购到货后销售出库草稿由谁生成？

非 BUG 后端自动生成 · UX 入口待查

初步判断：出库页禁止直接新建，DROP_SHIP 出库生成路径可能是黑洞。

核实真相：后端链路完全打通。

// ErpPurchaseOrderService.doCreateDropShipOutbound (L521-587)
// 采购确认到货后自动调用 SalesOutboundService.createDropShip
// 生成 DRAFT 出库单，fulfillment_source = FULFILLMENT_DROP_SHIP

// SalesOutboundService.createDropShip (L296-312) + doCreateDropShip (L380-400)
// 向 erp_sales_outbounds 插入 DRAFT 状态记录
// 过账时按代发豁免扣库存

因此 DROP_SHIP 链路：采购确认到货 → 后端自动生成出库草稿 → 销售出库页可见 → 过账（不扣库存）。后端正确。

唯一待确认：触发 doCreateDropShipOutbound 的前端入口在 PurchaseOrderView.vue 200 行之后（之前未读到）。若按钮不显眼属 UX 体验问题；若是后端事件触发则前端无感知也合理。这不是 BUG。

ErpPurchaseOrderService.java:521-587 + SalesOutboundService.java:296-312, 380-400

问题 3：STOCK 缺货转 MAKE 后评审是否失效？

UX 提示不足 后端逻辑正确

初步判断：STOCK→MAKE 转换可能跳过评审。

核实真相：评审 content_hash 明确包含 supplyMode，STOCK→MAKE 后 hash 变化 → reviewCurrent=false → 评审失效 → 提交审批被就绪度判定阻塞。后端逻辑正确。

评审 hash 参与字段：

productName · specification · salesProductId · supplyMode · unit
quantity · requestedDeliveryDate · remark
productionConfigJson · purchaseConfigJson · orderDeliveryDate

hash 是 SHA-256 快照，存于 erp_sales_order_fulfillment_reviews.content_hash（V349__sales_order_fulfillment_review.sql）。

真问题：SalesOrderView.vue 抽屉里失效行只是变色标签 + 「已失效，需重评」文字，没有强提示「这条必须重新送评才能提交」。用户可能在订单抽屉里直接点「提交审批」被后端 readiness 拦下，体验差。属 UX 缺失，不是 BUG。

SalesFulfillmentReviewService.java:101-118, 159-182, 185-200 + V349__sales_order_fulfillment_review.sql:5-11
3 个严重问题综合定性：0 个真 BUG，1 个 UX 提示不足，2 个后端完全正确。前一步「冲销不回退 shippedQuantity 是 BUG」的判断错误——因 shipped_quantity 根本不是存储字段，而是实时聚合，冲销后状态变化自动排除。

4UX 待改进问题清单

除问题 3 外，下列问题均属入口分散 / 信息重复 / 体验细节，非数据 BUG。

# 问题 表现 建议修复
1 STOCK→MAKE 评审失效强提示不足 SalesOrderView 抽屉失效行只是变色标签，无「必须重新送评」强提示 失效行加红色高亮 + 提示文案，引导用户重新送评
2 客户档案不该在 ERP 主轴里 navigation.ts 把客户档案作为 ERP children 第二项，但它是主数据不是交易节点 移到主数据独立区或系统侧栏，销售订单已支持就地建档
3 评审/变更信息在两处重复 SalesOrderView 抽屉 + ErpOrderWorkspaceView 都展示评审记录、变更列表，用户不知在哪操作 SalesOrderView 抽屉只读展示，变更发起集中在 ErpOrderWorkspaceView
4 出库「办理发货」与出库页「编辑」两步割裂 OrderDeliveryDialog 生成草稿后跳 /sales-outbounds 还要再编辑选货 OrderDeliveryDialog 一次完成仓库+批次+数量选择，草稿生成立即可过账
5 状态机术语混乱 ErpOrderWorkspaceView 的 statuses 字典混了 SalesOrder / ManufacturingOrder / PurchaseOrder 三套状态 拆成 orderStatuses / productionStatuses / purchaseStatuses 三组
6 履约评审失效无强提示 SalesOrderView 抽屉里失效行无「必须重新送评」强提示 同 #1，失效行加红色高亮
7 完工入库进度不透传订单协作 MO 行在 ErpOrderWorkspaceView 只显示状态，没显示「已入库 X / 待入库 Y」 MO 行加数量进度，避免用户跨页查
8 demandItemId 跳转参数消费不明 销售订单 BUY 行点「办理采购」跳 /purchase-orders?demandItemId=...&sourceOrderId=...，但 PurchaseOrderView 前 200 行未处理 查 200 行后逻辑，确认是否预填需求项
9 DROP_SHIP 出库生成入口前端不可见 触发 doCreateDropShipOutbound 的前端按钮位置待查 查 PurchaseOrderView 200 行后，若按钮不显眼则加视觉强调
10 变更操作入口分散 SalesOrderView 抽屉 + ErpOrderWorkspaceView 两处都能发起变更操作 只在 ErpOrderWorkspaceView 集中处理，SalesOrderView 抽屉只读
优先级建议：问题 1 / 6（评审失效强提示）影响提交审批通过率，先做；问题 2（客户档案移出主轴）符合用户偏好「主轴顺下来」；问题 3 / 10（信息收敛）需配合 ErpOrderWorkspaceView 改造；其余按业务优先级排。

核心判断

1. 数据层无 BUG。3 个疑似严重问题（冲销回退、DROP_SHIP 生成、STOCK→MAKE 评审失效）经后端代码核实，后端逻辑均正确。特别是「已发数量」采用实时聚合而非存储字段，从设计上根除「过账 increment + 冲销 decrement」的对称写入缺口，数据天然一致。
2. 体验层有改进空间。10 个 UX 问题集中在「入口分散」「信息重复」「失效提示不足」。最影响业务的是评审失效的强提示（用户可能直接提交被拦下），最影响主轴清晰度的是客户档案不该在 ERP 主轴里。
3. 前期误判修正。前一步判断「冲销不回退 shippedQuantity 是真 BUG」是错误的——因 shipped_quantity 根本不是存储字段，而是子查询实时聚合，冲销后状态变化自动排除。设计反而比存储字段更安全。

建议下一步

  1. 优先做 UX #1 / #6：评审失效行加强提示（影响提交通过率）
  2. UX #2：客户档案移出 ERP 主轴（符合用户偏好「主轴顺下来」）
  3. UX #3 / #10：变更操作收敛到 ErpOrderWorkspaceView
  4. UX #4：OrderDeliveryDialog 一次完成选货，减少跳转
  5. UX #8 / #9：读 PurchaseOrderView 200 行后，确认 demandItemId 预填与 DROP_SHIP 触发按钮位置
