# 氚云数据全链路串联文档

> 最后核对：2026-09-08  
> 核对依据：当前项目代码与数据库迁移；历史方案只作背景参考  
> 范围：氚云导入中心、历史台账、客户档案、产品库存、生产接入、月度提成

## 一、当前全链路

系统接收六类氚云数据，但后端分为两条导入管线。

```text
                         氚云 Excel
                             │
              ┌──────────────┴──────────────┐
              │                             │
         业务事实导入管线               产品库存台账管线
              │                             │
   ┌──────────┼──────────┐             ┌────┴────┐
 销售出库   生产任务   收款/多单结清       产品信息   仓库明细
   │          │          │              │         │
sales_    production_  receipts    h3_product_ h3_warehouse_
outbounds   orders                    catalog      stock
   │          │                          └────┬────┘
   ├─客户档案  └─接入正式制造工单                 ↓
   ├─历史台账                        产品库存合并与异常复核
   └─月度提成                                  ↓
                                 sales_products + 库存余额/流水
```

当前结构可概括为：

> **六类来源、两条导入管线、六类只读台账、四个消费场景。**

四个消费场景是客户档案、产品库存、生产工单接入和月度提成。氚云导入中心是统一操作及追溯入口，不表示六类数据由同一个后端服务处理。

## 二、六类来源的定位

| 氚云来源 | 类型 | 当前落库 | 主要用途 | 参与提成 |
|---|---|---|---|---|
| 销售出库 | `OUTBOUND` | `sales_outbounds`、`sales_outbound_items`、`sales_outbound_payment_snapshots` | 客户历史、销售、回款、运杂费、提成 | **是，唯一业务来源** |
| 生产任务 | `PRODUCTION` | `production_orders`、`production_order_components` | 生产历史、选择性接入制造工单 | 否 |
| 收款记录 | `RECEIPT` | `receipts` 及关联链接 | 历史核对台账 | 否 |
| 多订单结清 | `SETTLEMENT` | `receipts` 及结清链接 | 历史核对台账 | 否 |
| 产品信息 | `CATALOG` | `h3_product_catalog` | 补充产品名称、规格、单位、采购价 | 否 |
| 仓库明细 | `STOCK` | `h3_warehouse_stock` | 氚云库存台账、库存合并来源 | 否 |

三个核心边界：

1. 月度提成只认销售出库中的已核验收款明细和运杂费。
2. 产品信息和仓库明细是源台账，必须经过合并预览和复核后才能进入正式库存。
3. 氚云生产任务与正式制造工单是两个对象；接入建立关联，但不改写历史。

## 三、两条导入管线

### 3.1 业务事实管线

销售出库、生产任务、收款记录、多订单结清由 `H3FactImportService` 处理。

```text
上传 → h3_import_batches
     → 解析并暂存 h3_import_staging_rows
     → 新增/更新/不变预览
     → 用户确认
     → 写对应事实表
     → h3_import_rows 永久保留原始行快照
     → 完成；销售出库额外触发后续联动
```

销售出库确认时同步保存产品明细和收款快照，提交后跟踪可能影响已核算提成的变化。外部来源和外部标识用于识别同一事实，支持增量更新而非重复追加。

### 3.2 产品库存台账管线

产品信息和仓库明细由 `ProductInventoryLedgerImportService` 处理，复用导入中心的批次界面，但落入独立源台账。

```text
h3_product_catalog ─┐
                    ├─ ProductInventoryMergeService
h3_warehouse_stock ─┘          │
                    ┌──────────┴──────────┐
                    ↓                     ↓
             sales_products   product_inventory_balances
                                          ↓
                             product_inventory_transactions
```

“保存源台账”和“确认合并”是两个动作，避免重复产品、费用行、缺失采购价和错误仓库直接污染正式库存。

## 四、销售出库是核心连接点

```text
sales_outbounds
  ├─ customer_id / customer_name → 客户档案
  ├─ employee_id / salesperson_name → 员工、权限、提成
  ├─ sales_outbound_items → 出库产品明细
  ├─ sales_outbound_payment_snapshots → 提成实际回款
  ├─ freight → 提成运杂费扣减
  └─ import batch / external id → 批次和原始数据追溯
```

| 字段或关系 | 用途 |
|---|---|
| `external_source + external_id` | 标识氚云事实、保证导入幂等 |
| `outbound_no` | 业务出库单号 |
| `outbound_status` | 只有确认生效数据进入正式统计 |
| `ship_date / business_date` | 销售额和运杂费期间归属 |
| `customer_id / customer_name` | 连接客户身份并保留历史名称 |
| `employee_id / salesperson_name` | 连接员工、数据范围和提成 |
| `dealer_name / source_gross_profit` | 经销商/零售分类依据 |
| `sales_amount` | 销售额及回款率分析 |
| `freight` | 提成扣减来源 |
| 收款快照 | 提成认可的逐笔实际回款 |

旧“我的订单/订单利润”页面已下线。客户档案和月度提成直接消费销售出库事实，订单利润不再是主链中间层。

## 五、客户档案链路

公司不再单独导入客户信息，客户主要由销售出库建立和补充。保存出库时按客户名称匹配或建档，把 `customer_id` 写入出库事实，再从出库内容补充地址、联系人、电话和业务员关系。

- `customers` 保存稳定客户身份；
- `sales_outbounds.customer_name` 保存当时名称快照；
- 同一客户的历史出库通过 `customer_id` 聚合；
- 客户改名不会丢失历史单据原貌。

```text
客户档案 → customer_id → 销售出库列表
                         → 统一氚云出库详情抽屉
                         → 主单字段 + 产品明细
```

当前仍需治理同名误合并、简称形成重复客户、经销商与终端身份并存、业务员无法匹配员工、地址电话冲突。应通过客户合并、别名和异常清单解决，不能靠重复导入客户表掩盖。

## 六、产品库存链路

### 6.1 产品业务含义

仓库明细主要是设备、配件和包材，不应解释成原材料库存。公司多数产品是在标准产品基础上因客户使用模具不同形成定制差异，所以产品身份应采用“标准产品基础 + 交易名称/规格 + 定制标记”，不应把每条历史名称都解释成完全不同的产品体系。

`sales_products` 当前承担交易和库存产品身份。它应与产品中心产品档案保持可映射关系，同时避免再复制出更多产品主表。

### 6.2 自动匹配顺序

1. 使用 `sales_product_source_aliases` 中已确认的氚云编码映射；
2. 按“产品名称 + 规格 + 单位”匹配现有 `sales_products`；
3. 未匹配时新建 `H3-{源产品编码}` 的待复核交易产品，并建立来源别名。

仓库按名称匹配正式 `warehouses`。公司只有少量固定仓库，应先统一名称配置，不应随导入无限自动建仓。

### 6.3 自动过滤和人工复核

| 情况 | 处理 |
|---|---|
| 费用、制版费、税点、运费类目 | 跳过 |
| 数量为 0 | 跳过 |
| 数量为负 | 跳过并计入异常 |
| 产品编码找不到产品信息 | `PRODUCT_NOT_FOUND`，待复核 |
| 采购价为空或不大于 0 | `PRICE_MISSING`，待复核 |
| 仓库名称无法匹配 | `WAREHOUSE_MISSING`，待复核 |
| 产品、仓库、价格完整 | `READY`，允许确认 |

不需要把全部记录逐条手工映射。人工只处理自动规则无法判断的异常，并把结果沉淀为来源别名，供后续自动复用。

### 6.4 库存写入语义

仓库明细表示氚云某一时点的库存结果，因此合并采用**目标值语义**：

- 没有余额时创建，变化量等于导入数量；
- 数量或价格不同则修正为台账目标值；
- 完全一致则忽略，不重复累加、不写重复流水。

实际创建或修正都会写 `product_inventory_transactions`，可追溯变化前后结果。

## 七、生产任务与正式制造

氚云生产任务完整保存在 `production_orders + production_order_components`。用户可在“氚云导入中心 → 历史台账 → 生产任务工单”筛选待接入记录，单条或批量接入正式制造工单。

- 原氚云任务继续保留；
- `linked_manufacturing_order_id` 记录接入目标；
- 正式制造工单承担排产、报工、完工入库；
- 历史任务不会因接入自动增加库存，只有正式完工入库才产生库存流水。

## 八、收款记录和多订单结清

两者保存到 `receipts`，通过 `receipt_type` 区分，并保留与出库单的历史关联。它们用于历史查看、关联核对和批次追溯。

它们不用于重新计算销售出库已收款、不写正式收款分配、不参与月度提成，也不覆盖销售出库内由财务核验的收款数据。这样可避免三套收款数据重复计量。

## 九、月度提成完整链路

### 9.1 唯一来源

```text
销售出库内嵌收款详细
  → sales_outbound_payment_snapshots
  → receipt_date + CONFIRMED
  → 期间实际回款

sales_outbounds.freight
  → ship_date/business_date + CONFIRMED
  → 运杂费扣减
```

独立收款台账、多订单结清、订单利润和产品库存均不进入提成公式。

### 9.2 实时参考

对任意日期范围：

```text
经销商提成 =（期间经销商确认回款 − 运费窗口经销商运杂费）× 经销商比例
零售提成   =（期间零售确认回款   − 运费窗口零售运杂费）× 零售比例
提成合计   = 经销商提成 + 零售提成
```

经销商判定为 `dealer_name` 非空，或源毛利率低于 15% 的兜底判定。比例来自 `monthly_commission_rates` 及比例历史。

日期范围允许任意选择。运费默认取结束日所在月的前一完整自然月，也支持上一等长期间或自定义范围；自定义范围必须填写原因。

### 9.3 正式核算

```text
commission_calculation_versions       核算版本
commission_calculation_items          业务员冻结金额
commission_calculation_source_lines   本版本占用的回款、运费、调整来源
commission_outbound_changes           已核算后销售出库变化形成的修正
```

来源被有效版本占用后，重叠日期再次核算也不会重复计提；版本作废后来源可释放并重新核算。

页面必须区分：

| 金额 | 含义 |
|---|---|
| 实时参考 | 按当前氚云事实重算，会随重新导入变化 |
| 已核算累计 | 有效版本已经冻结的基础及修正提成 |
| 待核算基础提成 | 尚未被版本占用的正常来源形成的提成 |
| 待核算修正提成 | 已核算来源后来变化产生的差额 |
| 核算后预计累计 | 已核算累计 + 两类待核算金额 |

这解决了“已经核算但汇总仍展示实时金额”的问题：实时、已核算和待核算是三个独立口径。

### 9.4 已核算后重新导入

- 未核算来源按当前事实进入正常核算；
- 已核算来源变化时写 `commission_outbound_changes`；
- 下一版本只计变化差额，不重算原金额；
- 已发放版本保留原快照，修正通过后续版本体现。

## 十、导入中心和六类历史台账

历史台账通过统一接口 `/api/h3-imports/ledger/{kind}` 查询。

| 台账 | 来源 | 详情/能力 |
|---|---|---|
| 销售出库 | `sales_outbounds` | 主单 + 产品明细；客户和提成统一下钻 |
| 生产任务 | `production_orders` | 主单 + 制程明细；待接入/已接入筛选 |
| 收款记录 | `receipts` | 收款主单和相关出库 |
| 多订单结清 | `receipts` | 结清主单和覆盖出库链接 |
| 产品信息 | `h3_product_catalog` | 产品台账行；库存合并来源 |
| 仓库明细 | `h3_warehouse_stock` | 库存台账行；库存合并来源 |

`H3LedgerDetailDrawer` 是跨页面统一事实查看入口。销售出库详情不再依赖已下线的“我的订单”。

## 十一、身份与血缘

| 标识 | 作用 |
|---|---|
| 批次 ID | 回到上传、预览、确认和结果 |
| `external_source + external_id` | 标识氚云事实、支持幂等更新 |
| `h3_import_rows.raw_data` | 反查确认时原始数据 |
| `customer_id` | 把名称快照归入统一客户 |
| `employee_id` | 连接业务员、权限和提成 |
| 产品来源别名 | 连接氚云编码和正式交易产品 |
| `warehouse_id` | 连接氚云仓库名和正式仓库 |
| 提成来源行 | 证明来源被哪个版本使用 |
| `linked_manufacturing_order_id` | 证明生产任务接入目标 |

旧批次血缘抽屉中的部分候选和业务单信息属于历史匹配设计。当前可靠追溯组合是“事实外部标识 + 导入批次 + 原始行快照 + 各业务域来源链接”。

## 十二、已连通、特意隔离与待补强

已连通：

- 销售出库 → 客户档案 → 出库历史 → 统一详情；
- 销售出库收款/运杂费 → 提成实时参考 → 待核算 → 正式版本；
- 销售出库重导 → 已核算来源变化跟踪；
- 产品信息 + 仓库明细 → 复核 → 正式产品库存和流水；
- 生产任务 → 正式制造工单接入关系；
- 六类事实 → 导入中心历史台账。

特意隔离：

- 收款记录/多订单结清不进入提成和正式收款分配；
- 生产历史接入不自动增加库存；
- 仓库明细不进入原材料库存；
- 订单利润不进入月度提成；
- 氚云产品行不无条件覆盖正式产品档案。

待补强：

1. 客户别名、重复识别和合并结果沉淀；
2. 产品来源别名治理，减少找不到产品和重复 `H3-` 产品；
3. 仓库名称映射；
4. 业务员无法映射员工的异常清单；
5. 提成的实时、已核算、待核算、修正、预计累计在人员明细层完全一致；
6. 批次追溯按六类事实展示真实落库记录和业务影响。

## 十三、实际操作顺序

初始化或全量迁移：

1. 配置正式仓库及统一名称；
2. 导入产品信息；
3. 导入仓库明细；
4. 查看库存合并预览，只处理异常行；
5. 确认合并，形成正式产品、库存余额和期初流水；
6. 导入完整销售出库，建立/连接客户并生成收款快照；
7. 检查重复客户、业务员未匹配和出库异常；
8. 导入生产任务、收款记录和多订单结清作为历史台账；
9. 按需接入生产任务到正式制造；
10. 月度提成先核对实时数据和异常，再生成正式版本。

后续增量：

1. 上传新的氚云导出文件并检查差异统计；
2. 确认导入；
3. 销售出库更新后检查待核算修正；
4. 产品/仓库更新后重新预览库存合并，只确认差异；
5. 从历史台账抽查源字段和明细。

## 十五、最终业务理解

```text
第一层：原始事实和历史台账
  数据不丢、重复可识别、结果可回查

第二层：稳定业务身份
  客户、员工、交易产品、仓库、制造工单

第三层：业务结果
  客户业务历史、正式库存、生产执行、提成版本
```

销售出库是客户和提成的核心事实；产品信息与仓库明细共同建立库存；生产任务通过接入关系进入新制造流程；收款记录和多订单结清保留为核对台账。各模块共享导入中心和统一详情能力，同时保留清晰口径，避免同一金额、产品或业务被重复计算。

## 十六、现有链路为什么还需要优化

前面十五章描述的是当前已经实现的链路。它可以运行，但还不是最终领域模型，主要有六个结构性问题。

### 16.1 导入事实和正式业务混在一起

`sales_outbounds`、`production_orders` 和 `receipts` 同时承担氚云历史台账与新系统业务查询。短期开发方便，长期会让“氚云原始值”“人工修正值”“系统计算值”难以区分。

### 16.2 名称仍承担过多关联责任

客户、业务员、产品和仓库都存在按名称匹配。名称可修改、可缩写、可包含空格，也可能同名。只靠名称无法成为稳定外键。

### 16.3 销售出库产品与库存产品尚未稳定贯通

氚云能提供的是产品信息、仓库明细以及销售出库产品行。三者之间应通过交易产品
`sales_products` 和来源别名建立稳定关系。当前仍可能只按名称、规格和单位临时匹配，
导致重复产品或销售出库行没有 `sales_product_id`。

### 16.4 生产任务不能作为销售出库的强制前置关系

氚云生产任务没有稳定的产品 ID 和仓库 ID，也没有可与销售出库可靠连接的成品批次标识。
它应保留为独立生产历史，并可按需接入本地制造流程；不能根据产品名称、客户或日期猜测并绑定销售出库。

### 16.5 收款台账存在但没有形成统一业务语义

月度提成只认销售出库收款快照是正确的，但独立收款记录和多订单结清仍应能与销售出库做“核对关系”。完全隔离会失去发现氚云数据矛盾的机会，直接参与金额计算又会重复计量。

### 16.6 导入中心偏文件管理，缺少跨域结果

当前可以查看批次和单类台账，但用户更需要看到：

- 这一批生成或更新了哪些客户、产品和业务事实；
- 哪些行没有完成身份解析；
- 哪些变化影响库存或提成；
- 问题应该到哪个业务页面处理。

## 十七、优化后的四层数据架构

```text
┌─────────────────────────────────────────────┐
│ 第一层：原始来源层                           │
│ 文件、批次、原始行、原始主单、原始子表         │
└───────────────────┬─────────────────────────┘
                    ↓ 解析与身份解析
┌─────────────────────────────────────────────┐
│ 第二层：业务身份层                           │
│ Customer / Employee / SalesProduct /          │
│ Warehouse + 各类 source_identity_alias       │
└───────────────────┬─────────────────────────┘
                    ↓ 引用稳定 ID
┌─────────────────────────────────────────────┐
│ 第三层：业务事实层                           │
│ 销售出库、生产任务、库存余额/流水、收款核对      │
└───────────────────┬─────────────────────────┘
                    ↓ 冻结来源
┌─────────────────────────────────────────────┐
│ 第四层：核算快照层                           │
│ 提成版本、提成来源行、修正版本、发放状态        │
└─────────────────────────────────────────────┘
```

### 17.1 第一层：原始来源层

这一层只回答“氚云当时给了什么”，必须保持不可变或可版本追溯。

建议保留：

- `h3_import_batches`：文件和处理批次；
- `h3_import_rows`：原始行 JSON；
- 六类源台账及外部 ID；
- 同一外部事实的导入版本号、首次导入批次、最后更新批次；
- 原始值哈希，用于判断内容是否发生变化。

业务页面不应直接修改这一层的关键源字段。人工纠错应写映射、补充或调整记录。

### 17.2 第二层：业务身份层

所有跨模块连接先经过身份解析，不再直接使用名称连接。

建议形成统一概念：

```text
source_identity_alias
  source_system       H3YUN
  entity_type         CUSTOMER / EMPLOYEE / PRODUCT / WAREHOUSE
  source_key          氚云 ID、编码或标准化名称
  source_name         源名称快照
  target_id           系统正式对象 ID
  resolution_status   AUTO / CONFIRMED / REVIEW / IGNORED
  confidence          自动匹配置信度
  resolved_by/at      人工确认审计
```

现有产品别名可以保留，并逐步把客户、员工、仓库也收敛到相同治理模式。自动匹配只生成候选；存在歧义时进入异常队列，不应模糊匹配后静默建档。

### 17.3 第三层：业务事实层

事实层只保存已经解析的业务关系，同时保留源快照：

- 销售出库引用 `customer_id`、`employee_id`；
- 出库行引用 `sales_product_id`，仍保存源名称、规格和编码；
- 氚云生产任务独立保存；接入本地制造后才按本地流程继续执行；
- 出库行通过 `sales_product_id` 连接交易产品，但不反推生产任务；
- 库存只由库存流水产生，余额是流水的当前结果；
- 独立收款和结清只形成核对关系，不改变提成权威金额。

### 17.4 第四层：核算快照层

提成版本必须完全基于来源行冻结：

- 正常回款来源；
- 运杂费来源；
- 已核算后变化的修正来源；
- 采用的业务员和比例快照；
- 版本状态与发放状态。

实时数据变化不会改写历史版本，只会形成新的待核算来源或修正来源。

## 十八、优化后的核心业务链

### 18.1 客户与销售链

```text
氚云客户名称/ID
  → 客户身份解析
  → customers
  → sales_outbounds.customer_id
  → 客户档案业务历史
```

客户自动建档应调整为：

1. 外部 ID 或已确认别名精确命中；
2. 统一社会信用代码、电话等强标识命中；
3. 标准化全称唯一命中；
4. 相似名称只产生候选；
5. 无候选才创建“待复核客户”。

### 18.2 产品信息、仓库明细与销售出库链

```text
氚云产品信息 ─→ 产品来源别名 ─→ sales_products
                                      ├─ 氚云仓库明细 ─→ 库存余额/流水
                                      └─ 销售出库产品行 ─→ 销售与利润基础
```

产品中心的产品档案与氚云交易产品不是同一个概念，本阶段不强制互相绑定。一个来源产品编码
只能映射一个交易产品；同一映射同时供仓库明细和销售出库行复用。没有编码时才使用规范化的
“名称 + 规格 + 单位”候选，并由人工确认歧义项。

### 18.3 产品库存链

```text
氚云产品编码 → 产品别名 → sales_product/product
氚云仓库名称 → 仓库别名 → warehouse
氚云仓库数量 → 期初/校准流水 → 库存余额
销售出库产品行 → sales_product_id → 查询对应库存（只读参考）
```

仓库明细全量导入不能长期直接覆盖日常库存。建议区分：

- **系统启用前**：允许作为期初目标值；
- **系统启用后**：只生成库存对账差异；
- 财务/仓库确认差异后，生成带原因的盘盈盘亏或校准流水；
- 禁止绕开流水直接覆盖余额。

### 18.4 收款核对链

```text
销售出库收款快照 ─────→ 提成权威金额
          │
          ├─ 与收款记录建立 reconciliation_link
          └─ 与多订单结清建立 reconciliation_link

核对结果：
  MATCHED / AMOUNT_DIFFERENT / DATE_DIFFERENT /
  MISSING_RECEIPT / MISSING_OUTBOUND_PAYMENT / REVIEW
```

核对只提示矛盾，不自动更改权威金额。这样既不会重复算钱，也能利用另外两份台账发现问题。

### 18.5 提成链

```text
销售出库确认收款 + 运杂费
  → 可核算来源池
  → 核算预览
  → commission_calculation_version
  → source_lines 锁定
  → FINAL
  → PAID

已锁定来源后来变化
  → commission_outbound_changes
  → 下次调整版本
```

## 十九、统一导入结果与异常中心

导入中心每个批次应统一展示以下结果，而不只展示解析进度：

| 结果类型 | 示例 | 处理入口 |
|---|---|---|
| 原始事实结果 | 新增、更新、不变、失败 | 对应历史台账 |
| 身份解析结果 | 客户未匹配、员工未匹配、产品有歧义、仓库未匹配 | 映射治理抽屉 |
| 业务影响结果 | 新增客户、库存差异、待接入生产任务 | 客户/库存/生产页面 |
| 财务影响结果 | 新增回款来源、已核算金额变化、待修正提成 | 月度提成页面 |
| 数据核对结果 | 收款台账与出库收款不一致 | 收款核对页面 |

异常应使用统一状态：

```text
OPEN → RESOLVED / IGNORED
```

同时记录处理人、处理时间、处理方式和目标对象。相同来源标识再次出现时应复用已经确认的处理结果。

## 二十、数据唯一性和一致性规则

| 规则 | 约束 |
|---|---|
| 氚云事实唯一 | `source_system + fact_type + external_id` 唯一 |
| 来源别名唯一 | `source_system + entity_type + source_key` 唯一 |
| 客户身份 | 跨模块只使用 `customer_id`，名称仅作快照 |
| 员工身份 | 提成必须存在 `employee_id`，未解析数据不进入正式核算 |
| 产品身份 | 出库和库存引用统一产品 ID，同时保留源产品快照 |
| 仓库身份 | 库存流水必须引用 `warehouse_id` |
| 库存修改 | 必须通过流水；余额禁止无来源覆盖 |
| 提成来源 | 一个来源行同一时刻只能被一个有效版本占用 |
| 历史版本 | 已发放版本不可修改，只能追加修正 |
| 删除 | 原始事实和财务版本原则上不物理删除 |

## 二十一、优化建设顺序

### 第一阶段：先加固身份解析

1. 统一客户、员工、产品、仓库来源映射的数据结构；
2. 把当前名称匹配结果迁移为已确认别名；
3. 建立未匹配和歧义异常队列；
4. 调整新增导入：先查别名，再精确匹配，最后进入待复核；
5. 禁止模糊名称静默绑定错误对象。

这是优先级最高的一步，因为后续库存、客户和提成都依赖稳定身份。

> 建设状态（2026-09-07）：第一阶段基础闭环已落地并完成真实数据首轮审计。统一来源身份表和导入中心“身份解析”页签已经建立；员工、产品、客户、仓库历史映射已迁移；销售出库客户与员工解析、库存仓库与产品解析已使用统一映射。审计发现历史客户映射规模异常偏大，因此新增 V271：把长名称、电话混入、单字符名称以及未绑定销售出库客户纳入复核队列。历史事实不做破坏性解绑；人工确认客户或员工后回填现有未绑定事实。

### 第二阶段：贯通产品信息、仓库明细与销售出库产品

1. 以 `sales_products` 作为氚云交易产品与正式库存共用的身份；
2. 产品信息优先用源产品编码建立来源别名；
3. 仓库明细解析产品时复用该别名，形成库存余额和可追溯流水；
4. 销售出库产品行使用同一解析器回填 `sales_product_id`；
5. 建立“未解析、存在歧义、已确认”的产品治理队列；
6. 产品中心档案只保留可选关联，不作为氚云导入和利润核算的强制条件；
7. 生产任务与销售出库不做强制匹配，也不构造成品批次关系。

> 建设状态（2026-09-08 修正）：已撤回“成品批次关联销售出库”的错误方案及未执行的 V274。
> 当前真实底座已经包含 `sales_products`、产品来源别名、氚云产品台账、仓库台账、库存余额/流水。
> V274（修正版）已将历史销售出库行按“已确认编码别名 → 名称+规格+单位唯一命中”的顺序回填，
> 新销售出库导入也已复用同一产品身份解析；无法唯一判断的产品进入统一 `PRODUCT` 复核队列，
> 人工确认后会回填历史未关联出库行。后续界面只需强化产品复核专属筛选与库存参考，不再建设批次分配。

### 第二阶段同步完成的导入底层加固

这部分来自回款链路专项 P2，与上面的产品/批次第二阶段并行，但不改变业务边界：

1. V273 为销售出库增加自动生成的 `attribution_date=COALESCE(ship_date,business_date)` 及组合索引；
2. 月度实时提成、正式核算、运费与销售额查询改用该索引列；
3. 导入事务提交后的回款平衡、派生状态刷新和已核算变化跟踪改由独立异步服务执行；
4. 批次只有在异步收尾真正结束后才进入 `COMPLETED`，失败进入 `PARTIAL_FAILED`；
5. 尚未实施确认主事务的分片提交与子表批量写入，不能把导入性能专项 P2 标记为全部完成。

### 第三阶段：调整库存台账导入语义

1. 锁定系统库存启用日期；
2. 启用日前的仓库明细作为期初目标值；
3. 启用日后的仓库明细改为对账快照；
4. 差异经确认后转成库存调整流水；
5. 增加“系统余额、氚云余额、差异、处理状态”视图。

### 第四阶段：建立收款核对

1. 保持销售出库收款为唯一提成来源；
2. 建立收款记录/多订单结清与出库收款的只读核对链接；
3. 输出金额、日期、关联范围异常；
4. 财务处理异常后保留结论，不自动改写源事实。

### 第五阶段：完善提成闭环

1. 完成业务员级实时、已核算、待核算、待修正和预计累计对齐；
2. 每个汇总金额可下钻到来源行；
3. 核算前阻止未解析业务员和关键异常；
4. 明确 FINAL、PAID、VOID 的操作权限；
5. 增加跨批次变化影响提示。

### 第六阶段：改造导入中心

1. 批次详情展示事实、身份、业务、财务四类影响；
2. 异常可直接跳到对应处理入口；
3. 六类台账共享统一来源追溯；
4. 删除或替换仍依赖历史业务匹配模型的血缘展示。

## 二十二、优化后的最终关系

```text
氚云导入中心
  │
  ├─ 原始事实层：完整保留六类数据和版本
  │
  ├─ 身份解析层
  │    ├─ 客户
  │    ├─ 员工
  │    ├─ 交易产品
  │    └─ 仓库
  │
  ├─ 业务事实层
  │    ├─ 销售出库 ─→ 客户业务历史
  │    ├─ 生产任务 ─→ 可选接入本地制造（与出库独立）
  │    ├─ 产品信息 + 仓库明细 ─→ 产品库存余额/流水
  │    ├─ 交易产品 ─→ 销售出库产品行（同一产品身份）
  │    └─ 收款/结清 ─→ 与出库收款做只读核对
  │
  └─ 财务快照层
       └─ 出库收款/运费 ─→ 提成来源 ─→ 核算版本 ─→ 发放/修正
```

该目标结构保留现有可运行链路，同时把名称匹配、库存覆盖和收款重复等长期风险拆开治理。
生产任务、产品库存和销售出库按真实来源边界处理，不构造氚云并未提供的批次关系。
