## 用户最新明确范围（优先于下方历史建议）

- 本地仅补充跟单日期、说明和修订历史，重导不覆盖；不自动生成报工或库存单据。
- 已移除导航中的自建“生产任务单”“车间执行”“制程与工序管理”；旧路由跳到生产跟单，不沿用旧工单 ID。氚云导入中心的生产任务/报工等来源台账仍保留。
- 停止本任务内正式制造单、制造模板、产品配置 V330、报工和收货路线的扩展。已有并行修改和数据保留，不据此继续推进这条路线。
- 本轮仅收拢前端入口，未删除后端接口、权限或数据库表；旧后端仍存在，不能把隐藏菜单表述为后端已经下线。

## 当前建设结论（2026-09-22 再次现场复核）

本节是当前状态摘要；后文按建设过程留存，旧的“未部署”等表述不代表本节复核时状态。本次仅梳理，不删除代码或数据，不修改正在并行建设的正式制造功能。

### 当前唯一近期目标

以氚云导入的生产任务工单为基础，让跟单人员查看真实来源进度、补充跟进说明及日期，并查询修改历史。Excel 是工作方式参考，本轮不自动导入其行数据。当前借用氚云工单开展跟单，不等于已确定未来正式 ERP 永久依赖氚云。

### 混乱的具体原因

1. **两个工单体系同时建设**：氚云导入单与正式制造单彼此独立，V327 已撤回全量镜像；用户却在同一导航组看到跟单、车间执行、制程管理，容易理解为连续的一条流程。
2. **两套跟单后端并存**：V328 的 `/manufacturing/followup-board`、`/orders/{id}/follow-ups` 写正式制造单；V329 的 `/production-followups` 写氚云来源跟单。当前前端跟单页面只调用后者，前者仍暴露但没有对应的现行前端调用。
3. **三个“进度”混在一起**：氚云制程进度、跟单员按 Excel 阶段记录的日期、正式制造报工数量，不能互相直接替代。现有粗阶段仍按车间在代码中定义，不读取制程管理页面的模板。
4. **工程完成与业务验收混用**：单元测试、模拟页面测试、真实数据库、在线接口是四种证据；测试通过不表示跟单人员已拿真实工单完成业务验收。本地跟单目前仍 0 条。
5. **并行修改尚未收口**：当前工作区还有正式制造建单配置 V330 及对应代码变更，运行库尚未执行该迁移。其建设可以独立推进，但不应混入本期跟单发布包。

### 建议的收敛顺序（建议，不是已执行清理）

1. **确定一个日常操作入口**：本期只围绕“导入台账 → 生产跟单 → 跟进历史”验收。保留车间执行现有代码，停止把报工、SKU、正式收货作为本期跟单前置条件。
2. **明确重复实现的处置**：优先保留来源跟单这条线；确认没有其他消费者后退役 V328 的重复跟单 API。已应用迁移不回改、不直接删表，数据表清理另行验证。
3. **真实工单对拍**：取 3～5 张用户正在跟的工单，逐项对照氚云台账与 Excel：编号、车间、产品/尺寸、数量、交期、制程完成情况、延期说明。覆盖未完成、已完成缺日期、延期、模具/多件场景。未知或冲突字段显示待核对，不猜值。
4. **明确每个字段谁维护**：氚云负责导入原字段；跟单员负责本地说明/修订；系统仅依据明确规则计算倒计时。特别需要确认粗阶段是否手填、是否未来映射氚云制程，以及来源完工和本地日期冲突时如何呈现。
5. **按一个可回归版本交付**：分开记录“代码完成 / 数据库已应用 / 在线已更新 / 业务已验收”，将正式制造的并行变更独立提交和发布。验收重导不丢记录、无权限不能写、重复提交不重复、修订可追溯之后，再增加下一项功能。

### 本期验收终点

跟单员能从已导入的真实工单中找到自己当天跟的单，看懂来源进度，保存一次跟进；刷新与重导后仍能查到，其他获授权人员能看到一致内容。达到这个终点前，不把现有代码数量或迁移版本数作为“ERP 已建成”的依据。

## 跟单人员的操作

1. 在氚云导入中心导入生产任务工单；工单详情提供“查看跟单”入口。
2. 在生产跟单工作台按车间查看，支持完整工单号、产品名称、业务员、交期和跟单状态筛选。
3. 首次跟单时建立本地跟单记录，关联来源工单稳定标识；重复进入和重复导入不会产生另一份记录。
4. 填写计划开工、工序节点完成日期、预计完成日期、延期原因及本次跟进说明。
5. 可以修正误填日期或清空错误值，每次修改保留修改前后值、操作人、操作时间及原因。
6. 记录实际生产完成、入库和发货情况，后续继续追加跟进说明。

## 数据与计算约定

- 来源工单的完整编号、产品、规格、一出几、尺寸、数量、车间、业务员及原始要求日期提供只读对照。本地修订单独保存，重导不覆盖。
- 关联使用来源类型与外部唯一标识；工单号尾号只能辅助搜索，不能作为唯一关联键。
- 跟单节点采用表格中的车间阶段。它与细粒度报工工序不是天然一一对应；没有明确映射时不自动推算。
- 节点日期由跟单员记录时标明来源，不增加报工数量、不解锁工序、不生成库存流水。
- 原要求完成日期保留；修订预计日期可用于日常倒计时，但不能消除“已超过原交期”的提示。
- 实际生产完成日与入库日分开。交付评价按明确的实际生产完成日对比原要求日期；入库完成另外展示。表格把入库视作完工的公式不直接复制。
- 缺少原要求日期时显示“未设置交期”，不能显示“按期”。取消工单退出在办列表，但历史记录保留。
- 首期发货状态可作为跟单人员记录，须与正式出库单据区分；不自动生成销售出库。
- 无客户、无销售订单或尚未匹配 SKU 的来源工单仍可记录跟进，不把这些字段作为文字跟单的前置条件。

### 用户反馈后的来源核对与修正

用户指出跟单数据看起来不对。本轮只读检查运行库和 8081 跟单接口，确认运行库已执行到 V329：氚云 `production_orders` 共 5,691 行，本地 `production_followup_records` 为 0 行。页面读取的确实是氚云工单，不是 Excel 示例或正式制造工单。

发现上一版默认口径导致误解：按最早交期排序使 2025 年旧单占据首页；把缺实际完成日期等同于未完工，而来源有 12 张 `production_completed=1` 但日期为空的工单；已导入的数量和制程进度没有显示，却突出尚未填写的本地阶段日期。

修正如下：默认全部工单、按 ID 倒序，与氚云台账一致；保留未完成筛选和交期排序作为可选项。完成判定参考氚云完成标记、氚云完成日期及本地完成日期，源已完成缺日期不再误报超期未完工。展示氚云原单据状态、生产/入库进度及数量、申请/同步时间；详情展示来源 `production_order_components` 原始制程明细。粗粒度跟单日期明确标注为本地填写，不猜测细制程与粗阶段的对应关系。具有导入权限者可跳到台账按完整工单号核对。

运行库历史原值（如 200% / 400% 进度、异常交期）不在本次修复中改写。新增测试覆盖“完成标记有值但日期为空”和“台账排序一致、原始制程进度保留”。本轮没有新增数据库迁移；后端代码更新需重启运行实例才能生效。
