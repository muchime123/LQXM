# 车间执行段落地记录（工单 → 报工 → 交付收货）

日期：2026-09-21
上游：[ERP 决策登记](ERP决策登记-20260921.md) #4 / #10 / #12 / #13 / #14 / #16 / #17、[车间自治下的领料定位](车间自治下的领料定位-20260921.md)、[检验环节处置方案](检验环节处置方案-20260921.md)
范围：**只做制造数量闭环的报工段与收货段**。领料段经 #17 移出首批（车间自采自存），**本页与后端均不含任何领料/BOM/材料单位入口**。
性质：只写**已执行且可复核**的内容；未做到的一律列在 §5「未覆盖项」。

## 1. 结论

- 制造数量闭环的**报工段与收货段已经可操作**：工单 →（建单同事务）展开工序 → 报工 → 无检验工序时自动放行 → 交付收货 → 冲销。后端 **7 个写动作**全部接入 M0 契约（请求键 + 操作人 + 行级审计）。
- 验证过程中**发现并修复一个只在真库才暴露的生产缺陷**：审计写入器缺 Java 8 时间模块，导致 `changed_fields` 静默降级为 `{"_serializationError":…}` —— 审计行还在，但「改前改后是什么」全部丢失。已修复，并加了**永久回归断言**。
- 全量后端测试 **264/264 通过、0 跳过**（真库开关打开）；前端 e2e **3/3**；**正式库零污染**（`erp.idem_request` 0→0、`erp.row_change_log` 0→0、测试 schema 已 DROP）。

> **一句话经验**：接契约比写业务代码更容易出事。本轮真正的工作量不在报工/收货的 SQL，而在「让幂等与审计落到**正确的库**与**正确的事务**里」——这两件事做错都不会报错。

## 2. 交付清单

### 2.1 后端：7 个写动作接入 M0 契约

| 动作 | 接口 | 权限码 | 幂等 action |
|---|---|---|---|
| 建单 | `POST /api/manufacturing/orders` | `manufacturing.manage` | `manufacturing.order.create` |
| 展开工序 | `POST /api/manufacturing/orders/{id}/operations/generate` | `manufacturing.manage` | `manufacturing.operations.generate` |
| 报工 | `POST /api/manufacturing/orders/{orderId}/operations/{operationId}/work-reports` | `manufacturing.report` | `manufacturing.workReport.submit` |
| 冲正报工 | `POST /api/manufacturing/work-reports/{id}/reverse` | `manufacturing.report.override` | `manufacturing.workReport.reverse` |
| 登记检验 | `POST /api/manufacturing/orders/{id}/inspections` | `manufacturing.inspect` | `manufacturing.inspection.submit` |
| 交付收货 | `POST /api/manufacturing/orders/{id}/completion-receipts` | `manufacturing.receive` | `manufacturing.completionReceipt.post` |
| 冲销入库 | `POST /api/manufacturing/completion-receipts/{id}/reverse` | `manufacturing.receive.reverse` | `manufacturing.completionReceipt.reverse` |

**共同契约**（决策 #12 / #14）：`X-Request-Key` 必填（缺失即拒收，无键不直通）；命中须同时比对 `action` 与 `payload_hash`；操作人取自 `ErpActorResolver`（解析不出即拒绝，不产生占位操作人）；每个写动作在 `erp.row_change_log` 留行，与业务**同事务**双向回滚。

> 建单时「展开工序」在**同一请求键、同一事务**内完成，因此契约测试里只有 4 个 distinct action，而非 7 个 —— 这是有意设计（建单不完整就没有意义）。

### 2.2 前端：车间执行页

| 页签 | 内容 | 允许的写动作 |
|---|---|---|
| 执行看板 | 统计卡（总数/待执行/进行中/受阻/逾期/返工）可点击筛选；工序列表 | 报工、冲正报工 |

| 交付收货 | 待收货工单（`PENDING_RECEIPT` + `PARTIALLY_RECEIVED`）、已收货单 | 办理收货、冲销入库 |

- 页面头部**明写**「领料、BOM、材料单位由各车间自行管理，不在本页」（决策 #17），且**没有任何领料入口**（e2e 有断言钉死）。
- 报工弹窗展示「需求 / 已报 / 剩余」，超额时报错并要求勾选「允许超额报工」+ 填写超额原因；无 `manufacturing.report.override` 权限时**前端直接拦截**，不依赖后端兜底。

### 4.3 真库才暴露的生产缺陷（本轮修复）

**现象**：契约测试首次运行时，`changed_fields` 断言失败 —— 报工与收货的审计载荷是 `{"_serializationError":"InvalidDefinitionException"}`。

**根因**：`ErpChangeLogWriter` 由构造注入的 `ObjectMapper` 在**非 Spring 调用方**（测试直接 `new ObjectMapper()`）下**没有注册 Java 8 时间模块**。`changed_fields` 里只要有一个 `LocalDateTime`（报工 `reportedAt`、收货 `completedAt`），**整条载荷**就降级成失败摘要。

**为什么危险**：这类退化**不报错、也不缺行**。审计表行数正常、`operator_id` 正常、接口正常返回 —— 只有「改前改后是什么」静默消失。生产上只会在某天需要追责时才发现查不到内容。

**修复**：构造函数内 `objectMapper.findAndRegisterModules()`。对 Spring 容器传入的、已注册全部模块的 mapper 等价于空操作；对裸 mapper 则补齐。

**永久钉子**：契约测试加断言 —— 审计表里 `_serializationError` 行数必须为 0。将来任何新增审计字段带入新类型（`LocalDate`、`Duration`…）都会立刻红。
