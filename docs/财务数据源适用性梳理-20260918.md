## 1. 最关键发现：供应商台账与库内采购单**逐家分毫一致**

### 1.1 验证方法与结果

供应商明细每个 sheet 内含 `采购入库编号`（形如 `RK20260103008957`），与氚云已导入的 `purchase_receipts.source_no` **同源同格式**。

- 全文件抽取 RK 编号 **1,064 个** → 库内 `purchase_receipts` 命中 **1,064 / 1,064 = 100%**
- 逐供应商对拍「文件月度应付货款合计」vs「库内该供应商采购单 total_amount 合计」：

| 结果 | 家数 |
|---|---|
| **差额 = 0.00（逐家分毫一致）** | **32 家** |
| 有差异（已归因，见下） | 1 家 |
| 无 RK（当期无采购发生） | 24 家 |
| 物流/服务类（不经采购入库） | 11 家 |

**唯一差异「其他入库」差 11,810.00**：源文件 `其他入库` sheet 中 `RK20260103008958` 被**重复登记两次**（均为 4.4kw 空压机 2 台 / 合计 11,810），差额恰等于该重复额 → **属源文件重复行，非口径问题**。

### 1.2 这意味着什么（ERP 设计要点）

1. **`采购入库编号` 是已获验证的跨系统主键**。供应商身份不必走名称匹配（文件用的是内部简称：耀星/跃远/美时达…，60 家里仅 8 家名称命中），而应 **通过 RK 单号反查 `purchase_receipts.supplier_id`** ——实测可解析出 **34 家真实法人主体**（温州耀星包装有限公司 / 河南明鑫新材料有限公司 / …）。
   → **别名/简称不是障碍，因为有更强的业务键兜底。**
2. **这份文件恰好补上库内采购单"应付侧残缺"**。库内 `purchase_receipts` 的 `paid_amount` 全为 0、`unpaid_amount` = total_amount、`uninvoiced_amount` 全空 —— 而本文件提供 `付款日期 / 付款方式 / 付款金额 / 剩余货款 / 折让`。
   → **ERP 应付核销的权威来源在此，不在氚云。**
3. **「折让」是独立的一等业务概念**，不是四舍五入残差。例如耀星：应付货款 2,812,233.40 − 折让 9,945.90 = 合计应付 2,802,287.50。ERP 必须建独立折让字段与审批，不能并入"调整"。

### 1.3 口径公式（已实证）

```
文件「合计应付金额」 = Σ月度应付货款 − 折让
文件「剩余应付金额」 = 合计应付金额 − 合计支付金额
Σ月度应付货款      = 库内 purchase_receipts.total_amount 合计   ← 已验证一致
```

**规模**：61 家 → 合计应付 **1,091.4 万**、已付 **1,053.8 万**、剩余应付 **37.6 万**（含 3 家负余额：跃远 −34.0 万系预付/超付）。

**⭐ 核心价值：`供应商 / 客户 / 报销人 / 是否开票` 是人工标注**。银行原始流水（第 4 份）没有这些列 —— 它们是"这笔钱是谁付的、为什么、要不要开票"的业务语义，正是 ERP 资金模块最缺的部分。

### 2.2 结构性问题（ERP 设计必须处理）

1. **⚠️ 公私账户严重混用**：账户 sheet 同时包含
   - 公司账户：浙江利强×7、强子科技、安徽盒多多×2、安徽利强、温州永铭、浙江艺强、温州睿包×3、温州数创
   - **个人账户**：于清山×4、于帅帅×3、李南、李红伟×2、于士强×2、祁发红、宋文
   → **ERP 资金账户必须区分"公司主体账户"与"个人代收付账户"，并强制关联到公司主体 + 责任人。**
2. **⚠️ 至少 8 个法人主体**：浙江利强包装科技 / 温州强子科技 / 安徽盒多多塑业 / 安徽利强包装科技 / 温州永铭智能设备 / 浙江艺强机械 / 温州睿包国际贸易 / 温州数创。
   → 印证此前 DA1 决策「erp 独立 schema + 按主体隔离」的必要性；`owner_company_id` 是硬需求。
3. **「利强收银通」sheet（6,087 行）是另一类数据**：收单流水（交易完成时间/交易状态/交易金额/订单总扣费/付款人识别号/摘要/业务员），与账户日记账不同构，须拆成独立事实。
4. 汇总 sheet（64 行）是**资金年报表 + 资金日报表**，含 `#REF!` 断裂公式与 12-31 的未来日期占位 → **仅作口径参考，不入库**。

## 4. 各银行流水 vs 流水日记账：**互补而非重复**

| | 流水日记账 | 各银行流水 |
|---|---|---|
| 性质 | 人工登记的记账流水 | **银行原始导出** |
| 表头 | 38 sheet **统一 12 列** | 29 sheet，**各行格式不同**（工行 7 列 / 农行 10 列 / **中行 38 列** / 中信 22 列…） |
| 对手方 | 名称（人工填，93.9%） | 名称 **+ 对方账号** |
| 业务语义 | 供应商/客户/报销人/是否开票 | 无（仅摘要/用途/附言） |
| 用途 | 业务口径 | **金额与账号的校验基准** |

**⭐ 价值点：银行原始流水带对方账号**。日记账只有名字、名称命中率低（供应商 11.4%、简称不匹配），而银行侧有账号 → **账号可作为比名称更强的关联键**（与氤云「产品来源键」同思路）。建议：日记账靠业务键，银行流水靠账号，两者对账。

**⚠️ 银行流水表头异构是硬成本**：29 个 sheet 至少 15 种表头，必须**每行做"银行格式 → 统一字段"的映射**，不能一套表头解析到底（与`s 氚云导入` 的 `putHeader()` 同思路）。

## 6. 建议的落地顺序

**第一批（关键缺口，建议直接建导入）**
1. `各供应商明细` → 应付账款 + 折让 + 付款（**G1**，键 = 采购入库编号）
2. `流水日记账` → 资金日记账（**G1**，⚠️ 需先定"公私账户/多主体"建模）
3. `发票明细` → 进项 + 销项 + 收款核销（**G2**，键 = 数电发票号码）

**第二批（结构清晰、需先定建模）**
4. `退换货登记` + `机器退换货登记` → 合并为「退换货」一类（**G4**，两文件同构）
5. `利强采购下单表` → 采购订单
6. `封口机账单` → 机器发货明细

**第三批（体量大/表头异构，成本较高）**
7. `各银行流水` → 银行流水（**29 sheet × ≥15 种表头**，先做表头映射字典）
8. `各物流账单` → 物流费用 + 价格表（8 sheet 异构）
9. `店铺订单明细` → 电商订单（8 平台异构）
