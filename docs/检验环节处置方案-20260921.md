# 出厂检验环节处置方案（U4 收口）

日期：2026-09-21
触发：LQ 确认「**车间实际没有出厂检验这道动作（有人签字/打勾那种），只是车间人员在出厂之前进行机器调试，没有专门的签字打勾**」
结论位置：已写入 `ERP决策登记-20260921.md` **#16**（本文件为推导过程与实现依据）
影响：**P4 试点切片能否跑完闭环** —— 不处置则工单永远无法完工入库

---

## 1. 一句话结论

**不是"要不要建检验模块"的问题，是"已建成的检验闸门会卡死闭环"的问题。**

`manufacturing_inspections` 表、返工机制、三道检验工序全部**早已建成**，且**订单级检验被写成流程必经过渡态**。而车间没有检验岗、没有签字动作 → **工单会永久停在「待检验」**，无法进入「待收货/完工入库」。

**且这不是推演 —— 库里有一个活体证据。**

---

## 2. 关键发现：检验是「硬闸门」，不是可选装饰

### 2.1 决策链（`ManufacturingExecutionService.recalculate()`）

```
所有 required=1 的工序报工完成 (remaining == 0)
        ↓  硬编码，无条件
manufacturing_orders.status = 'PENDING_INSPECTION'
manufacturing_orders.inspection_status = 'PENDING'
        ↓  只能由 inspect() 推进
inspect() 要求状态 ∈ {PENDING_INSPECTION, PENDING_REINSPECTION}   ← 否则抛异常
        ↓
PASSED → status = 'PENDING_RECEIPT'（才能完工入库）
FAILED → status = 'REWORK'（返工）
```

`inspect()` 的硬约束（源码 `ManufacturingExecutionService.java:463-497`）：

- 只有 `PENDING_INSPECTION` / `PENDING_REINSPECTION` 才能调用，**无旁路**
- 必须填 `qualifiedQuantity + unqualifiedQuantity == plannedQuantity`（校验严格）
- 必须有人（`users.current()` → `inspector_employee_id` 必填）

> **即：没有检验员点这个按钮，工单就进不了 `PENDING_RECEIPT`，完工入库整段不通。**
> 这不是"少个模块"，是**闭环被一个不存在的岗位卡死**。

### 2.2 活体证据：`MO00000018` 卡了 17 天

```sql
SELECT id, order_no, status, inspection_status, planned_quantity,
       production_completed_at, inspection_at
FROM manufacturing_orders;
-- 18 | MO00000018 | PENDING_INSPECTION | PENDING | 1.000000 | 2026-09-04 10:23:09 | NULL
```

| 事实 | 值 |
|---|---|
| 工序快照 3 道 | 生产加工 → 整机装配 → **调试检验**，**全部 `COMPLETED`** |
| 报工 3 条 | `WR00000038/39/40`，全部 `VALID` |
| 最后一道「调试检验」 | **车间已按普通工序报工完成**（2026-09-04 02:23:09） |

> ⭐ **这张单子精确复现了真实场景**：车间把「调试检验」当普通工序做完了，**然后就没有然后了** —— 订单级检验没人做，也无法做。
> **「调试」这件事车间在做（有数据），「签字确认检验」这件事没有人做（永远为 0）。**

## 3. 三个方案对比

| | A. 末道工序报工即自动确认（**推荐**） | B. 删除/跳过检验状态 | C. 安排人每天点检验 |
|---|---|---|---|
| 车间是否需新增动作 | **否**（照旧报工） | 否 | 否 |
| 闭环能否跑通 | ✅ | ✅ | ✅（但依赖人肉执行） |
| 审计痕迹 | ✅ 自动写 `manufacturing_inspections`，记**调试人 + 时间** | ❌ 完全空缺 | ✅ |
| `manufacturing_inspections` 表 | 保留在用 | 变僵尸表 | 保留在用 |
| 返工机制 | **保留可用**（不合格时仍可触发） | 整条断掉 | 保留 |
| 未来增设检验岗 | **改 1 个字段即切换**，不动代码结构 | 需重建 | 天然就有 |
| 风险 | 需明确口径声明（见 §5） | 未来要"找回"检验，改动大 | 增加无效岗位动作，与事实不符；**且这条单子已证明没人会去做** |

**B 的问题**：`MO00000018` 证明流程不会自己走通；删掉检验状态等于把"将来可能要"的能力拆了 —— 而 `requires_inspection` 开关的存在说明设计者**本来就预期会有可/不可选两种形态**，删了可惜。

**C 的问题**：与 LQ 陈述的事实直接矛盾（**没有这个动作**），且实测 17 天无人处理。

## 4. 推荐方案 A：末道工序报工即自动确认

### 4.1 规则

> **订单的末道工序（`sequence_no` 最大且 `is_final=1`）报工完成时：**
> - 若该工序 `requires_inspection = 0` → **自动生成检验记录**（`PASSED`）并直接推进到 `PENDING_RECEIPT`
> - 若该工序 `requires_inspection = 1` → 维持现状，等人工 `inspect()`

**当前三道检验工序 `requires_inspection` 全 = 0** → 全部走自动确认。**语义天然自洽，零数据变更。**

### 4.2 实现要点

1. **改点只有一个**：`ManufacturingExecutionService.recalculate()` 里 `remaining==0` 的分支
   ```java
   // 现状（硬卡）
   if (remaining == 0) UPDATE manufacturing_orders SET status='PENDING_INSPECTION', ...

   // 改为：判定末道工序的 requires_inspection
   //   =0 → 写 manufacturing_inspections(PASSED, auto) + status='PENDING_RECEIPT'
   //   =1 → 维持 PENDING_INSPECTION
   ```

2. **自动记录的填法**（保留审计，不伪造"有人检验"）
   | 字段 | 值 |
   |---|---|
   | `inspection_result` | `PASSED` |
   | `qualified_quantity` | = 末道工序报工数量 |
   | `unqualified_quantity` | `0` |
   | `inspector_employee_id/name` | **末道工序报工人**（记事实来源，非"检验员"） |
   | `inspected_at` | 末道工序报工时间 |
   | `issue_description` | `自动确认：末道工序「组装调试」报工完成（本厂无独立检验岗）` |
   | `inspection_no` | `QI…`，**建议加 `A` 前缀或独立 `inspection_source='AUTO'` 列**便于筛分人工/自动 |

3. **建议新增 1 个字段**：`manufacturing_inspections.inspection_source ENUM('AUTO','MANUAL') DEFAULT 'MANUAL'`
   → 报表可一眼区分"自动事实记录"与"人工检验"（这对将来审计与口径澄清是刚需）

4. **不动的东西**（明确列出以免误改）
   - `manufacturing_inspections` 表结构（除新增 `inspection_source`）
   - `manufacturing_reworks` 返工机制（保留，人工检验启用后可用）
   - `manufacturing_operations` 14 道工序主数据
   - 7 条工艺路线的工序构成（**末道工序保持不变**，车间照旧报工）
   - `requires_inspection` 字段（**就是它承载切换语义**）

### 4.3 遗留数据处理

`MO00000018`（`PENDING_INSPECTION` / 卡 17 天）：属测试数据。
处置：**跑一次本方案的自动确认逻辑把它推到 `PENDING_RECEIPT`**，正好当第一个验收用例（也可直接作废重来，取决于是否要留作回归样本）。

## 5. ⚠️ 口径声明（必须写进文档与页面，否则以后会扯皮）

> **自动确认记录的语义是「工序完成事实」，不是「内控检验」。**

三条约束：

1. **页面/报表不得表述为"已检验合格"** —— 应表述为「**末道工序已完成**」。否则会给人"我们做了质检"的错觉。
2. **不适用"检验不能自检自"的内控要求** —— 自动确认的 `inspector` 就是报工人本人。这在**无检验岗**的前提下是可接受的，但必须写明白：**它不是内控意义上的检验**。
3. **对外/审计场景不要引用 `manufacturing_inspections` 作为质量证明** —— 它证明的是"这道工序做完了"，不是"这台机器合格"。

## 8. 复现用查询（全部只读）

```sql
-- 1. 卡住的工单
SELECT id, order_no, status, inspection_status, production_completed_at, inspection_at
FROM manufacturing_orders;

-- 2. 工序快照（确认三道全 COMPLETED）
SELECT sequence_no, operation_name_snapshot, required, reported_quantity, status
FROM manufacturing_order_operations WHERE manufacturing_order_id = 18 ORDER BY sequence_no;

-- 3. 检验开关（确认全为 0）
SELECT operation_code, operation_name, operation_category, requires_inspection
FROM manufacturing_operations WHERE operation_category IN ('INSPECTION','DEBUGGING');

-- 4. 路线末道工序
SELECT t.template_code, o.sequence_no, m.operation_name, m.requires_inspection, o.required, o.is_final
FROM manufacturing_process_template_operations o
JOIN manufacturing_process_templates t ON t.id = o.template_id
JOIN manufacturing_operations m ON m.id = o.operation_id
WHERE o.is_final = 1;

-- 5. 氚云侧工序（证明「组装调试」有数据、「检验」一项皆无）
SELECT component_name, COUNT(*) FROM h3_production_reports GROUP BY component_name;
```
