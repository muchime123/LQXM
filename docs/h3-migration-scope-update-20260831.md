## 新发现

### 库存快照

16,204条库存数量均可解析为数值：1,751条正库存、14,415条零库存、38条负库存。不同产品/单位不能直接相加成统一“库存总量”。

负库存不自动归零，也不直接作为正式期初放行；需要确认是否来自允许超卖、漏记入库、单位/产品映射错误或其他业务原因。这里尚未判定原因。

正式上线前需要：

1. 明确快照实际取数时点；文件名中的导出时间不能直接视为已确认盘点时间。
2. 将每条库存映射到既有产品的可交易规格、仓库和单位，核查重复余额键、未匹配产品和负数。
3. 到切换日重新取得或核对余额；期间库存变化不能遗漏。
4. 以一个可审计的期初批次写入数量余额，切换后的业务产生新流水；期初以前的出库/采购不得再次扣增库存。
5. 若首期需要库存估值，采购价格字段仅作来源参考，计价方法和期初成本另行确认。

接受的功能边界：本系统不能仅凭这张快照回答切换前每一次库存变化的原因。历史出库/采购可以查询，但不构成已验证、完整的历史库存总账。

### 客户恢复

当前 `H3FactImportService.enrichCustomerFromOutbound` 已能补空地址、解析联系方式并补业务员关系。~~`CustomerArchiveBackfillService`~~（2026-09-14 已删除：其聚合建索引逻辑对应的导入期能力保留在 `SourceIdentityService`/`H3FactImportService`，省市区解析并入 `ChinaAddressParser`）还会聚合出库、历史收款和生产台账，现有客户匹配包含按姓名建立索引的逻辑。

后续先进行只读质量核对：出库是否关联客户、同名是否误合并、联系方式是否混入经销商信息、历史地址是否应作收货快照。不能直接运行全量补档并覆盖人工维护信息；也不能把“有补档代码”当作“当前数据已经完整”的证据。

经销商188条用于补角色和来源映射，不另建与客户竞争的主数据，也不覆盖现有客户主体类型。

### 采购与开票

采购入库的产品明细里有6,433个非空“选择生产任务单”单元格，继续提示需区分外购和生产相关入库。付款明细仍没有显式子记录，不能从累计已付金额虚构付款凭据。

开票申请的红冲引用字段有459个非空显式单元格。这是字段填充数，不作为已完成红冲数量。历史申请、红冲关联与实际发票状态仍需分别处理。
