# 氚云导入全链路设计梳理

> 核对日期：2026-09-14　|　核对方式：逐类读后端 Java 源码 + 迁移脚本 + 前端路由/组件，与既有设计文档交叉验证
> 覆盖范围：从「上传氚云 Excel」到「客户档案 / 产品库存 / 生产接入 / 月度提成」的全部设计与不变量
> 关联文档：`docs/氚云导入中心统一设计.md`（A/B 管线统一）、`docs/h3-outbound-centered-redesign.md`（出库为中心）、`氚云数据全链路串联文档.md`（09-08 版全景）

## 0. 一页总览

系统接收氚云导出的 **6 类 Excel**，分成 **2 条导入管线**，共用 **1 套批次骨架**，落 **5 张事实/台账表**，再经 **1 层身份解析** 挂到 4 类稳定主数据上，最后由 4 个业务场景消费。

```text
                     氚云 Excel（6 类）
                            │
        ┌───────────────────┴───────────────────┐
        │                                       │
   业务事实管线（A）                        台账管线（B）
   H3FactImportService              ProductInventoryLedgerImportService
        │                                       │
  outbound  production  receipt  settlement   catalog  stock
        │        │         │         │            │       │
   sales_outbounds  production_     receipts   h3_product_  h3_warehouse_
   + _items         orders(+comps)                catalog      stock
   + _payment_
     snapshots
        │                                       │
        └──────────┬────────────────────────────┘
                   ↓  统一身份解析层（SourceIdentityService）
    Customer ── Employee ── SalesProduct ── Warehouse   （+ 各类 source alias）
                   ↓
   ┌───────────────┼───────────────┬──────────────────┐
 客户档案       产品库存        生产接入         月度提成
（出库反查）  （余额/流水）  （可选正式工单）  （出库收款快照）
```

**四条主线结论（改动时的判断依据）：**

1. **单一骨架、差异下沉**：登记/哈希幂等/异步解析/进度/落暂存/失败打标全部收口在 `BatchImportPipelineService`；`ImportKindDescriptor` 是六类数据源元数据的唯一事实源。两个域 Service 只保留"解析表头 + 分组 + 比对 + 写库"的差异。
2. **读合写分**：批次与台账的**读**端点统一到 `/api/h3-imports/**`（权限 `integration.h3` 或 `product_inventory.read` 任一）；**写**端点（stage/confirm）按域保留原前缀与各自 manage 权限。
3. **导入不猜身份**：自动绑定只处理"唯一命中"，其余一律进复核队列；人工结论落在领域映射表，重导时自动复用。
4. **口径隔离**：收款记录/多订单结清不参与提成与正式收款分配；生产历史接入不增加库存；仓库明细不进入原材料库存。提成的唯一权威来源是销售出库内嵌的收款快照 + 运杂费。

## 1. 六类数据源

元数据唯一事实源：`backend/.../service/ImportKindDescriptor.java`（枚举 6 常量）。

| 枚举 | route | data_type | 表头识别列 | 落库表 | 域 | 含子表 | 触发编排 |
|---|---|---|---|---|---|---|---|
| `OUTBOUND` | outbound | `OUTBOUND` | 销售出库编号 | `sales_outbounds` + `sales_outbound_items` + `sales_outbound_payment_snapshots` | 业务事实 | ✓ | ✓ |
| `PRODUCTION` | production | `PRODUCTION` | 生产工单流水号 | `production_orders` + `production_order_components` | 业务事实 | ✓ | ✗ |
| `RECEIPT` | receipt | `RECEIPT` | 流水号 | `receipts`（`receipt_type=SINGLE_OUTBOUND`） | 业务事实 | — | ✗ |
| `SETTLEMENT` | settlement | `SETTLEMENT` | 流水号 | `receipts`（`receipt_type=MULTI_OUTBOUND`） | 业务事实 | — | ✗ |
| `CATALOG` | catalog | `PRODUCT_INFO` | 无（固定列位） | `h3_product_catalog` | 台账 | ✗ | ✗ |
| `STOCK` | stock | `WAREHOUSE_STOCK` | 无（固定列位） | `h3_warehouse_stock` | 台账 | ✗ | ✗ |

## 2. 统一批次骨架

`backend/.../service/BatchImportPipelineService.java`（165 行，两个域 Service 共同委托）。

### 2.1 状态机与进度

| status | progress_stage | pct | 含义 |
|---|---|---|---|
| `UPLOADED` | `UPLOAD` | 0 | 批次已登记（只写批次头，不落文件字节） |
| `PARSING` | `PARSING` | 5→50 | 后台异步解析 Excel |
| `PARSING` | `STAGING` | 50→90 | 分批（200 条）落 `h3_import_staging_rows` |
| `PREVIEW_READY` | `PREVIEW` | 100 | 预览就绪，`preview_json` + `total_count` 已写；前端可确认 |
| `CONFIRMING` | `WRITING` | 5→95 | 从暂存写事实表 |
| `CONFIRMING` | `ORCHESTRATING` | 98 | 事实表写完，等编排收尾 |
| `COMPLETED` | `DONE` | 100 | 编排成功 |
| `PARTIAL_FAILED` | `DONE` | 100 | 编排有步骤失败（事实已落库） |
| `FAILED` | 失败时阶段 | — | 解析/落暂存阶段异常 |
| 编排中 | `ORCH_<STEP>` | 50→97 | 单步编排进度 |

**关键设计**：事实表写完**不立即置 COMPLETED**，而是停在 `CONFIRMING/ORCHESTRATING`，由异步收尾真正结束后才切终态。这样前端只看 `status` 就能判断"是否能进业务中心"，避免"编排还在跑却显示已完成"。

### 2.2 幂等

- **文件级**：`sha256(fileBytes)` 存 `file_hash`，命中 `(data_type, file_hash, status='PREVIEW_READY')` 即复用旧批次（`StageAccepted.hashHit=true`），不再解析。**COMPLETED 批次不复用**（数据已落库，旧预览计数已过期）。
- **事实级**：`external_source='H3YUN' + external_id`（氚云记录 ID）唯一，`ON DUPLICATE KEY UPDATE` 增量更新而非追加。
- **内容级**：`source_hash` 由归一后的业务字段算出，网页版与客户端的单元格格式差异不会造成伪更新。

### 2.3 失败打标

`markFailed`：`status=FAILED` + `progress_stage` + `error_message`（≤1000）+ `error_detail`（堆栈 ≤50 行、≤65535）。打标自身异常只告警不二次抛出。

### 2.4 暂存契约

`insertStagingRow(batchId, rowSeq, groupKey, externalId, sourceHash, mainJson, rowsJson)`，单条 `INSERT ... ON DUPLICATE KEY UPDATE`。
- A 域：`main_json` = 主表字段，`rows_json` = 明细行（产品明细 / 收款详细 / 制程）。
- B 域：整行放 `main_json`，`rows_json` 恒为 `[]`。

设计意图：**Excel 只解析一次**，预览与确认都从 DB 读，避免确认时重新解析大文件。

## 3. 解析层（A 域）

`backend/.../service/H3FactImportService.java`（1434 行）。

### 3.1 流式解析

氚云全字段出库单解压后可能 >1GB，`XSSFWorkbook` 会为每个空白/样式单元格建对象而 OOM。因此：

- 静态块放宽 POI 反 ZipBomb 保护：`IOUtils.setByteArrayMaxOverride(1_000_000_000)` + `ZipSecureFile.setMinInflateRatio(0.001)`；
- `parseXlsxStreaming`：`OPCPackage` + `XSSFReader` + `XSSFSheetXMLHandler`（SAX 事件模型）逐行读，`StreamingSheetHandler` 聚合分组；
- 错误文案做了人性化映射（"allocate an array"→提示拆分/精简导出字段；"not a valid ZipFile"→提示重新导出）。

### 3.2 分组与子表展开

氚云导出是"主子表扁平化"结构：一行 = 一条主记录 × 一条子记录（笛卡尔积），主子合并单元格留空。

- 分组键 `groupKey` = 该类的业务主键列（出库单编号 / 工单流水号 / 流水号）；
- `endRow` 只保留本行实际有值的单元格，避免上一条记录的值污染下一条；
- 出库单的 `rows` 里同时嵌了**产品明细**和**收款详细**两张子表 → 由 `saveOutbound` 与 `saveOutboundPaymentSnapshots` 各自按子表 ID 去重后落库（`收款详细.数据ID(不可修改)` 去重，笛卡尔积中同一笔收款重复出现只取有金额的那条）。

### 3.3 新/改/不变判定

`existingFacts`（按 external_id 预载现状）→ 逐组比较 `source_hash`：

| 判定 | 处理 |
|---|---|
| 无既有记录 | `CREATE` → `saveXxx` |
| 有记录且 hash 不同 | `UPDATE` → `saveXxx` |
| 有记录且 hash 相同 | `UNCHANGED` → 仅 `touch`（更新 `last_synced_at`）；出库另有 `syncUnchangedOutbound` |

> `syncUnchangedOutbound` 存在的原因：`source_hash` 只说明**氚云源记录**没变，不能保证本地派生/历史修复没改写主表金额。所以出库的收款主表值以本批原始快照为准重新同步，但**不计入本批 UNCHANGED 之外的动作统计**。

### 3.4 确认写库

`confirmFromStaging(batchId)`：

1. 幂等短路：已是 `CONFIRMING/COMPLETED` 直接返回缓存统计；非 `PREVIEW_READY` 抛"批次不在可确认状态"。
2. `status='CONFIRMING' / WRITING / 5`。
3. 逐组写库，每 100 组推一次进度。
4. 写 `h3_import_rows` 行级原始快照（`saveImportRow`，含 `raw_data`，用于事后反查）。
5. 写回统计：`created/updated/unchanged` + `missing_customer_count / missing_date_count / missing_quantity_count`（缺客户/缺日期/缺数量的行数，质量提示）。
6. `status='CONFIRMING' / ORCHESTRATING / 98`。
7. 注册 `TransactionSynchronization.afterCommit()` → 触发 `H3PostImportAsyncService.run(...)`。

**确认阶段只写事实表，不做任何同步编排**（P2 改造），HTTP 事务不承担对账工作。

### 3.5 出库单的特殊处理

`saveOutbound` 是整条链路的枢纽，逐项：

| 步骤 | 说明 |
|---|---|
| 客户名回退解析 | 氚云用户常把姓名写进「联系方式」/「客户信息」而空着「客户名称」→ `resolveOutboundCustomerName(m)` 回退 |
| 客户身份 | `customerId(name, address, phone)` → `SourceIdentityService.resolveCustomer` 三级重载 |
| 员工 | `memberEmployeeId("业务员(必填)")` → `employees.id` |
| 仓库 | `h3WarehouseId("选择出库仓库")` → 先查 `h3_warehouse_name_mappings`，再查 `warehouses` 唯一精确名 |
| 单号冲突释放 | 新建时若 `outbound_no` 被别的记录占用，先 `clearConflicts` 释放，避免触发 `uk_so_no` 误更新 |
| 主单写入 | 44 列 `INSERT ... ON DUPLICATE KEY UPDATE`；`employee_id`/`warehouse_id` 用 `COALESCE(employee_id, VALUES(...))` — **人工结论不被重导覆盖** |
| 明细重建 | 先 `DELETE FROM sales_outbound_items WHERE sales_outbound_id=?` 再全量重插 |
| 行类型 | `line_type` ∈ `PRODUCT` / `SERVICE`（费用类目）/ `FREIGHT`（费用类目且名称含"运费"）；仅 `PRODUCT` 行调 `resolveProduct` 填 `sales_product_id` |
| 客户档案补全 | `enrichCustomerFromOutbound(customerId, m)` + `enrichCustomerFromProduction` |
| 收款快照 | `saveOutboundPaymentSnapshots(id, g)` → `migration_batch='LIVE_IMPORT'` |
| 出库性质推断 | `outboundNatureService.refreshInference(id)` — 推断 SALE/RETURN/EXCHANGE 并分栏保存，不覆盖人工结论 |
| 利润重算 | 仅当 `数据状态` 归一到 `CONFIRMED` 时 `outboundProfitService.recalculate(id, "氚云导入联动")` |

## 4. 身份解析层

`backend/.../service/SourceIdentityService.java`（2308 行）。核心模型：

```sql
source_identity_aliases(
  source_system, entity_type,     -- H3YUN / CUSTOMER|EMPLOYEE|PRODUCT|WAREHOUSE
  source_key, source_name, normalized_name,
  target_id, resolution_status,   -- AUTO | CONFIRMED | REVIEW | IGNORED
  issue_code, confidence, resolution_note,
  occurrence_count, updated_at
)
```

统一读取入口 `resolvedTarget(entityType, sourceKey, sourceName)`：只认 `resolution_status IN ('AUTO','CONFIRMED')` 且 `target_id` 非空、**且唯一**。`saveDecision` 写入时对已 `CONFIRMED` 的行做保护（`IF(resolution_status='CONFIRMED', 原值, 新值)`），所以**人工确认结论永不被自动推断覆盖**。

### 4.1 客户识别（`resolveCustomer(name, address, phone)`）

按设计文档 §2「客户档案」定的优先级：

| 序 | 依据 | 置信度 | 命中后 |
|---|---|---|---|
| ① | `customer_source_cluster_mappings` 已确认簇（名称+地址/电话簇） | — | 直接返回 |
| ② | 名称级已决策结论复用（`resolvedTarget`）；已 `REVIEW`/`IGNORED` 的直接返回 null | — | 直接返回 |
| ③ | **标准化电话精确一致** | .99 | 自动绑定 |
| ④ | 客户名称 ∩ 电话 组合唯一 | .97 | 自动绑定 |
| ⑤ | 客户名称 ∩ 标准化地址 组合唯一 | .95 | 自动绑定 |
| ⑥ | 仅名称 | — | 只给候选，不自动合并 |

**边界（红线）**：
- 电话命中多个客户且名称收敛不了 → `REVIEW / AMBIGUOUS_CUSTOMER_PHONE`，不绑定；
- 泛化名称（`genericCustomerName`：王先生/李经理/客户…）不参与名称级比对 → `REVIEW / GENERIC_NAME`；
- 三级重载 `resolveCustomer(name)` / `(name,address)` 用于非出库场景，行为更保守（互为子串候选即停）。

### 4.2 产品识别（`resolveProduct(code, name, spec, unit)`）

1. `resolvedTarget("PRODUCT", sourceKey, name)` 命中已确认映射 → 返回；
2. `sales_product_source_aliases` 按 `source_product_code` 且 `resolution_status='RESOLVED'` 唯一命中 → 自动保存决策并返回；
3. `sales_products` 按 `名称+规格+单位` 三项全等唯一命中 → 返回；
4. 否则写 `REVIEW`（`PRODUCT_NOT_FOUND` 或 `AMBIGUOUS_PRODUCT`），**返回 null**。

> **绝不在出库导入过程中静默新建产品**——这是"未归类不阻塞销售金额和提成"的实现方式。

**来源键（三处必须同口径，改一处必须同步另两处）：**

| 位置 | 形式 |
|---|---|
| `SourceIdentityService.productSourceKey`（Java） | 有编码取 `code.trim()`；否则 `'NAME\|' + SHA256(归一名称\|归一规格\|归一单位)` |
| `OutboundRelationGovernanceService.PRODUCT_KEY_EXPR`（SQL） | `COALESCE(NULLIF(TRIM(i.product_code),''), CONCAT('NAME|',SHA2(CONCAT_WS('|',lower+去空格 名称/规格/单位),256)))` |
| PRODUCT 归类回填语句 | 同上 |

### 4.3 员工与仓库

- 员工：`EmployeeExternalImportService` 导入氚云/钉钉通讯录的真实外部 ID → `employee_external_mappings`（`SOURCE_H3YUN` / `DINGTALK`）；出库导入时按姓名映射，结论可复用到同名来源记录。氚云链路原有 `salesperson_id → company_team_members.employee_id` 桥接，无桥接时按姓名兜底。
- 仓库：`h3_warehouse_name_mappings(source_name, warehouse_id, match_method, confirmed_by)`；出库导入先查映射表，再查 `warehouses` 唯一精确名（`V291` 新建，同时给 `sales_outbounds` 加 `warehouse_id`）。

## 5. 销售出库关联工作台

页面 `/h3-outbound-relations`（`views/governance/H3OutboundRelationView.vue`），**替代已下线的泛化"身份解析"**。一行 = 一张销售出库，围绕业务单展示客户/员工/产品/仓库四类关系与完整度，可按"仅看缺客户、缺员工、缺产品、缺仓库"筛选。

`OutboundRelationGovernanceService`（789 行）+ `H3BusinessQueryService.outboundRelations`。

**自动绑定边界**：只有**唯一精确命中**才自动绑定，多候选一律不处理。

| 动作 | 端点 | 逻辑 |
|---|---|---|
| 员工/仓库精确关联 | `GET /outbound-relations/exact-preview`、`POST .../exact-apply` | 姓名唯一命中 → 写 `employee_external_mappings`；仓库名唯一命中 → 写 `h3_warehouse_name_mappings`；随后回填出库 `employee_id` / `warehouse_id`。**已 SETTLED 提成的出库不改 employee_id** |
| 客户安全关联 | `GET /outbound-relations/customer-preview`、`POST .../customer-apply` | 电话优先的安全匹配（已确认簇 → 电话唯一 → 名称级结论复用） |
| 新建客户簇 | `GET /outbound-relations/new-customer-preview`、`POST .../new-customer-apply`（另需 `customer.manage`） | 按电话集合聚类建客户，一个客户保留全部电话 |
| 客户异常 | `GET .../customer-exceptions` | 冲突/无法判断项 |
| 多电话 | `GET .../multi-phone-preview`、`POST .../multi-phone-apply` | 一个来源客户对应多个电话的合并 |
| 产品归类 | `GET .../product-preview`、`POST .../product-apply` | 按来源编码优先、名称规格单位辅助，只对唯一命中给建议 |
| 全链路验收 | `GET .../acceptance` | 见 §12 |

> **排序规则坑**：本库历史表 `utf8mb4_unicode_ci`、新表 `utf8mb4_0900_ai_ci`，**两个列直接比较会报 ERROR 1267**。所有列与列比较统一写 `LOWER(CONVERT(TRIM(x) USING utf8mb4))`，不要写死 `COLLATE`（MySQL 5.7 会语法失败）。

## 6. 客户建档与地区解析（2026-09-14 落地）

  province, city, district, address, relation_status, status, remark, created_at, updated_at)

- 客户编号 `CUS%06d` 带序号缓存（`nextCustomerCodeSeq`），批量建数千客户时不再逐条扫全表最大值；`DuplicateKeyException` 时 `resyncCustomerCodeSeq()` 重试（≤5 次）。

### 地址解析两级 API

| 方法 | 特性 |
|---|---|
| `ChinaAddressParser.parse()` | 正则切分，要求城市名带「市/自治州/地区/盟」后缀。**对完整地址里的长数字、公司名、电话干扰敏感，容易退化**（同一地址截短反而能解析对） |
| `ChinaAddressParser.parseLoose()` | `parse()` 不完整时用**区划字典对原文做文本扫描**兜底；**批量解析/诊断一律用它** |

`parseLoose` 的兜底防误判三板斧：
1. 全名优先于主干（长名优先）；
2. 区县主干与城市同名则跳过（`长沙市` ≠ `长沙县`）；
3. 排除「新区/城区/东区/开发区/工业区」等泛化主干；城市与省不符时按省重扫（`安徽省马鞍山市` 不再切成 `鞍山市`）。

### 客户地区治理口径（定稿，勿回退）

- **「未标注区域」= `province` 为空或不是官方省名**（上不了地图），与市/区县是否完整无关。
- 省份已合法但市/区县缺失或异常 → `PARTIAL`「待补市县」，列表筛选用 `regionPartial=true`，**不得再计入未标注**。
- `address_tidy_status` 取值：`NORMAL / NO_ADDRESS / MISSING / MISMATCH / PARTIAL / UNCLEAR / UNRECOGNIZED`。
- 批量解析是「能补多少补多少」：省必须是官方省名否则整条不写；市/区县能过校验就补、过不了留空；**按列写回，只填空或非法值，已有合法值不覆盖**；只有「档案省份合法且与解析省不一致」才整条否决。
- 县级市可当市级：有父地级市→父市（江阴市→无锡市）；省直辖→自身（仙桃/潜江/天门/济源/海南县级市）；区县允许与市同名。
- `CustomerRegionService.diagnose(address)` 是**唯一判定入口**（批量解析与 CSV 导出共用），返回 `ParseResult(省,市,区县,失败原因)`；分布弹窗计数与列表筛选必须同口径（都是省级判定）。

## 7. 确认后编排与异步收尾

### 7.1 异步入口

`H3PostImportAsyncService.run(scope, batchId, trackChanges)`（`@Async("h3ImportExecutor")`）：

1. `orchestrator.orchestrateAfterImport(scope, batchId)` → 按 `stepsFailed` 决定 `COMPLETED` 或 `PARTIAL_FAILED`，置 `progress_stage='DONE' / pct=100 / completed_at`；
2. 编排整体抛异常 → `PARTIAL_FAILED` + `error_message='自动编排异常：...'`；
3. `trackChanges`（仅出库批次）→ `commissionCalculationService.trackOutboundChanges(batchId, ids, "导入后自动识别")`，识别"已核算后又变化的出库"，写 `commission_outbound_changes`。

### 7.2 编排步骤矩阵

`H3ImportOrchestratorService.stepsFor(FactType)`：

| FactType | 步骤 |
|---|---|
| `OUTBOUND` | `REBALANCE_OUTBOUND_SNAPSHOTS` |
| `PRODUCTION` / `RECEIPT` / `SETTLEMENT` | 空（不触发回款一致性编排） |

`REBALANCE_OUTBOUND_SNAPSHOTS`（`OutboundBalanceService.reconcileAndRefresh`）：删除旧 `AUTO_BALANCE` 行 → 按主表补/冲差额行 → 刷新派生结算状态。这是"收款单一权威"的一致性守护。

**已下线的历史步骤**（避免误以为还在）：`REFRESH_OUTBOUND_SNAPSHOTS`、`INCREMENTAL_MATCH`、`INVALIDATE_LINKS`、`REFRESH_BUSINESS_AGG`、`MARK_OUTBOUND_PROFITS_PENDING`、收款分配相关三步。

**单步隔离**：每步用 `PROPAGATION_REQUIRES_NEW` 独立事务；单步失败不中断整体，异常写 `StepOutcome.errorSummary` 与批次 `error_message`；每步完成后推 `ORCH_<STEP>` 进度（50→97）。

**结果持久化**：编排结果序列化进 `h3_import_batches.preview_json` 的 `orchestration` 字段（超过 4MB 时裁剪 steps：保留前 3 + 末 1，中间插 `TRUNCATED` 占位）；随后 `BatchCandidateStatsService.refresh(batchId)` 刷新候选统计缓存。

## 8. 产品库存台账与合并入库

### 8.1 台账管线（B）

`ProductInventoryLedgerImportService`（593 行），同样委托 `BatchImportPipelineService` 走登记→异步解析→暂存→预览→确认；差异在于：

- 无表头识别（固定列位）；
- 确认是**同步单事务**（`SELECT ... FOR UPDATE` 锁批次 → 增量写台账 → `COMPLETED/DONE/100`），无中间态、无快照、无编排；
- 返回强类型 DTO（`StageAccepted` / `LedgerImportPreview` / `Result`，`childCount` 固定 0）。

**只增改不覆盖**：按产品编码 / (仓库+产品编码) 逐行比对后增量写。

### 8.2 合并入库（B2，无文件无批次）

`ProductInventoryMergeService.preview()` → `confirm(items)`。

**行状态判定（只对 READY 行执行确认）：**

| 情况 | 状态 | issue |
|---|---|---|
| 产品编码找不到产品信息 | REVIEW | `PRODUCT_NOT_FOUND` |
| 采购价空或 ≤0 | REVIEW | `PRICE_MISSING` |
| 仓库名无法匹配 | REVIEW | `WAREHOUSE_MISSING` |
| 产品、仓库、价格齐全 | READY | — |
| 费用/制版费/税点/运费类目、数量为 0、数量为负 | 跳过（负数计入异常） | — |

**写入语义 = 目标值语义**（仓库明细是氚云某一时点的库存结果）：

- 无余额 → 创建，变化量 = 导入数量；
- 数量或价格不同 → **修正为目标值**（不是累加）；
- 完全一致 → 忽略，不写重复流水；
- 实际创建或修正都写 `product_inventory_transactions`，可追溯变化前后。

链路：`h3_product_catalog` + `h3_warehouse_stock` → `ProductInventoryMergeService` → `sales_products`（产品归类）+ `product_inventory_balances` → `product_inventory_transactions`。

## 9. 重导与全量重置

### 9.1 重导幂等（设计契约）

- 相同氚云业务 ID 更新同一条销售出库；
- `source_hash` 只比较**归一后的业务字段**，不因网页版/客户端单元格格式差异触发伪更新；
- **人工结论不随重导丢失**：客户/员工/仓库/产品结论落在领域映射表，导入时先恢复结论再生成待处理项；
- 写库语句对人工列使用 `COALESCE(现有值, VALUES(...))`（`employee_id`、`warehouse_id`），已填值不被覆盖。

### 9.2 全量重置（`H3ResetService` + `V289`）

三步式，**删除必须带令牌**：

| 端点 | 作用 |
|---|---|
| `GET /h3-imports/reset/preview` | 只读影响预检 |
| `POST /h3-imports/reset/prepare` | 保存稳定业务键与人工治理结论到 `h3_reset_identity_snapshots` / `h3_reset_outbound_nature_snapshots`，发 `reset_token` |
| `POST /h3-imports/reset/execute` | 校验令牌后事务化删除来源数据 |

`execute` 用临时表（`tmp_h3_reset_outbounds/productions/receipts`）圈定 `external_source LIKE 'H3%'` 的记录，级联清理 `expense_allocations`（`target_type='SALES_OUTBOUND'`）、`product_inventory_transactions`（`source_type='OPENING' AND source_no='MERGE-IMPORT'`）等，再删三张事实表。

## 13. 不变量与红线（改动前必读）

1. **产品来源键三处同口径**：`SourceIdentityService.productSourceKey`（Java）、`OutboundRelationGovernanceService.PRODUCT_KEY_EXPR`（SQL）、PRODUCT 归类回填语句。改一处必须同步另两处，否则重导后人工结论无法复用。
2. **排序规则**：列与列比较统一 `LOWER(CONVERT(TRIM(x) USING utf8mb4))`；不写死 `COLLATE`。
3. **自动绑定只处理唯一命中**；多候选、泛化客户名一律 `REVIEW`；已 `CONFIRMED` 的映射不被自动推断覆盖。
4. **出库单/员工/仓库/产品的人工结论写在领域映射表**，不写在会被重导覆盖的事实行里。
5. **提成唯一来源**：`sales_outbound_payment_snapshots`（`receipt_date` + `CONFIRMED`）+ `sales_outbounds.freight`。独立收款台账、多订单结清、订单利润、产品库存均不进提成公式。
6. **库存只由流水产生**，余额是流水的当前结果；仓库明细是目标值语义的校准，不累加。
7. **历史台账只读**；所有关系修改集中在销售出库关联工作台。
8. **产品未归类不阻塞**销售金额与提成，只标记为产品/库存统计待治理。
9. **事实表写完不等于批次完成**：终态由异步收尾决定（`COMPLETED` / `PARTIAL_FAILED`）。
10. **客户建档即带省市区**（`createPendingCustomer`），不要再新增事后全量回填服务。

## 14. 特意隔离 vs 已连通

**已连通**：出库 → 客户档案 → 出库历史 → 统一详情抽屉；出库收款/运杂费 → 提成实时参考 → 待核算 → 正式版本；出库重导 → 已核算来源变化跟踪；产品信息 + 仓库明细 → 复核 → 正式产品库存与流水；生产任务 → 正式制造工单接入关系；六类事实 → 导入中心历史台账。
