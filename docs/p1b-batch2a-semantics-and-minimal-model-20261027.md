# P1-B 批次 2-A（二）：旧规格语义归属与最小模型建议（2026-10-27）

> 性质：**设计建议（不建表、不改代码、不迁移数据）**。事实底座见 `docs/p1b-batch2a-model-capability-inventory-20261027.md`。
> 前提：批次 1 已完成并推送；本轮只回答「已有模型能表达什么、缺什么、要不要补」。
> 仍遵守：官网独立内容模型（方案 A），不新增第三套内部规格体系。

---

## 1. 四个架构问题的答案

### 1.1 机型档位与可选配置是不是同一件事？——**不是，数据支持区分**

| 概念 | 定义建议 | 现有载体 | 实证 |
|---|---|---|---|
| **机型档位** | 设备型号 + 规格等级 + 相对稳定的技术/适配参数 | `product_machine_tiers`（`tier_code` 330/390/500 + 圆口直径范围 + 方盒长宽范围） | 3 个档位是按**封口尺寸范围**划分的，不是按模具组合划分 |
| **可选配置** | 同一机型下可选择的模具形状、腔数（一出几）、附加功能等组合 | 现状：内部**没有**「机型 × 模具组合」的正式关系；旧规格用文字标签表达（889/890/892） | 4 条旧规格**全部挂在同一个档位（330）**下 → 实证支持「330 可配方模一出一 / 方模一出二 / 圆模一出一，不必建四个档位」 |

结论：**机型档位 = 设备能力与适配范围；可选配置 = 模具与包材形状的组合能力**。两者不应合并，也不应在内部新建「配置档位」。

### 1.2 方模 / 圆模 / 一出一 / 一出二的语义归属

| 信息 | 建议归属 | 依据（实勘） | 确定性 |
|---|---|---|---|
| **一出几** | **模具属性**：`packaging_molds.cavity_count`（模具穴数） | 数据分布 1–65（3/6/8 穴为主），与 `mold_code` 后缀一致（`M20708-8F` → 8 穴） | 高 |
| **方模 / 圆模** | **由被封口盒型决定**：`packaging_variants.shape_type`（round/oval/square/rectangle/irregular）与 `packaging_mold_groups.shape_type + normalized_key`（`RECT:141x141` / `ROUND:178.7`） | 478 条包材规格显式带形状；模具侧 `mold_type_code` 仅 F/FG/FW 有关联可验证（F→方/长方 62 条、FG/FW→圆 各 1 条），W/B/G/WJ 无关联 | 中高（形状事实在包材侧更完整；模具侧类型码需业务确认） |
| **设备型号** | `ProductMachineTier.tier_code / tier_label` | 330 / 390 / 500，含圆口与方盒适配范围 | 高 |
| **产品宣传名称 / 展示文案 / 展示用技术参数** | **官网独立内容模型**：`website_products`（`technical_parameters` JSON）与 `website_product_variants`（`name / public_sku / dimensions / technical_parameters`） | 两张表已建且为 0 行，属方案 A 既定方向；官网「技术参数」「可选规格」区块当前读的字段接口并不输出，恒不渲染 | 高 |

**关于「一出几」的归属限定说明（你特别要求核实）**：
`cavity_count` 表达的是**模具本身一次出几个型腔**，这是模具事实；但机器上「一次封几盒」还受**机型可封口尺寸范围**（`product_machine_tiers` 的 round/rect min-max）与工艺限制约束。
因此准确表述是：**「一出几」= 模具事实（`cavity_count`），能否在该机型上使用 = 由机型适配范围 + 模具腔数共同决定**。这意味着它不需要第三种模型——现成的两个事实字段组合即可推导，缺的只是「是否需要在内部把这种组合显式登记下来」（见 §2 方案 B）。

### 1.3 现有模型是否足以承接 26 条素材？——**足以承接，且已经承接**

- 26 条素材**同时拥有**：产品级（`model_id`）、旧规格级（`variant_id`）、**机型档位级**（`machine_tier_id` 列 + `product_asset_machine_tier_links` 多对多，均指向 330 机型，由 `V124:13-14` 于 2026-08-21 回填）。
- 因此批次 2-B 的实质动作只有三项：
  1. **默认图 4698 裁定（前置阻断项）**：4698 挂在规格 889 上且是默认图，另一个默认图 5221 是产品级主图；`defaultImageOwnerType` 按素材 `variant_id` 是否为空派生。**未经业务确认不得自动切换默认图**。
  2. 4698 处置完成后，决定是否清理 `variant_id`（倾向清理，使归属收敛到产品级 + 机型级）。
  3. 明确两套机型归属机制（`machine_tier_id` 单值列 vs `product_asset_machine_tier_links` 多对多）以哪个为准，避免长期双写。
- **不建议**新增「模具级 / 配置级素材」归属：当前没有业务诉求，且模具 `website_enabled` 全为 0（模具不对外展示）。

### 1.4 官网与内部产品中心如何分离？——沿用方案 A，本轮只定边界

```
内部产品中心（事实）                 选择 / 审核 / 发布            官网独立内容模型（展示权威）
product_models（身份与分类）   ─┐
product_machine_tiers（型号+适配范围）─┤                          website_products（名称/摘要/正文/
packaging_molds（穴数=一出几）      ├─→ 人工选择 + 审核 + 发布 ─→   technical_parameters JSON / 媒体）
packaging_variants|mold_groups（形状）┤                          website_product_variants（可选配置）
product_assets（素材，含机型归属）   ─┘                          website_media_assets（官网媒体）
```

- 官网**不直接读**内部表作为长期权威源；内部提供事实参考，经选择审核后**写入官网自己的表**。
- 本轮不设计同步机制；只确认映射对象（机型型号/适配范围 → `technical_parameters`；模具形状+腔数组合 → `website_product_variants`）。
- 现状利好：`website_products`、`website_product_variants`、`website_media_assets` 均已建成且 0 行，官网三个相关区块（技术参数 / 可选规格 / 兼容适配）今天都不渲染 → 切换不会造成可见回退。

## 2. 三个方案对比

### 方案 A：完全复用现有机型档位与模具模型（**推荐，优先评估**）

内容：
- 设备型号与适配范围 → `product_machine_tiers`（现状即如此）；
- 一出几 → `packaging_molds.cavity_count`；
- 方模/圆模 → `packaging_variants.shape_type` / `packaging_mold_groups.shape_type`；
- 官网展示配置 → `website_product_variants`（已建表，人工维护）。

| 维度 | 评价 |
|---|---|
| 数据迁移影响 | **最小**。26 条素材无需新建归属（已有机型归属）；只需处置默认图 4698 与可选清理 `variant_id` |
| 维护成本 | **最低**。不新增表、不新增写入口；旧规格退役后语义不丢失（方/圆、一出几都有现成权威字段） |
| 官网边界 | ✅ 完全符合方案 A：官网配置内容落在 `website_product_variants`，内部只提供事实 |
| 对 26 条素材的承接 | ✅ 产品级 + 机型级已可承接 |
| 代价 / 缺口 | ① 机型档位覆盖度低（49 个产品中仅产品 67 有 3 档；机身尺寸/重量字段全 NULL）；② 内部**无法枚举**「某机型可选哪些模具组合」，只能靠人工在官网侧录入；③ `MachineTierView.variantCount` 仍按旧规格计数，需随退役清理（属语义污染，非新需求） |

### 方案 B：复用现有模型 + 仅补充缺失的「关系或字段」（**A 不足时的首选**）

触发条件（满足其一才考虑）：
1. 业务需要在**内部系统**里回答「330 机型可以选哪些模具组合」（例如报价、选型、生产配置依赖）；
2. 需要把「方模/圆模」沉淀为**模具自身的显式属性**（当前模具侧类型码证据不足，需业务先确认 F/W/B/G 等类型码含义）。

可能的补充（二选一，不新增规格主数据）：
- 一张关系表（如「机型 × 模具可用组合」）或扩展现有关联，补齐「机型 × 模具」这层缺失；
- 或给 `product_machine_tiers` 补「支持腔数范围 / 支持形状」等字段。

| 维度 | 评价 |
|---|---|
| 数据迁移影响 | 中：需一次性补录组合关系（当前无任何「机型×模具」数据，全部要人工/导入建立） |
| 维护成本 | 中：新增一张表或若干字段，需要新的维护入口与校验 |
| 官网边界 | ✅ 仍可保持：内部关系表只服务内部选型，官网侧仍写 `website_product_variants` |
| 对 26 条素材的承接 | ✅ 不受影响（素材归属与组合关系正交） |
| 风险 | 若补充的是「枚举组合」而非「事实字段」，很容易在几年后变成新的难维护规格体系 → **只补关系/范围，不补枚举规格** |

### 方案 C：建立新的内部配置模型（**不建议**）

| 维度 | 评价 |
|---|---|
| 数据迁移影响 | 大：需把「方模/圆模 × 一出几 × 机型」重新建模并迁移，而这三个事实在现有库里已有权威来源 |
| 维护成本 | 高：第三套配置体系，与机型档位、模具、包材形状并存，语义重叠 |
| 官网边界 | 反而更差：容易让官网重新依赖内部新表 |
| 结论 | **仅在 A、B 都无法表达真实业务关系时才考虑**。目前没有出现 A、B 无法表达的关系 |

## 3. 建议路径（最小可行）

1. **内部侧采用方案 A**：不新增表；机型档位承担型号与适配范围，模具承担腔数，包材承担形状。
2. **官网侧采用已建好的 `website_products` / `website_product_variants`**：把「可选配置」作为**官网可独立编辑的展示内容**，内部事实只作为录入参考。
3. **旧规格语义保留但不依赖**：退役 `product_variants` 前，把 889/890/892 三条的「方/圆 × 一出一/一出二」语义**转写为可检索、可理解的内容**（官网 `website_product_variants` 的 `name/description/technical_parameters`，或素材 `tags`），确保历史资料不丢；这属于批次 2-B 的素材语义承接事项。
4. **仅当业务确认需要「内部可枚举机型×模具组合」时，再走方案 B**，且只补关系/范围，不补枚举规格。
5. 随退役一并清理的语义污染（后续批次，不在本轮）：`MachineTierView.variantCount` 按旧规格计数、机型界面展示的「配置数」、`ProductVariantFileAssetAdapter`、`CatalogTrashService` 的规格回收站方法族、`ArchiveScheduler:72` 的 `product_variants_archive` 归档。

## 4. 本轮明确不做（沿用你的禁令）

- 不迁移 26 条旧规格素材；

- 不调整官网完整度评分算法；
- 不修改官网「可选规格」页面；

- 不因模型设计问题重新打开批次 1（除非出现真实功能回归）。

## 5. 需要业务/你拍板的问题（不代为决定）

1. **模具类型码 `mold_type_code` 的业务含义**（F / W / B / FB / FW / FG / G / WJ）：它是否就是「方模/圆模/碗/…」的分类？若业务确认，则方/圆可落到模具侧；在确认前，形状事实以包材侧为准。
2. **是否需要在内部系统枚举「机型 × 模具组合」**（决定走 A 还是 B）。
3. **产品 67 最终默认展示哪张图**（4698 vs 5221）——这是批次 2-B 的阻断项，不是本轮模型设计问题。
4. **机型档位覆盖度**：49 个产品中仅 1 个有档位数据，是否需要为其它产品补齐（属产品资料建设，非 P1-B 技术前置）。
