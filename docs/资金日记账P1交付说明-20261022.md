## 二、对拍 A 的口径已整体纠正

### 旧写法（已废弃）

```
/accounts 期末余额 == ORDER BY entry_date DESC, id DESC LIMIT 1 的来源结存
```

两个问题（LQ 指出）：
1. 同一天可能有多笔交易，**id 不代表真实交易顺序**；
2. 自定义期间内有历史补录时，计算期末**不一定**等于按库序取到的某条来源结存。

### 新口径

| 对拍项 | 验证方式 | 是否依赖 id |
|---|---|---|
| 期间期初 | 年度期初 + 期间开始前的累计净流量（独立子查询复算） | 否 |
| 期间收入 | 期间内全部有效收入之和 | 否 |
| 期间支出 | 期间内全部有效支出之和 | 否 |
| 期间期末 | 期间期初 + 期间收入 − 期间支出（**只做恒等校验**） | 否 |
| 来源结存 | 仅在「末行身份有可靠证据」时单独比较 | **否** |
| 逐笔衔接 | 只在「账户内 entry_date, id」这一展示顺序下检查，结果本身不作为交易顺序断言 | 仅作展示序 |
| 相邻期间 | 上期末 == 本期初（同账户、无重叠无空洞） | 否 |

### 「末行身份可靠」的判据（两个条件同时成立）

1. 该账户**期间内逐笔链 0 断点**——链条自洽时，任何截点的结存都能由期初 + 累计净额推出；
2. 期间内最后一个有结存的日期上，**所有行的结存值唯一**——此时「当日结束结存」与同日内部顺序无关。

两条都不含 id。不成立的账户记为 **SKIPPED 并输出原因**（例如「10-15 当日 7 行、3 个不同结存，当日结束结存无法确定」），不当作失败，也不为了让测试通过而放宽判据。

### 已知会大量 SKIPPED 的原因

全年 8751 行中，存在同日多笔的账户占绝大多数（单日最多 30 笔，覆盖约 89.5% 的行）。因此**能够做「来源结存」直接比对的账户天然是少数**——这是数据事实，不是实现缺陷。探针会把「可比 / 不可比 / 不可比原因」三类数量都打出来。

## 三、三个维度彻底分开（不再混淆「可计算」与「已核对」）

| 维度 | 字段 | 含义 | P1 取值 |
|---|---|---|---|
| 期间余额 | `closingStatus` / `closingStatusLabel` | 期初 + 收支能否算出期末 | `OK`→「期末可计算」；`OPENING_MISSING`→「缺期初，期末不可计算」 |
| 逐笔结存 | `sourceBalanceStatus` / `sourceBalanceExceptionCount` / `sourceBalanceCheckedLinks` | 相邻两行能否接上 + 参与核对的链接数 | `DETAIL_OK` / `DETAIL_EXCEPTIONS` |
| **人工对账** | `manualReconcileStatus` / `manualReconcileStatusLabel` | 财务是否已与银行/实际余额确认 | **恒为 `NOT_STARTED`「未人工对账」** |

**结论陈述**由 `CashflowReviewRules.reconcileSummaryOf()` 单一来源生成，形如：

- `期末可计算；流水逐笔衔接`
- `期末可计算；3 处明细不衔接`
- `缺期初，期末不可计算；流水逐笔衔接`

有测试钉死：这段文字**不允许**出现「已核对」「核对一致」「已对账」。账户整体对拍通过只作为历史数据验证结果，不代表财务已完成正式对账——这句话也写进了页面的口径说明里。

对账视图第 4 张卡片直接显示「已人工对账 0 个账户」，避免把前 3 张卡片的数字读成对账结论。

## 四、快捷期间：自然季度 + 默认截至今天

| 季度 | 完整区间 |
|---|---|
| 第一季度 | 01-01 — 03-31 |
| 第二季度 | 04-01 — 06-30 |
| 第三季度 | 07-01 — 09-30 |
| 第四季度 | 10-01 — 12-31 |

快捷期间一律**截到今天**（今天 2026-10-22）：

- 本月 → 2026-10-01 ~ 2026-10-22
- 本季 → 2026-10-01 ~ 2026-10-22
- 本年 → 2026-01-01 ~ 2026-10-22

自定义期间仍可选择未来日期，页面上始终显示一行 `查询范围：A 至 B`，并标注是「默认截至今天」还是「自定义期间，可包含未来日期」。

**按钮高亮不从区间反推**：10-22 当天「本月」和「本季」区间完全相同，若按区间匹配会出现「点了本季却高亮本月」。改由最后点击的预设决定（`useCashflowPeriod` 的 `preset`）。

- 账户筛选从「流水视图的工具栏字段」提升为**页面级唯一状态**（`accountFilter`），三个视图共用；

## 七、组件职责复核结论

**已拆出去的**（都有独立逻辑，不是纯排版）：

| 拆出物 | 为什么独立 |
|---|---|
| `useCashflowPeriod.ts` | 期间口径会被三个视图和导出同时使用，且「截至今天 / 预设识别」是需要被单独验证的规则 |
| `CashflowAccountTable.vue` | 12 个月月报的自加载 + 导出，是账户行自己的生命周期 |
| `CashflowReviewDrawer.vue` | 批次选择 / 账户过滤 / 分页三个状态与外层完全无关 |
| `cashflowFormat.ts` | 金额格式与徽标映射，前端唯一来源（原来分散在模板与 CSV 导出里） |
| `CashflowEntryTable` / `CashflowIssueTable` | 纯展示，无状态 |

**刻意留在主页面的**：三个视图的 `DataState` 容器与工具栏。它们的 props 主要是「加载状态 + 重试回调 + 空态文案」，抽出去只会变成一层透传，不会增加内聚；真正的重逻辑（加载、错误态、请求竞态）本来就在主页面。

主页面 1124 → **795** 行，其中模板 ~330、脚本 ~330、样式 ~130。如果 P2 再加记账/更正功能，建议届时把「流水明细」整块（含工具栏与分页）抽成 `CashflowEntriesPanel`，而不是现在预先拆。

## 九、已知限制（明确不做）

1. **没有人工对账操作**（P3）。所以「已人工对账」永远是 0，系统计算 ≠ 财务确认。
2. **逐笔「交易后余额」不落库**，也不由 id 推断。
3. **2026 年限制**保留（`validatePeriod` 未动），跨年靠 P2 年度期初。
4. 同日多笔账户的「当日第 N 笔」顺序无法证实，相应对拍项一律 SKIPPED。
5. 流水与对账视图没有币种筛选（后端不支持该参数），只有账户汇总视图有。
