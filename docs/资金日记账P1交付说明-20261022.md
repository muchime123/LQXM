## 二、对拍 A 的口径已整体纠正

### 旧写法（已废弃）

```
/accounts 期末余额 == ORDER BY entry_date DESC, id DESC LIMIT 1 的来源结存
```

两个问题（LQ 指出）：
1. 同一天可能有多笔交易，**id 不代表真实交易顺序**；
2. 自定义期间内有历史补录时，计算期末**不一定**等于按库序取到的某条来源结存。

### 新口径

| 对拍项 | 验证方式 | 是否依赖 id |
|---|---|---|
| 期间期初 | 年度期初 + 期间开始前的累计净流量（独立子查询复算） | 否 |
| 期间收入 | 期间内全部有效收入之和 | 否 |
| 期间支出 | 期间内全部有效支出之和 | 否 |
| 期间期末 | 期间期初 + 期间收入 − 期间支出（**只做恒等校验**） | 否 |
| 来源结存 | 仅在「末行身份有可靠证据」时单独比较 | **否** |
| 逐笔衔接 | 只在「账户内 entry_date, id」这一展示顺序下检查，结果本身不作为交易顺序断言 | 仅作展示序 |
| 相邻期间 | 上期末 == 本期初（同账户、无重叠无空洞） | 否 |

### ⚠️ 「末行身份可靠」的旧判据已废弃（2026-10-23 纠正）

初版写的两条判据都**隐含了不可靠的交易顺序假设**，已作废：

| 旧判据 | 为什么不能用 |
|---|---|
| ① 按 `entry_date, id` 逐笔链 0 断点 | 只证明「在这个排序下不断」，**不证明这个排序就是真实交易顺序**。换一种排序同样可能自洽。 |
| ② 期间末最后一个日期上所有结存值唯一 | 只证明同日几笔没有分歧，**不证明这个值就是该账户真实的期末余额**。 |

**实测反证**（真库，2026-10-23）：

- `external_id` 尾号在大多数日子都是 `1`，只有 915/2406 个账户日构成 `1..n` 全排列 ⇒**导出件里没有可用的序号**；
- 按 `source_no / external_id` 字符串排序：仅 2/28 个账户 0 断点（共 6610 处断点）⇒ **字符串序不是交易序**；
- 典型反例：浙江利强工商银行 2026-01-03 按 `id` 排序 0 断点，但同日结存走的是
  `937651.99 → 931519.57 → … → 863997.55 → 863997.55`（含一笔「账户有误退回」等额冲回）。
  按 id 的「连续」纯属巧合，末行值也不能代表当日真实结束结存。

### 现判据：逐日路径锁定

由 `CashflowOrderEvidence.resolveClosingEvidence()` 实现。对每一天：

1. 取当日各行的净额（收入 − 支出）与来源结存；
2. 求**所有**能让「每行结存 = 上一行结存 + 本行净额」成立的排列；
3. **恰好 1 个**排列 ⇒ 当日顺序被数据唯一锁定，可用；**>1 个** ⇒ 顺序不可证实，判 `MULTIPLE`。

整个期间：任意一天 `MULTIPLE` ⇒ 不做来源末行比对；任意一天链断 ⇒ `SOURCE_CHAIN_BROKEN`；
所有天都是「单笔/结存相同」这类无信息日 ⇒ 同样不可比。

**工程保护**（三条都是实测踩出来的）：

| 保护 | 原因 |
|---|---|
| 同日存在**结存相同且净额相反**的两笔 ⇒ 直接 `MULTIPLE`，不搜索 | 这种两笔互换后仍自洽，必然多解。⚠️ 仅「结存值重复」不够——被别的行隔开时互换会断链，真实解可能唯一（实测误杀 13 个账户日） |
| 搜索预算 `SEARCH_BUDGET = 120_000` 节点，耗尽保守判 `MULTIPLE` | 对称 `+a/−a` 排列会 2^k 爆炸：实测 20 行 354ms、25 行超过 180s 超时 |
| 按**完整排列指纹**去重，不按首行累加 | 同一排列会被它的 n 行各「认领」一次，naive 累加会让任何 n>1 的日子都假 `MULTIPLE` |
| 容差传 `null` 时回退 1 分（`DEFAULT_TOLERANCE`） | 曾经 null 一路传到 `BigDecimal.compareTo` 直接 NPE |

**跳过原因四类各带自己的文案**，任何文案都**不允许**出现「无法核对」这种含糊说法：

| code | 文案 |
|---|---|
| `NO_RELIABLE_SOURCE_ORDER` | 缺少可靠来源顺序（同日多笔的层内顺序不可证实） |
| `SOURCE_CHAIN_BROKEN` | 来源结存链本身存在断点 |
| `NO_BALANCE_ROWS` | 期间内没有带来源结存的行 |
| `NOT_ENOUGH_ROWS` | 期间内不足两行，无从衔接 |

来源末行比对因此被明确降级为**独立辅助核对**：它不参与「期间余额是否可计算」的判定，也不能作为账户验收的通过条件。

### 已知会大量 SKIPPED 的原因

全年 8751 行中，存在同日多笔的账户占绝大多数（单日最多 30 笔，涉及 7,836/8,751 行 ≈ 89.5%）。因此**能够被数据唯一锁定顺序的账户天然是少数**——这是数据事实，不是实现缺陷。探针与页面都把「可比 / 不可比 / 不可比原因分布」三类数量显式打出，不静默跳过。

## 三、三个维度彻底分开（不再混淆「可计算」与「已核对」）

| 维度 | 字段 | 含义 | P1 取值 |
|---|---|---|---|
| 期间余额 | `closingStatus` / `closingStatusLabel` | 期初 + 收支能否算出期末 | `OK`→「期末可计算」；`OPENING_MISSING`→「缺期初，期末不可计算」 |
| 逐笔结存 | `sourceBalanceStatus` / `sourceBalanceExceptionCount` / `sourceBalanceCheckedLinks` | 相邻两行能否接上 + 参与核对的链接数 | `DETAIL_OK` / `DETAIL_EXCEPTIONS` |
| **人工对账** | `manualReconcileStatus` / `manualReconcileStatusLabel` | 财务是否已与银行/实际余额确认 | **恒为 `NOT_STARTED`「未人工对账」** |

**结论陈述**由 `CashflowReviewRules.reconcileSummaryOf()` 单一来源生成，形如：

- `期末可计算；流水逐笔衔接`
- `期末可计算；3 处明细不衔接`
- `缺期初，期末不可计算；流水逐笔衔接`

有测试钉死：这段文字**不允许**出现「已核对」「核对一致」「已对账」。账户整体对拍通过只作为历史数据验证结果，不代表财务已完成正式对账——这句话也写进了页面的口径说明里。

对账视图第 4 张卡片直接显示「已人工对账 0 个账户」，避免把前 3 张卡片的数字读成对账结论。

### ⚠️ 零流水账户曾被整批跳过（2026-10-23 财务视角检查发现并修复）

`CashflowJournalController.accounts` 原有一行：

```java
if (((Number) item.getOrDefault("entryCount", 0)).longValue() == 0) continue;
```

本月 35 个账户里 **18 个零流水**，这批被整条 `continue` 划过，后果有三个：

| 后果 | 财务实际看到 |
|---|---|
| 三个证据字段根本没写 | 表格「来源末行（辅助）」列取值 `undefined` ⇒ 显示「不可比」，**但悬停时拿不到任何原因** |
| 不计入 `sourceClosingSkippedCount` | 「可比 13 + 不可比 4 = 17」，与页面上 35 个账户对不上 |
| 违反「所有不可比都要说清缺哪类证据」 | 一半以上账户属于「沉默的不可比」 |

修法：删掉这行守卫。`resolveClosingEvidence` 对空行集本就返回 `NO_BALANCE_ROWS` +「期间内无流水」，交给它判即可，服务层无需改动。

修复后口径：本月 **可比 13 / 不可比 22（4 + 18 零流水）/ 合计 35** —— 三个数相加等于账户总数，这是可验证的闭环。
上季 17 + 18，全年 20 + 15，同理。

> 这也说明「可比数」和「跳过数」必须满足 **comparable + skipped == 账户总数**。脚本已把这条作为断言。
