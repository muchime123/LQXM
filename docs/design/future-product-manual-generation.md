# 产品说明书生成功能重建设计

## 1. 文档状态

本文是未来功能设计草案，不代表当前系统已经提供说明书生成能力。

旧版说明书模板、Markdown 草稿、发布、过期检测和版本回滚链路已在 V47 清理。清理原因是旧功能无法形成稳定可用的业务闭环，并持续增加产品档案页面、接口和数据库维护负担。

当前系统仅保留：

- 产品默认说明书文件 `defaultManualFile`。
- `manual` 类型的产品素材。
- 说明书附件上传、预览和档案完整度检查。

## 2. 重建前置条件

只有同时满足以下条件时才重新进入开发：

1. 明确最终输出格式，例如 DOCX、PDF 或两者同时支持。
2. 至少提供两份已确认的真实说明书样本。
3. 产品字段、配置字段和机器组件字段的数据质量达到可生成要求。
4. 明确谁负责编辑、审核、批准和发布。
5. 明确生成文件是否属于正式受控文档，以及版本保留期限。

## 3. 建议业务流程

```text
选择产品与配置
  → 执行数据完整性检查
  → 选择受控模板版本
  → 生成不可发布的预览
  → 人工编辑与校对
  → 提交审核
  → 审核通过后生成正式文件
  → 正式文件登记为 manual 素材
```

生成失败、审核拒绝或正式文件写入失败时，不得覆盖产品现有的默认说明书附件。

## 4. 建议领域边界

未来实现应建立独立的 `manual-generation` 领域，不把生成状态直接堆叠到 `ProductModel`：

- `ManualTemplateDefinition`：模板元数据和固定版本，不直接保存任意可执行表达式。
- `ManualGenerationJob`：一次生成任务及输入快照、状态、失败原因。
- `ManualDraft`：可编辑草稿，与正式文件分离。
- `ManualApproval`：审核记录和审批意见。
- `ProductAsset`：只保存最终生成并确认的说明书文件。

产品只通过资源关系引用当前默认说明书，生成任务和版本历史由独立表维护。

## 5. API 草案

- `POST /api/manual-generation/preflight`：返回缺失字段和阻断项。
- `POST /api/manual-generation/jobs`：创建异步生成任务，必须带幂等键。
- `GET /api/manual-generation/jobs/{id}`：查询进度、错误和输出预览。
- `PUT /api/manual-generation/drafts/{id}`：保存人工修订草稿。
- `POST /api/manual-generation/drafts/{id}/submit`：提交审核。
- `POST /api/manual-generation/drafts/{id}/approve`：审核并生成正式文件。
- `POST /api/manual-generation/drafts/{id}/reject`：退回并记录原因。

生成任务不得使用同步长请求，也不得直接修改产品主数据。

## 6. UI 草案

使用页面内操作区或全屏工作区；只有出现第二个稳定消费者后才评估抽取公共布局。页面分为：

1. 数据检查。
2. 模板与配置选择。
3. 内容预览和人工编辑。
4. 审核确认。
5. 生成结果与文件登记。

页面必须覆盖保存防重入、脏数据关闭确认、生成失败重试、审核拒绝、任务恢复和焦点管理。

## 7. 验收标准

- 同一输入和模板版本可以稳定复现相同结果。
- 生成过程不会修改产品档案字段。
- 未审核内容不能成为默认说明书。
- 正式输出作为 `manual` 文件资产登记并可预览、下载和追踪来源。
- 模板、输入快照、人工修改、审核和最终文件之间可以完整追溯。
- 失败任务可重试且不会产生重复正式文件。
- 前后端具备契约测试、生成器单元测试和真实样本回归测试。

## 8. 明确不沿用的旧设计

- 不在 `product_models` 中保存 Markdown 草稿、模板版本、生成时间和发布状态。
- 不使用一个全局“启用模板”隐式决定所有产品的输出。
- 不以产品更新时间简单判断说明书是否过期。
- 不在一次接口调用中同时生成、保存和发布。
- 不把附件存在、草稿存在和正式发布混为同一种状态。
