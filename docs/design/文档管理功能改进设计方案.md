# 文档管理功能改进设计方案

> 2026-07-01 | 版本 v2.0

---

## 一、诊断：当前功能盘点

文档管理模块已具备基础 CRUD 能力，但与项目中产品管理模块对比，缺失以下治理能力：

| 能力 | 产品管理 | 文档管理(现状) | 优先级 |
|------|---------|---------------|--------|
| 软删除 / 回收站 | ✅ | ❌ | 🔴 高 |
| 操作审计日志 | ✅（29种操作） | ❌ | 🔴 高 |
| 批次操作（批量删/改/导出） | ✅ | ❌ | 🔴 高 |
| 版本历史追踪 | — | ❌（只有版本号字段） | 🟡 中 |
| 文档编号自动生成 | — | ❌ | 🟡 中 |
| 全文检索 | — | ❌（仅标题关键词） | 🟡 中 |
| 文档审批工作流 | — | ❌（仅 draft/published/archived 状态） | 🟢 低 |
| 有效期/到期提醒 | — | ❌ | 🟢 低 |
| 使用统计（查看/下载量） | — | ❌ | 🟢 低 |
| 文档模板 | — | ❌ | 🟢 低 |

## 三、分阶段实施计划

### 阶段一：补齐治理短板（高优先级，2-3天）

三个改动全部复用产品管理模块的成熟模式，改动量小。

#### 3.1 回收站（软删除）

复用产品管理模块的 `deleted_at` + `@SQLRestriction` 模式：

**数据库变更**：
```sql
ALTER TABLE documents ADD COLUMN deleted_at DATETIME NULL;
CREATE INDEX idx_documents_deleted ON documents(deleted_at);
```

**实体层**：
```java
@Entity
@SQLRestriction("deleted_at IS NULL")
public class Document { ... }
```

**服务层**：
- `delete(id)` → 改为软删除（设 `deletedAt = now()`）
- `restore(id)` → 清除 `deletedAt`
- `permanentDelete(id)` → 物理删除 + 删除文件
- `getDeleted(pageable)` → 回收站列表
- 定时任务：每天凌晨3点清理超过30天的软删除记录

**前端**：
- 文档管理视图顶部增加「回收站」入口
- 回收站页面：三标签页（文档/产品关联/...），批量恢复/彻底删除

#### 3.2 操作审计日志

复用现有 `audit_logs` 表，增加文档相关操作类型：

**新增操作类型**（8种）：
| 操作码 | 说明 |
|--------|------|
| `DOC_CREATE` | 创建文档 |
| `DOC_UPDATE` | 更新文档 |
| `DOC_DELETE` | 删除文档 |
| `DOC_RESTORE` | 恢复文档 |
| `DOC_PERM_DELETE` | 彻底删除 |
| `DOC_UPLOAD` | 上传/替换文件 |
| `DOC_DOWNLOAD` | 下载文档 |
| `DOC_ASSOCIATE` | 关联产品 |

**代码改动**：在 `DocumentService` 各操作点注入 `AuditLogRepository`，写入日志。

#### 3.3 批次操作

在文档列表视图增加批量操作能力：

- **列表多选**：表头复选框 + 行复选框
- **批量操作栏**（选中后出现）：
  - 批量删除（移入回收站）
  - 批量修改分类
  - 批量修改状态（发布/归档）
  - 批量修改部门
  - 批量导出
- 复用产品管理的 `useBatchSelection` composable 模式

### 阶段二：功能深化（中优先级，3-4天）

#### 3.4 版本历史追踪

当前 `version` 字段只是字符串，无法追溯历史。需要在文件内容变更时自动存储历史版本。

**新增表**：
```sql
CREATE TABLE document_versions (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    document_id BIGINT NOT NULL,
    version VARCHAR(20) NOT NULL,          -- 版本号（如 v1.0, v1.1）
    file_name VARCHAR(500),                -- 该版本文件名
    file_size BIGINT,                      -- 文件大小
    content TEXT,                          -- Markdown内容快照
    change_summary VARCHAR(500),           -- 变更说明
    created_by VARCHAR(100),               -- 修改人
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_dv_document FOREIGN KEY (document_id) 
        REFERENCES documents(id) ON DELETE CASCADE,
    INDEX idx_dv_document (document_id),
    INDEX idx_dv_created (document_id, created_at DESC)
);
```

**触发时机**：
- 替换文件时（`replaceFile`）
- 修改在线编写内容时（`update` 中 content 变更）
- 更新元数据时可选是否记录版本

**前端展示**：
- 文档详情弹窗增加「版本历史」标签
- 时间线展示各版本，可对比查看（简单 diff）
- 支持回滚到历史版本（还原文件+内容）

#### 3.5 文档编号自动生成

**规则**：`{部门编码}-{分类编码}-{年份}-{序号}`
- 例：`JS-SC-2026-0001`（技术部-操作手册-2026年-第1号）
- 部门编码和分类编码在配置表中维护
- 创建文档时自动生成，也可手动修改
- documents 表新增 `doc_number VARCHAR(50) UNIQUE`

#### 3.6 全文检索

当前 `search` 接口仅匹配 `title LIKE %keyword%`。

**MySQL 方案**（无需引入 ES，数据量小）：
```sql
-- documents 表新增 FULLTEXT 索引
ALTER TABLE documents ADD FULLTEXT INDEX ft_documents (title, content, tags, summary);
```

**Repository 查询**：
```java
@Query(value = "SELECT * FROM documents WHERE MATCH(title, content, tags, summary) AGAINST(:keyword IN BOOLEAN MODE) AND deleted_at IS NULL", nativeQuery = true)
Page<Document> fulltextSearch(@Param("keyword") String keyword, Pageable pageable);
```

**前端**：搜索框支持切换「标题搜索」/「全文搜索」模式。全文搜索结果高亮匹配片段。

### 阶段三：体验与业务整合（低优先级，2-3天）

#### 3.7 文档有效期追踪

**数据库**：
```sql
ALTER TABLE documents ADD COLUMN valid_from DATE NULL;
ALTER TABLE documents ADD COLUMN valid_until DATE NULL;
ALTER TABLE documents ADD COLUMN review_cycle INT DEFAULT 0;  -- 复审周期（天），0=不需要
ALTER TABLE documents ADD COLUMN next_review_date DATE NULL;
```

**功能**：
- 创建/编辑文档时可设置有效期和复审周期
- 首页仪表盘增加「即将过期文档」卡片（30天内）
- 定时任务：每天检查 `next_review_date`，生成待复审提醒

#### 3.8 使用统计

**新增表**：
```sql
CREATE TABLE document_stats (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    document_id BIGINT NOT NULL,
    view_count BIGINT DEFAULT 0,
    download_count BIGINT DEFAULT 0,
    last_viewed_at DATETIME,
    CONSTRAINT fk_ds_document FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE,
    UNIQUE INDEX idx_ds_document (document_id)
);
```

增加计数在 Controller 层 `preview` 和 `download` 端点。

#### 3.9 文档模板

```sql
CREATE TABLE document_templates (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(200) NOT NULL,
    category VARCHAR(50),
    description VARCHAR(500),
    content TEXT,                          -- Markdown 模板内容
    file_name VARCHAR(500),               -- 关联模板文件
    is_system BOOLEAN DEFAULT FALSE,       -- 系统预置不可删除
    created_at DATETIME,
    updated_at DATETIME
);
```

预置模板：操作手册模板、使用说明书模板、检验标准模板、安全操作规程模板。
用户可基于模板快速创建文档，自动填充结构框架。

#### 3.10 审批工作流

对 `draft → review → published` 的流程增强：

```sql
ALTER TABLE documents ADD COLUMN reviewer VARCHAR(100);
ALTER TABLE documents ADD COLUMN reviewed_at DATETIME;
ALTER TABLE documents ADD COLUMN review_comment VARCHAR(500);
```

- 草稿提交审核 → 状态变为 `review`
- 审核人（可指定）审核通过 → 状态变为 `published`
- 审核不通过 → 退回 `draft`，附审核意见

## 七、实施建议

1. **先做阶段一**（回收站 + 操作日志 + 批次操作），改动最小、收益最大，且与产品管理模块保持一致的用户心智模型
2. **阶段二的版本历史**最有业务价值——封口机设备的操作手册、检验标准等文档频繁更新，版本追溯是刚需
3. **全文检索**如果现有数据量不大（目前14条），简单的 MySQL FULLTEXT 足够用，无需引入 Elasticsearch
4. **审批工作流**和**模板系统**属于锦上添花，等前两阶段稳定后再说
