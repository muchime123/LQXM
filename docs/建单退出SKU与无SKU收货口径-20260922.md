# 建单退出 SKU 与「无 SKU 收货不落库存账」口径

> 定于 **2026-09-22**，LQ 拍板。登记于 `ERP决策登记-20260921.md` **#30**。
> 相关：`#27`（台账运行定位 / 串联主轴 = SKU）、`#28`（产品身份锚定 SKU）、`#18`（车间交付收货段 5 条口径）、`U15-Q3`（**本条修订**）。

---

## 1. 起因（LQ 原话）

> 「车间执行部分点击新建生产任务单的抽屉当中，这里不需要这个可售产品（sku）相关的选择，而且这个 sku 的设计不是很好，我后面会重新设计」

拆成两条要求：
1. **抽屉里去掉 SKU 选择**（下单不该问业务员「这单产出哪个 SKU」）；
2. **SKU 主数据本身要重设计** → 现在不要围绕它做投入，也不要把链路设计绑死在它上面。

---

## 2. 为什么这不是「删一个表单项」

排查后发现 SKU 是**贯穿到完工入库落账的键**，不是界面字段：

| 位置 | 现状 | 结论 |
|---|---|---|
| `ManufacturingService.doCreate()` | `requireProduct(request.salesProductId())` → null 直接抛「生产产品必须选择产品」 | 删下拉必然 400，后端必须一起改 |
| `manufacturing_order_outputs`（产出清单主行） | 由建单的 SKU 生成，`sales_product_id` 是**收货的唯一入口** | 主行无 SKU 需明确表达方式 |
| 收货对话框 | 只有「按产出清单逐项确认数量」，**没有选 SKU 的地方** | SKU 断在建单就无法在收货补 |
| `finished_goods_lots` / `product_inventory_transactions` / `product_inventory_balances` | `sales_product_id`、`canonical_product_id` **NOT NULL**（`uk_pib_warehouse_canonical_unit`） | 无 SKU ⇒ 无法成为库存身份 |
| `manufacturing_completion_receipt_items` | `sales_product_id`、`canonical_product_id` **NOT NULL** | 无 SKU 的收货明细**写不进去** → 需迁移 |
| 单位 | `unit` 100% 取自 SKU 主数据（`sales_products.unit`）；`manufacturing_task_config_items` 无单位字段 | 摘掉 SKU 后单位**没有来源** |

→ 必须回答的问题是：**「无 SKU 的工单，完工收货该怎么办」**。

---

## 3. 拍板结果（LQ 二选）

| 问题 | 结论 |
|---|---|
| 收货段的 SKU 怎么处理 | **全链路先不带 SKU**：建单 / 报工 / 收货都只按「制程品类 + 配置 + 数量」走；**生产完工暂不写库存流水**，等 SKU 主数据重新设计后再把库存入账接回来 |
| 单位从哪来 | **默认「台」**（不新增表单项） |

### 3.1 落成四条实现口径

1. **建单**：抽屉移除「可售产品（SKU）」下拉与「单位」只读框；只带 产线 + 产品名称（制程品类）+ 产品配置 + 数量。
2. **单位判据链**：显式传入 → SKU 主数据单位（若调用方传了 SKU）→ 默认 **「台」**。
3. **身份退化**：无 SKU 时，工单与产出清单主行的 `sales_product_id` / `canonical_product_id` / `product_code_snapshot` **一律留空**；成品身份由 `product_name_snapshot`（= 制程品类）+ `product_config_json` 表达。
4. **收货分支**：
   - 产出行**有 SKU** → 原路径不变（成品批次 + 成品流水 + 统一库存流水 + 收货明细带 SKU）；
   - 产出行**无 SKU** → **只写收货明细**（SKU / 批次列留空）并累加工单数量，**不建批次、不写流水、不动库存余额**。

### 3.2 制程解析不受影响（关键前提，已实测）

制程解析走的是**制程品类**，与 SKU 无关：`ManufacturingTaskTemplateResolver` 按
`manufacturing_task_config_items.config_name`（`config_type='PRODUCT_NAME'`，49 项，全为品类级）精确匹配。
反向不成立（SKU 名 → 品类：4,916 个 SKU 中 **74.5% 零命中、13% 命中多个**）——
所以「品类」与「SKU」本来就是两个维度，摘掉 SKU 不会让工序展开不出来。

## 6. 过程中挖出的真缺陷（顺带修掉）

**`doReverseReceipt` 无批次时抛 `EmptyResultDataAccessException`（冲销 500）**

```java
// 改前：queryForObject 在「0 行」时抛异常（不是返回 null）
Long reversalMovementId = jdbc.queryForObject(
        "SELECT id FROM finished_goods_movements WHERE source_type='COMPLETION_RECEIPT_REVERSAL' AND source_id=? ...",
        Long.class, receiptId);
```

改造前这条语句**只在有批次时可达**（有批次必产生反向流水），所以一直没暴露；
一旦「无 SKU ⇒ 无批次」成为常态，它就成了**必然命中的 500**。
已改为 `query(...).stream().findFirst().orElse(null)`。

> 这条正是「无批次可冲销」用例存在的意义 —— 断言的是**边界行为**，不是接口没报错。

## 9. 09-23 补记：SKU 设计错在哪（LQ 定调，重设计的第一锚点）

> LQ（2026-09-23）：「现在的产品是根据**任务单配置**中的产线对应的产品名称和可选配置来的，之前的 SKU 设计是不对的，因为『任务单配置中的产线对应的产品名称和可选配置』这个是**确定的**，数量定了的，而**仓库库存得到的 SKU 是混乱的**。」

由此定下三条口径：

1. **根因确认**：现行 SKU 主数据源自仓库库存/台账侧，口径混乱，不配作下单时的产品身份 —— 这正是本文档（决策 `#30`）退出建单 SKU 的根因，不是权宜之计。
2. **重设计第一锚点 = 任务单配置**：未来的产品/SKU 身份模型必须以「产线 → 产品名称 + 可选配置」为第一锚点（建单时即确定、数量绑定）；库存侧身份（批次 / 流水 / 余额的挂接，含 `#28` 四步重排与 P3 ③④）全部等新模型定稿后再接回。
3. **过渡期身份不变**：无 SKU 工单的成品身份继续由 `product_name_snapshot`（制程品类）+ `product_config_json` 表达（`#30` ③「身份退化」的既定口径不变），后续接回时用 `product_config_json` 做血缘映射。
