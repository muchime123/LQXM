### 1.2 需要修正或补充的（这几条影响方案选型）

**① 现有账户期间汇总口径是"脆"的，但结果目前是准的。**

`before_net` 用 `entry_date >= '2026-01-01'` 从年初累加。这在 2026 年内正确，**跨年时第二个年度的期初会算成"期初 + 全年净流量"**，直接错。这是"只支持 2026"的真正根因，不只是前端限制。

**② 结存链是干净的 —— 之前我一度误判，必须纠正。**

我第一版 SQL 用连续 `LAG(balance)` 得到"8710/8722 行断裂"，**这是错的**。真实原因是：同日同账户多行时，数据库没有确定的行内顺序（同日最多 30 行）。改用"账户内结存单调性"切段后：

| 口径 | 断裂行 |
| --- | --- |
| 连续 LAG（错误口径） | 8710 |
| 按 `entry_date, id` 排序 | 19 |
| **按结存下降点切流水段后** | **14 / 8723 条链接** |

结论：**Excel 里的结存与收支是对得上的**（37 个账户里 34 个完全闭合）。剩下 14 行集中在 3 个账户（于士强农业银行5277 有 11 行），是真实的数据现象（历史补录/跨段错位），**不是算法问题，也不是 bug**。

**③ 账户"缺期初"其实只有 5 户，且性质是"中途启用"，不是缺失。**

我第一版也错报成"多账户有 20 万级差额"，原因同样是同日排序不确定。按结存单调序取真正首行后：

| 账户 | 库中期初 | 实际首行 | 性质 |
| --- | --- | --- | --- |
| 温州永铭农业银行 | 6879.88 | 2026-01-05 收 200000 → 206879.88 | 期初值取自**月中**某行，不是月初 |
| 李红伟中信银行 | 547576.12 | 2026-01-08 支出 14090 → 463244.12 | 同上，期初晚于首笔 |
| 安徽盒多多工商银行 | 34107.14 | 2026-01-02 支出 4.5 → 30622.64 | 同上 |
| 温州睿包中信银行人民币 | 249135.90 | 2026-01-05 支出 84.89 → 247213.01 | 同上 |
| 浙江利强工商银行 | 916043.25 | 2026-01-01 两笔手续费 160.5 → 915792.75 | 同上 |
| 于清山兴业/于帅帅兴业/宋文温州 | 0 | 首笔就是收入，之后完全闭合 | 账户中途启用，期初 0 正确 |

**这 5 户的差额不是错误凭证，而是"期初余额取数位置"问题** —— Excel 的「上期结存」行放的位置因账户而异。这类必须进对账核对，不能当"账户缺期初"笼统报。

**④ 同键重复是真实存在的，规模 213 行 / 145 组。**

`account_name + entry_date + income + expense` 组合有 145 组重复（多出 213 行）。这是**当前行键 `账户#日期#收入#支出#结存#n` 里 `#n` 存在的原因**，也是"同日同额多笔"进入人工确认的必然来源。任何"稳定身份"方案都必须处理它，不能靠假设唯一。

**⑤ 差异复核抽屉在当前库里是"空转"的。**

批次 328（10-22 11:36 确认）和 327 都已 COMPLETED，`h3_import_staging_rows` 对应暂存行 **0 行**。所以现在打开抽屉只会看到"该批次暂存行不可用"。这不是显示 bug，是留存策略的结果：确认后自动清理。**要在"确认前"做处置闭环，处置动作必须坐在导入确认流程里，而不是日记账页面的只读抽屉里。**

**⑥ 导入保护当前是"拒绝式"而非"处理式"。**

`rejectCashflowHistoryRewrite()` 的策略是：旧行键消失 → **抛异常，整批不让确认**。`rekeyCashflowBalanceShifts()` 做唯一匹配换键，`isCashflowData()` 为空的占位行**自动 DELETE**（`H3FactImportService:1912`）。后者是"自动删除历史数据"，虽然限定了 `income IS NULL AND expense IS NULL`，但它不在预览里显性列出数量就直接执行了 —— 这与设计文档 §9.1.3「必须在预览里列明数量」不符。

## 3. 与你的方案的分歧点（请重点确认）

你的整体方向我**全部认同**（保留能力、不推倒、三视图、四件事）。以下 4 处我建议调整，理由都来自上面的实测：

### 分歧 1：不要新建 `fund_entries` 平行账本表 —— 在 `h3_cashflow_entries` 上演进

你的数据结构表里列了「资金流水 / 流水业务信息 / 导入处理记录」等 6 个对象。如果照此新建一套，**8751 行历史要搬运，且导入侧、复核侧、报表侧三处都要改成双源**，正是你担心的"新旧并存冗余"。

实测支撑在**现有表里演进**：

- `external_source` 是现成的来源判别列（当前恒 `H3YUN`，手工录入用 `MANUAL` 即可）—— 不需要新表
- `id` 已经是稳定的 `BIGINT` 主键，**可直接充当你说的"稳定内部 ID"**，设计文档 §9 也这么写
- `uk_cashflow_ext(external_source, external_id)` 天然支持"手工行 + 导入行"共存（手工行 `external_id` 用 `MANUAL-{uuid}`）
- 需要**新增的只有列**：`account_id`（消掉文本关联）、`biz_category`/`counterparty_type`、`voided_at`、`void_reason`、`reconcile_status`、`locked` 等，全部 `NULL` 可空、自带默认值，**历史行零回填风险**
- 真正需要**新建表**的只有 3 张：`cashflow_account_opening`（年度期初）、`cashflow_reconcile_confirmation`（对账结论）、`cashflow_import_decision`（导入差异处置决定）

这样第一阶段的迁移就是"加列 + 建 3 张新表 + 一次 `UPDATE ... SET account_id`"（35 行映射，不是 8751 行搬运）。

### 分歧 2：不要在导入确认流程里做"人工逐行匹配 UI"

你的第五点说"导入时根据来源交易号、账户、日期、金额和其他证据尝试匹配，无法唯一确定时进入人工确认"。方向对，但**手工日记账没有交易号**，能匹配的只有 `账户+日期+收支`，而这组键有 145 组重复 —— 逐行人工确认会成为日常负担。

建议改成**差异决策三选一 + 批量**（而不是逐行配对）：

| 场景 | 系统行为 | 人工动作 |
| --- | --- | --- |
| 行键完全命中 | 无变化 / 更新 | 无需动作 |
| 旧行键消失，但同账户同日同收支**唯一** | 自动视为同笔（沿用 id，结存更新） | 无需动作（已有 `rekeyCashflowBalanceShifts`） |
| 旧行键消失，**无法唯一** | 归入「待确认删除」桶 | 批量：确认删除 / 保留 / 是某新行的修订 |
| 新行无对应旧行 | 归入「新增候选」桶 | 批量：确认新增 / 忽略 |

关键改动：**预览必须给出每个账户的五类计数与金额影响，且未处理完的桶不允许确认**（现在是抛异常拒绝，体验差且不可处置）。这就是你要的"闭环"，但代价比逐行配对低一个数量级。

### 分歧 3：`integration.h3` 不能"直接替换"，要"并行过渡 + 一期切换"

你说"逐步改为 `cashflow.read` 等独立权限"。**逐步**这个词要落成具体动作，否则会出现"改完权限后财务看不见页面"：

- 现在能访问这个页面的只有拥有 `integration.h3` 的人（管理员）
- 新权限 `cashflow.read/write/reconcile/manage` **必须同落 `system_permissions` + `system_feed_actions` + `system_role_feature_grants` 三处**（项目铁律：只加 `permissions` 不落 grants，等于没授权）
- 过渡期用 `@RequirePermission({"cashflow.read","integration.h3"})` —— 注解是 **any-of** 语义，两码都能进，切换零中断
- 财务角色配置完成后，再单独一次迁移把 `integration.h3` 从日记账端点摘掉

### 分歧 4：三个视图的默认值要按"月末财务在做什么"定，不是按"流水最重要"定

你建议"流水明细为默认主视图"。我认同它是**记账主战场**，但请确认一个细节：**月初头几天的实际工作是"上月对账 + 结转"，不是记账。** 建议默认视图跟随日期：月初 1~5 号默认落在「对账核对」，其余时间默认「流水明细」。这一点你可以直接否掉，改动成本只有一行。

## 4. 目标设计

### 4.1 页面结构（一个工作台，路由不变）

`/cashflow-journal?tab=entries|accounts|reconcile&start=&end=&accountId=`

| 视图 | 面向 | 核心内容 | 复用的项目组件 |
| --- | --- | --- | --- |
| 流水明细（默认） | 记账、查账 | 期间流水表（含**结存列**、来源标签、核对状态、行操作）+ 顶部期间指标卡 + 新增/导入/导出 | `ListPageLayout` `SearchToolbar` `LqPagination` `MetricGrid` `DataState` |
| 账户汇总 | 查家底 | 账户期间报表（保持现有口径）+ 主体筛选 + **点击账户直接跳流水明细并带期间** + 账户管理入口 | 同上 + `LqDialog` |
| 对账核对 | 收尾、确认 | 三类独立结论：银行余额对账 / 导入差异处置 / 平台结算核销 | `LqTabs` 内嵌 + `BatchActionBar` |

**必须拿掉的**：12 个月月报抽屉。月报应作为「账户汇总」视图里的**展开行**（`el-table` 的 `expand`）或独立列组，不要藏在抽屉。

### 4.2 流水明细的列设计

按你的三组字段，落成可执行列清单：

| 组 | 列 | 说明 |
| --- | --- | --- |
| 定位 | 日期、账户、收支方向 | 方向由 income/expense 哪列非空推出，不新增列 |
| 金额 | 收入、支出、**结存** | 结存目前页面没显示，是缺口 |
| 业务 | 业务分类、摘要、往来对象、经办人、开票状态 | `biz_category` 新增列；`supplier_raw`/`counterparty_raw` **原样保留不合并** |
| 状态 | 来源（氚云导入 / 手工 / 银行）、核对状态、锁定 | 三个独立徽标，**不合成一个"已核对"** |
| 操作 | 编辑 / 作废 / 查看来源 | 仅 `external_source='MANUAL'` 或未锁定行可编辑 |

**关于"供应商"**：你的判断正确 —— 不要强制关联供应商档案。现有 `supplier_raw`（原文）与 `counterparty_raw`（客户供应商）已分开存，**再加一个 `biz_category` 就够**，不要为了"往来对象"去建外键关联（涉及 1129 个不同供应商文本，关联成本远高于收益）。

### 4.3 对账核对的三类结论（必须分开存）

| 类型 | 判定对象 | 数据落地 | 与另两类的关系 |
| --- | --- | --- | --- |
| 银行余额对账 | 账户 × 期间 | `cashflow_reconcile_confirmation(account_id, period_start, period_end, statement_balance, system_balance, diff, status, confirmed_by)` | 独立 |
| 导入差异处置 | 导入批次 × 流水 | `cashflow_import_decision(batch_id, entry_id, decision, decided_by)` | 独立 |
| 平台结算核销 | 收银通交易 × 银行流水 | 复用 `cashier_log`，加关联表 | 独立 |

一笔流水可以同时"银行已核对"且"客户回款未核销" —— 所以**绝不能用一个 `reconciled` 布尔列**。

### 4.4 跨年度与期初（必须一期就解决，不能留）

```
账户期初(年Y) = cashflow_account_opening.amount  WHERE account_id & fiscal_year = Y
期间期初 = 年度期初 + SUM(该账户 entry_date >= Y-01-01 AND entry_date < start 的 收入-支出)
```

2026 年的 `cashflow_account_opening` 种子 = 现有 `h3_cash_accounts.opening_balance`（35 行，一次性迁移）。**注意上面第 ③ 条的 5 户问题**：种子迁移时如实搬值，同时把这 5 户列入首轮对账清单，不要静默修数。

年度结转 = 上一年的期末自动成为下一年的期初候选（需人工确认后生效），不是自动写入。

## 5. 实施路线（对映你的四阶段，细化为可验收单元）

### 阶段一：页面重构，零数据库变更

| 单元 | 产出 | 验收 |
| --- | --- | --- |
| 1.1 视图重排 | 三视图 + URL 参数 + 月报从抽屉移到展开行 | 期间/账户/视图三参数可分享、刷新不丢 |
| 1.2 流水表升级 | 加结存列、来源标签、行操作占位、`MetricGrid` 期间指标 | 与库里 8751 行逐行一致 |
| 1.3 组件统一 | 换 `ListPageLayout`/`LqPagination`/`DataState`，删自建 CSS | 页面无自定义分页与空态 |
| 1.4 账户下钻 | 点击账户跳明细并保留期间 | 期间不变、账户筛选生效 |

**这一阶段可以今天就开始，不动库，风险最低。**

### 阶段二：写入能力 + 稳定身份（1 次迁移）

迁移内容（版本号现查现用，当前基线 V401）：

1. `h3_cashflow_entries` 加列：`account_id BIGINT NULL`、`biz_category VARCHAR(32) NULL`、`voided_at DATETIME NULL`、`void_reason VARCHAR(255) NULL`、`reconcile_status VARCHAR(16) NOT NULL DEFAULT 'NONE'`、`locked TINYINT(1) NOT NULL DEFAULT 0`、`manual_note VARCHAR(500) NULL`
2. 建 `cashflow_account_opening(account_id, fiscal_year, amount, source)`，种子 35 行
3. 建 `cashflow_reconcile_confirmation`、`cashflow_import_decision`
4. `UPDATE h3_cashflow_entries e JOIN h3_cash_accounts a ON a.account_name=e.account_name SET e.account_id=a.id`（8751 行，单会话内毫秒级）
5. 加索引 `idx_cashflow_account_date(account_id, entry_date)`

写端点（全部带幂等键 + 同事务审计）：

- `POST /api/cashflow-journal/entries`（手工新增，`external_source='MANUAL'`）
- `PUT /api/cashflow-journal/entries/{id}`（仅 MANUAL 或未 locked；改写留审计快照）
- `POST /api/cashflow-journal/entries/{id}/void`（**作废不删除**，`voided_at` 置位，报表排除）
- `GET/POST /api/cashflow-journal/accounts/{id}/opening`

**关键约束（必须写进代码注释）**：导入 upsert **不允许覆盖** `MANUAL` 行，也不允许覆盖任何人工字段（`biz_category`、`manual_note`、`reconcile_status`）。现在的 `ON DUPLICATE KEY UPDATE` 会覆盖全部业务列 —— 这是安全隐患，阶段二必须改。

### 阶段三：导入与对账闭环

1. 导入预览改为"五类计数 + 金额影响 + 待处理桶"，未清空桶不允许确认（替换现在的抛异常拒绝）
2. `cashflow_import_decision` 落人工决定，`OLD_ONLY` 支持批量处置
3. 把 `isCashflowData()` 的自动 DELETE 改为**预览里显性列为"空占位行 N 条待清理"**，由人确认（现在是无提示自动删）
4. 账户余额对账：录入银行对账单余额 → 算差额 → 列出未核对流水 → 确认
