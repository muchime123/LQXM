# 任务单产品与配置（设计定稿）

> 2026-10-21 定稿。本页 `/manufacturing-task-configs`（导航「制造域 · 任务单产品与配置」）是**生产任务单取数的底座**：
> 上游决定「这个车间能生产什么、能勾什么配置」，下游决定「这张任务单每道节点该等几天」。
> 参考间隔的算法细节另见 [产品级参考间隔](production-tracking-product-duration-20261020.md)，样本质量见
> [样本质量报告](production-tracking-duration-quality-20261020.md)，本文只定结构与边界。

## 一句话

产品身份＝**车间 + 产品名称文本**（没有编码、没有冗余副本）；配置＝**产线级勾选项清单**（不与产品关联、不进产品名）；
参考间隔挂在**产品 × 节点**上，未发布就沿用车间基准。

> **定位（2026-10-21 LQ 修订，推翻了本页此前的「本地产品主数据」假设）**
>
> 两类配置都是**氚云生产任务单下拉字典的镜像**，不是本地主数据：
> `PRODUCT_NAME` ← 「产品名称」下拉项，`OPTIONAL_CONFIG` ← 「可选配置」下拉项。
> 能不能被选中由氚云决定，LQXM 既不判断、也不用本地开关去模拟。本页只负责一件事：
> 把「产品 ↔ 历史生产任务 ↔ 跟单节点参考间隔」对上，并保留一份与氚云一字不差的选项清单。
> 早期在本地人工整理的产品档案不准确，与本页无依赖关系，**暂不合并**（等档案足够准了再谈映射）。
>
> 由此产生的四条硬约束（都已落地，改代码前先读）：
> 1. **两类配置都没有「启用/停用」**。产品匹配（跟单参考工期、产品级基准矩阵、覆盖率）一律不判 `active`，
>    可选配置也没有开关；`active` 列已随 V400 删除。否则「氚云照常在用 + 本地被停用」会让该产品所有
>    在制单静默退回车间基准，页面上还没有任何提示。
> 2. **名称只读**。产品身份是文本匹配键，可选配置与工单 `optional_configuration` 也是文本对齐；
>    本地改名只断本地匹配，氚云那边仍叫原名。没有 `PUT /task-configs/{id}`（405）。
> 3. **补录是唯一的本地写入路径**，所以必须有删除作纠正；删除按类型带硬保护（见 §7）。
> 4. **补录文本必须逐字照抄下拉项**（空格、括号、全角半角都算）。否则不是「多一个选项」，
>    而是「一个永远匹配不上的孤儿选项」。

## 0. 先分清两个「可选配置」

这是本页最容易混淆、也最容易改错的一条。库里同名两样东西，生命周期、消费方完全不同：

| | 本地主数据（本页维护） | 工单字段（氚云带过来） |
|---|---|---|
| 表/列 | `manufacturing_task_config_items.config_type='OPTIONAL_CONFIG'` | `production_orders.optional_configuration` |
| 形态 | 70 条平铺的选项值（`灌装(量杯式)`/`易撕口`/`出口木箱`/`双工位`…） | 单张单上的自由文本，多个值用 `;` 拼（`出口木箱;易撕口`） |
| 谁写 | 氚云任务单「可选配置」下拉字典的镜像；本地只做补录/删除 | 氚云导入（只读） |
| 谁读 | **目前无人读**（0 消费方） | 跟单：`ProductionTrackingPolicy.configuredOptionalStage()` 判定「氧化/木箱」节点是否适用 |
| 作用 | 建单时的勾选候选（等建单页落地才生效） | 已生效：决定按需节点出不出现在跟单里 |

结论：**配置不进产品名**（2026-10-21 LQ 定），它的去向是「建单时勾选 → 落到工单 `optional_configuration` 文本 → 驱动按需节点」。
在「新建任务单」页落地之前，这 70 条只是产线能力清单，读不到不要当 bug 查。

## 1. 数据模型

### 1.1 三张主表

| 表 | 角色 | 关键约束 |
|---|---|---|
| `manufacturing_workshops` | 生产车间 | `workshop_name` 唯一；`enabled`；`default_process_template_id`（建单时默认制程） |
| `manufacturing_task_config_items` | 车间下的配置行 | `config_type` ∈ `PRODUCT_NAME`（产品名）/ `OPTIONAL_CONFIG`（可选配置）；业务唯一＝`(workshop_id, config_type, config_name)` |
| `production_tracking_product_benchmarks` | 产品 × 节点的参考间隔 | 唯一键 `(task_config_id, stage_code)`；随产品行级联删除 |

车间基准仍在 `production_tracking_node_benchmarks`（按 `workshop_kind` 分封口机 / 其他机器），作为**产品的兜底**，两套并存是刻意的。

### 1.2 产品身份＝`workshop_id` + `config_name`

- **没有 `config_code`**。历史上它有三种口径并存（`BP-00000001` 种子 / `BP-H3YUN-<uuid>` / `BP-<uuid>`），页面从不展示、全库没有一张表拿它做关联键——已在 V398 删列。需要编码时再用 `id` 派生，不预埋第二真相。
- **没有 `workshop_name` 副本**。副本靠 `ManufacturingTaskConfigController.updateWorkshopMaster` 里一句 UPDATE 手工级联，漏一处（导入 / 脚本 / 直改库）就与外键漂移，而旧匹配口径恰好读副本 ⇒ 静默错配到别的车间。V396 对齐过一次，V398 直接删列：车间名只有 `manufacturing_workshops` 一个来源。
- 其余删掉的列（V398，均确认零消费）：`product_type`（由名称字面推 `PART`/`MOLD`，改名不重算 ⇒ 漂移）、`option_group_code`（全 `UNCLASSIFIED`）、`sort_order`、`process_template_id`（制程自 2026-10-20 起按车间分配）。

### 1.3 为什么不做「产品 × 配置」关联表

按需求直觉会想给每个产品挂它能选的配置，但：

1. 真实的配置维度是**产线级**的（全自动车间的灌装方式，半自动车间根本不用），按产品挂会把同一份清单复制 13 遍；
2. 更关键的是产品名**不含配置**（`LQ260气调机卷膜` 而不是 `LQ260气调机卷膜·气流式·色带打码`），氚云 6038 张历史单里 `product_name` 从未出现「灌装」字样（实测 0 命中）——没有「产品名 = 型号 + 配置串」的拆分口径，任何关联表都只是摆设。

⇒ 配置保持产线级平铺；若将来要做「某产品不支持某配置」，再补一张稀疏的**排除表**（默认全可用），不要反过来做全量笛卡尔。

## 2. 页面结构

单页三列，无 Tab（1500px 以下降为两列、参考间隔落到底部整行；900px 以下单列）：

```
┌ 全局状态条：四个数字都是入口（点开「按车间+产品」的覆盖率明细）· 参考日期口径说明
├ 左 210px 生产车间   │ 中 弹性 产线详情                                  │ 右 ≥430px 选中产品的画像 + 节点参考间隔
│ 卡片：默认制程      │ 默认制程卡 + 任务单产品表 + 可选配置表              │ 画像卡（历史任务 / 已建跟单 / 有效样本段 + 最近 5 单）
│ 产品数 / 配置数     │ 产品表行可点选，选中驱动右栏；表头可排序            │ + 节点表（车间基准 / 本产品间隔 / P50·P75 / 来源）
└───────────────────┴──────────────────────────────────────────────┴────────────────────────
```

**下钻链（2026-10-22 定，四层都可达）**：页头统计数字 → 覆盖率明细（按车间+产品，可筛「有跟单 / 唯一匹配 / 未匹配或重名 / 已有发布」）→ 点行跳到该车间该产品（右栏节点间隔）→ 产品表「历史任务单 / 跟单记录 / 发布节点」三个数字分别点开历史任务抽屉、样本明细抽屉、节点发布明细。
- 页头统计的四层下钻走新端点 `GET /manufacturing/master/duration-coverage/breakdown`，判据与 `/duration-coverage` 同源（`configCount===1` 才算匹配），一行＝「车间 + 产品名」，带回 `configId` 供点行进产品；产品名为空的单自成一组（`configCount=0`），属源数据缺口，不隐藏。
- ⚠️ **中栏数字必须落到「被点的那一行」**（2026-10-22 修）：这两个按钮都 `stopPropagation`、不触发 `row-click`，早期实现里只开了抽屉、没先改选中项，于是点 B 行看到 A 行的数据且不报错。现在打开前先 `selectedTaskConfigId = row.id`；样本抽屉还要 `await nextTick()`，等新的 `taskConfigId` 传进右栏面板后再开，否则抽屉拿到的仍是上一个产品。

**中栏 · 产品表**（2026-10-21 起是「字典 + 关联数据」，不是管理表）：产品名**只读文本**（唯一弹性列）、**历史任务单**数（同车间同名的 `production_orders` 全部张数，只表示这个产品做过多少单）、**跟单记录**数（其中的已建跟单记录张数，**这才是参考间隔的样本基数**）、已发布节点 `x/y`、删除。两列必须同屏：2026-10-21 实测「手动片膜」历史任务单 1116 张、跟单记录 103 条，只显示前者会让人以为样本有上千条。
- **两个数字都是入口**（2026-10-21 新增）：点「历史任务单」打开该产品的历史生产任务明细抽屉（单号 / 状态 / 申请日 / 排产日 / 要求交期 / 数量 / 是否已跟单 + 完成节点 x/y）；点「跟单记录」打开右栏同一个样本明细抽屉（每单每段间隔、计入还是排除、为什么）。数字不可点就是死数，用户只能靠猜。
- **「发布节点 x/y」也是入口**（2026-10-22 新增）：点开节点发布明细（节点 / 区间 / 发布值 / 来源（人工·P50·复制 + 发布日）/ 样本与零天 / P50·P75），未发布的节点同样列出并显示「沿用车间」，回答的是「差的到底是哪几个节点」。编辑仍在右栏。
- **表头排序 + 默认跟单记录降序**（2026-10-22 LQ 定）：产品名（中文 Collator，`numeric` 模式）、历史任务单、跟单记录、发布节点四列可排序，首次进入默认 `trackedTaskCount` 降序。理由：历史任务单多但没人跟单的产品对参考工期没有价值，按跟单记录排才能让「能算出间隔的产品」浮在前面。排序在本地做（单车间仅二十来行、一次全量加载），不加后端参数。
- **没有启用列、没有「含停用」勾选、没有行内保存**：产品全部参与匹配，能否下单由氚云决定（见开头定位）。
- **名称不可改**：没有 `PUT /task-configs/{id}`（整体下线，请求返回 405）。补录错了删掉重录。
- **「补录产品」是低频例外**：名称必须与氚云下拉项逐字一致（文本匹配，空格/括号/大小写都算）。行上打「本地补录」标签（`external_source='MANUAL'`）以便与字典来源区分。
- **重名要提示不猜测**：`sameNameCount > 1` 时打「重名 ×n」标签。同名多行时参考日期匹配**不猜**，全部回落车间基准——把这个歧义显示出来，而不是让它静默失效。消歧手段是删掉多余的那行（名字不能改）。
- 选中态只用一个受控 class（`is-selected`），不叠 Element 自带 `highlight-current-row`——两套高亮会在抽屉/弹窗焦点变化后互相打架，出现「莫名高亮」。

**中栏 · 可选配置表**（产线级，不随产品切换）：配置名**只读文本**（与产品表同样的口径：氚云「可选配置」下拉字典的镜像）、搜索框、删除；行上同样打「本地补录」标签与「重名 ×n」提示。**没有启用列、没有行内保存**。目前**没有维度/分组**——见待决项 P1。
- 这类名称虽然不影响产品匹配，但影响**按需工序判定**：工单 `optional_configuration` 里出现「氧化 / 木箱」时才生成对应节点，本地改一个字（如「木箱」→「木箱包装」）不会改到氚云，只会让本地字典与工单文本对不上。
- 删除保护走文本整项匹配：作为独立一项出现在该车间历史任务的 `optional_configuration` 里 → 409（2026-10-21 实测 70 条里 67 条真被用过）。用 `LOCATE(CONCAT(';',?,';'), …)` 而非 `LIKE`——配置名里带下划线时 `LIKE` 会把它当通配符放宽。

**右栏 · 产品画像卡**（2026-10-21 新增，`ProductProfileCard.vue`）：选产品后右栏顶部先给「这个产品是什么」——产品名 + 车间 + 已发布 `x/y`，三格指标（**历史任务 / 已建跟单 / 有效样本段**），下面挂最近 5 张历史任务（单号、申请日、状态、`完成 x/y 节点`或「未跟单」），「查看全部」进明细抽屉。
- 三个数字的口径与中栏完全同源（同一份 `product-orders` 接口），不另算一套：`历史任务` = 该车间+产品名的全部 `production_orders`（**含草稿与已取消**）；`已建跟单` = 其中 `production_tracking_state` 存在的张数；`有效样本段` = 样本明细里 `used=true` 的段数之和。**三格都是入口**（2026-10-22 补齐，原先「有效样本段」是不可点的静态格）：历史任务 → 任务抽屉，另两格 → 样本明细抽屉。
- **含已取消是刻意的**：配置页的计数本来就含它们（存在即历史），明细若剔掉就会「数字 1116、点开只有 1113」，看起来像丢单。页面上把已取消单独标注（「含 3 张已取消」+ 状态标签），而不是从分母里抹掉。
- 有效样本段需要 `manufacturing.baseline.manage`（读样本接口）；没有权限时该格显示「—」而不是误导性的 0。

**右栏 · 节点参考间隔**：见 §3。

## 3. 参考间隔：挂在产品上，兜底到车间

### 3.1 匹配与生效

```
生产任务（production_line + product_name）
  └─ 按「车间名 + 产品名」精确匹配产品配置行（**不判启用状态**）
       ├─ 唯一命中 → 该产品该节点已发布 → 用它
       │                          未发布 → 车间基准
       ├─ 没有命中 → 车间基准
       └─ 同车间同名多行 → 不猜，全部车间基准
```

产品名原文**永不改写**。节点序列按车间类别定（车间名含「封口」即封口机序列），两类节点数与必经节点数：

| 车间类别 | 全部节点 | 按需工序 | 必经节点（进度分母） |
|---|---|---|---|
| 封口机 | 备料 / 模具生产 / 氧化喷特氟龙 / 组装 / 入库 / 木箱 | 氧化、木箱 | **4** |
| 其他机器 | 画图 / 备料 / 钣金 / 模具 / 组装 / 调试 / 入库 / 木箱 | 木箱 | **7** |

「已发布节点 x/y」的分母＝**必经节点**，分子也只数必经节点：按需工序没做不算缺，否则分母虚高、永远显示不满。

### 3.2 三种发布来源

`published_source` 三态，界面标注「谁定的、什么时候定的」，撤销后回到 `NULL`（＝未发布）：

| 来源 | 触发 | 规则 |
|---|---|---|
| `MANUAL` | 单行「保存」 | 0~60 天；空值保存＝**撤销发布**（清发布值与来源、留候选、回车间基准） |
| `P50` | 「按 P50 填充」 | 只补「未发布 + 候选 ≥ 8 段 + 零天占比 < 50%」，已发布不动（2026-10-21 晚收紧，原 3 段——外部复查 P1：3 段门槛一条补录就能定参考值，且封口机备料/入库零天占比 73%/90% 不适合自动发布；零天多的节点人工看样本后单行发布。**只限批量填充**，管理员单行手工发布不受限） |
| `COPY` | 「复制其它产品」 | 只补目标产品**未发布**的节点；源与目标必须同车间类别（节点序列不同不能复制）；不能从自身复制 |

三条都留审计（`row_change_log`，目标表 `product_archive.production_tracking_product_benchmarks`，撤销记 `DELETE`）。

### 3.3 候选怎么算（与样本明细同源）

样本＝该产品自己的**跟单记录**（`production_tracking_state` 存在，且 `production_line + product_name` 精确匹配；已取消单排除），**不是**该产品的全部历史任务单——6038 张任务单里目前只有 593 条跟单记录（2026-10-21 实测）。只取了跟单记录里已登记完成日期的节点，算「上一节点完成 → 当前节点完成」的自然日：
- 首节点锚点**从排产时间起算**（2026-10-21 LQ 定）：优先级＝本地计划开工 `t.planned_start_date`（0/593 全空，实际不命中）→ **氚云排产时间 `p.schedule_time`（585/592 有值）** → 申请日兜底；前两者算排产锚点、首段进正式候选，申请日兜底片段单独计数与分位，不进正式 P50/P75（仅 7 条）。
- 排除：缺锚点、缺相邻节点完成日、日期倒序、完成日在未来、间隔 > 60 天；零天间隔**保留但单独展示**（发布前抽查是否批量补录）；
- 按需节点没有记录就跳过，不进分母；
- P50/P75 线性插值、保留 1 位小数。超参考日期只提醒填原因，**不阻断**跟单保存。

「样本明细」抽屉把每条跟单记录的锚点、每段天数、被排除原因摊开——发布前抽查的依据，否则产品行上只有一个「P50 3.0 / 75 段」，看不出能不能信。抽屉顶部的「命中数」已改为**跟单记录条数**（原先按全部历史任务单计，会显示成 1115 条）。

## 7. 不做什么（明确边界）

1. **不做产品编码**、不做产品 × 配置关联表、不用配置拼产品名（§1.2 / §1.3）。
2. **删除按来源分级**（2026-10-21 晚，外部复查 P0 修正）：
   - **第一道闸＝来源**：`external_source='H3YUN'`（氚云字典镜像行）**一律不可删**——没被用过 ≠ 氚云侧不存在，
     可能是新增还没人下单的项；氚云真正移除后随导入同步消失，本地不替氚云做主。
     （此前的「有历史任务/被用过才拒绝」判据有漏洞：氚云新导入的下拉项会被误放行。）
   - **第二道闸＝使用证据**（只对本地补录 `MANUAL` 行生效）：
     产品：`production_tracking_product_benchmarks` 随产品行级联删除 ⇒ ① 已有参考间隔记录（含只有候选统计的）→ 409 拒绝；
     ② 该车间 + 该产品名能匹配到历史任务单 → 409 拒绝。可选配置：作为独立一项出现在历史任务
     `optional_configuration` 里 → 409 拒绝。两条闸都不占的 MANUAL 行必然是补录错了的，删掉零损失。
3. **不做「不适用 / 待确认」状态**，也不改节点完成判断——这一版只做「间隔从哪来」。
4. **不把参考间隔搬回「制程与工序管理」页**：那页是氚云实际工序主数据，氚云工序不按时报工，与跟单节点口径无关。
5. **任务级动态节点模板**属下一阶段：实施前必须先统一后端节点白名单、列表进度 SQL、详情、Excel 导入导出与历史兼容，不能只改配置页。

  `ManufacturingTaskConfigControllerTest` 钉死「列表不 select active、新增不写 active、无改名端点、覆盖率唯一匹配判据、删除＝来源闸（H3YUN 一律拒）＋MANUAL 使用证据保护、可选配置整项匹配」。
- 接口层：`PUT /api/manufacturing/master/task-configs/{id}` → **405**（端点整体下线）；`DELETE` 对产品/可选配置分别按上述保护返回 409 或 200。
  产品历史任务明细（2026-10-21 活体实测）：「手动片膜」`total=1116 / tracked=103 / cancelled=3 / draft=3`，与列表两列 `1116 / 103` 完全一致；`requiredStageCount` 封口 **4**、机器 **7**；`status=已取消` 返回 3 行且 `summary.total` 仍为 1116（画像不随筛选跳动）；500 行全扫 `doneStages ≤ 4`，无越界。
