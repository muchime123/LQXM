## 0. 结论先行

### 0.1 一句话总评

**14 类数据的价值不在数据本身，在于它用真实体量证明了「哪些业务口径可自动化」，也用真实脏度暴露了「ERP 设计期必须堵死的 9 个结构性缺口」。**

### 0.2 三个最重要判断

| # | 判断 | 依据 |
|---|---|---|
| 1 | **「金额/数量」类字段可以先信氚云的，但「身份/关系」类字段必须重建** | 销售出库金额→收款权威链已验证闭合；而客户关联 1457 条未关联、开票资料 customer 关联率仅 3.2% |
| 2 | **ERP 不能用「名称」做任何业务主键** | 供应商无编号（必须建别名表）、产品编号跨台账冲突 47 组、同物不同码 354 组、客户 `customer_name == customer_code` 384 条 |
| 3 | **ERP 不能按「单据一行一事实」建明细，必须预留「一行承载多子表」能力** | 开票申请实测 11 537 行同时携带「开票内容」+「收款引用」；调拨主表两个同名「仓管员」列 |

### 0.3 源数据缺口（需向业务侧索取）

这些东西**在现有 14 类里根本不存在**，靠本地推导补不出来，是 ERP 闭环的硬缺口：

| # | 缺什么 | 卡住什么 | 严重度 |
|---|---|---|---|
| G1 | **采购付款单**（付款事实 + 核销关系） | 应付账龄、供应商对账、付款计划全做不了。实测 `purchase_receipts.paid_amount` **10 487 单全为 0** | 🔴 高 |
| G2 | **实际开票记录**（发票号、开票日期、红冲） | 开票进度只能有「申请」，没有「实际」。实测 `sales_outbounds.invoiced_amount` **18 966 行全空** | 🔴 高 |
| G3 | **生产实耗/报工明细** → **09-17 更新：已找到「报工」一半的源**。氚云「报工单」12 252 行（工单×零部件制程完工报工，4 997/5 691 工单覆盖 87.8%）。⚠️ 它是**工序完工事实**（谁/何时/哪车间/报了几件），**不是材料领用实耗**——「是否使用零部件库存」全「否」、库存调用全 0，氚云从未启用领料。BOM 材料实耗/损耗率仍缺 | 工序进度与完工事件有源；成本归集仍缺材料实耗 | 🟠 中（补了一半） |
| G4 | **退货/换货单** | 销售退货目前只能从出库表推断，无独立单据 | 🟠 中 |
| G5 | **盘点单** | 氚云盘点表已停更（32 单），「其他入库」备注「调整库存」实为盘点替代承接 | 🟠 中 |
| G6 | **客户经营属性**（类型/行业/信用代码/规模） | 客户分层、信用额度、账期策略无依据。实测 6 个经营字段**100% 缺失** | 🟡 低 |
| G7 | **经销商与终端客户的归属关系** | 三层渠道模型只到「利强→经销商」，「经销商→其终端客户」无表 | 🟡 低 |
| G8 | **模具/工装台账** → **09-17 更新：生产任务单里已有半结构化模具字段**——`入库模具名称` 762 值、`模具入库数量`（1 264 单非空）、`是否需要额外模具`/`额外模具数量`、`模具入库进度`。但仍**无独立模具主档、无「模具↔适用机型」关系**，名称是自由文本（如「套278x197用184x128模具」） | 模具可从任务单字段起步建主档（关联 Q3 拍板） | 🟡 低（有源可扩） |

> G1/G2 是**最优先**的：应付与开票两条线目前都是「只有一半」的状态，ERP 若照现有数据设计，会天然缺失这两个闭环。

### 0.3.1 报工单与生产任务单补充探查（2026-09-17，G3/G8 取证）

LQ 提供「报工」导出件（此前未纳入 14 类），与「生产任务单管理」对拍后的发现：

**报工单**（12 252 行 / 32 列，最新报工 2026-09-17 14:12——**活表单**）：

- **粒度 = 生产工单 × 零部件制程**：`生产工单编号`（SCGD 前缀）4 997 去重，与已导入 `production_orders` 精确可关联；`零部件流水号` 全氚云只有 **10 个值**——所谓「零部件」实为 10 个固定**工序模板**（设计/画图、采购/下料、钣金加工/机壳、表面处理/氧化、模具加工、零部件组装/所有组件…），不是物料清单（BOM）。
- `报工数量` 29 个去重值（小整数 1/2/8/3），`是否超额生产` 全「否」、`是否自定义报工数量` 全「否」——报工量由工单需求带出，不是自由填报。
- `数据状态` 全「已生效」：报工即时生效无审批流；但氚云无撤销原语（C7），误报无法红冲 → ERP 必须设计报工冲销。
- `报工人` 含 `Anonymous`（未登录扫码）；同名列 ×2：`生产零部件`（F0000039/F0000002）与 `报工人`（F0000005 主报工/F0000038 辅助 22 人）——调拨「仓管员」同款坑。
- 空壳列：`已生产数量`（9 996 非空全 0）、`生产工单中是否有该零部件`（全 0）、`销售订单编号`（全空）、`上传设计文件`（全空）。
- 一行多角色又一例：报工单同时携带 `接单员`（陆伟/李玉强）与 `入库员`（曹义山/李玉强）——「报工→接单→入库」三事实塞一张表。

**生产任务单管理**（14 551 行 / 97 列，与已导入 `production_orders` 5 691 / `production_order_components` 14 367 精确同构）：

- ⚠️ **生产工单 ↔ 销售订单在氚云里是断的**：`销售订单编号`/`关联销售订单`/`产品订单子OBJid` 全空，`计划类型` 全「非合同生产」。单据链「订单→生产」目前靠人工对——ERP 必须把这条链建起来（契约的订单占用/领用正是为此）。
- `数据状态` 有 草稿/进行中/已生效/已取消 四态（报工单只有已生效）——同域两表状态语义不同。
- **Q3 的直接证据**：`填充配置项展示` 一列 = 产品名称 × 盒子形状 × 盒子尺寸 × 模具排列 × 材质 × 插头 × 电压 × 品牌 的拼接串；实测基数：产品名称仅 **40**、盒子尺寸 **1 740**、模具排列 **18**、盒子形状 48（打印列）、电压 8、品牌 27——若按全组合建 SKU 必然爆炸，「型号 SKU + 订单行配置属性」是唯一可行粒度。
- `备注` 4 945 条高价值自由文本，含**模具互换性**线索（「做能和278*197互换的机型」）——互换是属性关系，不是新 SKU。

**索取建议**：不需要全量导出，**每类 1 条完整链 + 1 条异常链**即可（对应蓝图 D09 的取证办法）。
G1/G2/G3 恰好就是蓝图 D09 的原文：「采购付款、实际开票、生产实耗是否有可靠流程和凭据」。本文为该决策项提供了实测依据——**答案是：现有数据里没有**。

### 1.1 已跑通并被验证的口径（可以直接带进 ERP 设计前提）

| # | 口径 | 验证方式 | 结论 |
|---|---|---|---|
| V1 | **收款权威 = 销售出库主表内嵌收款快照** | 18 966 单出库，`receipts` 6 452 条与快照做交叉核对 | ✅ 成立。财务多轮确认，`receipts` 只做关联+校验，**不重复建收款事实**。⚠️ **这是历史样本口径，不是 ERP 规则**——ERP 仍须建独立的收款单+核销关系（见 §1.3） |
| V2 | **采购价唯一来源 = 产品信息台账 `purchase_price`** | 产品台账 14 520/15 304 有值（94.9%）；仓库明细 `purchase_price` **16 319 行全为空** | ✅ 成立。仓库明细的采购价是**空槽位**，设计时不得作为取值来源 |
| V3 | **开票口径只能来自开票资料/开票申请** | `sales_outbounds.invoiced_amount` 18 966 行**全空** | ✅ 成立。出库表不具备开票能力，ERP 必须独立开票域 |
| V4 | **库存合并必须先解析身份、再按（仓库, 解析后产品）聚合** | 修复前每轮 60+ 伪更新；修复后 harness 两轮 CREATE/UPDATE/VANISHED = 0 | ✅ 成立。**不能按编号分组**（会把同编号不同产品拆散）、**不能按名称分组**（会把同名不同规格混同） |
| V5 | **业务键必须含单位** | 21 组同编号多单位；仓库明细唯一键 = 仓库+编码+单位；切刀曾因不含单位 37→24 丢 13 行 | ✅ 成立。ERP 的库存键必须显式含单位维度 |
| V6 | **多候选一律不自动绑定** | 客户 `resolveCustomer` 降级链实测；产品归类只自动执行唯一候选 | ✅ 成立。ERP 的所有身份解析都应遵循「唯一命中才自动，多候选进人工」 |
| V7 | **草稿单保留但排除出正式口径** | 18 966 - 18 855 = 111 单草稿 | ✅ 成立。ERP 必须有独立草稿态，且草稿不参与统计分母 |
| V8 | **单据编号与内部 ID 必须分离** | 采购入库主表「数据ID」列被子表列首命中吞掉，bare「数据ID」取到的是明细行 UUID | ✅ 成立。ERP 幂等键用内部 UUID，业务单号只做冲突校验 |
| V9 | **供应商无编号 → 别名表是必需的，不是优化** | 76 条供应商无一有编号；73 条别名；混内部车间 4 条；未命中不静默新建 | ✅ 成立。ERP 往来方必须有别名表 + 人工确认门槛 |

### 1.3 ⚠️ 口径 ≠ 规则：不要把历史样本的妥协带进 ERP

**这是本文最容易被误读的地方，必须显式说明。**

历史样本里有大量「因为氚云做不到，所以本地这样折中」的口径。它们**证明了业务可行性**，但**不是 ERP 应该照抄的模型**。

| 历史样本口径（本地妥协） | 证明了什么 | ERP 应该怎么做（不得照抄妥协） |
|---|---|---|
| 收款权威 = 出库单内嵌快照（V1） | 出库金额与回款确实能对上，可信 | 建**独立收款单 + 核销分配关系**（契约 §7.1），出库单不承担收款权威 |
| 库存余额 = 两台账查询时并集 | 产品×仓库×单位的快照能表达库存 | 建**库存事件 + 余额**（契约 §6.1），快照只是期初来源 |
| 采购价取自产品台账 `purchase_price`（V2） | 采购价有可信来源、可用于毛利估算 | 价格进**独立价格/成本记录**（字典 §3.1），主档不承担历史成本账 |
| 重导容忍脏值 + 告警 | 真实脏度下链路能跑通、不崩 | 正式录入**校验并阻断**，不接受同样问题（蓝图 §1.1、§7） |
| 产品身份靠编号+名称+规格+单位降级链（V6） | 多字段降级能覆盖绝大多数场景 | 稳定 ID + CONFIRMED 映射表，降级链只用于**历史样本区** |
| `data_status='草稿'` 与 `outbound_status` 并存 | 草稿与正式单据能区分 | 审批状态与执行进度**分成独立维度**（契约 §3.1） |
| 用「备注/自由文本」表达原因 | 能人工还原业务场景 | **结构化原因码** + 依据引用（蓝图 §7） |

> **判据**：凡是历史口径里出现「因为氚云没有 X，所以用 Y 代替」的地方，ERP 都必须把 X 建出来，而不是把 Y 搬过去。本文 §2 各类的「ERP 设计输入」已逐条标注这一区分。


| # | 缺口 | 实测证据 | ERP 设计的硬约束 |
|---|---|---|---|
| **C1** | 名称被当身份键 | 供应商无编号；客户 `customer_name == customer_code` 384 条；开票资料 44 组同名户名 | 名称**永不唯一**。用稳定 ID 关联，名称/电话仅作**证据** |
| **C2** | 空壳值伪装成有值 | 供应商地址 5 278 行「非空」但去重后仅 1 个 `{"adcode":"","adname":"","Detail":""}` | JSON/结构字段必须**按内容判空**，不能按 `IS NOT NULL` |
| **C3** | 表头/列名会串 | 其他入库明细前缀被写成「其他出库明细.」；调拨两个同名「仓管员」 | 解析**不得依赖前缀或列名唯一性**；ERP 导入契约须锁定「语义标签 + 列序」双保险 |
| **C4** | 明细行可承载多类子表 | 开票申请 11 537 行同时携带「开票内容」+「收款引用」 | ERP 明细模型须支持**一行多角色**，不能假设「一行一子表」 |
| **C5** | 浮点残差导致永不收敛 | Excel `8.88e-16` 级残差 → 61 条记录每轮都判「有变化」 | 数量/金额一律**十进制定点**；比较用容差（1e-9）；**禁用二进制浮点** |
| **C6** | 阈值/口径变更无法回填 | `unchanged()` 的「修改时间回退判据」使新增列/改口径**不回填已入库行** | ERP 必须有**规则版本号**：口径变更即可触发定向重算，不依赖「源未变」偷懒 |
| **C7** | 缺少撤销/冲销原语 | 全链路无单行 REJECT；退货只能靠人工；调拨「调出仓=调入仓」只能告警 | ERP 从第一天就要有**红冲/更正单**模型，不能靠「改原单」 |
| **C8** | 权限粒度按「域」而非「对象」 | 持 `product_inventory.read` 任一即可读 A 域全量销售数据（历史过渡设计） | ERP 权限须**按对象 + 数据范围**，不做「一个权限看全量」 |
| **C9** | 状态语义混装 | 审批状态与履约进度混用一个 `status`；`data_status` 与 `outbound_status` 并存 | ERP 必须**分离审批状态与执行进度**（蓝图 §5.1 已提，此处有实测依据） |

## 2. 逐类口径与质量发现

> 每一类给：实测规模 → 跑通的口径 → 暴露的坑 → **ERP 设计输入**。

### 2.1 销售出库（18 966 单 / 35 159 明细）

**跑通的口径**
- 收款权威：主表内嵌收款快照（`sales_outbound_payment_snapshots` 20 186 行）是回款的唯一可信来源。
- 利润/毛利：`unit_price` 与 `purchase_price` 双价并存，未结算利润参考可算。
- 关联链：`customer_id` 缺失仅 209/18 966（1.1%），历史回填链路是通的。

**暴露的坑**
- `invoiced_amount` 全空（见 V3）。
- 出库明细里的 `stock_quantity` 是**当时快照**，曾被误当当前库存；现已明确禁止。
- 退换货无独立单据，只能从「业务性质推断」字段体现。
- 软删除客户的残留引用曾导致「关联统计虚高」——只看 ID 非空不成立。

**ERP 设计输入**
1. 出库单必须保存**当时快照**（客户名/业务员/仓库/价格），且快照与主档分离存储。
2. 「有效关联」判定必须是 `ID 非空 AND 目标存在 AND 目标未删除/未停用`，四条件齐全才计「完整」。
3. 出库单**不得内嵌收款金额作为权威**——ERP 要用独立的收款单 + 核销关系（蓝图 §5.1 已定），历史快照只作参考样本。
4. 销售退货须独立单据，不与出库混表。

### 2.2 生产工单（5 691 单 / 14 367 构成行）

**跑通的口径**
- 定制配置、制程、完工字段可解析；`production_order_components` 承载零部件构成。

**暴露的坑**
- **实耗侧缺失**：有构成（BOM-like）无实际领用/报工明细，成本无从归集。
- 工单与销售出库无显式关联键，只能靠产品+时间推断。

**ERP 设计输入**
1. BOM 与「实际耗用」必须是**两层数据**，ERP 不能只有一层构成表。
2. 工单必须与销售订单/出库行**显式关联**（`order_line_id` 一类），不接受推断。
3. 完工入库、检验、报工是三个独立事实（蓝图 §5.1「完成报工不等于已检验入库」有实测支撑）。

### 2.3 / 2.4 收款记录（2 425）与多订单结清（4 027）

**跑通的口径**
- 两类共用 `receipts` 表 + `receipt_type` 区分，方向正确。
- 「多订单结清」在语义上就是一收款对多单，天然是**核销关系**而非收款事实。

**暴露的坑**
- **与出库快照无核对链**：同一笔收款在两条来源里金额/日期不一致时，系统不提示。
- `receipts.receivable_amount` 曾出现语义错位（已收写在应收列）。
- 「选择出库单匹配开票内容」是日期+联系人+金额的**自由文本、无单号**。

**ERP 设计输入**
1. 收款与核销**必须分开建模**：收款是资金事实，核销是分配关系；取消核销不产生第二笔资金事实（蓝图 T03/T04 已定）。
2. 一个收款可分配多单、可部分分配、可产生未分配余额——需要有「可分配余额」概念。
3. 跨单/跨公司分配默认阻断（蓝图 T16）。
4. 任何「文本引用单据」的字段，ERP 中必须换成显式 ID 关联，文本仅作展示与人工确认线索。

### 2.5 产品信息台账（15 304）与 2.6 仓库明细台账（16 319）

**跑通的口径**
- 两张台账 = 唯一事实源，页面查询时组合、不落物化。
- 口径 util 单一来源（单位归一 / 费用项过滤 / 表头指纹）。
- 仓库明细粒度**天然稀疏**：13 726 个产品只出现在 1 个仓库。

**暴露的坑（这是全项目质量最集中区）**
- **编号不可靠**：47 个编号跨两张台账指向不同产品；354 组「同物不同码」；21 组同编号多单位。
- **采购价偏斜**：仓库明细采购价 100% 空（见 V2）。
- **零库存占比高**：14 572/16 319（89.3%）数量为 0；负库存 8 行（数据现象，非 bug）。
- **费用项混进数量列**：费用金额曾出现在「数量」列，需靠 `ProductFeeFilter` 名单过滤。
- **`product_code` 跨两张台账不稳定**：47 个张冠李戴码 + 354 个同物不同码。

**ERP 设计输入**
1. **禁止按编号聚合**，也禁止按编号做产品身份判定；编号只能作为**候选证据**之一。
2. ERP 的 SKU 身份 = 编码 + 名称 + 规格 + 单位 + 属性集合（蓝图 §3.2 `identityAttributes`），且有 **CONFIRMED 映射表**才能跨系统引用。
3. 单位归一 ≠ 数量换算：`UnitNormalizer` 含「kg/箱→kg」这类**文字别名**，但 ERP 必须把「文字别名 / 包装比率 / 计量单位」三者分开（字典 §4 已定，此处有实测来源）。
4. 包装换算**必须按产品定义**：A 一箱 12 个、B 一箱 24 个，不存在全局「箱→个」。
5. 数量/金额用 Decimal，禁用二进制浮点（C5）。
6. 零库存行**不等于**无效产品；下架是**状态**不是删除（状态化台账 V304 已验证）。

### 2.7 经销商信息（188 条）

**跑通的口径**
- 经销商是**渠道归属**，客户是**终端收货方**，两者必须分开。
- 出库单上 97 种 `dealer_name` 写法，导入台账后 100% 命中。
- 经销商名与员工名零交集的前提已被打破过：李楠（经销商）≠ 员工李南（LQ005）。

**暴露的坑**
- 经销商曾长期只有自由文本、无编号；五种脏写法（编号变体 / 对账后缀 / 前缀空格 / 职务混入 / 全角逗号）。
- TOP12 经销商里有 3 个无客户档案（李楠 531 单、耀星包装 299 单、金佰克 27 单）。
- 「经销商 → 它自己的下游终端客户」这层关系**没有表**。

**ERP 设计输入**
1. 往来方**一身份多角色**：一个对象可同时是经销商和客户（蓝图 §6.1），但渠道关系与往来身份**分开建模**。
2. 渠道关系要有**有效期**，历史单据保存当时归属，改了不覆盖历史（蓝图 §6.1 `dealerRelation.effectiveFrom/To`）。
3. 同名不同实体**不得自动合并**（李楠/李南的教训）。
4. 三层渠道模型若要完整，需补「经销商→终端客户」归属（见 G7）。

### 2.8 供应商信息（76 条 + 73 别名）

**跑通的口径**
- **无编号 → 别名表是唯一可行方案**，且已验证（`h3_supplier_aliases` 自愈：解析命中落别名，未命中不静默新建）。

**暴露的坑**
- 76 条里混了**内部车间 4 条**与串名脏值——供应商表不纯。
- `供应商地址` 是**空壳 JSON**（C2 的原始来源）。
- 主数据量极小（76），样本不足以验证「大量供应商」场景。

**ERP 设计输入**
1. 往来方分 `kind`（ORGANIZATION/PERSON），**内部车间属于组织，不得冒充供应商身份**（蓝图 §6.1）。
2. 主档合并流程必须有「证据 → 选择保留身份 → 冲突检查 → 授权确认 → 记录指向」，且**不批量改写已过账记录**（字典 §6.3）。
3. 别名歧义不自动匹配；多对象同别名合法（字典 §6.2 别名表）。
4. 地址按**结构化字段**存储 + 内容级判空（C2）。

### 2.9 采购入库（11 087 单 / 63 818 明细）

**跑通的口径**
- Σ金额一致率 99.94%（已验收）；供应商解析失败率 0。
- 幂等收敛（两轮 UNCHANGED，updated=0）。

**暴露的坑（应付侧系统性残缺）**
- `paid_amount` **10 487 单全为 0**、`unpaid_amount` 与 `uninvoiced_amount` 各 10 786 单非 0 —— **应付侧只有「欠」，没有「付」**。
- 幂等键选择有陷阱：主表「数据ID」列被子表列首命中吞掉，bare「数据ID」取到的是明细行 UUID → 必须用「采购入库编号」。
- 主表**未记录采购订单号**，无法与采购订单关联。

**ERP 设计输入**
1. **应付不来自采购入库单**，来自独立的「应付确认事件」（蓝图 D06 未决）。采购入库只记数量与暂估。
2. 采购入库必须携带**采购订单号**；ERP 要能追溯「订单 → 收货 → 入库 → 应付 → 付款」全链。
3. 零价/缺价必须**明确原因并留权限**，超容差阻断过账（蓝图 §7）。
4. 付款事实与应付核销分开（同收款侧逻辑）。

### 2.10 / 2.11 其他入库（1 934 / 4 840）与其他出库（4 230 / 15 350）

**跑通的口径**
- 两表结构高度相似 → 合并一张表 + `direction` 位是可行的。
- 「其他入库」实为**盘点/调整的替代承接**（备注常见「调整库存」）。

**暴露的坑**
- **串名最严重**：两表明细前缀**都叫「其他出库明细.」**（氚云表单复制导致），只能靠主表「选择入库仓库」/「选择出库仓库」识别方向（C3 的原始来源）。
- 其他出库单笔金额/数量偏大，**疑似「数量」列被写成金额**（数据现象）。
- 原因全靠备注自由文本，无结构化原因码。

**ERP 设计输入**
1. 库存调整**必须有结构化原因码**，关联盘点/报损/报废等依据（蓝图 §7「备注中的调整库存」行）。
2. 一个方向位比两张表更利于 ERP 统一过账模型，但**需要结构化区分业务性质**（不能靠备注）。
3. 导入解析契约不得依赖子表前缀（C3）。

### 2.12 库存调拨（218 单 / 2 311 明细）

**跑通的口径**
- 仓库与仓管员填充 100%；同仓调拨实测 0 单；两轮 UNCHANGED 收敛。
- `judge_raw` 语义已确认 = 氚云「调拨数量超调出库存」校验标记（2 311 行中 3 行为 1，恰属一张超快照的草稿单）。

**暴露的坑**
- 主表**两个同名「仓管员」列**（调出/调入），通用解析 `putIfAbsent` 会静默吞掉调入方。
- **无金额列**（纯数量），所以调拨不产生价值转移。
- **无在途概念**：一单两仓，调出与调入之间没有时间差表达。

**ERP 设计输入**
1. 调拨必须区分**调拨发出**与**调拨收货**两个动作，之间有**在途**状态（蓝图 §5.2 已定，T09 已设计用例）。
2. 调出/调入责任人是**两个不同角色字段**，不是同名列表头。
3. 差异（短收/丢失）单独处理，不覆盖原单数量。
4. **保存原文不解读**是正确的——ERP 需要在自己的校验层重建库存校验，不能依赖源系统的标记位。

### 2.13 开票资料（3 429 条）

**跑通的口径**
- 税号 ↔ `customers.credit_code` 等值关联（唯一命中才绑），未命中只标记不进复核。
- 44 组同名户名是**合法事实**（同名不同税号），绝不能按户名分组。

**暴露的坑**
- customer 关联率实测仅 **3.2%（111/3 429）**，以外协户名为主。
- 氚云表单**无格式校验**：内勤把整段开票信息粘贴进「户名/税号」字段（户名最长 150、税号最长 140）→ 宽列 + blob 等值匹配天然不命中。
- 地址/电话/银行资料空值率约 80%。

**ERP 设计输入**
1. 开票资料**按版本管理**（蓝图 §6.2 `开票资料版本`），单据使用当时快照。
2. 同户名**不自动合并**；税号是强标识但需「核实状态」（VERIFIED / CONFLICT）。
3. 字段需格式校验与长度约束，**禁止宽列兜底**（宽列会让脏值静默通过）。
4. 税号等标识的**组合查重**而非单字段唯一。

### 2.14 开票申请（10 986 单 / 内容 14 888 / 收款引用 12 697）

**跑通的口径**
- 幂等键必须用「数据ID(不可修改)」而不能用流水号——实测文件尾部 **18 单整行缺流水号**，按流水号分组会串进上一单。
- 一行可同时携带「开票内容」+「收款引用」（实测 **11 537 行**）→ 按 `source_item_id` 各取去重。

**暴露的坑**
- 「选择出库单匹配开票内容」= 日期+联系人+金额**自由文本、无单号** → 出库/收款关联只能存原文，自动勾稽不可行。
- 单条记录的来源与用途未核实。

**ERP 设计输入**
1. **开票申请 ≠ 实际开票**。ERP 必须区分「申请 / 实际开票 / 红冲」，只有实际开票改变开票余额（蓝图 §5.1、T15）。
2. 合并开票、部分开票、超额规则需显式定义（蓝图 §6 未决项）。
3. 收款不因开票改变；开票不生成第二笔收款。
4. 明细模型须支持一行多角色（C4）。
