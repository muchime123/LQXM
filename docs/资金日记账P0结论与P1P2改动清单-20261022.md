# 资金日记账 P0 报告与 P1/P2 改动清单

日期：2026-10-22。承接 `docs/资金日记账审查与重设计方案-20261022.md`。
本文按 LQ 的决定执行：**保留既有资金表增量演进；双余额设计（来源结存 / 计算余额）；余额单调性不得用于推断流水顺序**。

> 全部数据来自本机真库 `product_archive` 只读查询（`_p0_probe*.java`）。无写库、无改数。

## 0. 先撤销上一版的一个错误方法

上一版方案写「按账户内结存单调性切流水段」，LQ 指出这是错的，**该判断成立，已撤销**：

- 财务账户余额本来就随收支上下波动，单调性既不能证明连续，也不能证明断段；
- 用它切段，等于把"数据现象"当成"推断依据"，会把 Excel 里尚未解释的内容固化成系统规则。

本文改用**确定性证据**：不推断顺序，只对拍两个口径（来源末行结存 vs 期初+收支），并逐点列举断链位置供人工判断。

## 1. P0 结论

### 1.1 核心对拍：计算口径与来源结存是否一致

**35 个账户中，27 个有流水的账户全部一致，零例外。**

| 口径 | 账户数 | 说明 |
| --- | --- | --- |
| 一致（来源末行结存 == 期初 + 收入 − 支出） | **27** | 差额 < 0.01，无一对不上 |
| 无来源结存可比（无流水） | 8 | 余额 = 期初，无需推导 |
| 不一致 | **0** | — |

**这条结论是 P1 能安全展示「计算余额」的全部依据。** 它同时说明：`h3_cash_accounts.opening_balance` + 全年收支，与 Excel 账面对得上，期初值本身是正确的月初/启用值。

### 1.2 「期初可疑 5 户」—— 上一版判断需降级，不是问题账户

上一版我按"首笔流水对不上期初"列出 5 户（温州永铭、李红伟中信、安徽盒多多工商、温州睿包中信人民币、浙江利强工商），并标注"期初取数位置可疑"。**本轮验证推翻了该定性**：

- 这 5 户的 `opening_balance` 值**不等于任何一条流水的结存**（匹配 0 行）；
- 但它们的「期初 + 全年收支 = 来源末行结存」**完全成立**；
- 差异只出现在"期初 vs 第一笔流水之后"这一刻，且方向、金额与该账户首日流水吻合（如浙江利强工商：期初 916043.25 − 首日两笔手续费 160.50 = 915882.75，账户首行结存 915792.75，差 90.00 来自同日后一笔手续费）。

**结论：这是正常的"期初余额发生在首笔交易之前"的时序，不是取数错误。** 处理方式：无需标待核对，但**全期余额首次展示时应有一次人工签字确认**（见 4.3 的 `confirmed` 字段）。

### 1.3 「14 条断裂」—— 收敛为 1 个账户、1 个未解释区间

| 账户 | 断点数 | 分布 |
| --- | --- | --- |
| 于士强农业银行5277 | 13（前段）/ 0（后段） | 前段 ≤2026-06-13 有 13 处断点；**2026-06-14 之后 280 条链接零断点** |
| 安徽盒多多工商银行 | 2 | 2026-10-16~17，疑似同日顺序问题 |
| 李红伟农业银行 | 1 | 2026-07-13~16，同上 |

于士强5277 的形态很明确：结存分布在三个量级（<40 万 141 条 / 40–80 万 236 条 / >80 万 327 条），且在 2026-04~06 有 5 处 id 与日期逆序（补录痕迹），6-13 之后完全恢复正常。

**这不是"多条并行流水链"，而是"历史补录期间结存未同步重算"。** 但按 LQ 的原则：**不推断、不改数**。处理方式：

- 该账户 2026-06-14 之前：逐笔余额**不显示**，显示「该区间历史补录，结存未同步」标记；
- 该账户 2026-06-14 之后：正常显示；
- 期末余额：**仍可用**（因为整体对拍一致）；
- 进「对账核对」待人工确认项，确认后转正常。

### 1.4 同日多笔规模 —— 支持双余额设计

| 项 | 值 |
| --- | --- |
| 有同日多笔的「账户×日」组合 | 1491 |
| 落在同日多笔日内的流水行 | **7836 / 8751（89.5%）** |
| 同日单日最多笔数 | 30 |

**89.5% 的流水无法确定日内先后顺序。** 所以：

- 「每笔之后的精确余额」对整个系统**基本不可得**，不是个别账户的问题；
- 系统可提供的是：**来源结存（原样）** + **期间末计算余额**；
- 不允许在任何列上写"交易后余额"这种暗示日内顺序的字段名。

### 1.5 唯一约束检查（LQ 要求项）

| 约束 | 列 | 风险 |
| --- | --- | --- |
| `uk_cashflow_ext` | `(external_source, external_id)` | **安全**：手工用 `external_source='MANUAL'`，与 H3YUN 天然不冲突 |
| `uk_cashflow_no` | `source_no`（单列唯一） | **有风险**：手工流水若也用 `source_no`，必须保证全局唯一。现有前缀 `MANUAL-` 占用 0 行、`#期初` 占用 0 行，可用 |
| `uk_cash_acct_name` | `account_name`（单列唯一） | 改名必须同步流水表，过渡期保留 |
| `uk_cash_acct_no` | `source_no` | 账户表同样需要前缀约定 |

**结论**：沿用现有唯一约束可行，但必须新增约定 —— 手工流水 `external_id = source_no = 'MANUAL-' + UUID`，并在服务层集中生成（不散落在各 Controller）。

### 1.6 一个必须提前说的口径边界

现有 `opening_balance` 来自 Excel「上期结存」行，语义是**"年初 + 逐年累计"还是"账户启用时"**，数据本身无法区分（对拍只能证明年内在用）。因此：

- **2026 年可作为首年基线**，期初种子如实搬值；
- **2027 年不能自动继承**（见 4.2 结转规则）；
- 若未来发现期初实际是"账户开户日"而非"2026-01-01"，只影响跨年结转，不影响 2026 年内任何数字。

## 2. 双余额口径（P1 落地定义）

| 概念 | 字段 | 来源 | 展示规则 |
| --- | --- | --- | --- |
| **来源结存** | `balance`（现有列，保留原名不动） | Excel 原始行 | 始终展示；带核对状态徽标；**永不修改** |
| **计算余额（期间末）** | 后端派生，不落库 | 期初 + Σ收入 − Σ支出 | 期初已确认 + 期间完整 才展示；否则显示原因（见下表） |
| **逐笔计算余额** | **不提供** | — | 89.5% 的流水日内无序，一律不显示 |

**计算余额不可用的四种原因**（必须分别提示，不能笼统显示 0 或「期初缺失」）：

| 原因码 | 含义 | 展示 |
| --- | --- | --- |
| `OPENING_UNCONFIRMED` | 期初未人工确认 | 「期初待确认」 |
| `OPENING_MISSING` | 无期初值 | 「缺期初」 |
| `SEGMENT_UNEXPLAINED` | 区间含未解释补录段（如于士强5277 前段） | 「历史补录未同步」 |
| `ORPHAN_ACCOUNT` | 流水 account_name 无对应账户 | 「账户未建档」 |

## 4. P2 改动清单（正式记账能力）

### 4.1 迁移（1 次，版本号现查现用，当前基线 V401）

```sql
-- 1) 流水表演进：全部可空，历史行零回填
ALTER TABLE h3_cashflow_entries
  ADD COLUMN account_id BIGINT NULL AFTER account_name,
  ADD COLUMN biz_category VARCHAR(32) NULL,
  ADD COLUMN counterparty_type VARCHAR(16) NULL,
  ADD COLUMN manual_note VARCHAR(500) NULL,
  ADD COLUMN voided_at DATETIME NULL,
  ADD COLUMN void_reason VARCHAR(255) NULL,
  ADD COLUMN locked TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN reconcile_status VARCHAR(16) NOT NULL DEFAULT 'NONE',
  ADD COLUMN created_by BIGINT NULL,
  ADD COLUMN updated_by BIGINT NULL;

-- 2) 回填 account_id（35 账户映射，非 8751 行搬运）
UPDATE h3_cashflow_entries e
  JOIN h3_cash_accounts a ON a.account_name = e.account_name
   SET e.account_id = a.id
 WHERE e.account_id IS NULL;

-- 3) 年度期初（新建）
CREATE TABLE cashflow_account_opening (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  account_id BIGINT NOT NULL,
  fiscal_year SMALLINT NOT NULL,
  amount DECIMAL(18,4) NOT NULL,
  source VARCHAR(16) NOT NULL,            -- H3_OPENING / CARRY_FORWARD / MANUAL
  confirmed TINYINT(1) NOT NULL DEFAULT 0,
  confirmed_by BIGINT NULL,
  confirmed_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_opening (account_id, fiscal_year)
);

-- 4) 对账结论（新建，与"核对状态"分离）
CREATE TABLE cashflow_reconcile_confirmation (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  account_id BIGINT NOT NULL,
  period_start DATE NOT NULL,
  period_end DATE NOT NULL,
  statement_balance DECIMAL(18,4) NULL,
  system_balance DECIMAL(18,4) NOT NULL,
  diff DECIMAL(18,4) NULL,
  status VARCHAR(16) NOT NULL,            -- PENDING / CONFIRMED / DISPUTED
  note VARCHAR(500) NULL,
  confirmed_by BIGINT NULL,
  confirmed_at DATETIME NULL,
  UNIQUE KEY uk_reconcile (account_id, period_start, period_end)
);

-- 5) 导入差异处置决定（新建）
CREATE TABLE cashflow_import_decision (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  batch_id BIGINT NOT NULL,
  entry_id BIGINT NULL,
  decision VARCHAR(24) NOT NULL,          -- CONFIRM_DELETE / KEEP / REVISED / CONFIRM_NEW / IGNORE
  decided_by BIGINT NOT NULL,
  decided_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  note VARCHAR(255) NULL,
  KEY idx_decision_batch (batch_id, decision)
);

-- 6) 账户主数据补业务列
ALTER TABLE h3_cash_accounts
  ADD COLUMN entity_name VARCHAR(64) NULL,     -- 所属主体
  ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE';
```

**注意**：不加 `UNIQUE` 到 `(account_id, entry_date, income, expense)` —— 145 组重复会直接迁移失败。

### 4.2 年度结转规则（LQ 要求：不能自动写）

```
上年期末核对 CONFIRMED
  → 生成下年期初候选（source = CARRY_FORWARD，confirmed = 0）
  → 财务确认 → confirmed = 1，生效
上年已结账后发生追溯调整
  → 计算受影响年度期初的差额，生成"影响提示"
  → 不自动改写已确认的下年期初
```

补充一条 LQ 没提但必须处理的：**上年未结账时不允许新建下年期初**（否则两个年度的期初来源冲突）。未结账的判断依据 = `cashflow_reconcile_confirmation` 上年 12 月期间无 `CONFIRMED` 记录。

### 4.3 写端点与保护

| 端点 | 权限 | 关键约束 |
| --- | --- | --- |
| `POST /entries` | `cashflow.write` | `external_source='MANUAL'`，`external_id = source_no = 'MANUAL-' + UUID`，`account_id` 必填 |
| `PUT /entries/{id}` | `cashflow.write` | 仅 `MANUAL` 或 `locked=0`；写入前落审计快照 |
| `POST /entries/{id}/void` | `cashflow.write` | **作废不删除**，置 `voided_at`；报表排除但保留可查 |
| `GET/POST /accounts/{id}/opening/{year}` | `cashflow.manage` | 同 4.2 结转规则 |
| `POST /reconcile` | `cashflow.reconcile` | 落 `cashflow_reconcile_confirmation` |

**必须改掉的现有行为（安全隐患）**：

`H3FactImportService.saveCashflowEntry()` 的 `ON DUPLICATE KEY UPDATE` 覆盖全部业务列。P2 必须改为：**导入只更新来源事实列**（`entry_date`/`income`/`expense`/`balance`/`fx_*`/`source_hash`），**不得触碰** `biz_category`/`counterparty_type`/`manual_note`/`reconcile_status`/`locked`/`voided_at`/`account_id`/`created_by`。

### 4.4 权限（读取并行，写入立即用新码）

| 端点类别 | 过渡期 | 切换后 |
| --- | --- | --- |
| 读取（GET） | `{cashflow.read, integration.h3}` any-of | `cashflow.read` |
| 写入 | **仅 `cashflow.write`**（不从旧码继承） | 同 |
| 对账核销 | **仅 `cashflow.reconcile`** | 同 |
| 账户管理/结账 | **仅 `cashflow.manage`** | 同 |

新权限必须同落 `system_permissions` + `system_feature_actions` + `system_role_feature_grants` 三处。前端 `can()` 只控显隐，**不作为校验依据**。

## 5. P3 导入与对账闭环要点（概览，P2 后再细化）

### 5.1 分类桶规则表（按 LQ 的四档约束细化）

| 桶 | 判定条件 | 处理 | 是否需要人工 |
| --- | --- | --- | --- |
| `UNCHANGED` | 行键完全一致 | 自动 | 否 |
| `UPDATE_CANDIDATE` | 同账户 + 同日期 + 同收支，**两侧唯一** | 批量可确认 | 可批量 |
| `NEW` | 无对应旧行，且不与任何旧行冲突 | 批量新增 | 可批量 |
| `MISSING_FROM_FILE` | 旧行在本批**来源范围内**未出现 | 批量保留 / 人工确认停用 | **默认保留** |
| `AMBIGUOUS` | 同日同金额多笔 / 账户日期金额变化 / 多候选 | 只列出，**不配对** | 必须人工 |

**来源范围比较（LQ 明确要求）**：全量文件只比对本批实际出现的账户页。手工流水（`MANUAL`）**永不计入 `MISSING_FROM_FILE`** —— 否则财务在系统里新增的流水会被误判删除。这条要写成 `WHERE external_source = 'H3YUN'` 的硬过滤，并且注释说明原因。

### 5.2 现有代码要改的两处

1. `rejectCashflowHistoryRewrite()` 现在是抛异常拒绝整批 → 改为产出 `MISSING_FROM_FILE` 桶并允许处置后继续；
2. `rekeyCashflowBalanceShifts()` 里对空行的 `DELETE`（`H3FactImportService:1912`）→ 改为预览里列明「空占位行 N 条待清理」，由人工决定。
