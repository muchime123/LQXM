# 氚云导入中心职责重划与库存快照设计

> 2026-09-16 · 基于真实库与真实导出文件的实测结论
> 关联：`docs/氚云导入全链路设计梳理-20260914.md`（权威）、`docs/产品台账合并口径诊断-20260914.md`

---

## 0. 一句话结论

**氚云导入中心作为「统一入口」的定位成立，不需要删任何导入类型。**
要改的是两件事：

1. **把「接入」与「参与核算」拆成两个显式属性**，而不是靠菜单排版暗示（七类数据都从这个门进，但只有销售出库参与经营核算）。
2. **把「合并」从日常动作降级为派生视图**：产品信息是维表、仓库明细是事实表，日常看到的应该是两者关联出的**库存快照**；`product_inventory_balances` 保留，但定位为**低频对账产物**，不再是"导入完还要点一下才算数"的步骤。

采购价问题已实测澄清：**仓库明细的采购价列恒为空，采购价唯一来源是产品信息**。现有代码的优先级（产品信息优先、仓库明细兜底）恰好是对的，**不需要改**。

| 台账 | 行数 | 采购价有值 | 采购价为空 |

- 不存在"仓库价与产品价不一致"的场景（一边恒空），Codex 方案第九节的「优先级 + 差异标记 + 双价保留」整套设计**没有落点**。

  `purchasePrice = matched && pi.purchasePrice != null ? pi.purchasePrice : sr.purchasePrice`
  语义正确（产品信息优先）。`sr.purchasePrice` 是**当前恒为 null 的空槽位**，应予保留并注释，以便上游将来启用时开关式切换，但不得参与优先级推理。

## 2. 问题一：七类数据怎么放进「统一入口」

### 2.1 主张

统一入口 = 一个门，七类数据都从这里进。**但"进门"和"进门之后去哪"是两件事**，必须显式区分。当前页面的问题不是类型太多，而是这个区分没有落到数据模型上，只能靠菜单排版和文案暗示，于是每类数据都获得了同等的一级入口、同等的批次列、同等的操作菜单。

### 2.2 三组定性（建议写进枚举，而非仅做 UI 分组）

| 数据类型 | 分组 | 参与方式 | 日常可见 | 去向 |
|---|---|---|---|---|
| 销售出库 | 核心业务 | 进入业务核算 | 是（第一位） | 客户 / 订单 / 回款 / 利润 / 提成 |
| 产品信息 | 基础数据 | 更新产品维表 | 是 | 产品维表（**含唯一采购价来源**） |
| 仓库明细 | 基础数据 | 更新库存事实 | 是 | 库存快照 |
| 经销商信息 | 基础数据 | 更新经销商主档 | 是（可选） | 经销商主档 |
| 生产任务工单 | 参考归档 | 仅归档 | 折叠 | 历史追溯 / 未来生产模块数据基础 |
| 收款记录 | 参考归档 | 仅归档，不参与回款 | 折叠 | 历史查询 / 出库单争议旁证 |
| 多订单结清 | 参考归档 | 仅归档，不参与回款 | 折叠 | 历史查询 / 出库单争议旁证 |

### 2.3 落点（已落地，全在前端）

**实际落点只有前端两处**：`types/h3Import.ts` 加类型，`constants/h3Import.ts` 加字段与分组元数据。

| 字段 | 取值 | 用途 |
|---|---|---|
| `group` | `core` / `base` / `archive` | 下拉分组、台账页签排序 |
| `participation` | `in_accounting` / `updates_master` / `archive_only` | 批次行「处理结果」标签、提示文案 |
| `entryStage` | `daily` / `advanced` | 是否进「历史数据导入」折叠区 |

这样「仅归档」不是 UI 上的视觉降权，而是**一个有依据的字段**；将来某类数据要启用，改一个字段值即可，不必回头重排菜单。

**为什么不给后端 `ImportKindDescriptor` 也加一份**：该枚举是「执行侧」事实源（`domain` 决定走哪条管线、`orchestrates()` 决定是否触发编排、`dbType` 是批次表原值），而 `group` / `entryStage` 是**纯展示语义**，后端当前没有任何消费者。加了就是死字段。等后端真需要按「是否参与核算」做决策时再加，那时会有明确的调用点。

### 2.4 与 Codex 方案的差异

| 项 | Codex 建议 | 本文建议 | 理由 |
|---|---|---|---|
| 分组 | 三组下拉 + 表格说明 | 三组**字段化**，UI 从字段派生 | 避免文案与事实两处维护、两处漂移 |
| 归档类数据 | 降低视觉优先级 | 保留类型 + `ARCHIVE_ONLY` 字段 + 默认折叠 | 与你的"统一入口"诉求一致，不删任何类型 |
| 收款/结清 | 建议移出标准导入步骤 | 同意，但**保留入口**（折叠） | 历史数据与旁证价值需要落地通道 |
| 生产工单 | 建议从中心移除 | 保留，标 `ARCHIVE_ONLY` | 将来建生产模块时数据已在，不必重新补导历史 |

## 3. 问题二：库存这块怎么设计

### 3.1 你的判断是对的，但可以再往前一步

你说"只有产品信息（含采购价）+ 仓库明细（含数量）合在一起，才得到实际产品库存"——**这个判断成立**（实测编号命中 98.12%、单位一致 99.37%，拼接条件比预想好）。

但**"合并"不该是一个用户动作**：

- 产品信息 = **维表**（编号 → 名称 / 规格 / 单位 / 采购价），编号唯一、无重复
- 仓库明细 = **事实表**（仓库 + 编号 + 单位 → 数量）
- 这两者是天然的 JOIN 关系，不是两份需要"合并"的账

做成"合并入库"动作后，产生的是**第二份真相**（`product_inventory_balances`），随之而来的是"什么时候重算 / 覆盖还是追加 / 余额与台账不一致怎么办"这一整类问题——这正是 MergeService 933 行、`VANISHED_FROM_SNAPSHOT` 反向对账、`matchUnitRowBalance`、`FOR UPDATE` 锁行这些机制的来源。

### 3.2 三层模型（不回退现有链路）

| 层 | 内容 | 定位 | 刷新时机 |
|---|---|---|---|
| L1 源台账 | `h3_product_catalog` + `h3_warehouse_stock` | 只进不出，导入即落地 | 每次导入 |
| L2 库存快照 | 两表关联的派生结果（可物化） | **日常看库存就看这个**，永远不落后于台账 | 台账变更后自动 |
| L3 正式库存余额 | `product_inventory_balances` | 对账产物，未来作为实时库存期初 | **仅重导 / 对账时点** |

**这不推翻合并链路**（你此前明确"勿回退"，且产品库存页已是台账并集驱动）。变化的只是**定位与入口层级**：

- 产品库存页 = L2 快照（日常）
- 「库存合并入库」→ 更名「库存对账（生成正式余额）」，从日常入口移入 `更多 → 建设期工具`

收益：不再出现"忘了点合并所以库存是旧的"这类误解；正式余额表仍在、仍服务对账与未来期初。

### 3.3 采购价口径（按实测事实定死）

```
库存行   = 仓库明细行（仓库 + 编号 + 单位 + 数量）
           LEFT JOIN 产品信息（编号）取 名称 / 类目 / 规格 / 单位 / 采购价

有效采购价 = 产品信息.采购价格            ← 唯一来源
             （为空 → 该行标「缺采购价」，金额置 null，不填 0）
库存金额   = 数量 × 有效采购价             （两者都有值才计算）

仓库明细.采购价格 = 空槽位
  语义：氚云该列当前未启用（实测 100% 空）
  规则：恒不参与计算；若上游将来启用，以显式开关切换为「仓库价优先」，不得默认生效
```

### 3.4 必须专门处理的边界（均为实测存在，不是假设）

| 边界 | 实测 | 建议处理 |
|---|---|---|
| 缺采购价 | 产品信息侧 15 行；仓库侧 307 个编号无对应产品 | 金额置 null，标「缺采购价」，**不阻断**快照生成；单列「缺价清单」入口 |
| 编号对不上 | 307 个编号（仓库有、产品无） | 保留行、数量有效；名称 / 规格用仓库明细自带值兜底 |
| 同编号多单位 | 22 个（如 `1455YX` 有 kg / 个） | 业务键 = 仓库 + 编号 + 单位，**禁止按编号聚合**；页面按编号折叠、按单位展开 |
| 零库存行 | 14,497 / 16,305（88.9%） | 快照默认过滤，保留「显示零库存」开关（反向对账清零需要它） |
| 负库存 | 39 行 | 保留展示，**不进 REVIEW 阻断**（已归类为数据现象） |
| 名称 / 规格不一致 | 62 / 293 行 | 以产品信息为准（现状已如此），差异可列审计清单 |

### 3.5 用「批次可追溯」替代「快照版本化」

Codex 建议"每次生成新版本、不覆盖"。**建议现在不做**：

- 源台账本身是"最新导出覆盖旧值"的增量模型，**没有历史版本**；给快照做版本，只能反映"哪次合并跑过"，追溯价值有限。
- 更重要的是：快照的正确性依赖**两份文件导出自同一时点**。你这次是 11:38 一次导出两份（时间差 18 秒，前提成立）；若将来两份导出相差数天，JOIN 出来的就是两个时点的拼接。

**更便宜且解决同一问题的做法**：快照页面显示来源批次与导出时间差

```
本次快照基于：产品信息 批次#148 · 仓库明细 批次#147（导出时间差 18 秒）
```

时间差超阈值（如 > 1 天）时给黄标提示"两份台账导出时点差异较大，快照仅供参考"。

### 补充优化（13:19）：正式账「该对账了」信号

三层定位澄清（LQ 问「合并不该是用户动作」的含义）：**产品库存页（L2 快照）本来就是自动的**——
`ProductInventoryService.VIEW_FROM` 每次查询实时 JOIN 两张台账，导入完成即生效，无需任何点击。
LQ 的理解正确。剩下的唯一手动动作是「库存对账」（L3），它的存在意义**不是得到产品库存**，
而是给正式库存账（`product_inventory_balances` + 流水，制造领料/完工入库的唯一账本）建立余额。

原设计的问题：**对账时机靠人记**——台账重导后台账变了，正式账静默过期，没有信号。

修复：`snapshot-info` 新增 `balanceVanished` / `balanceDrifted`（数量>0 的余额行中，
台账快照已无此行 / 数量与台账不一致），键口径与合并预览一致（编号 trim+单位+映射后仓库 id）。
快照页口径条 >0 时黄标「正式库存账偏离 N 行，建议运行库存对账」。

## 6. 台账「导入与系统信息」（2026-09-16 追加）

### 6.1 问题

氚云全字段导出的**业务列之后**带着一整套系统列，但此前只有经销商台账（V294）落了这些列；产品信息与仓库明细台账只落了业务列 + `source_hash`。结果是同一批氚云数据，在详情里有的能溯源、有的不能：销售出库能看到「源创建时间 / 源修改时间 / 创建人」，产品信息与仓库明细看不到。

### 6.2 实测列布局（2026-09 导出样本）

**产品信息 25 列**（主表 + 产品明细子表结构）：

| 列位 | 中文表头 | 用途 |
|---|---|---|
| 0–7 | 产品类目 / 产品明细.编号 / 名称 / 规格 / 单位 / 备注 / 状态 / 采购价格 | 现有业务列（固定列位 + `LedgerHeaderGuard` 指纹校验） |
| 8 | 产品明细.数据ID(不可修改) | **行级**外部 ID，每行独立 |
| 10 | 产品明细.数据标题 | 行级 |
| 14–24 | 数据ID / 数据标题 / **修改时间(必填)** / 所属部门(必填) / 所属部门 / 拥有者(必填) / 创建人(必填) / **创建时间(必填)** / 附件 / 编号序号 / 数据状态 | **主表级**，只在每个主记录首行有值 |

**仓库明细 19 列**（扁平表）：列 8 = `数据ID(不可修改)`、9 = 数据标题、10 = 创建人、11 = 拥有者(必填)、12 = 所属部门(必填)、13 = 创建时间、14 = 修改时间、18 = 数据状态——每行独立有值。

### 6.3 实现

- **迁移 `V301__h3_ledger_source_system_columns.sql`**：`h3_product_catalog` / `h3_warehouse_stock` 各补 10 列
  （`source_object_id` / `source_title` / `owner_name` / `department_name` / `created_by_name` /
  `data_status` / `source_created_at` / `source_modified_at` / `last_synced_at` / `updated_at`）；
  `h3_dealer_catalog` 补 `last_synced_at` 与另两张对齐。
- **解析**：业务列**仍用固定列位**（错位即整批拒绝）；系统列**按第 2 行中文表头名匹配**
  （`headerIndex` + `colOf`，精确优先再退化包含匹配）——报表增删字段会挪列位，写死必错。
  产品信息的主表系统列与「产品类目」同法**向下填充**（主-子结构的既有约定）。
- **写入语义**：`source_*` 是**观测值**，**不参与**业务相等判定（否则主记录改一次，其下几十行产品全被判 UPDATE）；
  只在新行插入、业务字段更新、或 **UNCHANGED 但观测列与库内不一致** 时写入。
- **`source_hash` 排除系统列**：哈希只表达业务内容指纹。
- **前端**：`H3LedgerDetailDrawer` 的 product / stock / dealer 三类共用同一「导入与系统信息」区块
  （外部 ID / 数据标题 / 创建人 / 拥有者 / 所属部门 / 数据状态 / 源创建时间 / 源修改时间 / 来源哈希 /
  最后同步 / 导入批次 / 入库时间 / 更新时间 / 记录 ID）；`ProductInventoryDetailDrawer` 的两张来源台账卡片补
  源创建时间 / 源修改时间 / 创建人。

### 6.4 顺带修复：数值浮点残差导致的「永不收敛」

仓库明细重复导入时稳定有 **61 条**「库存数量：`0.0000` → `8.88178419700125E-16`」。成因是 Excel 单元格
本身带浮点噪声（公式结果本应为 0 却是 1e-16），写入 `DECIMAL(18,4)` 后变成 `0.0000`，下一轮再读又得到
`8.88178419700125E-16` → 精确比较判不等 → 每轮都报更新。

修法（双向）：`cellDecimal()` 对超过 6 位小数的值四舍五入、归零统一成 `BigDecimal.ZERO`；
`nEq()` 加 `1e-9` 容差（台账有效精度 4 位小数，1e-9 不可能掩盖真实差异）。
