### ⑥ 拍板：双层权威 + 银行 API 预留

LQ 明确：**"流水日记账更全，但后续可以接入银行 API key，银行的还是更权威的"**。

**这个区分是对的，而且是关键区分**——它把"记录完整"和"事实可信"分开了：

| 维度 | 流水日记账 | 银行流水（API） |
|---|---|---|
| 记录**完整度** | ✅ 更全（含**人工业务标注**：供应商/客户/报销人/是否开票） | ❌ 只有银行字段，无业务语义 |
| 事实**可信度** | ⚠️ 人工记账，可能漏记/错记 | ✅ **权威**（钱真的动了，且**带对方账号**） |
| 覆盖范围 | 38 个账户 sheet（含个人账户） | 29 个银行账户 |
| 未来获取方式 | 人工导出 Excel | **银行 API 直连** |

**结论（修订 §6 方案）**：

```
资金唯一身份 ＝ 主体公司 + 账户 + 发生日期 + 金额 + 方向 + 对方
    ↑ 这个键本身不变，无论数据从 Excel 还是 API 来
```

| 角色 | 归位 | 说明 |
|---|---|---|
| **事实权威（未来）** | **银行流水（API 直连）** | 带对方账号，强于名称；用于**核验** |
| **事实权威（当期）** | 银行流水（人工导出） | API 未接入前的过渡 |
| **业务语义补充** | **流水日记账** | 提供"这笔钱是什么业务"——**银行流水没有这个信息** |
| **业务关联方** | 销售出库收款、发票收款 | 不做独立资金记录 |

**关键设计决定（因 API 预留而变）**：

1. **账户表需区分"公司账户 / 个人账户"**，并预留 `bank_code`、`account_no`、`api_source` 字段——API 直连后账户身份靠账号而非名称。
2. **拉取不得覆盖人工标注**：API 同步的是"钱动了"这一事实，**日记账里的供应商/客户/报销人/是否开票是人工标注，必须独立存储、不得被 API 同步覆盖**。这是最容易踩的坑。
3. **⚠️ 判重规则（2026-09-21 修订）**：~~同主体 + 同账户 + 同日期 + 同金额 + 同方向 → 视为同一事件~~ **作废**。该组合**不是唯一键**——同一天向同一对象发生两笔同金额收付款完全可能（例如同日分两笔付同一供应商同一金额的两张单）。修订后的规则见下方「⑥ 修订：资金身份与判重」。
4. **银行流水表头异构 ≥15 种** → 需建「银行格式 → 统一字段」映射字典（这是接入 API 的前置工作，Excel 和 API 都能用）。

### ⑥ 修订：资金身份与判重（2026-09-21 收口）

原「主体+账户+日期+金额+方向（+对方）」只能作为**候选匹配条件**，用于提示"这两条可能是同一笔钱"，
**不能作为资金事件的唯一身份**，更不能据此自动合并。修订如下：

| 层 | 身份/键 | 说明 |
|---|---|---|
| **资金事件** | **独立 `fundId`**（系统生成，永不复用） | 每一条"钱真的动了"的事实各占一行，不靠业务字段拼主键 |
| **来源幂等** | 银行来源：`账户 account_no` + **银行稳定交易号**；日记账来源：`账户 + 台账行身份` | 同一来源重复拉取（Excel 重导 / API 重推）靠这个键去重，与资金身份分开 |
| **无交易号时** | **逐条保留 + 冲突复核** | 银行格式缺交易号时，不得按金额+日期合并；保留每条来源记录并进入人工复核队列 |
| **既有弱键** | `主体+账户+日期+金额+方向(+对方)` | 降级为**候选匹配条件**，只用于"疑似同一笔"的可疑提示 |

**三层信息必须分表存储，不得合并**：

| 层 | 内容 | 来源 | 可否被同步覆盖 |
|---|---|---|---|
| 来源事实 | 账户、账号、日期、金额、方向、余额 | 银行流水（Excel/API） | 可（新数据覆盖旧数据） |
| 人工标注 | 供应商/客户/报销人/是否开票 | 流水日记账人工填写 | **不可** |
| 业务分配 | 核销到哪张应收/应付单 | ERP 内业务动作 | 不可（业务事实） |

**因此 ⑥ 的答案确定为**：资金唯一身份**现在就定**（独立 `fundId`，与来源无关），**权威来源分两期**（当期 = 银行流水 Excel；未来 = 银行 API），**日记账永久保留为业务语义层**，**弱键仅作候选匹配**。

## ⑤ 成本归集与在制品规则

### 已核实的项目立场
文档明确写着：**"不用采购价假装制造成本"**。

### 默认方案（强烈建议采纳）

> **首批不做成本，明确写"库存只有数量账，无金额账"。**

理由：
1. 做成本的代价是**在制品规则**（一道工序完成算多少完工？）+ 工时/费用分摊 + 期末调整——ERP 里最重的一块；
2. 首批目标是"打通一个闭环"，**数量账闭环已能验证 90% 的流程正确性**；
3. 强行上成本，政策一旦定错，**已入库成本数据全要重算**，比不做贵得多。

### ⚠️ 采纳这条的硬约束

> **一旦承诺"无金额账"，页面上就不能显示库存金额与毛利**，否则数字是假的。这条必须同步告知业务方。

⚠️ 注意一个现状：出库明细里有 `purchase_unit_price` / `purchase_total` / `source_profit` 字段，**它们是历史台账的参考值，不是正式成本**。首批不要把这两个概念混起来。

### 只需确认 1 项

> **能接受"首批库存只看数量、不看金额、不算毛利"吗？**
>
> ☐ 接受，首批不做成本（推荐）　☐ 不接受，必须含成本（需另立专项评估）

## ⑥ 资金唯一身份定义

### 核心事实：同一笔钱会出现在 4 个地方

| 来源 | 性质 |
|---|---|
| 销售出库单收款 | 业务视角（谁欠我钱） |
| 发票明细收款字段 | 税务视角（开票核销） |
| 流水日记账 | 人工记账视角 |
| 各银行流水 | 银行视角（**唯一带对方账号**） |

**它们不是 4 笔钱，是 1 笔钱的 4 个证据。** 若各记一遍，资金账会翻 4 倍。

### 建议的唯一身份设计

```
资金事件（唯一身份）＝ 独立 fundId（系统生成）
候选匹配条件（仅用于提示"疑似同一笔"）＝
    主体公司 + 账户 + 发生日期 + 金额 + 方向 + 对方
```

| 角色 | 归位 |
|---|---|
| **权威（唯一资金事实）** | 流水日记账 + 银行流水（只有它们记录"钱真的动了"） |
| **业务关联方（不做独立资金记录）** | 销售出库收款、发票收款 |
| **判重规则（2026-09-21 修订）** | 弱键仅作**候选匹配条件**，不自动合并；来源去重靠「账户 + 银行稳定交易号」，无交易号则逐条保留 + 冲突复核。详见下方「⑥ 修订：资金身份与判重」 |

### 决策结果 ✅

> **LQ 已答：「流水日记账更全，但后续可以接入银行 API key，银行的还是更权威的」。**
>
> **→ 采纳「双层权威 + API 预留」方案（详见上方「决策记录 §⑥」）。**

具体落地：

| 层 | 定稿内容 |
|---|---|
| **唯一身份键** | ~~`主体公司 + 账户 + 发生日期 + 金额 + 方向 + 对方`~~ → **独立 `fundId`**（2026-09-21 修订）；上式降级为候选匹配条件 |
| **事实权威** | 当期 = 银行流水 Excel；**未来 = 银行 API 直连** |
| **业务语义层** | 流水日记账（供应商/客户/报销人/是否开票），**永久保留** |
| **业务关联方** | 销售出库收款、发票收款（不做独立资金记录） |

**三项必须现在就写进表结构的设计约束**：

1. **账户表预留 API 字段**：`bank_code` / `account_no` / `api_source`，并保留**公司账户 vs 个人账户**的区分（当前 38 个日记账账户里含大量个人账户：于清山/于帅帅/李南等）。
2. **⚠️ 人工标注不得被 API 覆盖**：日记账的供应商/客户/报销人/是否开票是**人工补充的业务语义**，银行流水没有这些信息。API 同步只写"钱动了"的事实字段，**业务标注必须独立存储**——这是接入 API 时最容易踩的坑。
3. **银行格式映射字典**：银行流水表头异构 ≥15 种（工行 7 列 / 中行 38 列 / 中信 22 列…），需建「银行格式 → 统一字段」映射字典。**这个字典 Excel 和 API 都要用，属接入前置工作。**
