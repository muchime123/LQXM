## 3. 三个必须记录的工程决策

### 3.1 主库装配被**显式接管**（不是可选优化，是必需）

Spring Boot 的条件装配在引入第二个数据源后会自动退让，必须显式补齐：

| 自动配置 | 条件 | 若不接管的后果 |
|---|---|---|
| `DataSourceAutoConfiguration` | `@ConditionalOnMissingBean(DataSource.class)` | 主库数据源不再创建 → 启动失败 |
| `DataSourceTransactionManagerAutoConfiguration` | `@ConditionalOnMissingBean(TransactionManager.class)` | 主库事务管理器被 `erpTransactionManager` 顶掉 |
| `JdbcTemplateAutoConfiguration` | `@ConditionalOnMissingBean(JdbcOperations.class)` | **容器里只剩 `erpJdbcTemplate`，现有 300+ 处注入会静默连到 erp 库**（比启动失败更危险） |

处理：`PrimaryDataSourceConfig` 以 `@Primary` 提供 `dataSource` / `jdbcTemplate` / `transactionManager`，
erp 侧一律 `@Qualifier` 指名注入。副作用已记录在类注释里——`spring.datasource.hikari.*` 不再自动绑定，调池参数改该类。
事务管理器保持 `JpaTransactionManager`（与 Boot 自动配置一致），确保现有 JPA 的 EntityManager 生命周期与 flush 时机不变。

### 3.2 erp 迁移**不走** Spring 的 Flyway 自动配置

`FlywayAutoConfiguration` 带 `@ConditionalOnMissingBean(Flyway.class)`：若把 erp Flyway 注册成 bean，
会连**主库迁移**一起顶掉。故改用 `ApplicationRunner`（在主库迁移之后执行），并提供
`migrate-on-startup` / `fail-fast-on-migration-error` 两个开关；默认失败即阻断启动——
宁可起不来，也不要带着半个 schema 对外服务。

### 3.3 「公共列基类」在 M0 用**常量 + DDL 片段**，不用 `@MappedSuperclass`

M0 的 erp 访问层是独立 `erpJdbcTemplate`，尚未引入第二个 EntityManagerFactory（拆 EMF 会牵动主库 JPA 装配，
属可直接验证但收益为零的风险）。M1 若为 ERP 实体启用 JPA，`ErpCommonColumns` 可直接转成 `@MappedSuperclass`，
列清单与 DDL 保持单一事实来源。

## 4. 部署前提与运维

1. **erp 库需先存在**（一次性）：
   ```sql
   CREATE DATABASE IF NOT EXISTS erp DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
   ```
   （Flyway 的 `createSchemas` 只兜底 schema 内的表，连不上库时无法兜底。）
2. 环境变量：`ERP_DATASOURCE_URL` / `ERP_DB_POOL_MAX` / `ERP_MIGRATE_ON_STARTUP` / `ERP_MIGRATE_FAIL_FAST`；
   账号密码复用 `DB_USERNAME` / `DB_PASSWORD`。
3. erp 迁移版本号**从 V1 起独立编**，新增迁移放 `backend/src/main/resources/db/erp-migration/`，
   **不要**放主库的 `db/migration/`（两边版本号会互相干扰）。
