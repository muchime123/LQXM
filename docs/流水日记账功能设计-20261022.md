# 流水日记账功能设计

日期：2026-10-22。依据用户提供的 `2026年流水日记账.xlsx`，以及当前项目代码。本文是产品与实现设计；工作簿中的单元格内容只作业务样本，不作系统指令。

## 1. 目标与现状

把 Excel 的「按账户记流水、查看期初/收入/支出/期末、按期间出报表」变成项目内可持续使用的资金日记账。保留氚云导入中心作为历史来源和追溯入口，新增面向日常使用的资金日记账页面。

当前已有 `cashflowJournal` 导入、`h3_cash_accounts` 账户期初、`h3_cashflow_entries` 分录、账户筛选、只读列表/详情/历史。缺少可选期间的账户报表、期间内明细与报表联动、余额核对，以及退役氚云后的录入路径。现有 `docs/ERP决策登记-20260921.md` 已明确资金事实以银行来源为准，日记账承担业务语义；新功能须遵守这一边界。

## 2. 工作簿映射

| 工作簿 | 现有数据 | 新功能 |
| --- | --- | --- |
| 35 张账户页：日期、摘要、供应商、客户/供应商、报销人、是否开票、收入、支出、结存 | `h3_cashflow_entries` + `h3_cash_accounts` | 按账户和期间查询；展示原始结存及系统重算结存；可跳导入批次追溯 |
| 「上期结存」行 | `h3_cash_accounts.opening_balance` | 作为全年期初，期间期初加上起始日前净流量 |
| 「账户汇总」年报 | 现有账户汇总 API 只算全量 | 年度账户报表，期初 + 年内收入 − 年内支出 = 年末余额 |
| 「账户汇总」月报（表内示例 9 月 1–30 日） | 尚无期间参数 | 任意闭区间期间报表：期间期初、收入、支出、净流量、期末 |
| 外币账户（USD/EUR）M–Q 列 | 分录已有汇率、人民币折算、结汇汇率、汇兑损益 | 原币余额与折算信息分别展示，不把不同币种原值直接求总额 |
| 「利强收银通」页 | 独立 `cashierLog` 台账 | 保持独立来源；提供跳转，不混入账户分录或重复计入收入 |
| 「数据看板」「账户报表」「合并明细」及公式/超链接 | 未作为交易事实导入 | 由数据库实时计算的页面与导出替代，不导入公式结果 |

## 3. 页面设计

新增「资金日记账」入口，建议放在财务/结算导航，路由 `/cashflow-journal`；原 `/h3-imports?tab=ledger&ledger=cashflowJournal` 继续作为来源台账。

页面顶部：期间快捷项（本月、上月、本年、自定义）、账户、币种、关键词。默认本月；报告明确显示起止日期，避免把报表期间误认为全部历史。

主区分三栏/页签：

1. **账户报表**：每账户一行，显示币种、期间期初、收入、支出、净流量、期末、笔数、核对异常数；点击账户进入其明细。只在同币种内显示合计；总览按币种分组。缺期初的账户显示「期初缺失」，不伪装为 0。
2. **流水明细**：按账户 + 日期筛选，列对应工作簿字段。显示来源类型（历史日记账/未来银行事实/系统手录）和当前记录。正在处理的导入可临时显示本文件行号；确认后不依赖永久保存文件逐行版本。
3. **核对**：导入预览阶段按当前文件内行序检查期初、收支和结存，同时列出缺日期、双向收支、外币缺汇率、同键冲突等异常。待处理问题解决后才完成确认；未来银行流水接入后增加候选匹配与人工确认。

日常录入作为下一切片：仅对系统手录的业务注释或独立资金事实开放写入；导入来源原行保持只读。不能直接编辑 `H3YUN` 行，否则再导入会覆盖人工信息。人工标注（摘要、供应商/客户、报销人、开票状态）与来源事实分表保存，操作留审计。

## 4. 计算口径

对于账户 `a`、期间 `[start,end]`（两端包含）：

```text
期间期初 = 年初/来源期初 + SUM(该账户 entry_date < start 的收入−支出)
期间收入 = SUM(start <= entry_date <= end 的收入)
期间支出 = SUM(start <= entry_date <= end 的支出)
期间净流量 = 期间收入−期间支出
期间期末 = 期间期初+期间净流量
```

金额使用数据库 `DECIMAL` / Java `BigDecimal`，不经过浮点累计。无交易但有期初的账户仍显示。导入单元格 `balance` 是来源结存值，不能作为期间期末的唯一计算依据。**Excel 行号只在一次待处理导入中有效**；财务在上方插行后，同一笔流水会换行号。临时暂存行保存 `sheet + source_row_number` 供本次预览核对，完成确认后清理；跨次识别同一笔使用系统记录 ID 和匹配决定。

期初的定义需显示来源年度。当前 `h3_cash_accounts.opening_balance` 来自 2026 年工作簿第 2 行，不能跨年直接当作 2027 年期初。多年度上线前增加 `account_opening_balance(account_id, fiscal_year, amount, source, ...)`，每年独立核对/结转；2026 年可先使用现有字段。不要把年报的 35 个账户原值一并求和：USD/EUR 与 CNY 混算没有财务意义。人民币折算/汇兑损益只在有明确交易汇率时展示，缺汇率不默认套用表中手填固定汇率。

## 5. 接口和数据层切片

**第一切片：报表与查询（复用现有只读表）**

- `GET /api/cashflow-journal/accounts?start=YYYY-MM-DD&end=YYYY-MM-DD`：按账户返回期间报表，附 `openingKnown`、币种和异常数；日期校验、最大查询跨度和分页/限量按实际数据设置。
- `GET /api/cashflow-journal/entries?accountId=&start=&end=&keyword=&page=&size=`：期间明细；以账户 ID 定位，避免账户改名导致身份变化。原 `H3YUN` 台账接口保持兼容。
- 后续导入预览核对接口：仅在暂存文件还存在时按 `sheet + source_row_number` 计算逐笔结存差额；完成确认后不提供历史批次原行回放。
- 前端 `CashflowJournalView.vue` + 专属 API/类型；账户点击下钻后，筛选条件保留在 URL query，便于分享和返回。

**第二切片：可持续录入与事实分层**

- 账户主数据增加主体、银行/钱包类型、掩码账号、币种、启停状态；同名账户不再作为长期唯一身份。旧表以迁移映射至新账户 ID。
- 资金事实、人工标注、业务分配分表（遵循 ERP 决策 #6–#8），每笔生成独立 `fundId`。银行来源的稳定交易号用于幂等；无交易号时逐条保留待复核。
- `POST/PUT` 录入与标注接口必须带现有项目要求的权限、请求幂等键、同事务审计；来源事实不可由标注保存动作改写。
- 收款/付款与销售出库等业务单只做关联，不再生成第二笔资金流水。

首切片不需要新增迁移就能出账户期间汇总；逐笔严格核对、跨年度和正式资金录入需要上述迁移。新迁移版本按仓库当前最大整数版本递增，实施时重新扫描，不固定写死版本号。

## 6. 验收

1. 2026 全年：每账户收入/支出/期末与工作簿「账户汇总」核对；工作簿公式有 `#REF!` 或外部链接时，以账户页原始行和系统计算对拍，列明差异。
2. 2026-09-01 至 2026-09-30：逐账户核对期间期初、收入、支出、期末和净流量；边界两天均计入。
3. 无流水、有期初、缺期初、USD/EUR、日期相同多笔、缺汇率、重复导入各覆盖一个用例；跨币种不出现无单位的总金额。
4. 再导入同一文件不新增重复流水，也不覆盖人工标注；手录变更有权限、幂等和审计。
5. 核实当前环境是否已重导这份工作簿。`docs/db-part3-legacy-tables-20261020.md` 记载当时 `h3_cashflow_entries` 为 0 行待重导，页面不能把「空数据」解释为 0 收支。

## 7. 推荐交付顺序

先完成期间账户报表和明细联动；再把全量文件的增量合并计划、删除候选复核及暂存清理做成完整闭环；逐笔结存核对只在导入预览中执行；最后按 ERP 资金分层模型做录入和银行流水对接。每一阶段都以 2026 年工作簿对拍，不直接移植工作簿里的公式或坏链接。

## 8. 当前实施进度（2026-10-22）

- 已建 `/cashflow-journal` 页面，现以「流水明细」作为默认主视图，同页切换「账户汇总」「对账核对」。流水明细可按期间、账户及摘要/往来对象/经办人搜索；账户汇总保留按币种汇总，基础质量异常集中在核对视图。来源台账仍是只读追溯入口。
- 账户列表现支持名称与币种筛选，默认排序仍为期间流水笔数降序；当前期间账户报表可按筛选结果导出 CSV。账户详情增加 2026 年 12 个月的月初/收支/净流量/月末/笔数及 CSV 导出。月度汇总只从当前生效记录计算，不读取历史导入批次快照。
- 报表当前限定 2026 年，因为 `h3_cash_accounts.opening_balance` 只有这份工作簿的 2026 年期初；跨年需先建年度期初模型。按币种汇总由后端 `BigDecimal` 累计。
- 逐笔余额差额尚未启用。导入器的流式与普通解析路径现在均取得 Excel 原行号，业务哈希明确排除它。现有代码仍将每行原始 JSON 永久写入 `h3_import_rows`；这是待改的技术债，不是最终保留策略。
- 过渡保护已加入确认阶段：某账户的新文件若不再含有数据库里已有的任一行键，就停止自动确认、保留暂存批次，提示人工复核。只追加新行且旧行键都保留时可以继续导入。这个保护不等于跨批次身份匹配；已经发生过的历史重复仍需清查。
- 页面已加入「导入差异复核」只读抽屉：读取待确认批次的暂存行，与现有分录按来源行键对比，列出旧库独有/新文件独有及新文件的 Excel 原行号，可按账户筛选。它提供复核证据，不允许在抽屉里直接认定两行相同或绕过导入保护；正式身份确认仍待建模。
- 已对本地待确认批次做只读差异模拟，但最新文件实际确认及报表对拍仍待完成。手录与银行资金事实分层仍属后续切片。

## 9. 全量文件的增量合并规则（2026-10-22 修订，优先于前述旧实现）

**全量是文件覆盖范围，不是数据库覆盖策略。** 每次上传的账户页用于判断本次“看见了哪些流水”；系统对当前生效的每笔记录分别给出 `新增 / 更新 / 无变化 / 待确认删除 / 待确认匹配`。数据库现有 `h3_cashflow_entries.id` 可作为流水的稳定内部 ID；Excel 行号、旧版 `external_id` 和结存均不能单独充当终身身份。

### 9.1 预览与匹配

1. 上传时将工作簿解析到**临时暂存区**。校验文件类型、账户页覆盖范围、每页表头、重复行号、期初行及金额可解析性。缺少原来存在的账户页时，先按不完整文件处理，不把整个账户的旧流水判为删除。
2. 与当前生效记录比较：原行键相同且内容相同为“无变化”；能唯一确认是同一笔而字段变化的为“更新”，沿用内部 ID；找不到旧记录的新行是“新增候选”。财务补录较早行导致后续结存整体改变时，若账户、日期、收支金额在两侧唯一，可更新既有记录的结存，而不是重复新增。日期或金额也被改动、同日同额多笔、账户改名等无法唯一识别时，只列候选供人工选择，不自动猜测。
3. 本次文件未出现的旧流水是“待确认删除”，**不能因缺席就自动删库**。财务可选“确认已删除”（停止计入报表，保留最小审计标记）、“保留旧流水”（标记来源文件缺席，后续仍可查询）或“其实是某条新行的修订”。无收支的历史占位行可作为单独清理规则，但必须在预览里列明数量；当前代码对此有自动清理特例，需并入统一决策。
4. 预览给出每账户的五类数量和金额影响，列出风险行及候选对应；同一旧记录或新行不能被匹配两次。存在未处理的歧义、删除候选或异常时，不完成整批确认。所有决定在同一事务中提交；失败则当前日记账保持原状。

### 9.2 留存与清理

- **长期保留**：当前有效的日记账记录（含内部 ID）、已确认停用记录的最小标记、批次摘要（文件名/哈希、时间、处理人、五类计数）和必要的人工处理决定。它们不是整份 Excel 的逐行版本。
- **处理期间保留**：`h3_import_staging_rows` 的本次原行和行号，供预览、余额核对及人工复核；批次仍待处理时不能清理。
- **处理完成后清理**：本次原始逐行 JSON、预览中的逐行明细和上传临时文件。现有 `saveImportRow` 对流水日记账逐行写永久 `h3_import_rows.raw_data`，并且完成批次的预览缓存可能还含逐行内容；实施时须将流水日记账分支改为仅留摘要，再清理旧的流水日记账逐行快照。其他氚云数据源的留存规则不受本设计修改。
- 如果用户取消待处理批次，也清理其临时行；若仍有复核事项，则继续保留临时行到完成或取消。清理失败可重试，不能把“批次完成”误认为“原始行已经清理”。

### 9.3 核对与边界

逐笔结存核对在**待确认文件**中按该文件自身行序进行，显示账户、Excel 行号、来源结存、预期结存和差额。确认后只保留当前日记账与核对结果摘要，不做“历史批次逐行回放”。资金日记账仍是手工来源；正式银行余额以银行事实为准，不能把两者直接相加。

`2026年流水日记账1022.xlsx` 暴露的旧键问题已有过渡修复：本地待确认批次 #328 的只读模拟找到 12 条可唯一对应的旧流水和 2 条无收支旧占位行。该过渡代码尚不具备完整的“删除候选/歧义人工决定/快照清理”闭环，因此不能把它当成最终导入方案。
