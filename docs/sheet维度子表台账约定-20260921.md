# sheet 维度子表台账约定（2026-09-21）

## 背景与决策

利强的氚云导出件大量使用「**一个实体一个 sheet**」的组织方式（流水日记账 35 张账户 sheet、
各供应商明细 59 张供应商 sheet、店铺订单 8 渠道 sheet、各银行流水 29 账户 sheet、
各物流账单 8 物流商 sheet、封口机账单 8 月份 sheet）。LQ 于 2026-09-21 拍板：
台账必须还原这一结构心智——**方案 A「汇总条 + 主从筛选」**：
选中实体 → 只看该 sheet 的行（后端精确筛选）；不选 → 全量平铺 + 全局合计小计。

已落地两类（本日）：

| 台账 | sheet 维度列 | 汇总端点 | 筛选参数 |
|---|---|---|---|
| 流水日记账 `cashflowJournal` | `h3_cashflow_entries.account_name` | `GET /api/h3-imports/ledger/cashflowJournal/accounts` | `?account=` |
| 供应商应付 `supplierPayable` | `h3_supplier_payables.supplier_name` | `GET /api/h3-imports/ledger/supplierPayable/suppliers` | `?supplier=` |

## 约定（今后新增导入必须遵守）

凡源文件为「每实体一个 sheet」且 sheet 名有业务含义（账户/供应商/渠道/物流商/月份…）：

1. **sheet 名必须落列**：解析层把 sheet 名写入事实表的专用列（如 `account_name`、
   `supplier_name`），并参与幂等键（流水日记账先例：`账户#日期#收入#支出#结存#序号`）。
   禁止只留在 `raw_data` 里不建列——没列就没法筛选与汇总。
2. **台账必须配「汇总条 + 主从筛选」**：一个 sheet 维度汇总端点（`GROUP BY` 维度列 + 金额合计，
   参照 `H3BusinessQueryService.cashflowJournalAccounts()`），台账列表端点加同名列的
   精确筛选参数；前端复用 `H3LedgerPanel.vue` 的 `ledger-facet` 样式块。
3. **实体档案表优先**：若 sheet 同时对应实体档案（如账户 → `h3_cash_accounts`），期初类
   伪行回写档案表（先例：「上期结存」行 → `opening_balance`），汇总端点以档案表为
   LEFT JOIN 主表——**无分录的实体也要出现在汇总里**。
4. **外币合计不折算**：账户汇总按原币种展示期末；全局合计为原值混算时必须以提示标注
   （先例：「含 N 个外币账户，合计为原值混算」）。
5. **汇总条非关键路径**：前端加载失败静默降级为无下拉，不阻断台账列表。

## 未做 / 边界

- 35 个账户的「公司 / 个人代收付」归类（owner_company）已有既定事实基础
  （≥8 法人主体、公私混用），但本轮未加字段——归入 ERP M1+ 资金域再定。
- 收银通 `cashierLog` 源为单 sheet，无此维度。
- 账户余额的**日期穿越**（查某日时点余额）本轮未做：期末=期初+全期收−支，
  日期筛选只作用于分录行、不重算余额。需时点余额时另立需求。
