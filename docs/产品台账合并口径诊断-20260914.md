# 产品信息台账 × 仓库明细 合并口径诊断（2026-09-14）

> 背景：产品库存页目前只显示 4866 个交易产品中的 1551 个有库存项。
> 台账侧共有 15586 个产品（产品信息 15279 ∪ 仓库明细 14993）。
> 本文核实差额构成，并给出「完整合并」的实现口径。
>
> 全部数字来自 2026-09-14 对生产库 `product_archive` 的只读查询。

---

## 一、结论先行

用户判断成立，但真相比"每个产品有单独名称编号"更严重：

**氚云的 `product_code` 在两张台账之间不是稳定的身份标识。**

- 两表都有该编码的 14686 个码里，**47 个码在两张表里指向完全不同的产品**（名称对不上）
- **354 个码存在"同物不同码"**（名称+规格+单位相同，编码不同）
- 纯顺序漂移：`001QDZPJ` ↔ `001DDZPJ`、`模具389` ↔ `模具381`、`1736YX` ↔ `1733YX`
- 前后缀互换：`108YY` ↔ `仓库 YY108`、`165YY` ↔ `仓库 YY165`

**直接后果**：现有合并逻辑按 `product_code` 精确匹配
（`ProductInventoryMergeService:143` `productMap.get(sr.productCode)`），
那 47 个码会**给产品挂上别人的采购价**，且不报错。

## 三、要改的两处

### 3.1 合并的身份解析（必须改）

`ProductInventoryMergeService` 目前是单键匹配。应改为与
`OutboundRelationGovernanceService` 一致的降级链：

```
① product_code 命中 且 名称/规格/单位不冲突  → 采信
② product_code 命中 但 名称明显不符          → 视为编码漂移，降级到 ③
③ 名称+规格+单位唯一命中                     → 采信
④ 名称唯一命中                               → 采信
⑤ 多候选 / 无候选                            → 只入 REVIEW，不自动绑定
```

`OutboundRelationGovernanceService` 已有现成的 `nsuKey(name, spec, unit)` 与
`productCodeKey(code)`，可直接复用，不必新写。

### 3.2 零库存与台账独有产品的处理（口径待定）

`ProductInventoryMergeService:140`：

```java
if (sr.quantity == null || sr.quantity.compareTo(BigDecimal.ZERO) == 0) { skippedZero++; continue; }
```

零库存行既不建档也不写余额，所以 9824 个产品永远进不了库存页。
台账独有产品则根本不进入循环。

## 四、待决策：落点在数据层还是查询层

| | 方案 A：数据层全量建档 | 方案 B：查询层合并视图 |
|---|---|---|
| 做法 | 改 merge：零库存也建档、也写零余额；补 NSU 降级 | 库存页直接以 台账∪仓库明细 为驱动，余额表不动 |
| `sales_products` | 4866 → ~15586 | 不变（4866） |
| `product_inventory_balances` | 1678 → ~16273 行 | 不变（1678） |

| 副作用 | 产品主数据涨 3 倍；`OutboundRelationGovernanceService` 的候选索引从 1678 涨到 16273，产品归类自动率可能下降（更保守，但不报错） | 无数据副作用 |

## 五、核查命令留档

```sql
-- 跨表同码但名称不符的编码（47 个）
WITH w AS (SELECT DISTINCT product_code, LOWER(TRIM(COALESCE(product_name,''))) nm
             FROM h3_warehouse_stock),
     p AS (SELECT product_code, LOWER(TRIM(COALESCE(product_name,''))) nm
             FROM h3_product_catalog)
SELECT p.product_code, COUNT(*) w_rows,
       SUM(CASE WHEN w.nm=p.nm THEN 1 ELSE 0 END) name_ok
  FROM p JOIN w ON w.product_code=p.product_code
 GROUP BY p.product_code HAVING name_ok=0;

-- 同物不同码（354 个台账码）
WITH p AS (SELECT product_code, LOWER(TRIM(COALESCE(product_name,''))) nm,
                  LOWER(TRIM(COALESCE(specification,''))) sp,
                  LOWER(TRIM(COALESCE(unit,''))) un FROM h3_product_catalog),
     w AS (SELECT DISTINCT product_code, LOWER(TRIM(COALESCE(product_name,''))) nm,
                  LOWER(TRIM(COALESCE(specification,''))) sp,
                  LOWER(TRIM(COALESCE(unit,''))) un FROM h3_warehouse_stock)
SELECT COUNT(*) FROM p
 WHERE EXISTS (SELECT 1 FROM w
                WHERE w.nm=p.nm AND w.sp=p.sp AND w.un=p.un
                  AND w.product_code<>p.product_code);

-- 仓库明细的 (产品,仓库) 实际组合数
SELECT COUNT(*) FROM (SELECT DISTINCT product_code, warehouse FROM h3_warehouse_stock) t;
```

## 六、已落地的口径（2026-09-14 实现）

**落点：查询层合并视图**（不动产品主数据与库存余额表），
**行粒度：仓库明细里实际出现的「产品 × 仓库」组合**（不做全仓展开）。

### 6.1 驱动集

`ProductInventoryService.VIEW_FROM`：

| 来源 | 行数 | 说明 |
|---|---|---|
| 仓库明细里实际出现的 (编号, 仓库) 组合 | 16273 | 每个组合一行，仓库来自 `warehouses` 名称匹配（`h3_warehouse_name_mappings` 为空表，作为覆盖入口保留） |
| 产品信息台账里、仓库明细完全没有该编号的产品 | 593 | 仓库留空，前端显示「未记录」 |
| **合计（已剔除费用项）** | **16839** | 覆盖 15574 个产品 |

初版曾做「每个产品 × 3 个启用仓」笛卡尔展开（约 4.7 万行），已废弃——
仓库明细是各仓自己的台账，**13726 个产品只出现在 1 个仓库**，展开会凭空造出 2/3 的伪零行。

### 6.2 字段口径

| 字段 | 取值 |
|---|---|
| 类目 | 产品信息台账优先，仓库明细补齐 |
| 名称 / 规格 / 单位 | 仓库明细该行优先（该行代表仓里实际那件东西），缺失时回退台账 |
| 数量 | 仓库明细最新值；台账独有产品按 0 |
| 采购价 | 产品信息台账优先，回退仓库明细价 |
| 库存金额 | 数量 × 采购价，保留 4 位 |

库存余额表**不参与字段取值**（实测仅 1 行与台账分叉：`模具281` 台账 11 / 余额 24）。
它只在取到当页数据后单独查一次，用于给出「查看流水」入口与更新时间——
这样每页 5 次汇总查询不必付左连接成本。

### 6.3 费用项过滤

台账里的费用行「数量」列装的是金额，混进清单会虚增库存：

| 编码 | 合计"数量" | 类目 |
|---|---|---|
| 定制片材 | 1,344,071 | 费用 |
| 运费 | 120,813 | 费用 |
| 税点 | 10,900 | 费用 |
| 制版费 | 8,100.5 | 制版费 |
| 加工费 | 1,918.4 | 空 / 费用 |
| 样品费 / 模具费 / 优惠 / 加急费 / 认证费 / 代发运费 / 打样费 | 少量 | 费用 |

过滤规则：类目命中 `费用/制版费/税点/运费` **或** 编号命中内置费用名单。
后者是必需的兜底——实测存在 `code=加工费、类目为空` 的行，已混入库存余额表（H3-加工费，220 元）。

### 6.4 编码冲突标记

`codeConflict=1` 表示台账同编号存在但名称与该仓库明细行不一致，页面用警告图标提示。
这类行的编号已被证明不可信，采购价可能取自别的产品，**不再静默采信**。

### 6.5 性能

| 版本 | 首屏耗时 |
|---|---|
| 初版（逐句 COUNT/DISTINCT/SUM 5 次 + 3 个左连接） | 3208 ms |
| 最终（5 项聚合压成 1 次 SELECT + 余额查询移出热路径） | **1057 ms** |

分句剖析（优化前）：派生表 13 ms → +台账左连接 59 ms → +产品主数据左连接 117 ms → +余额左连接 137 ms。
主开销是重复物化同一个派生表，因此合并汇总查询收益最大。

## 七、尚未处理的遗留：同物不同码会显示成两行

实测 297 个台账编号能在仓库明细里按「名称+规格+单位」找到同物（编码不同），
另有 268 个反向情形。这些在清单里会**各占一行**：

```
001DDZPJ  订做138x98气动转盘机一出二卷膜+六工位   温州仓   数量=0       价=—        仓库记录=1
001QDZPJ  订做138x98气动转盘机一出二卷膜+六工位   （未记录）数量=0       价=17500    仓库记录=0
```

即：仓库那一行有数量没有价，台账那一行有价没有仓库——同一件东西被拆成两行。

**为什么没有自动合并**：按名称合并存在误合风险（台账内部就有 31 组同名同规格同单位、
1 组高达 10 个编码）。若两个真实不同的产品恰好同名，合并会把它们的库存与价格混在一起，
后果比重复显示更严重。

**建议的修法**（低成本、影响面小）：只对「编号对不上」的行做名称认领——
当仓库明细行的编号在台账里找不到、而「名称+规格+单位」在台账里唯一命中时，
用台账那一行的采购价，并把台账那一行从「台账独有」段移除。
编码一致的 14686 行完全不动，因此不引入全局归并风险。
