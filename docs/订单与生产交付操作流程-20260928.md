## 0. 一条主线

```
销售订单草稿 → 履约评审（自产找车间/外采找采购）→ 销售审批确认
                                                        ↓
                       现货直接发 ｜ 自产下达生产 ｜ 外采办理采购   （三路并行）
                                                        ↓
                                          回到原订单明细「办理发货」→ 出库过账
```

订单**确认前**和**确认后**是两个世界：确认前可以随便改（改了评审自动失效）；确认后原明细不可直接改，只能走「登记风险／问题 → 变更」。

## 1. 角色与权限速查

| 动作 | 页面 | 权限 |
| --- | --- | --- |
| 看订单/出库 | 销售订单、销售出库 | `sales_order.read.self` / `.department` / `.all` |
| 建单、改单、提交、送评、办理发货 | 销售订单 | `sales_order.manage` |
| 销售审批通过／驳回 | 销售订单 | `sales_order.approve` |
| 自产履约评审 | 销售需求履约评审（车间·自产） | `manufacturing.manage` |
| 外采履约评审 | 销售需求履约评审（采购·外采） | `purchase_order.manage` |
| 接单下达生产 | 待下达生产需求 | `manufacturing.manage` |
| 建/提交生产任务单 | 本地生产任务 | `manufacturing.manage` |
| 报工 / 报工冲正 | 本地生产任务 | `manufacturing.report` / `manufacturing.report.override` |
| 检验、检验合格入库 | 本地生产任务·待完工检验 | `manufacturing.inspect` |
| 完工入库冲销 | 本地生产任务·完工入库记录 | `manufacturing.receive.reverse` |
| 跟单记录 | 本地生产任务 | `manufacturing.followup` |
| 采购建单/提交/到货/到货冲正/代发/取消 | 采购订单 | `purchase_order.manage` |
| 采购审批通过／驳回 | 采购订单 | `purchase_order.approve` |
| 出库建单/过账/冲销/取消 | 销售出库、销售订单明细 | `sales_order.manage` |

两条注意：
- **提交与审批是两个独立权限**。有 `*.manage` 不等于能审批。系统默认**不禁止自审**（同一人建单又审批），但有留痕。
- **`@RequirePermission` 是「任一满足」语义**。读取接口必须同时列出三个 `read` 变体，否则某一数据范围的角色会 403。

## 2. 分步操作

### 第 1 步 · 业务员新建销售订单

入口：**订单与生产交付 → 销售订单 → 右上「新建订单」**

1. **客户**：下拉远程搜索（名称/简称/编号/联系人），数据来自客户档案。档案里没有 → 点「新增客户」就地建档（`POST /api/customers/quick-create`，同名未删除客户**直接复用**，不会重复建档）。
   - 保存前必须已锚定档案客户，否则存不了。
2. 填订单日期、要求交期、备注。
3. **逐行录明细**。每行独立定：产品及配置、单位、数量、单价、明细交期、**供货方式**。

   | 供货方式 | 录什么 | 当时的约束 |
   | --- | --- | --- |
   | 现货 `STOCK` | 从**可售库存**选产品，填数量价格 | 选中产品**不等于**预留或扣减库存；发货时才真正校验 |
   | 自产 `MAKE` | 点「配置自产产品」，复用建任务单表单选产线/产品/配置 | 只保存**需求配置**，不等于已下达生产任务 |
   | 外采 `BUY` | 填产品名称、规格型号、品牌、技术、验收、包装、交付要求 | 只保存需求，不提前生成采购单 |
   | 待确定 `UNDECIDED` | 先存草稿 | **不能送评、不能提交审批** |

4. 「保存草稿」或直接进下一步。

### 第 2 步 · 送履约评审

明细里有自产或外采时，点 **「保存并送履约评审」**（= 保存 + `request-fulfillment-review`）。
只有现货明细的订单不需要这一步。

- 车间在 **销售需求履约评审 → 车间·自产** 页，点行内「查看并评审」，结论二选一：
  - **可按要求执行 `ACCEPTED`** → 通过
  - **需要销售调整 `CHANGE_REQUIRED`** → 必须填原因，退回销售改单
- 采购在 **采购·外采** 页做同样的事。
- **改了明细，旧评审自动失效**（按内容快照 `content_hash` 比对），列表会显示「已失效，需重评」。
- 评审人填的**建议可交日期不会直接改掉客户要求交期**，只是个参考。

### 第 3 步 · 销售审批确认

订单明细齐全、所有需评审的明细都有**有效通过意见**后，点 **「提交审批」**。

提交前系统会逐条校验（任一不过就报错）：
- 订单没有明细 → 「订单没有明细，不能提交审批」
- 有明细还是 `UNDECIDED` → 「明细 N 尚未确定供货方式」
- 外采明细没做采购需求配置 → 「外采明细 N 尚未完成采购需求配置」
- 自产明细没做产品配置 / 配置读不出来 → 报错
- 履约评审未就绪 → 「请先将自产／外采明细送履约评审」

审批人点 **「审批通过」** → 订单变 **已确认 `CONFIRMED`**；点 **「驳回」**（原因必填）→ 退回草稿，审批历史保留。

> 订单状态：`DRAFT 草稿` → `PENDING_APPROVAL 待审批` → `CONFIRMED 已确认`。
> 审批态单列：`NONE / PENDING / APPROVED / REJECTED`，完整历史在 `erp_approvals`（append-only）。

**订单一旦确认，需求就锁定，原明细不能直接改。**

### 第 4 步（并行三选一或全选）

一笔订单可以同时有三类明细，三条路各走各的，没有先后。

#### 4A 现货 · 业务员发货

在**已确认订单详情**里，对现货明细点 **「办理发货」**（行内按钮只在"未发数量 > 0"且该明细未被暂停时出现）。

1. 选发货仓库 + 来源（现货是直接从可售库存选产品）
2. 填本次数量 → 生成出库草稿
3. 页面跳到该出库单，**核对后点「过账」**才真正扣库存

草稿**不扣库存**；过账在同一事务里扣余额并写流水。

#### 4B 自产 · 车间接单生产

1. **待下达生产需求**页点行内「查看并下达」→ 核对「销售确认的产品配置」→ 点 **「生成生产任务」**。
   - 列表只显示：订单已确认 + 供货方式为自产 + 还没建过任务单的明细。
   - 前置校验：订单必须已确认、明细必须是自产、必须有产线和生产配置、该明细没建过任务单。
2. **任务单不再二次审批**。从销售需求生成的工单直接写 `approval_basis='SALES_ORDER'`、`approval_status='APPROVED'`，沿用销售订单的审批依据：
   - **有工序 → 已下达 `RELEASED`**
   - **0 工序 → 待检验 `PENDING_INSPECTION`**（不是一律 RELEASED，否则 0 工序单会卡死）
3. 车间在**本地生产任务·车间执行**页报工（`manufacturing.report`），报错可**冲正**（`manufacturing.report.override`，必填原因）。
   - 跟单员可另记跟进内容（`manufacturing.followup`），**跟单不替代报工**。
4. 全部必做工序完成后进「待完工检验」。质检点 **「检验入库」**：
   - **合格 → 检验与完工入库在同一次提交里完成**（`quality-completion`），写完工入库单 + 成品批次 + 库存流水
   - 不合格 → 指定返工起始工序，返工后复检
   - 没有库存产品身份的产出，必须先在检验页选对应产品档案才能入库

#### 4C 外采 · 采购员办理采购

入口二选一：销售明细行内 **「办理采购」**（跳转带上该明细），或 **采购订单 → 待采购需求 → 「建采购单」**。

1. 建单：销售确认的名称、规格、单位、数量带入并受保护；采购补供应商、采购单价、预计到货、**履约方式**、默认入库仓库。
   - 履约方式：**到货入库 `WAREHOUSE`** ／ **供应商直发 `DROP_SHIP`**
2. **采购审批**（`purchase_order.approve`）通过 → 已确认 `CONFIRMED`。这是**采购支出授权**，不是重复判断客户需求。
3. 执行：
   - **到货入库型**：点「到货入库」填实际数量（可分批）→ 写本地库存余额与流水；填错可「冲正」
   - **供应商直发型**：点「生成代发出库单」→ 生成出库草稿（`POST /{id}/drop-ship-outbound`）→ 过账。**货从不进本地仓，过账与冲销都豁免库存。**

### 第 5 步 · 回到原订单明细「办理发货」

> **这一步容易漏。** 自产完工入库、外采到货入库之后，都要**回到原销售订单详情**，对那条明细点「办理发货」——而不是在普通出库页自己开一张单。只有这样才能把发货回写到原需求。

1. 打开原销售订单详情，找对应明细 → **「办理发货」**
2. 选「仓库 + 来源」：
   - **自产** → 选该任务**主产品的成品批次**
   - **外采（本地到货）** → 选该采购明细**在该仓库的实际到货**
   - **现货** → 直接从可售库存选品（且不能指定生产批次）
3. 填本次数量 → 生成出库草稿 → 页面跳到该出库单 → 核对后**过账**

**数量口径（明细行「发货进度」列直接显示）**：

```
已发     = 关联的 POSTED 出库数量
草稿待发 = 关联的 DRAFT 出库数量
未生成   = 需求数量 −（DRAFT + POSTED）
```

- 本次数量必须 > 0 且 ≤ 未生成量
- 每张自产出库草稿只选一个成品批次；多批次就分别生成草稿，支持分批
- `CANCELLED` / `REVERSED` 不占用待发需求，可以重新办理
- **原订单生成的出库草稿不能在普通出库页改产品、仓库或数量**。要调整就取消原草稿，回订单重新生成

### 第 6 步 · 出库过账与撤销

- **过账 `POSTED`**：同一事务扣总库存 + 来源批次可用量，写流水。任一步失败整体回滚。
- **冲销 `REVERSED`**：同一事务回补库存与批次。终态，要重发请新建。
- **取消（草稿）`CANCELLED`**：不增加库存，只释放该明细的来源占用。

**联锁**：
- 已被关联待发／已发出库占用的**完工入库不能直接冲正** → 先取消或冲销关联出库
- **采购到货冲正**后若剩余到货量不够覆盖关联待发／已发量 → 会被拦截
- 明细处于**执行异常未解决**状态 → 禁止生成关联出库及过账

## 3. 确认后发现问题：登记风险／问题

**四个入口共用同一个弹窗**：待下达生产需求的「登记条件变化」、关联销售订单的生产任务详情、采购订单详情、销售订单明细的「登记风险／问题」。

填具体问题 + 处理方案，选**影响**：

| 影响 | 效果 |
| --- | --- |
| **风险提醒，继续办理** | 保留问题待办，**不阻止**后续执行 |
| **暂停本明细后续下达及发货** | 阻止新建生产/采购单、采购提交/审批、出库过账 |

注意边界：**已有报工、检验、到货不会自动停止**，要执行人员自己协调。每条明细同时只保留一条未解决问题，先处理原记录。无客户依据不能直接生效。

### 出路一 · 内部能解决 → 原约定不变

点 **「原约定不变，解决问题」**，填依据 → 关闭记录，**订单版本不变**。

### 出路二 · 客户接受执行方原方案

1. 执行方（车间/采购）先登记「执行方确认的可行客户交期」，核对关联单据并说明安排
2. 销售与客户协商（**协商期间原订单交期不变**）
3. 客户明确接受 → 在问题记录点 **「客户接受原交期方案」**，填客户确认日期 / 记录位置 / 补充协议等依据
4. 系统校验原数量、原交期与执行快照仍有效 → 生成已生效变更、**订单版本递增**、同步未完成生产任务的需求交期、关闭问题
5. **无需重复执行复评，也不需要 `sales_order.approve` 权限**

### 出路三 · 客户提出其他方案

1. 销售点 **「协商其他数量／交期」**，填客户提出的日期与沟通记录
2. 自产由车间、外采由采购确认新方案是否可行；需要调整则退回销售继续协商
3. **仅交期变化**且执行方确认可行 → 状态「待客户确认」
4. 销售记录客户最终接受依据 → **「登记客户接受并生效」**（不再要求第二次商业审批）
5. 客户不接受 → **「客户未接受／撤回」**，原订单不变，问题继续保留
6. **数量变化仍需商业审批**（`sales_order.approve`）——执行方复评确认数量方案**不能**替代增购金额的授权

### 快照失效

如果报工、入库、到货、单据状态或关联单据已经变化，旧执行快照就不能再用。要走 **「协商其他数量／交期」** 重新提交方案、重新确认执行可行性，再登记客户接受结果。**不会直接覆盖生产事实。**

## 4. 状态速查

| 单据 | 状态 |
| --- | --- |
| 销售订单 | `DRAFT` 草稿 / `PENDING_APPROVAL` 待审批 / `CONFIRMED` 已确认 |
| 审批态（三单共用） | `NONE` 未提交 / `PENDING` 待审批 / `APPROVED` 已通过 / `REJECTED` 已驳回 |
| 生产任务单 | `DRAFT` 草稿 → `PENDING_APPROVAL` → `RELEASED` 已下达 / `PENDING_INSPECTION` 待完工检验 → `IN_PRODUCTION` → `PENDING_RECEIPT` 待入库 → `PARTIALLY_RECEIVED` → `COMPLETED`；另有 `REWORK` 返工中 / `PENDING_REINSPECTION` 待复检 / `CLOSED` / `CANCELLED` |
| 工序 | `PENDING` 待开工 / `READY` / `IN_PROGRESS` 进行中 / `BLOCKED` 受阻 / `COMPLETED` 已完成 |
| 采购订单 | `DRAFT` → `PENDING_APPROVAL` → `CONFIRMED` → `RECEIVING` 履行中 → `CLOSED` / `CANCELLED` |
| 采购履约方式 | `WAREHOUSE` 到货入库 / `DROP_SHIP` 供应商直发 |
| 销售出库 | `DRAFT` 草稿 / `POSTED` 已过账 / `REVERSED` 已冲销 / `CANCELLED` 已取消 |
| 履约评审 | 待评审 / 评审通过 / 需要调整 / 已失效需重评 |

## 5. 独立生产任务（不走销售订单）

展会、展厅、打样、备货、内部领用等可以在 **本地生产任务 → 右上「新建生产任务单」** 直接建单，**不需要虚构销售订单**。

计划类型：`SALES_ORDER` 承接销售需求 / `STOCK` 备货 / `EXHIBITION` 展会 / `SHOWROOM` 展厅 / `SAMPLE` 打样 / `SPECIAL` 特殊定制 / `INTERNAL` 内部领用 / `REWORK` 返工 / `REPLACEMENT` 返工替换。

与销售需求生成的任务有两点不同：
1. **要自己走审批**：落草稿 → 提交审批 → `manufacturing.approve` 通过才下达
2. **不能借用订单审批依据**（`approval_basis` 不会是 `SALES_ORDER`）

完成后按检验入库流程形成库存，真正销售时再建现货订单。

## 6. 已知卡点与待定（本轮流：核对代码所得，非猜测）

以下三条是**代码口径本身不一致**，会影响实际操作，建议排期处理：

**① 采购取消后重下会撞唯一键。**
`pendingPurchaseDemands` 的判定是 `NOT EXISTS(... AND p.status<>'CANCELLED')`——取消后这条明细会**重新出现在待采购需求列表里**。但 `V344` 的 `uk_epo_sales_order_item` 是**无条件 UNIQUE**，取消的采购单仍占着这个键。→ 列表里看得到，点「建采购单」会被 DB 拒绝，返回 409 加一段**原始 SQL 片段**（`Duplicate entry ... for key ...`）：看得见错误，但看不出下一步该做什么。

**② 生产任务单根本没有作废通道，比采购侧更死。**
`pendingProductionDemands` 和 `acceptProductionDemand` 的判重都是 `WHERE sales_order_item_id=?`，**没有任何状态过滤**；`V342` 的 `uk_mo_sales_order_item` 同样无条件 UNIQUE。而 `ManufacturingController` **没有任何 cancel/void 端点**，全仓也没有 `UPDATE manufacturing_orders SET status='CANCELLED'` 的写入方（`CANCELLED` 只出现在 6 处读过滤器里）。→ 该明细一旦建过任务单（**无论它后来怎样**），就**再也不会回到待下达列表**；而任务单本身是"直接进已下达"的，**车间接错了单也没有回收手段**。与采购侧"取消后重新出现"的行为相反，两处口径应当统一。

**③ 代发存在跨岗权限断层。**
`POST /erp-purchase-orders/{id}/drop-ship-outbound` 需要 `purchase_order.manage`，但它生成的出库草稿要过账得走 `POST /sales-outbounds/{id}/post`，需要 `sales_order.manage`。→ **只有采购权限的采购员能生成草稿却过不了账**，会卡在 `DRAFT`，需要跨岗协作。

另外两点是**已知设计边界**，不是缺陷，但操作时要心里有数：

- **出库建单端点已废弃**：`POST /api/sales-outbounds` 恒抛 409，出库单**必须**从销售订单明细或采购代发生成。若页面上还留着「直接新建出库单」入口，用户会看到「请先创建并确认销售订单」。
- **履约评审是手动步骤**：不会自动触发。漏点「保存并送履约评审」，提交审批时才报「请先将自产／外采明细送履约评审」——流程顺序对新用户不直观。

**尚未建设的部分**（不要按已有能力使用）：客户收款登记与归单、应收核销、定金/尾款、退款结清；跨订单库存预留；混合供货；多供应商拆单；执行后的数量/配置变更（本轮只开放**数量不变**的交期调整）。月度提成与结算侧仍用氚云出库中的最终收款数据，**新销售订单不能据此认为财务闭环已完成**。

---

## 7. 一句话总结

**建单定需求 → 评审定可行性 → 审批定承诺 → 三路并行备货 → 回原明细办理发货 → 过账扣库存。** 订单确认是分水岭：确认前随意改（改了评审失效），确认后只能走登记问题与变更。
