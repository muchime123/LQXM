## 0. 一句话结论

**这个项目已经建成了一套"档案 + 运营 + 历史数据资产"平台，但 ERP 本体还停在「设计齐备、实现≈0」。**

- **设计**：28 条决策、64 份文档、S0 模型层 43 例验证 —— 完工度很高。
- **实现**：**ERP 自产业务数据只有 1 张工单 + 3 条工序 + 3 条报工**（`MO00000018` 那次试跑）。`erp` schema 3 张表、`erp` Java 包 8 个文件，**全是 M0 契约基础设施，零业务实体**。
- **最要紧的发现**：主库里那 **19 万行"看起来像 ERP 业务表"的数据，实际全是氚云台账**（`sales_outbounds` 18,966 行 **100% `external_source='H3YUN'`**）。

所以「接下来怎么做」的答案不是"再补哪些功能"，而是：**把手上的设计变成能跑的正式单据，一个族一个族地纵向贯通**。而第一步只有一个 —— **让库存账活过来**。

## 2. ⚠️ 五个必须知道的结构性事实

### 2.1 台账表占用了 ERP 业务表的命名空间（**最大的架构风险**）

`sales_outbounds`、`purchase_receipts`、`receipts` 这些**看起来是 ERP 核心单据表**的名字，实际装的全是氚云台账（18,966 / 11,087 / 6,452 行，100% `H3YUN`）。

**后果**：ERP 上线后要建"真的销售出库单"，这个名字已经被占用。若挤进同一张表：

| 报表 | 会出错的方式 |
|---|---|
| 「今年出库多少」 | 把**台账全年历史**和 **ERP 上线后增量**混算 → 数字翻倍 |
| 「这张单走完流程没」 | 台账行没有流程状态，与 ERP 行混在一起无法区分 |
| 「谁录的」 | 台账行没有录单人 |

→ **这正是决策 #11「ERP 独立 `erp` schema」要解决的问题，但目前没有执行**（`erp` schema 只有 3 张契约表）。**这是路线里必须最先处理的一件事。**

### 2.2 同域两套表：制造域有"氚云版"和"ERP 版"各一套

| 氚云台账版 | ERP 自建版 |
|---|---|
| `production_orders`（5,691） | `manufacturing_orders`（**1**） |
| `production_order_components`（14,367） | `manufacturing_order_operations`（3） |
| `h3_production_reports`（12,252） | `manufacturing_work_reports`（3） |

按 #23「ERP 接管下单、氚云转只读历史」，这是**预期形态**；但 ERP 侧目前只有 1 张试跑单，**离"接管"还很远**。

### 2.3 库存主轴已贯通 99.8%，只差把流水写进去

串联主轴实测定为 **SKU**：出库明细 `product_code` 99.9% 填充 → 台账产品 99.8%。**库存主轴（入库 → 库存 → 出库）本已贯通**，但五类出入库事实**一条都没写入流水**：

| 台账事实 | 行数 | 已写入流水 |
|---|---|---|
| 销售出库 | 18,966 | **0** |
| 采购入库 | 11,087 | **0** |
| 完工入库（内部主体） | 3,331 | **0** |
| 其他出入库 / 调拨 | 台账侧 | **0** |

→ **这是"有货直接出库 / 无货下工单"这个业务分叉的判断依据，也是全流程跑通的第一块砖**（见 #27）。

### 2.4 唯一硬断：工单没有 SKU

工单 `product_name` 是**品类级**（手动片膜 1,058 / 按钮自动片膜 574 …共 25+ 种），SKU 只在完工入库时产生，且**一单产出 1~29 个**（多 SKU 占 14.0%，模具占入库行 27.9%）。→ 这是「微信传名」的**结构性根因**，也是 #28 要解决的核心。

### 2.5 导入中心的"非完成态"批次**都是已定性的历史事故**，不是活跃故障

| 批次 | 类型 | 原因 | 定性 |
|---|---|---|---|
| 146 | PRODUCT_INFO | 表头校验拒绝（第 1 列错位） | ✅ **正确行为**，防列错位 |
| 193 | SUPPLIER_PAYABLE | V313/V314 迁移时序窗口 | ✅ 已被 194/195 取代并收敛 |
| 211 | CASHFLOW_JOURNAL | OLE2 格式（WPS 私有 AES 未另存） | ✅ 08/21 后续 4 批已 COMPLETED |

→ **不需修代码**，只需在界面上标注"已闭环"。

## 3. 差距分析：一个"完善的 ERP"该有什么 vs 现在有什么

按标准制造业 ERP 能力域对照：

| 能力域 | 应有能力 | 现状 | 差距 |
|---|---|---|---|
| **主数据** | 物料/客户/供应商/仓库/员工/工艺 | 产品✅ 客户✅ 员工✅ 仓库✅（3 个）/ 供应商⚠️（有台账无模块）/ BOM❌（#17 决定不建） | 中 |
| **销售** | 报价 → **订单** → 发货 → 开票 → 应收 | **无订单模块**；出库只有台账 | **大** |
| **采购** | 请购 → **订单** → 收货 → 对账 → 应付 | **无订单模块**；入库只有台账；应付有财务台账 | **大** |
| **库存** | 入库/出库/调拨/盘点/批次 | 表已建✅ 期初已开✅ **流水空❌** 盘点（#G5 无源）❌ | **中（只差写流水）** |
| **生产** | 工单 → 报工 → 完工入库 → 批次 | 后端齐✅ 前端有页✅ **但只有 1 张试跑工单**❌ | **大（实现侧）** |
| **财务** | 应收应付/收付款/核销/资金（#21 范围，不含总账） | **全部只有台账**，无模块 | **大** |
| **报表分析** | 经营看板 / 库存 / 往来账龄 | 只有台账分析视图 | 中 |
| **系统管理** | RBAC / 审计 / 幂等 / 单据编号 | ✅ **成熟，可直接复用**（#11 已定） | 无 |

**一句话**：**横向（数据来源）已经够了，纵向（业务闭环）几乎是零。**

## 5. ⭐ 路线：接下来应该怎么做

### 5.0 核心主张

> **停止把"新增数据源数量"当作完成度指标。** 下一步的全部价值，在于**把已设计的正式单据真的建出来，一个族一个族地纵向贯通** —— 每个族的验收标准是同一句话：**「能录单 → 单据产生库存/资金影响 → 能查能追溯」**。

**不要**再以"再补一类导入"推进，除非它是某个闭合能力的必需证据。

### 5.1 分阶段路线

| 阶段 | 工作 | 具体动作 | 退出条件 |
|---|---|---|---|
| **P0**<br>今天 | **清技术债 + 落决策** | §4 清单 1/3/4 项；Q1~Q4 入登记；确认 `erp` schema 边界 | 决策登记无"已定未做"项 |
| **P1**<br>**最关键** | **库存主轴上电** | ① 拍 **U13**（流水起点）② 建"台账事实 → 库存流水"写入器（复用导入器链路，不手工搬）③ 五类出入库按 U13 口径写 `product_inventory_transactions` ④ 交付「现在有没有货」查询 | ERP 能回答任一 SKU 的当前库存，且能追到来源单据 |
| **P2** | **销售出库录入**（#22 明确的第一缺口） | ① 在 `erp` schema 建正式销售出库单（**不复用台账表名**，见 §2.1）② 出库从可售库存选（#28 第④步）③ 落 `sales_outbound_finished_goods_allocations` | 业务员能在 ERP 里录一张出库单并扣减库存 |
| **P3** | **生产闭环**（#28 落地） | ① 建单**绑 SKU + 产出清单必填**（Q3 已定）② 收货按清单逐项填数量（收货单改主子结构）③ 收货即生成**可售通知**替代微信 ④ 出库选可售库存 | 一张工单从建单到出库全程无自由文本 |
| **P4** | **往来与资金**（#21 范围） | ① 拍 **U1**（应收触发节点）② 应收应付 + 收付款 + 核销 + 未分配余额（#9）③ 资金账户（#6/#7/#8） | 一笔销售能算出"已收/未收"，且与银行流水可对 |
| **P5** | **切换** | ① 拍 **U12**（历史迁不迁）+ **U14**（完工入库口径）② 定"氚云停用日"③ 在办单据收尾方案（#23：938 张在办工单）④ 对账与回退演练 | 业务签认 |

**关键路径**：**P1 → P3**。因为「有货直接出库 / 无货下工单」这个分叉的**判断依据就是库存**，而工单接 SKU 是唯一的硬断。

### 5.2 现在**不要**做的事

1. **不要**再补导入种类（除非是闭合能力的必需证据，如 G5 盘点）。
2. **不要**在台账表上加 ERP 业务流程字段 —— 台账是只读历史，**要在 `erp` schema 另建**（§2.1）。
3. **不要**把氚云台账当正式期初直接迁（#15/#22/#23 仍成立）。
4. **不要**在成本政策未定义时承诺库存价值/毛利（#10）。
5. **不要**做无收益的全仓重构。

### 6.2 ⚠️ Q1「保留」需要澄清一处（否则会保留一个缺陷）

**现状**：`V236` 按 `CONCAT('MFG-', order_no)` **给每张工单造一个独立产品身份** → 生产 100 张「2014半自动卷膜」= 库存里 **100 个 `product_id`、各 1 件**；而 `product_inventory_balances` 按 `(warehouse_id, sales_product_id, unit)` 唯一 → **同一件商品的余额永远聚合不起来**。业务员从"猜 SKU"变成"猜单号"。

**「保留」的两种可能含义，后果完全不同**：

| 口径 | 含义 | 后果 |
|---|---|---|
| **(甲) 保留为"订单专属产出标识"（推荐）** | `MFG-<工单号>` 仍存在、仍挂工单、仍可追溯"这张单做出的东西"，**但不再是库存聚合维度** —— 库存按标准 SKU（`H3-`）聚合，`MFG-` 通过 `canonical_product_id` 指向标准 SKU | 保留编码（满足 Q1）+ 库存可聚合（消除缺陷） |
| **(乙) 维持现状** | 每张工单一个独立产品身份，库存按单号分裂 | 库存永远聚合不起来 → 「有货直接出库」无法判断 |

**建议取 (甲)**：在 `sales_products` 增加 `canonical_product_id`（归一到标准 SKU），库存余额与流水按归一口径聚合，`MFG-` 作为订单专属产出批次标识保留。
