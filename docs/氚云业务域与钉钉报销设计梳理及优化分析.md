## 1. 五域设计全景图

```
┌────────────────────────── 外部数据源 ──────────────────────────┐
│                                                               │
│  [氚云 Excel 导出]                 [钉钉审批平台]               │
│   生产任务 / 出库 / 收款 / 结清       日常报销审批流             │
└───────────────┬──────────────────────────┬─────────────────────┘
                │ 4 类 FactType 导入          │ 审批实例拉取 + hash 增量
                ▼                             ▼
┌───────────────────────────────┐  ┌────────────────────────────────┐
│  事实层（只读镜像，可追溯）     │  │  报销层（只读镜像 + 同步审计）    │
│  production_orders            │  │  expense_claims / expense_items │
│  sales_outbounds              │  │  dingtalk_sync_runs             │
│  receipts / receipt_allocations│  │                                │
│  settlement（结清明细）        │  │                                │
└───────────────┬───────────────┘  └──────────────┬─────────────────┘
                │ 匹配 + 人工确认                    │ 费用归集
                ▼                                   ▼
┌─────────────────────────────────────────────────────────────────┐
│                 business_orders（统一业务生命周期）                │
│                 business_order_links（事实关联）                  │
└───────────────┬─────────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────────┐
│  BusinessProfitService.calculate（利润快照）                      │
│  收入=出库sales_amount（已生效/CONFIRMED）                        │
│  成本=出库purchase_amount                                        │
│  费用=expense_allocations(BUSINESS_ORDER, CONFIRMED)             │
│  调整=business_profit_adjustments(ACTIVE)                       │
│        ↓ 联动                                                    │
│  BusinessCommissionService.recalculateOne（提成重算）             │
└─────────────────────────────────────────────────────────────────┘
```

**核心思想**：所有外部数据以"**只读镜像 + 来源追溯（external_source/external_id/source_hash/last_synced_at）**"进入本地；本地只新增两类自主行为——① 事实间的关联（匹配/分配/核销），② 衍生计算（利润/提成）。业务生命周期（business_orders）是唯一的"合流点"。

## 2. 数据模型（V127 事实域基线）

### 2.1 表结构与关键字段

| 表 | 唯一键 | 关键业务字段 | 角色 |
|---|---|---|---|
| `production_orders` | `uk_po_external`(source,ext_id)、`uk_po_work_order`(work_order_no) | work_order_no、status、plan_type、完成/入库数量、production_completed/warehousing_completed 标志、linked_sales_order_no（关联销售单号） | 生产执行事实 |
| `production_order_components` | — | 零部件制程：required_quantity/requirement_factor/stock_quantity/completed、process_drawing、reporting_qr | 生产明细 |
| `sales_outbounds` | `uk_so_external`、`uk_so_no`(outbound_no) | status、ship_date、business_date、purchase_amount/sales_amount、source_gross_profit、**received_amount/outstanding_amount**（收款冗余）、invoiced/uninvoiced_amount、payment_status | 出库财务事实 |
| `sales_outbound_items` | — | 产品明细：quantity、sales_total/purchase_total、source_profit | 出库明细 |
| `receipts` | `uk_receipt_external`、`uk_receipt_no` | receipt_type（**SINGLE_OUTBOUND/MULTI_OUTBOUND**）、status、receipt_amount/receivable_amount、**allocated_amount/unallocated_amount** | 收款主单 |
| `receipt_allocations` | V152 后补唯一约束 | sales_outbound_id、allocated_amount、allocation_status（**PENDING/CONFIRMED**）、快照字段（outbound_no/sales_date/sales_amount/received_before/outstanding_before） | 回款↔出库分配 |
| `business_orders` | `uk_bo_no`(business_no) | business_type、lifecycle_status（PENDING…）、contract_status（UNKNOWN…）、**match_status（UNMATCHED…）**、first/last_activity_date | 统一业务生命周期 |
| `business_order_links` | `uk_bol_object`(object_type,object_id) | object_type（PRODUCTION/OUTBOUND/RECEIPT…）、link_method、confidence、match_reason、confirmed_by/at | 业务↔事实关联 |
| `business_match_candidates` | `uk_bmc_pair`(production_id,outbound_id) | confidence、match_reason、status（PENDING→CONFIRMED/REJECTED） | 生产↔出库模糊匹配候选 |

### 2.2 关键设计决策

1. **导入镜像**：所有事实表带 `source_hash`（SHA-256）做增量判断——hash 变则 update，不变则 skip。这是"氚云仍为主系统、本地并行"阶段的正确选择。
2. **分配快照**：`receipt_allocations` 冗余了 `received_before_snapshot/outstanding_before_snapshot`，保留分配发生时的上下文，防追溯漂移。
3. **结清语义**：`receipts` 表注释明确"**单订单与多订单结清**"，即一张收款单可以分配到多个出库（多订单结清），也可以一对一（单订单收款）。
4. **本地自主状态只有两个**：`allocation_status`（PENDING→CONFIRMED 核销）和 `match_status`（匹配/确认）。其余都是氚云原文。

## 3. 生产任务域设计

### 3.1 数据流

```
氚云"生产任务"Excel
  → H3FactImportService（FactType.PRODUCTION）
  → preview 预览 → confirm 确认导入（upsert，hash 增量）
  → production_orders + production_order_components
  → autoOrchestrateAfterImport：
      生产任务 ↔ 出库匹配（BusinessOrderMatchingService）
      → 合并 business_orders
      → 链接 production → business_order
```

### 3.2 状态与字段语义

- 生产任务状态（`status`、`production_progress`、`warehousing_progress`）是**氚云原文透传**，本地不修改。
- `production_completed / warehousing_completed` 布尔标志来自氚云。
- `linked_sales_order_no` / `linked_sales_order_ref` / `product_order_external_id` 是氚云侧的关联线索——**本地匹配引擎的重要输入**。

### 3.3 生产看板（ProductionBoardService / ProductionBoardView）

- `/production-board` 生产执行看板：按客户/销售员/状态分组展示生产任务，跟踪生产进度与入库进度。
- 只读消费生产事实 + 业务关联信息，不做写操作。

### 3.4 现状评价

生产任务域本身较薄——它本质是"氚云生产数据的展示 + 关联入口"。复杂度和痛点集中在**它与出库/收款的关联（匹配）**上，而非生产任务自身。

## 4. 销售出库域设计

### 4.1 数据流

```
氚云"销售出库"Excel（含内嵌收款行）
  → H3FactImportService（FactType.OUTBOUND）
  → preview → confirm
  → sales_outbounds + sales_outbound_items
  → 内嵌收款保存（saveEmbeddedReceipts）：出库行内嵌的收款 → receipts + receipt_allocations
  → 自动编排：出库 → business_order（合并链接）
  → 利润重算
```

### 4.2 关键字段与状态

- `sales_amount / purchase_amount / source_gross_profit`：氚云计算好的源毛利，**本地直接采用**（这是"源毛利校验"页的基础）。
- `payment_status`：氚云付款状态原文。
- `received_amount / outstanding_amount`：**氚云口径的已收/未收**（冗余快照）。
- `invoiced_amount / uninvoiced_amount`：开票状态。
- 本地结清状态（已结清/部分结清/未结清）由 `SalesOutboundSettlementService` **按收款分配 SUM 反推**，显示在出库列表筛选器（`已结清` 等 option）。

### 4.3 服务逻辑（SalesOutboundSettlementService）

- `saveOutbound`：导入 upsert；**保护已 CONFIRMED 的本地分配**（导入覆盖时不清除已核销分配），未核销明细的分配可重建。
- `syncUnchangedOutbound`：hash 未变化的出库不重写。
- `saveEmbeddedReceipts`：出库单内嵌的收款行 → 自动生成收款记录 + 分配。
- `refreshReceiptOutbounds`：**手动触发**的"按现有分配刷新出库已收/未收金额"。
- `allocateReceipt`：手动把一张收款的剩余可分配余额分配到指定的多个出库。
- `confirmAlloc`：分配行 PENDING → CONFIRMED（前端"核销"按钮）。
- `doReconcileReceiptLinks`：收款分配引用缺失出库（历史出库未建档）时重新关联。

### 4.4 前端交互（SalesOutboundSettlementView，~43KB）

- 两个 Tab：**销售出库** / **收款单**，各带指标卡（已结清数、本月出库、已全部分配、可分配余额等）。
- 出库详情抽屉：出库明细 + 回款分配列表（已核销/待核销标签）+ 核销按钮。
- ~~三个补偿按钮（回填/去重内嵌收款、补齐出库关联）~~：数据修复功能已随数据质量中心整体下线。
- ~~收款单 Tab~~：收款核销已下线（收款/结清文件停止导入），回款统一在销售出库的收款子表中查看。

## 5. 收款记录域设计

### 5.1 数据流

```
氚云"收款记录"Excel（FactType.RECEIPT）
  → preview → confirm → receipts（主单）
  → 内嵌的分配行 → receipt_allocations（PENDING 待核销）
  → 自动编排：收款全量分配 → 合并到对应 business_order
```

### 5.2 关键校验（saveReceipt）

- **单收款总额 = 分配行合计**（autoCreateMissing=true 时允许补齐缺失行）。
- 幂等：按 external_id upsert；分配行按 `sequence_no + external_title` 幂等。

### 5.3 状态模型

- `receipts.status`：氚云原文。
- `allocated_amount / unallocated_amount`：本地冗余汇总（分配确认后需刷新）。
- `receipt_allocations.allocation_status`：**PENDING（待核销）→ CONFIRMED（已核销）**，这是本地唯一"确认"动作，意味着本地承认该笔回款归属。

### 5.4 现状评价

收款主单模型（SINGLE/MULTI 类型 + 逐行分配）在设计上是正确的。问题在于：**分配确认（核销）是一个本地自主状态，但出库的结清状态、收款的已分配汇总、利润/提成重算之间缺乏"事务内联动"**——核销后需要依赖刷新/重算入口，容易产生"核销了但出库还没结清、利润还没更新"的中间态。

## 6. 多订单结清域设计

### 6.1 语义

"多订单结清"= 一张收款单（`receipt_type='MULTI_OUTBOUND'`）**覆盖多张出库单**的应收。实现上是 `receipt_allocations` 一张收款 N 行分配，每行指向一个 `sales_outbound_id`，每行一个 `allocated_amount`。

### 6.2 导入路径（FactType.SETTLEMENT）

```
氚云"多订单结清"Excel（结清明细：收款 + N 个出库 + 每单金额）
  → preview → confirm
  → 合并写 receipts + receipt_allocations（每行 = 一个出库的分配）
  → 自动编排：关联 business_orders
```

### 6.3 结清状态判定（汇总反推型）

```
出库已收金额   = Σ(该出库 CONFIRMED 的 receipt_allocations.allocated_amount)
出库结清状态   = 已收 ≥ 应收 → 已结清；0 < 已收 < 应收 → 部分结清；否则未结清
出库 outstanding = sales_amount - 已收（冗余字段，需 refresh 刷新）
```

### 6.4 与"单订单收款"的差异

| 维度 | 单订单收款 SINGLE_OUTBOUND | 多订单结清 MULTI_OUTBOUND |
|---|---|---|
| 分配行数 | 1 张出库（可能多行） | N 张出库，每张一行 |
| 导入来源 | 出库内嵌收款 / 收款 Excel | 结清 Excel（专项） |
| 结清影响 | 单出库 | 多出库同时推进结清 |

### 6.5 现状评价（重点优化区）

1. **结清是"反推状态"而非"事件"**：没有"结清流水/结清事件"表，出库结清状态 = `SUM(receipt_allocations)` 实时推导 + 冗余字段。优点是无需额外表，缺点是：
   - 无法回答"这笔出库是什么时候结清的、由哪笔收款结清"（只能靠分配表时间线）
   - 冗余 `outstanding_amount` 需要刷新动作，易漂移
   - 回滚/红冲（REVERSED）历史难以表达
2. **V152 才补分配唯一约束**：说明此前存在重复分配风险（同收款重复分配到同出库），是设计早期的一个坑。
3. **补偿按钮三连**（回填/去重/补齐）说明导入链路不闭环，内嵌收款与出库的关联在导入时未被可靠建立。
4. **收款-出库关联审计**（missingOutbound）显示存在"分配引用了未建档出库号"的脏数据，靠事后 reconcile 兜底。

## 7. 钉钉报销审批域设计

### 7.1 数据流（P6.1 只读同步 + P6.2 费用归集）

```
钉钉审批实例（PROC- 模板，v2 API）
  → DingtalkSyncService.doSync(from, to, trigger)
  → listProcessInstanceIds → 逐单拉详情
  → upsertOne：source_hash 判断 → expense_claims + expense_items
  → 员工匹配：dingtalk_user_id → employee_external_mappings → 姓名兜底（mapping_missed 累计）
  → dingtalk_sync_runs 审计（fetch/created/updated/unchanged/failed/mapping_missed）
       ↓  P6.2 费用归集（前端 /expenses）
  expense_allocations（1 条 claim → 多目标：BUSINESS_ORDER/DEPARTMENT/COMPANY/CORP_PAYMENT）
       ↓
  BusinessProfitService.calculate 将 CONFIRMED 的 BUSINESS_ORDER 分配计入该业务成本
```

### 7.2 表结构要点（V138/V139）

- `expense_claims`：external_id=processInstanceId；approval_status（APPROVED/REJECTED/PENDING/CANCELED/TERMINATED）；expense_category（TRAVEL/OFFICE/ENTERTAIN/TRANSPORT/MEAL/OTHER/CORP_PAY）；total/approved_amount；employee_id **可空**（未匹配员工时 NULL，需管理员归位）。
- `expense_items`：claim 下的多明细；item_date/amount/tax/invoice；**明确注释 P6.1 不直接放 business_order_id，键必须独立关联表**（正确的多对多建模）。
- `dingtalk_sync_runs`：同步审计（含 error_details JSON）。
- `expense_allocations`：target_type 多态（BUSINESS_ORDER/DEPARTMENT/COMPANY/CORP_PAYMENT）；allocation_ratio_pct + allocated_amount 共存（二选一录入，Service 补另一项）；状态 DRAFT/CONFIRMED/REVERSED；**撤销=REVERSED 更新而非物理删**；服务层强校验（已确认合计 ≤ approved_amount、比例×金额≈金额 ±0.01）。

### 7.3 同步可靠性设计（亮点）

- 所有写操作 `REQUIRES_NEW` 独立事务——**单条 claim/item 校验失败只回滚该条**，不污染 SyncRun 与其他审批单。
- SyncRun 永远存在（含 stage=meta 诊断快照），前端永远能看到 runId + 错误明细。
- 路由分支显式化：ProcessCode 以 `PROC-` 开头强制 v2 API，避免两版 API 混乱。

### 7.4 现状评价

报销域设计是**五域中建模最规范的一个**（镜像+审计+归集+多态目标+比例/金额双轨）。主要缺口：
1. **P6.1/P6.2 阶段性痕迹明显**：`CORP_PAYMENT` 对公付款目标类型已预留但**无独立表**；`expense_allocations` 只按 claim 粒度归集（`expense_item_id` NULL 为主），明细级归集未启用。
2. **报销与结清域缺乏联动**：费用归集只影响利润快照，不参与出库/业务单的"成本完整性"判断；没有"该业务费用尚未归集完"的告警。
3. **审批状态同步滞后**：依赖手动/定时触发 `doSync`，钉钉侧撤回/改单在本地有窗口期。
4. **employee_id 可空**：未匹配员工时靠管理员手动归位，报表按员工聚合会漏数据。

## 8. 五域联动：数据流与控制流

### 8.1 正向数据流（导入 → 合并 → 核算）

```
[1] 生产任务 Excel ──▶ production_orders
[2] 销售出库 Excel ──▶ sales_outbounds（+ 内嵌收款 → receipts）
[3] 收款记录 Excel ──▶ receipts
[4] 多订单结清 Excel ─▶ receipts + receipt_allocations（N 出库）
[5] 钉钉审批 ────────▶ expense_claims/items
            │
            ▼ autoOrchestrateAfterImport（每次导入后自动执行）
  匹配生产↔出库 → 合并 business_orders → 链接所有事实（business_order_links）
            │
            ▼
  BusinessProfitService.calculate（出库收入-成本 - 费用归集 - 调整）
            ▼
  BusinessCommissionService.recalculateOne（提成）
```

### 8.2 手动操作流（本地自主行为）

```
核销（confirmAlloc）      —— 分配 PENDING→CONFIRMED
手动分配（allocateReceipt）—— 收款余额 → 多出库
匹配确认/驳回            —— business_match_candidates → business_order_links
费用归集（/expenses）     —— expense_claim → expense_allocations(BUSINESS_ORDER)
利润调整（/profit）       —— business_profit_adjustments → 重算快照 → 重算提成
```

### 8.3 关键耦合点（优化的切入点）

| # | 耦合点 | 现状 | 问题 |
|---|---|---|---|
| C1 | 核销 → 出库结清状态 | `confirmAlloc` 只改分配状态；出库 `outstanding_amount` 靠 `refreshReceiptOutbounds` 手动刷新 | 中间态：核销后出库可能仍显示旧未收金额 |
| C2 | 核销/分配 → 利润/提成 | 利润在导入后自动重算；**手动核销后未自动联动重算** | 利润快照滞后于资金确认 |
| C3 | 导入覆盖 vs 本地状态 | `saveOutbound` 保护 CONFIRMED 分配；未核销分配可被重建 | 规则较隐晦，边界靠代码注释 |
| C4 | 出库状态口径 | 利润 SQL 用 `o.status IN ('已生效','CONFIRMED')`——**中英文状态混用** | 状态归一化不彻底（V135 只修了 NORMAL） |
| C5 | 报销 → 业务成本 | 费用归集独立于业务生命周期 | 无"成本未归集完"提示，结清/利润口径可能偏乐观 |
| C6 | 结清语义 | 无结清事件表，全链路 SUM 反推 | 无法回答"何时结清、由谁结清、是否红冲过" |

## 9. 亟待优化的问题清单

### 9.1 数据模型层

1. **缺"结清流水/结清事件"概念**：结清状态是反推值，无事件记录。建议新增 `settlement_events`（或扩展 allocation 增加 `settled_at/settled_by` 事件语义），支持"何时/由谁/哪笔收款"结清的历史追溯与红冲。
2. **冗余金额字段漂移风险**：`sales_outbounds.received_amount/outstanding_amount`、`receipts.allocated_amount/unallocated_amount` 均为派生值，存在多处写入口（导入/刷新/回填），建议收敛为**单一计算入口**（统一由 `refreshOutboundPayment()` 与 `refreshReceiptAllocation()` 两个收口方法，任何写操作后事务内调用）。
3. **出库状态中英文混用**：`status IN ('已生效','CONFIRMED')` 并存。建议全量迁移为英文枚举（V150 已引入 outbound_status 雏形），利润/筛选统一走枚举。
4. **多订单结清的"业务单级结清聚合"缺失**：`business_orders` 无结清金额/结清状态汇总。建议增加物化列或视图（`business_order_settlement_summary`），供经营看板直接消费。
5. **`CORP_PAYMENT` 目标无落表**：expense_allocations 的 target_type 已预留但对公付款无独立实体，P6.2 若启用对公付款需补表。

### 9.2 流程/事务层

6. **手动核销/分配后缺事务内联动**：`confirmAlloc`/`allocateReceipt` 应在一个事务内完成：更新分配状态 → 刷新出库已收/未收 → 刷新收款已分配/未分配 → **触发该出库关联业务单的利润与提成重算**。当前是分离的，靠用户后续手动触发，产生中间态。
7. **导入补偿按钮三连**（回填/去重/补齐）说明导入管线不完备。建议在 `saveEmbeddedReceipts` 时**即做去重 + 关联建档**，将三个事后修复按钮降级为一次性数据治理脚本，而不是常规操作。
8. **收款分配引用了未建档出库**：`receiptLinkAudit.missingOutboundCount` 持续出现说明历史脏数据长期存在。建议导入时对 `outbound_no_snapshot` 匹配失败的行**显式标记（REFER_UNRESOLVED）并拦截**，而非静默落库后靠 reconcile 兜底。
9. **V152 唯一约束补齐后需清理存量重复**：约束新增后需一次性 SQL 清理历史重复分配，并校验存量数据通过约束。

### 9.3 报销域

10. **报销与结清域零联动**：费用归集结果只进利润快照，不影响业务成本完整性/结清判断。建议增加"**费用未归集告警**"（已 APPROVED 的 claim 未 100% 归集到目标时，在业务单/利润页提示）。
11. **明细级归集未启用**：`expense_item_id` 维度留了扩展但未实现。若业务需要"某张发票对应某业务单"的精确分摊，需启用明细级归集并补齐 UI。
12. **审批状态同步窗口**：建议对 APPROVED 单变更提供 webhook/定时高频拉取（如每日多次），或至少在利润计算时提示"存在未同步的近期审批"。

### 9.4 前端/体验层

13. **操作链分散在 6 个页面**：生产看板 / 氚云数据管理 / 出库回款 / 利润 / 提成 / 费用 相互独立，业务人员需跨页面完成"出货→收款→核销→结清"操作。建议：
    - 业务单详情（/business/:id）聚合展示生产/出库/收款/费用/利润/提成的**全链路时间线**
    - 出库详情抽屉内直接完成"核销 + 查看结清变化"，不必跳利润页
14. **H3BusinessCenterView 是"管理/修复"导向**：4 个 Tab（导入/匹配/出库差异审计/关系审计）都是治理功能，建议与业务运营视图分离（治理入口收敛到"数据集成"菜单，业务入口在业务单/出库页）。

### 9.5 一致性与精度

15. **金额精度混用**：`DECIMAL(14,2)`（金额）与 `DECIMAL(14,4)`（数量/单价）混用，利润链路需明确舍入规则（HalfUp）并在服务层统一。
16. **"已结清"定义不唯一**：出库页的"已结清"（Σ分配≥sales_amount）与氚云 `payment_status` 原文、与利润口径（status IN 已生效）是**三套口径**，前端筛选与后端计算需显式统一。

## 11. 优化实施记录（V156，2026-08-25）

### 11.1 迁移 `V156__settlement_events_and_status_normalization.sql`

| 变更 | 内容 |
| --- | --- |
| `sales_outbounds.outbound_status` | 新增列 + 按 `status` 归一化回填（已生效/CONFIRMED→CONFIRMED，其余→DRAFT），索引 `idx_so_outbound_status` |
| `sales_outbounds.settlement_status` | 新增列 + 按存量金额推导回填（SETTLED/PARTIAL/UNSETTLED），索引 `idx_so_settlement_status` |
| `receipt_allocations.reference_status` | 新增列，默认 `REFER_RESOLVED`（导入/补齐逻辑显式写 REFER_UNRESOLVED），索引 `idx_ra_reference_status` |
| `settlement_events` | 新增结清事件表（分配/核销/撤销/导入四类事件 + 前后快照），FK → receipts / sales_outbounds |
| `business_orders` 聚合列 | 新增 `receivable_amount/received_amount/settlement_status`，三步 UPDATE 从出库+分配回填，索引 `idx_bo_settlement_status` |

### 11.2 服务层改造（SalesOutboundSettlementService）

- `normalizeOutboundStatus(String)` 公开，导入共用同一归一化口径。
- 新增 `refreshOutboundPayment(oid)`：CONFIRMED 分配汇总 → 出库 `received_amount/outstanding_amount/settlement_status`。
- 新增 `refreshReceiptAllocation(receiptId)`：CONFIRMED 分配汇总 → 收款 `received_amount`。
- 新增 `refreshBusinessOrderSettlement(boId)`：业务单聚合列回填（应收=CONFIRMED 出库 sales_amount，实收=CONFIRMED 分配）。
- 新增 `recordSettlementEvent(...)` / `listSettlementEvents(oid)`。
- `confirmAllocation`/`cancelAllocation`/`allocateReceipt` 事务内：事件记录 + 三处收口刷新 + `BusinessProfitService.calculate` + `BusinessCommissionService.recalculateOne` 联动。
- `refreshOutboundSnapshot` 升级：统一写 `outbound_status/settlement_status`；`refreshAllOutboundSnapshots` 后同步刷新全部业务单聚合。
- 出库候选查询 / 看板统计 / 列表筛选全部切换到 `outbound_status` 与 `settlement_status` 枚举（兼容中文入参）。

### 11.3 导入管线闭环（H3FactImportService）

- `saveOutbound` 写入并幂等更新 `outbound_status`（normalizeOutboundStatus）。
- `saveEmbeddedReceipts` / `saveReceipt` 的旧分配清理限定 `allocation_status<>'CONFIRMED'`，**本地已核销分配不被导入覆盖**；新增 `hasConfirmedAllocation` 防同单冲突。
- 分配行写入 `reference_status`（REFER_RESOLVED / REFER_UNRESOLVED）；导入成功即调用 `refreshOutboundSnapshotById` + `refreshReceiptAllocation` 联动刷新。

### 11.4 其余统一引用

`MyWorkbenchService` / `BossDashboardService` / `BusinessProfitService` / `BusinessCommissionService` / `BusinessOrderMatchingService`（出库别名 o/so/o2，production_orders 不动）/ `BusinessRelationAuditService` / `H3BusinessQueryService` 中指向出库表的 `status IN ('已生效','CONFIRMED')` 全部统一为 `outbound_status='CONFIRMED'`；receipts 表的 `r.status` 判断保持不变。

### 11.5 前端

- `SalesOutboundSettlementView`：出库详情新增"结清记录"时间线（el-timeline，CONFIRM 绿/REVERSE 红/ALLOCATE·IMPORT 主色），核销/撤销后自动重载。
- `BusinessOrderDetailView` 费用 Tab：`pendingExpenseTotal > 0` 时展示"待归集报销"告警，引导至费用管理归集。
- `api/salesOutbound` 新增 `SettlementEvent` 类型与 `fetchOutboundSettlementEvents`；`api/business/profit` 扩展 `ProfitDetail`。

### 11.6 结清三口径对照（P2-3）

- `SalesOutboundSettlementService.settlementReconciliation()`：三口径汇总——
  - **资金口径**（receipts）：收款单数 / 总额 / 已分配 / 未分配；
  - **出库口径**（sales_outbounds）：出库单数、确认数 / 确认应收 / 已收 / 结清·部分·未结分布；
  - **利润口径**（business_orders）：业务单数、结清数 / 业务应收·实收 / 当前核算利润（`is_current=1`）/ 预计提成；
  - 对照差值：`cashAllocatedVsOutboundReceived`（应=0）、`outboundVsBusinessReceivable`（应≥0，未关联业务单的应收）、`businessReceivableVsReceived`（未结清差额）。
- 端点：`GET /api/sales-outbound-settlement/settlement-reconciliation`。
- 前端：出库页顶部新增"结清口径对照"折叠面板（三列指标 + 差异告警 el-alert + 一致性标签）。

### 11.7 业务单全链路时间线（P2-2）

- `H3BusinessQueryService.businessTimeline(id)`：聚合八类事件按时间升序——
  `BUSINESS_CREATED`（建档）/ `PRODUCTION_LINKED`（生产关联）/ `OUTBOUND_LINKED`（出库关联）
  / `RECEIPT_ALLOCATED`（收款核销）/ `SETTLEMENT_*`（结清事件，经出库关联到业务）
  / `EXPENSE_ALLOCATED`（费用归集）/ `PROFIT_CALCULATED`（利润快照）/ `COMMISSION_CALCULATED`（提成快照）。
- 端点：`GET /api/h3-facts/business-orders/{id}/timeline`（权限与业务详情一致）。
- 前端：业务单详情新增"时间线"Tab（el-timeline，类型着色：撤销红/核销绿/利润蓝/提成橙；可按"全部/业务流转/资金往来"筛选）。
