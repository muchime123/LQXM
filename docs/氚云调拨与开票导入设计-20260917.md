# 氚云 P2 库存调拨 / P3 开票域 导入设计（2026-09-17）

> 前置：`氚云新增7表ERP适用性梳理与导入设计-20260917.md`（§1.5/§1.6/§1.7 原始梳理、§2.5/§2.6 骨架）。
> 本文为落地级设计：**全部结构以 2026-09-17 10:33~10:34 真实导出件实测为准**，并已对拍 P1（V306）落地模式。
> 结论先行：**两类三张表全部走 A 域统一管线（stage→预览→confirm→幂等），零编排联动；调拨纯数量事实；开票域是本批唯一开票口径来源，但出库单/收款单关联只能存原文、无法精确勾稽**——这是氚云表单设计的固有限制，不是本项目的缺陷。

> **实施回执（2026-09-17 13:45 更新）**：§2 调拨已落地（**V307**+**V308**），§3 开票域已落地（**V309** 四表 + **V310** tax_no 加宽），生产实例 8081 端到端验证通过——开票资料 3429 行、开票申请 10986 单/14888 内容行/12697 收款引用行，两轮 UNCHANGED 收敛，勾稽告警=§3.3 基线（Σ差异 1 / 收付不平 0）。落地记录见 `氚云新增7表ERP适用性梳理与导入设计-20260917.md` **§11**。**实施修正（与本文档设计的差异）**：① ⚠️ **keyHeader 用「数据ID」而非流水号**——实测文件尾部 18 单整行缺流水号，按流水号分组会串单（§3.2 的 `source_no 流水号` 仅作落库列，不作分组键）；② `customer_id` 关联率实测仅 3.2%（111/3429），「只标未关联」决策正确；③ tax_no 需 VARCHAR(255)——内勤把整段开票信息粘贴进该字段（最长 140 字符）；④ 主表税号 vs profile 税号对照告警**未实现**（快照时点差属正常值，告警噪音大）。**三处实测修正（P2，12:10 回执）**：① 表名实际为 `h3_inventory_transfers` / `h3_inventory_transfer_items`（对齐 h3_ 前缀惯例）；② ⚠️ `judge_raw` 并非恒 0（3 行为 1，语义已实测=氚云自带超调出库存标记）；③ 「调出仓=调入仓 → REJECT」暂以告警实现，**待拍板**。

## 0. 实测基线（2026-09-17 导出件，openpyxl 全量统计）

| 表 | 规模 | 数据状态 | 勾稽/质量 |
| --- | --- | --- | --- |
| 库存调拨 | **218 单 / 2 311 明细行** | 已生效 216 · 草稿 1 · 已取消 1 | 调出=调入 **0 单**；调拨数量>「调出仓库数量」快照 **1 单**；仓对安徽↔温州 212 + 温州↔安徽 6（warehouses 表 3 仓全可绑） |
| 开票资料 | **3 429 行（单表）** | — | 户名去重 3 383（**46 个户名有多行资料**）；**税号缺失 348（10.2%）**；地址/电话/开户行/账号空值率均 **≈80%** |
| 开票申请 | **10 968 单 / 开票内容 14 888 行 / 收款情况 12 697 行** | 已生效 10 944 · 草稿 20 · 已取消 2 · 进行中 2 | Σ开票内容≠申请金额 **1 单**；已收+未收=申请金额 **0 偏差**；发票类型：专票 6 569 / 普票 4 390 / **空 9** |

**三个决定设计的实测发现**：

1. **开票资料的「户名」不唯一**（46 个重名）→ 幂等键不能用户名，也不能用「户名+税号」当分组键（税号 10% 缺失）。氚云行级稳定键 = 数据ID UUID，**单表无子表列吞位**，`数据ID(不可修改)` 直接可用作 keyHeader。
2. **开票申请的「选择出库单匹配开票内容、收款情况」是自由文本**（实测 1 973 个去重值，格式如 `2026-03-23     邹女士    2,050` = 日期+联系人+金额，**无出库单号、无收款单号**）→ 无法精确关联回 `sales_outbounds` / `receipts`，只能原文存档（详见 §3.4）。
3. **`customers` 表已有 `credit_code` 列** → 开票资料「税号」↔ 客户档案可直接等值匹配（税号=统一社会信用代码），不需要借道客户簇。

## 2. P2 库存调拨（V307 迁移）

### 2.1 表设计

```sql
inventory_transfers（主表，A 域系统列同款：external_source/external_id/source_hash/
  source_updated_at/last_synced_at/created_at/updated_at + data_status + 系统列 10 件套）
  source_no          流水号 DB…（唯一键）
  transfer_date      调拨日期
  out_warehouse_id / out_warehouse_name / out_keeper   -- 选择调出仓库 + 仓管员（F0000018/F0000020）
  in_warehouse_id  / in_warehouse_name  / in_keeper    -- 选择调入仓库 + 仓管员（F0000019/F0000021）
  warehouse 绑定规则沿用 P0/P1：**同名唯一才绑 warehouses.id**，否则存名不绑（不阻塞）
  remark；data_status（草稿 1 / 已取消 1 原样标记，不进正式口径）

inventory_transfer_items（子表，按单整删重插 + source_item_id 行级幂等键）
  line_no（调拨明细.序号）、product_code/product_name/category/spec/unit
  quantity           调拨数量
  out_stock_quantity 调出仓库数量快照（col21）
  judge_raw          调拨明细.判断（隐）（col22 原值 → 存原文不解读）
                     ⚠️ 实测修正（2026-09-17 12:10）：**并非恒 0** —— 落库 2311 行中 0=2308 行 / 1=3 行；
                     3 行全部来自同一张**草稿单** DB20260130000183，且恰是「超快照 1 行（qty 1 > snap 0）
                     + 快照缺失 2 行（snap NULL）」→ 该列 = **氚云自带的「调拨数量超调出库存」校验标记**，
                     与 `transferWarnings` 告警口径吻合（已生效单 2308 行全 0）。存原文不解读的判断正确。
  remark（调拨明细.产品备注）
```

**不落库**：「校验调拨数量」（F0000026，氚云端校验残留，恒 0）、「调拨明细.产品图片/附件/数据标题/隐列」、主表附件。
**调拨无金额列**（明细只有数量）→ 纯数量事实，与「不动库存余额」的既定决策天然一致；未来 ERP 若要金额化，须另行计价，不在本期。

### 2.2 校验与告警（进预览 warnings + confirm 异常计数）

| 规则 | 级别 | 实测基线 |
| --- | --- | --- |
| 调出仓 = 调入仓 | **REJECT 整单**（物理不成立，防御性） | 0 单 |
| 调拨数量 > 调出仓库数量快照 | 告警不阻断（快照是导入时点值，调拨可能发生在库存变动之后） | 1 单 |
| 草稿/已取消 | 导入并标 `data_status`，不计入异常 | 2 单 |
| 出/入仓库名匹配 warehouses | 未匹配告警（存名不绑） | 实测应 0（三仓全命中） |

### 2.3 台账展示

历史台账 Tab「库存调拨」：列表列 = 流水号/状态/日期/调出仓→调入仓（含两仓管员）/明细行数/合计数量/所属部门/源创建时间；详情 = 主单全字段 + 明细子表。行级更新历史：DATA_TYPES 加 `TRANSFER`，业务键=流水号。

## 3. P3 开票域（V307 同迁移或 V308，见 §5）

### 3.1 开票资料 `customer_invoice_profiles`

```sql
  external_id        数据ID UUID（唯一键 + 幂等键）
  customer_name      户名；normalized_name（归一化，同 SupplierNameNormalizer 口径，用于重名对拍与展示）
  tax_no             税号（可空，348 行缺失）
  address / phone / bank_name / bank_account
  customer_id        关联 customers（可空，关联规则见下）
  + A 域系统列件套
  KEY idx_cip_tax (tax_no)  —— 不设 (tax_no,customer_name) 唯一键：tax_no 可空且 46 组同户名是合法事实
```

**customer_id 关联规则（`resolveInvoiceCustomer`，只读不动 customers）**：
1. `tax_no` 非空 → 等值匹配 `customers.credit_code`（唯一命中才绑；多命中/零命中留空）；
2. 税号空或未命中 → `customer_name` 精确等值 `customers.customer_name`（唯一命中才绑）；
3. 均未命中 → `customer_id` 留空。**未命中不是错误**（开票资料含大量外协/一次性户名），不进 REVIEW，只在台账列表给「未关联」标记。命中率实测后回填本文档。

### 3.2 开票申请 `invoice_requests` + `invoice_request_items` + `invoice_request_receipt_refs`

```sql
invoice_requests（主表）
  source_no          流水号（唯一键，纯数字）
  invoice_type       发票类型（专票/普票/空 9 单原样存）
  redflush_ref       选择已开发票申请红冲（原文，col07，实测多空）
  request_date       开票日期
  salesperson        业务员
  profile_external_id  选择开票资料 → 按数据ID/户名反查 customer_invoice_profiles.id（可空）
  customer_name / tax_no                    户名 + 税号（主表 F0000005/F0000006 直读）
  snapshot_address / snapshot_phone / snapshot_bank_name / snapshot_bank_account
                     开票时点冗余快照（col21-24）——只存不校，profile 是"当前值"、快照是"开票时点值"
  request_amount     本次申请开票金额
  received_amount    已收款金额
  unreceived_amount  未收款金额
  remark；data_status（草稿 20 / 已取消 2 / 进行中 2 标记）
  + A 域系统列件套

invoice_request_items（开票内容，source_item_id=开票内容.数据ID 行级幂等）
  line_no/product_name/spec_model/unit/quantity/unit_price/amount（金额小计）

invoice_request_receipt_refs（收款情况——§2.7 决策：只建引用，不写 receipts/allocations）
  receipt_date / receipt_method / receipt_amount（col38-40 逐行解析）
  raw_title          收款情况.数据标题原文
  receipt_id         恒 NULL 预留（文本无收款单号，无从关联）
```

### 3.3 勾稽校验（实测基线极好，校验是廉价保险）

| 规则 | 级别 | 实测基线 |
| --- | --- | --- |
| Σ开票内容.金额小计 vs 主表申请金额 | 告警（差异进 warnings） | 1 单 |
| 已收款 + 未收款 = 申请金额 | 告警 | 0 单 |
| 发票类型 ∈ {增值税专用发票, 普通发票}（空容差） | 告警 | 9 单 |
| 主表税号 vs 选择开票资料指向的 profile 税号 | 告警（快照时点差属正常，仅提示） | 待实测 |
| 草稿/已取消/进行中 | 标记，不计异常 | 24 单 |

### 3.4 出库单关联：只存原文，不做自动勾稽（核心定调）

实测「选择出库单匹配开票内容、收款情况」= **日期 + 联系人 + 金额的自由文本，无任何单号**（1 973 个去重值）。由此：

- 本期：`outbound_ref_raw` 原文存档 + 台账详情展示，**不做概率匹配**。理由：销售出库 18 966 单中同客户同金额同日期的多单碰撞率不可控，错误关联比没有关联危害大（会污染未来的应收核对）。
- 未来（P3+ 可选）：若 ERP 应收模块确需「开票↔出库」勾稽，建人工工作台按 日期窗 ±N 天 + 金额精确 + 客户/联系人名做候选推荐，**人工确认落 `confirmed_outbound_id`**（与销售出库退换货人工确认同模式）。本文档不展开。

## 6. 风险与既有限制的明确记录

1. **出库单/收款单无法精确勾稽是氚云数据形态的固有限制**（自由文本引用），不是实现缺陷；任何「自动关联 100%」的期望都不成立。
2. 开票资料 80% 空值率（地址/电话/银行）→ 「开票资料完整度」是**长期治理项**，导入只如实落库；若要推动补全，属于业务动作（让内勤在氚云补录后重导）。
3. 与 P0/P1 相同：并行会话活跃，迁移版本号与 `FactType` 改动**动手前先查冲突**（本次设计基于 V306 已应用、flyway=306 的状态）。
