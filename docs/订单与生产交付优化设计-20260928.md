## 1. 设计原则

这五条是本设计的判据，后续任何改动都可以用它们判定"该不该这么改"。

**原则 1 —— 一个业务判据只允许一处实现，DB 约束必须与业务判据同义（不是"更严格"）。**
本项目已有铁律「同一源字段禁第二套词表、同一业务概念禁两套表」。A 问题正是这条的反例：业务说"取消即释放"，DB 说"永远占用"。**DB 约束比业务判据更严格，是一种静默错误**——它不会报编译错，只会在某个操作路径上突然拒绝。

**原则 2 —— 动作权限按「单据语义」划分，不按「谁先建单」。**
一张单据从创建到终态，不应该强制换岗接力，除非业务上确实换了责任主体。代发（C）本质是采购在履行，货不进本地仓、销售根本看不到货，让销售去点过账是语义错位。

**原则 3 —— 任何能被写入的状态，必须有写入方；任何能被过滤的状态，必须有到达路径。**
这是 `workflow-state-gate-audit` 的对偶：那个 skill 找的是"没有岗位去推的**必经**状态"，这里找的是"没有任何代码去写的**终态**"。B 问题中 `manufacturing_orders.CANCELLED` 被 6 处查询过滤，却全仓没有一个写入方。

**原则 4 —— 前置校验只写一次，同时服务两个消费者：前端做「就绪度」，后端做「拒绝」。**
现在校验只存在于 `requireSubmittable`（提交时抛异常），前端无法复用，于是只能"先点、再被打回"。抽出纯函数后，一个接口喂前端，同一个函数喂后端。

**原则 5 —— 用户看到的失败必须能指导下一步动作：给单号 + 状态 + 可选动作。**
`Duplicate entry '123' for key 'uk_epo_sales_order_item'` 不可执行；`该明细已关联采购订单 CGDD00000012（已取消），可直接重新建单` 可执行。

## 2. P0 — 口径自相矛盾

### 2.1 问题 A：「需求占坑」判据 6 份副本，DB 索引与业务判据不同义

#### 取证（同一语义，6 处各写一遍）

| # | 位置 | 写法 | 语义 |
| --- | --- | --- | --- |
| 1 | `ErpPurchaseOrderService:162` | `NOT EXISTS(... p.status<>'CANCELLED')` | 列表：取消后**重新出现** |
| 2 | `ErpPurchaseOrderService:577` | `COUNT(*) ... AND status<>'CANCELLED'` | 建单校验：取消后**放行** |
| 3 | `ErpSalesOrderService:417` | `WHERE sales_order_item_id=? AND status<>'CANCELLED'` | 找有效采购单（发货来源判定） |
| 4 | `SalesOrderExceptionService:471` | `... AND p.status<>'CANCELLED'` | 异常处理时列举下游单 |
| 5 | `SalesOrderExceptionService:484` | `... AND status<>'CANCELLED' FOR UPDATE` | 变更生效时的加锁判定 |
| 6 | `V344__erp_purchase_orders.sql:37` | `UNIQUE KEY uk_epo_sales_order_item (sales_order_item_id)` | **无条件唯一，取消不释放** |

前 5 处一致，第 6 处相反。**业务判据与 DB 约束不同义。**

#### 后果（两条，都是真实操作路径）

- **采购**：取消采购单 → 明细重新出现在「待采购需求」→ 点「建采购单」→ 应用层校验放行 → **DB 层抛 `Duplicate entry`**。经 `GlobalExceptionHandler:158` 兜底，前端收到 409「数据操作冲突，请检查关联数据是否存在或重复：\<原始 SQL 片段\>」。用户看得见错误，但看不出为什么——因为按列表口径，这条明细**明明是可建的**。
- **生产**：`pendingProductionDemands:188` 与 `acceptProductionDemand:219` 都是 `WHERE sales_order_item_id=?`，**没有任何状态过滤**；`ManufacturingService:534` 是第三份同款判重。加上 `V342` 的 `uk_mo_sales_order_item` 同样无条件 → 该明细一旦建过任务单，**再也不会回到待下达列表**。生产侧比采购侧更死：采购是"看得见但建不了"，生产是"看不见也建不了"。

两处应当**统一为同一条语义**，选哪条？——**取消即释放**。理由：取消的语义就是"这件事不做了"，占坑应当是可撤销的；而"建过就永久锁死"会让一次误操作变成终态，没有补救路径（配合 B 才能闭合）。

#### 设计

**① 把「占坑」升格为一个显式的领域概念，落在 DB 上：用生成列造"部分唯一索引"。**
这是本项目已成熟的既有手法（`V281` / `V282` / `V322` / `V336` / `V338` 共 5 处先例），不需要引入新技巧：

```sql
-- V356__demand_occupancy_released_on_cancel.sql（编号现查现用，当前最大 V355）
-- 口径：CANCELLED 视为"不占坑"；其余状态（含 DRAFT/待审批/已确认/履行中）均占坑。

-- ⚠️ 陷阱：uk_epo_sales_order_item 同时被外键 fk_epo_sales_order_item 依赖，
--    直接 DROP INDEX 会报 errno 1553（Cannot drop index needed in a foreign key constraint）。
--    必须先补一个普通索引顶上。
ALTER TABLE erp_purchase_orders
  ADD KEY idx_epo_sales_order_item (sales_order_item_id),
  ADD COLUMN demand_guard BIGINT
    GENERATED ALWAYS AS (IF(status='CANCELLED', NULL, sales_order_item_id)) STORED,
  DROP INDEX uk_epo_sales_order_item,
  ADD UNIQUE KEY uk_epo_demand_guard (demand_guard);

ALTER TABLE manufacturing_orders
  ADD KEY idx_mo_sales_order_item (sales_order_item_id),
  ADD COLUMN demand_guard BIGINT
    GENERATED ALWAYS AS (IF(status='CANCELLED', NULL, sales_order_item_id)) STORED,
  DROP INDEX uk_mo_sales_order_item,
  ADD UNIQUE KEY uk_mo_demand_guard (demand_guard);
```

选生成列而不是"应用层每次记得置 NULL"的理由：**它无法被忘记**。状态一改成 `CANCELLED`，占坑自动释放；哪怕将来有人用 SQL 手工改状态也一样生效。这正是原则 1 要的"同义"——约束跟着业务事实走，而不是跟着某段 Java 代码走。

**② 谓词收敛为一处。** 新增 `util/ErpDemandOccupancy.java`：

```java
public final class ErpDemandOccupancy {
    /** 占坑判据的唯一来源，必须与 demand_guard 生成列同义。 */
    public static final String OCCUPIES = "status<>'CANCELLED'";
    public static boolean occupies(String status) {
        return status != null && !"CANCELLED".equals(status);
    }
}
```

§2.1 表里的 1–5 处全部改为拼 `OCCUPIES`，**且这 5 处必须在同一次改动里完成**（只改一半等于新增第 6 份副本）。

**③ 建单校验改成"预检 + 业务文案"**（与 E 合并）：冲突时给单号与状态，而不是让 DB 报错：

```java
// 该明细已有关联采购订单 CGDD00000012（已确认）；请打开原单处理，或先取消原单再重新建单。
```

#### 验收

1. **口径对拍（契约测试）**：全量遍历销售明细，断言三个口径结果集完全相等——
   - 列表口径（`pendingPurchaseDemands` 的反集）
   - DB 索引口径（`SELECT sales_order_item_id FROM erp_purchase_orders WHERE demand_guard IS NOT NULL`）
   - 业务口径（`WHERE sales_order_item_id=? AND status<>'CANCELLED'`）
   任意一条明细，三者不一致即失败。这条测试就是防 A 复发的钉子。
2. **活体 HTTP**：建 PO → 审批 → 取消 → 该明细回到待采购需求 → **重新建单成功**（旧行为：409）。
3. **反向不回归**：同一明细存在未取消 PO 时，再次建单仍被拒，**且文案含原单号**。
4. **变异检验**：把 `OCCUPIES` 改成恒 `true`，契约测试必须变红（证明测试有效，不是恒绿）。

### 2.2 问题 B：生产任务单没有作废通道

#### 取证

- `ManufacturingController` 的全部 `@PostMapping/@PutMapping` 已逐个核对：**没有 cancel / void / close 端点**。
- 全仓检索 `'CANCELLED'`：`manufacturing_orders` 的取值**只出现在读过滤器里**（`ManufacturingService:316/334/341/1113/1117`、`ManufacturingExecutionService:228`、`ProductInventoryService:93/99`），**没有任何 `UPDATE ... SET status='CANCELLED'` 写入方**。
- 同理 `'CLOSED'` 在 `manufacturing_orders` 与 `erp_purchase_orders` 上也都只有读过滤器，**无写入方**（见 H）。

#### 后果

从销售需求生成的任务单**直接进 `RELEASED`（有工序）/ `PENDING_INSPECTION`（0 工序）**，不经过草稿缓冲。也就是说：车间在「待下达生产需求」点「生成生产任务」时若选错车间、数量或配置——**没有任何回收手段**。该任务单会：

- 一直占着 `uk_mo_sales_order_item`，销售明细永不再回到待下达列表（A 的生产侧）；
- 出现在车间执行看板/逾期统计里（因为 `CANCELLED` 过滤是死的，它到不了）；
- 与订单明细的"已下达但实际不做"长期不一致。

#### 设计

**新增「作废任务单」动作。判据按「事实」而不是按「状态白名单」**——因为 `PENDING_INSPECTION` 意味着工序已全部完成（有报工），按状态白名单很容易放错：

```
可作废 ⇔ ① 无任何报工行（manufacturing_work_reports 无记录，含已冲正的）
        ∧ ② 无完工入库（production_execution_completions / 库存流水无关联）
        ∧ ③ 无未退回的领料发出（manufacturing_materials 无 ISSUE 净额）
        ∧ ④ 无关联的未取消出库单（erp_sales_outbound_items 无 DRAFT/POSTED）
```

任一条不满足 → 拒绝，并**说清是哪一条**（原则 5）：

```java
throw new IllegalStateException("该任务单已报工，不能作废；如需调整请登记风险/问题或走交期变更");
```

- 端点：`POST /api/manufacturing/orders/{id}/void`，权限 `manufacturing.manage`；`body.reason` 必填；走幂等模板（`idem.execute`，action 如 `manufacturing.order.void`）。
- 效果：`status='CANCELLED'` + 变更日志（含原因）+ `demand_guard` 自动置 NULL（§2.1 的生成列）→ 明细立即回到「待下达生产需求」。
- 与交期变更的联动：`SalesOrderExceptionService` 同步需求交期时**必须跳过已作废单**（现在它按 `sales_order_item_id` 找下游，作废后仍会命中——这是本次改动引入的新耦合，要一并处理）。

**同时把 §2.1 的生成列建到 `manufacturing_orders` 上**，两件事必须在同一批：

> 只改索引不加作废通道 → 索引永远释放不了（死代码）。
> 只加作废通道不改索引 → 作废后明细还是回不到列表（等于没做）。

#### 验收

1. 建任务单 → 作废 → 明细回到「待下达生产需求」→ 重新下达成功。
2. 已报工 / 已入库 / 已发料 三种情况各构造一例，断言**拒绝且文案指明具体原因**。
3. 作废单不再出现在车间执行看板与逾期统计（用 `CANCELLED` 过滤的 6 处逐一把关）。
4. 变异检验：把事实判据①（无报工）去掉，验收 2 的第一例必须失败。

### 2.3 问题 C：代发出库的跨岗权限断层

#### 取证

| 动作 | 端点 | 权限（源码） |
| --- | --- | --- |
| 生成代发出库草稿 | `POST /api/erp-purchase-orders/{id}/drop-ship-outbound` | `purchase_order.manage` |
| 草稿**过账** | `POST /api/sales-outbounds/{id}/post` | `sales_order.manage` |
| 草稿冲销 | `POST /api/sales-outbounds/{id}/reverse` | `sales_order.manage` |

中间那道断层是确定的：**采购员有 `purchase_order.manage`、没有 `sales_order.manage` → 能建草稿，过不了账**，单据停在 `DRAFT` 等人接力。而代发业务里，货由供应商直发客户，**销售既看不到货也管不到物流**，"必须由销售过账"是语义错位（违原则 2）。

#### 方案对比

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ① 放宽过账端点注解 | `@RequirePermission({"sales_order.manage","purchase_order.manage"})` | 改动最小 | **权限面过宽**：持采购权者能对*任意*出库单调用过账端点（靠服务层再拒），一个"能调但不能用"的端点，且权限语义变模糊 |
| ② **代发专用推进端点（推荐）** | 新增 `POST /api/erp-purchase-orders/{id}/drop-ship-outbound/post`，权限 `purchase_order.manage`，内部**复用同一个 `SalesOutboundService.post(outboundId, actor, key)`** | 权限按单据语义（原则 2）；销售侧零改动；过账逻辑仍只有一份 | 多一个端点（但无逻辑副本） |
| ③ 给采购员加 `sales_order.manage` | 改角色配置 | 零代码 | 权限过宽：连销售订单的建单/改单/提交都一并给了。**不建议** |

**推荐 ②**。冲销同理补 `.../drop-ship-outbound/reverse`（或让冲销也走同一出入口，按 `fulfillment_source` 分派可见性）。

#### 验收

1. 以仅持 `purchase_order.manage` 的身份：生成代发草稿 → **过账成功**（旧行为：403）。
2. 同一身份对**普通销售出库单**调用新端点（或旧端点）→ 仍 403（不越权）。
3. 契约测试：断言代发推进端点与销售过账端点**调用的是同一个 Service 方法**（用注入 spy 或断言两者产生的库存流水/状态迁移完全一致）。
4. 活体验证：确认代发过账**确实不扣本地库存**（`fulfillment_source='DROP_SHIP'` 豁免），且冲销不回补。

## 3. P1 — 防呆与可诊断

### 3.1 提交/送评前置校验同源化（问题 D）

**现状**：`ErpSalesOrderService.requireSubmittable` 里串行 5 条校验（无明细、`UNDECIDED`、外采无需求配置、自产配置读不出、履约评审未就绪），全部在**提交那一刻**抛出。用户在建单页看不到还差什么，只能"先点、再被打回"。

**设计**：把校验体抽成纯函数，一次实现、两个消费者。

```java
// 纯函数：只读、不抛异常、可被前端直接消费
public Readiness evaluateReadiness(long orderId);   // {ready, blockers[], hints[]}

// 原方法变为薄壳，行为不变
private void requireSubmittable(long id) {
    var r = evaluateReadiness(id);
    if (!r.ready()) throw new IllegalStateException(r.blockers().get(0).message());
}
```

- 新增 `GET /api/erp-sales-orders/{id}/readiness`（读权限，`sales_order.read.*` 三变体齐列）。
- 前端：建单页 / 详情页顶部常驻「就绪度」清单；未就绪时「提交审批」「保存并送履约评审」置灰 + tooltip 列出 blocker；点 blocker 可定位到具体明细行。
- 「送履约评审」的可用条件与「提交审批」**共用同一份 blocker 列表**（前者只看评审相关项，后者看全部）——避免两套判据再次分裂。

**验收**：构造 N 个处于不同缺口状态的订单，断言 `readiness.ready == (提交接口返回 200)` 对全部 N 个成立；变异检验：把某条 blocker 判断短路，断言该用例由绿转红。

### 3.2 唯一键冲突的业务化文案（问题 E）

保留 `GlobalExceptionHandler` 的 409 兜底（并发下仍可能触达），但**业务路径上不应再落到它**：所有"可能撞唯一键"的入口都在 Service 层用 §2.1 的同一判据预检，并给出可执行文案。

文案模板：`该销售明细已关联{单据类型} {单号}（{状态}）；{可选动作}`。
可选动作按状态生成：`已取消 → 可直接重新建单`／`草稿 → 打开原单继续`／`履行中 → 打开原单查看到货`。

**验收**：逐个入口构造冲突，断言返回 4xx 且 body 文案**不含** `Duplicate entry` / 表名 / 索引名。

### 3.3 死入口与死代码清理（问题 F）

| 位置 | 现状 | 处置 |
| --- | --- | --- |
| `SalesOutboundView.vue:122` | 弹窗标题有 `新建销售出库单` 分支，但**没有任何入口以 `editingId=null` 打开它**（右上角已是「从销售订单发起」） | 删掉 create 模式分支与 `submitForm` 的建单分支，标题固定为「编辑销售出库单」 |

## 4. P2 — 治理与可观测

### 4.1 状态机 / 权限串 / 占坑口径的唯一登记（问题 G）

A 问题的根源不是某一行代码写错，而是**同一个判据没有唯一登记处**，于是被抄了 6 遍、其中一遍抄反了。

**设计**：在既有 `docs/ERP决策登记-20260921.md` 下新增一节「订单与生产交付 · 口径登记」，三张表：

1. **状态机表**：每张单据的每个状态 → 由谁（权限串）→ 通过哪个端点 → 迁入；以及每个状态的所有迁出。
2. **权限串表**：动作 → 端点 → `@RequirePermission` 原文 → 执行层 + 配置层是否都已写（`erp_approvals` 那轮的教训：两层都要写）。
3. **占坑/判重口径表**：业务概念 → 唯一实现位置（util 常量 / 生成列名）→ 引用点清单（改了要同步改哪几处）。

**配套契约测试**（这是关键，文档会腐化、测试不会）：
- 状态可达性测试：枚举每张单据的状态常量，断言"要么有写入方，要么在登记表里被显式标记为不可达"（防 B / H 复发）。
- 权限覆盖测试：对每个写端点断言存在 `@RequirePermission`（防漏注解）。
- 口径对拍测试：见 §2.1 验收 1。

### 4.2 状态合法组合矩阵

`status`（业务流转态）与 `approval_status`（审批态）是**两个独立字段**（决策 #35）。目前没有地方约束二者组合，理论上能出现 `status='RELEASED'` 而 `approval_status='NONE'` 这类自相矛盾的行（`#30`/`#31` 那轮就踩过"提交人被误显为审批人"的同型问题）。

**设计**：定义合法组合矩阵（如 `DRAFT` ⇒ `approval_status ∈ {NONE, PENDING, REJECTED}`；`CONFIRMED` ⇒ `APPROVED`），以**契约测试**形式落地（不主张加 MySQL `CHECK`：建设期需要可重导可回退，约束硬编码在 DB 里会让清库/重导变复杂）。

### 4.3 明细行下游聚合（问题 I）

现在要回答"这单为什么还没发出去"，需要在 4 个页面之间跳：销售订单 → 待下达生产需求 / 待采购需求 → 任务单详情 / 采购单详情 → 出库单。

**设计**：扩展 `GET /api/erp-sales-orders/{id}` 的 `items[]`，每行带上：

```
manufacturing: {orderId, orderNo, status} | null
purchase:      {poId, poNo, status, fulfillmentMode} | null
outbound:      {posted, draft, remaining}     // 与"发货进度"列同源
blockers:      [{code, message}]              // 与 §3.1 就绪度同源
```

前端明细行新增一列「下游」，用状态色显示三单编号，点开跳转；有 blocker 时行内标黄。

**验收**：随机抽 10 个真实订单，人工按 4 页面跳转统计的结果必须与接口返回值逐项一致（口径一致性对拍，不是"看起来对"）。

## 5. 分阶段路线

每阶段都是**可独立上线、独立验收**的完整闭环，不留半成品。

| 阶段 | 内容 | 为什么这个顺序 | 风险 |
| --- | --- | --- | --- |
| **一 · 止血** | §2.1 生成列迁移 + 谓词收敛为一处；§2.3 代发专用推进端点；§3.2 预检文案 | 两个 P0 都不改业务语义，只让"业务说的"和"DB 做的"一致；止血后再谈别的 | 低。迁移含外键索引陷阱，需在影子库先跑通 |
| **二 · 闭合** | §2.2 任务单作废通道（含事实型前置判据）+ `manufacturing_orders` 生成列 + 交期同步跳过作废单 | 与阶段一同款手法，必须成对上线（只做一半等于死代码） | 中。要盘清报工/入库/领料/出库四条引用面 |
| **三 · 防呆** | §3.1 就绪度接口 + 前端面板；§3.3 死代码清理；§3.4 常量收敛 | 阶段一二是"能不能做对"，这里是"会不会做错" | 低 |
| **四 · 治理** | §4.1 登记表 + 三条契约测试；§4.2 状态矩阵；§4.3 下游聚合列 | 前面改完再固化，否则登记的是旧口径 | 低（测试为主） |

**建议起步**：阶段一。它把 A 与 C 一起清掉——**A 是唯一会真实卡死操作的缺陷，C 是唯一会被跨岗用户每天遇到的权限墙**，两者改动面都很小（1 迁移 + 4 处收敛 + 1 端点）。

## 6. 统一验收方式

每一条改动都必须给出**可证伪**的证据，不接受"编译通过 / 单测绿"：

1. **活体 HTTP**：在真实服务实例上跑完整业务路径（不是单连接 harness）。新建写库链路必须真实 HTTP 走通。
2. **契约/口径对拍测试**：断言"两个独立口径结果集相等"，而不是断言"某接口返回 200"。
3. **变异检验**：故意破坏被测判据，测试必须变红。**没做变异检验的测试视为无效**。
4. **回归基线**：后端全量（`-Derp.foundation.mysql=true`，防真库测试静默跳过造成假绿）+ 前端 vitest/`vue-tsc`。
5. **迁移验证**：影子库先跑迁移 + 回滚演练；`flyway_schema_history` 连续性核对。
6. **并行会话**：迁移号现查现用（当前最大 V355）；共享文件提交后 `git show HEAD:<file> | grep` 复核只剩自己的改动。

## 7. 明确不建议改的（设计边界，不是缺陷）

写在这里是为了避免后续被当成"待办"反复讨论：

| 现状 | 为什么不改 |
| --- | --- |
| 订单确认后明细不可变，只能走登记问题/变更 | 需求源唯一且可追溯（决策 #33）是整条链的地基；可变会让"承诺"失去意义 |
| 出厂值「自产任务单不二次审批」，沿用 `approval_basis='SALES_ORDER'` | 订单确认已是商业授权，重复审批是收敛掉的冗余（决策 #35 那轮的结论） |
| 出库单不能直接新建 | 没有来源批次的出库单无法回写需求，会制造"孤儿出库"。要清的只是前端死代码（§3.3） |
| 已审批采购单可由 `purchase_order.manage` 直接取消，不触发二次审批 | 取消是**减损**动作，不增加支出授权；且取消后重新建单仍需走审批，授权没有被绕过。（若 LQ 认为需要留痕加强，可单列，但不属缺陷） |
| 履约评审与销售审批分立 | 两个控制针对**不同事实**：评审判"能不能做出来"，审批判"这份承诺要不要批"。合并会让两者都失去判据 |
| 氚云镜像表保留中文状态值 | 决策 #23「氚云生产链只读」，源值原样保留；只做常量收敛（§3.4） |

## 8. 需要 LQ 拍板的

1. **`CLOSED` 状态去留（问题 H）**：`erp_purchase_orders` 与 `manufacturing_orders` 上 `CLOSED` 都不可达，但被多处过滤引用。
